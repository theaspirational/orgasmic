How the manager delegates code work, closes every landing with review, and keeps
long-running dispatches recoverable. Read before dispatching code work.

** Always choose driver, harness, model and effort explicitly
Every dispatch is executed by a specific model at a specific reasoning effort,
and `--model` / `--effort` are optional flags. Omitting them does not mean "the
sensible default" — it means the harness picks, silently, and nothing in the run
record or tx says what it picked. `orgasmic run list` reports `driver` and
`harness` for a live run but carries no model or effort field, so an omitted
value is not recoverable afterwards from state: it is gone.

Pass all four on every dispatch. Choose them deliberately per task — a P0
concurrency fix and a docs typo do not deserve the same tier — and say why in the
`--reason` when the choice is unobvious. Then carry all four into every place you
report that run: the launch message, the task's `** Evidence`, and the handoff.

Two failures this rule exists to prevent, both observed 2026-07-26:
- a manager dispatched a review of a P1 concurrency fix and could not afterwards
  say what model was reviewing it;
- an implementer silently ran on a far more expensive model than the manager
  assumed, discovered only by reading a live process.

A worker claim whose author is unidentified cannot be weighed. If you find
yourself writing "the implementer reported", name the worker id, driver, harness,
model and effort instead.

** The standing worker matrix
Operator-set 2026-07-26. Use these unless the task gives you a reason to
deviate, and state the reason in `--reason` when you do. "Choose explicitly"
above still governs — this is the default you are choosing, not a licence to
stop passing the flags.

| stage       | --kind      | --mode | --harness | --model         | --effort |
|-------------+-------------+--------+-----------+-----------------+----------|
| implementer | implementer | rmux   | claude    | claude-opus-5   | high     |
| reviewer    | reviewer    | rmux   | codex     | gpt-5.6-sol     | high     |
| fixer       | implementer | rmux   | claude    | claude-opus-5   | medium   |

Three things this encodes deliberately:

*Every dispatch runs in an rmux TUI pane.* Not acp-stdio. A pane is attachable,
so the operator can watch a live worker and intervene; an acp-stdio worker is a
black box until it writes its report. `--mode rmux` with `--kind reviewer` still
selects the reviewer persona; there is no `--worker` flag.

*The reviewer is a different vendor from the implementer.* Adversarial review by
the same model that wrote the code shares its blind spots. Keeping claude on the
implement side and codex on the review side is the point of the split, so do not
"simplify" it by matching them.

*The fixer drops to medium.* A fix pass works from findings that already name the
file, the line and the direction — the expensive reasoning was spent producing
them. Reserve high effort for the passes that have to discover something.

Before dispatching in rmux mode, confirm `rmux ls` responds and that the daemon's
launchd PATH reaches the rmux binary; a dispatch that cannot find it fails at
spawn rather than reporting a missing tool. Note also that rmux sessions are not
currently reaped — check `rmux ls` for accumulation and kill stale
`orgasmic-rmux-run-*` sessions during housekeeping.

*Do not pass `--governance-json '{"stall_timeout_secs": 0}'` on rmux dispatches
any more.* It was the interim workaround for TASK-RWCRN, where a pane emitted no
driver events and the 600-second stall detector released every healthy worker at
exactly ten minutes. The rmux driver now publishes a coalesced `pane_activity`
driver event while the pane writes output, so the stall detector reads real pane
liveness and the default 600 s threshold applies unchanged. Keeping the override
would disable the only guard against a genuinely wedged pane, leaving the
four-hour ceiling as the sole backstop.

What the stall detector can and cannot see on a pane: silence means silence, so a
harness parked on an interactive gate (trust prompt, login) or one that finished
without calling `dispatch finalize` is still released at 600 s. A harness that
hangs while its TUI keeps animating a spinner still looks alive — same blind spot
the acp-stdio heartbeat has, and the one TASK-VZMZE is about. The `bytes` count on
each `pane_activity` event is diagnostic volume only — it is NOT a progress
classifier. The supervisor never interprets it; any `pane_activity` resets the
same clock. A full-screen renderer can repaint thousands of bytes for a
spinner-only frame, an SDK lag notice is counted as zero bytes of real activity,
and `PaneOutputStart::Oldest` can replay retained output after a reattach. Do not
read a healthy verdict out of that number.

The unit is raw pane output bytes, not lines (TASK-RWCRN.1). The first
implementation observed newline-terminated lines, so a TUI that redraws in place
with ANSI/CR and never emits LF produced no `pane_activity` at all and was still
released at 600 s — exactly the full-screen harnesses the event exists to
protect. The driver now drains `PaneOutputStream` and counts chunk lengths;
pane content is still never persisted. tmux dispatches do not yet have any
liveness signal (TASK-XHP43) and remain unprotected past 600 s.

An orphaned dispatch also blocks re-dispatch: `manager.dispatch_orphaned` is not
in `scan_open_dispatches`'s terminal set, so the next attempt fails with
"dispatch already open for overlapping task(s)". Close it first with
`manager dispatch-close --task TASK-NNN --started-tx <started_tx> --status
aborted --reason <why>`.

** Typed stage authority
Prefer explicit stage transitions over implicit continuation. Implementer,
verifier, adversarial reviewer, fixer, lander, and housekeeping are distinct jobs
with distinct authority; do not ask one worker to quietly perform another
stage's responsibilities unless the task brief explicitly grants that authority.

Each dispatch brief must stand alone. Do not rely on hidden shared context between
workers; pass prior-stage summaries, changed-file lists, gates, findings, and
unresolved risks in the next brief as labeled claims for the worker to verify.

** Every code-landing pass closes with a reviewer
After an implementer merge:
1. Dispatch a reviewer agent (kind `reviewer`) over the merged diff.
2. Reviewer files findings as `reviewer.finding` tx entries linked to the
   original task.
3. Non-trivial findings → file a fix sprint task as a subtask, then dispatch a
   fresh implementer. Parentage lives in the ID, not in a property: mint the fix
   task as `TASK-<parent>.N` (`TASK-2BPWM.1`), because the schema derives
   `parent_task` from the id grammar via `derive_task_parent_id` and reads no
   `:PARENT_TASK:` drawer key. A `:PARENT_TASK:` property is accepted, stored and
   never read — verified 2026-07-26.
4. Trivial findings → note and roll into the next pass over the same area.

This applies even when the implementer's verification (tests, clippy, fmt)
is clean. Tests verify code correctness; reviewers verify design and
architectural fit.

** Pre-flight tx for long-running dispatches
Before launching any background work that outlives a single manager reply
(codex implementer, reviewer agent, watcher, daemon-side recovery):

Append a `manager.dispatch_started` tx with `:TASK:`, `:KIND:`
(implementer / reviewer / etc.), `:WORKTREE:` (if applicable),
`:BRIEF_PATH:` (harness-neutral; legacy `:CODEX_BRIEF_PATH:` still read),
`:STARTED_AT:`, `:OWNER_PID:` (your own PID if observable).

If you die before the dispatch finishes, the next manager:
1. Sees the pre-flight tx in recall.
2. Checks worktree state (`git -C <worktree> log`), brief, stdout log
   (`ls <project_root>/.orgasmic/tmp/dispatch/` — one subfolder per task, e.g. `task-NNN-impl/`), and live process (`ps -ef | grep codex`).
3. Decides: resume integration (merge + record `implementer.done`) if the
   codex finished, or abort (worktree cleanup + record
   `manager.dispatch_aborted`) if the brief is stale or the worktree
   diverged.

** Dispatching a worker via the =orgasmic manager dispatch= CLI
When code work needs implementing, dispatch a worker per task in an isolated git
worktree, through the daemon's dispatch endpoint. Set `--model` and `--effort`
explicitly on every dispatch (they pass through verbatim) — see the rule above;
they are optional to the CLI, not to you. The stage defaults are in the standing
worker matrix; the example below shows the shape, not the choice.

For `--mode` and `--harness`, run `orgasmic manager drivers`. It prints every
supported pair, which of them run unattended, and what each one requires on this
host, sourced from `orgasmic_drivers::SUPPORTED` so it cannot drift from what
the daemon will accept.

An earlier revision of this paragraph said that verb did not exist and told you
to discover the pairs by submitting a bogus one and reading the rejection. It
does exist (TASK-JQARS); the rejection still names the whole set, but it is the
fallback, not the method. Pair a real dispatch with `--dry-run` when you want to
check the rest of the invocation too.

1. *Minimal self-contained brief.* Write the prompt to =<project_root>/.orgasmic/tmp/dispatch/task-NNN-brief.md=. The worker has no access to this chat, but the compiled bundle already injects the task heading (description, acceptance criteria, read/write scope, activity) and the worker persona — do not restate them. The brief carries only the delta: read-first anchors, target behaviour, non-negotiable invariants, verification gates, and the exact commit message. Shorter is better; never paste project conventions or file contents the worker can read from disk.
2. *Dispatch.* From the project root:
   #+begin_src bash
   orgasmic manager dispatch \
     --task TASK-NNN \
     --kind implementer \
     --mode rmux \
     --harness claude \
     --model claude-opus-5 \
     --effort high \
     --brief <project_root>/.orgasmic/tmp/dispatch/task-NNN-brief.md \
     --reason "<one-line reason — surfaces in tx + run.created>"
   #+end_src
   The CLI atomically: creates the per-task git worktree at =/tmp/orgasmic-worktrees/task-NNN= on branch =task-NNN-impl= based on HEAD (defaults; override the branch via =--branch=, the worktree path via =--worktree=, the base commit via =--from=); writes the =manager.dispatch_started= pre-flight tx; spawns the worker via the daemon's =/dispatch= endpoint; emits a =run.created= tx with the run_id, pid, brief path, last path, stdout path, session jsonl target. The worker runs as a =codex app-server= process talking ACP (JSON-RPC 2.0) over stdio to the daemon. Use =--dry-run= to print the resolved plan without launching anything; useful before non-trivial dispatches.
3. *Wait.* Prefer the harness completion notification. If a shell watcher is
   needed, install exactly one watcher for the dispatch and declare a finite
   observation deadline before starting it. The watcher may observe the
   terminal =last.txt=, dispatch log/status artifacts, worktree evidence, and
   the exact worker PID/process group. It exits with one of three summaries:
   terminal evidence found, owned worker exited, or attention required because
   the deadline passed without observable progress. A live PID alone is not
   proof of progress, and heartbeat-only/session-token activity must not reset
   the deadline. Let the harness deliver the watcher's one completion notice;
   do not run periodic status checks from the manager conversation.

   On =attention required=, inspect the preserved log/status artifacts and the
   concrete owned process/session once. Apply the shared
   =command_session_policy= from the worker prompt: do not launch duplicate
   verification, stop only a duplicate proven to be manager-owned, permit at
   most one non-restarting detached retry after a vanished subprocess, and
   close blocked with evidence after a second interruption. Escalation is a
   manager decision; it does not redefine supervisor heartbeat or stall-timeout
   semantics.
4. *Integrate.* Read =<project_root>/.orgasmic/tmp/dispatch/task-NNN-impl/task-NNN-impl-last.txt= for the worker summary, then from your base branch — the branch HEAD was on at dispatch (=git branch --show-current=): =main= in the default upstream flow, or your feature branch when developing a feature via parallel worktrees for a PR — run =git merge --no-ff task-NNN-impl=, resolve any same-file conflicts (usually only =use= statements when two tasks added imports to the same crate), run =cargo test --workspace && cargo clippy --workspace --all-targets -- -D warnings=, record evidence in the sprint task's =** Evidence= section. *Do not remove the worktree or delete the branch by hand.* Success-path cleanup belongs to =dispatch-close --worktree-remove --branch-delete= and only to it: that path salvages uncommitted worker output to =refs/orgasmic/salvage/<sha>= first (TASK-2BPWM, TASK-D0GA3) and removes without =--force=, so git's own clean check gates the removal. =dispatch finalize --commit= is optional, so a worker may legitimately leave dirty or untracked output that never reached the merged branch; [DANGEROUS-EXAMPLE] =git worktree remove --force && git branch -D= destroys exactly that, which is the data-loss path those two tasks exist to close. The worker signals completion itself, as its terminal action, via =orgasmic dispatch finalize --summary-file <path> [--commit]= (dec_3M7M0) — the SOLE success signal: it writes the report verbatim, optionally commits the worktree, emits its =implementer.reported= completion tx, and releases the lease in one call over the same worker→daemon channel used for every other write. The =implementer.done= close tx is yours, emitted by =dispatch-close= (see below). Every worker persona's contract ends with this call. Pane/process exit or stall/max-duration timeout without finalize is a failed/orphaned run (=manager.dispatch_orphaned=) — there is no scrollback-scrape or end-of-turn-marker fallback. If the worker never finalized (manager-rescued merge, aborted dispatch), record the close yourself via =orgasmic tx record= or =orgasmic manager dispatch-close=. Never leave orphan pre-flight tx — see the exit checklist.

   *=dispatch-close= is how you finish, including after a successful finalize*
   (TASK-6AYEJ). The worker's finalize emits =implementer.reported= — "I am
   finished", not "the dispatch is closed" — so the dispatch stays open, listed
   by =dispatch-status= as =[reported]=, until you run =orgasmic manager
   dispatch-close --task TASK-NNN --started-tx <started_tx> --status done
   --merge-sha <your merge sha> --worktree-remove --branch-delete=. That close
   emits =implementer.done=, records YOUR merge sha, runs worktree/branch
   cleanup with the salvage path, and flips the lifecycle stage.

   *=--started-tx= is mandatory whenever a dispatch is live* (TASK-6AYEJ.1,
   TASK-6AYEJ.2). It is the =TX_ID= of the =manager.dispatch_started= this close
   belongs to — the dispatch GENERATION — printed by =manager dispatch= as
   =started_tx== and by =dispatch-status= as =TX_ID==. Close identity is a
   generation, not a task: a task outlives its dispatches, so closing the
   implementer flips the task to IN_REVIEW and a reviewer is then opened for the
   SAME task. A close bound only to the task would select whatever is open for
   it — at that point the live reviewer, which it would release, clean up and
   close under the wrong tx type. So a tokenless close is now REFUSED while any
   dispatch for the task is open, and the refusal prints the candidate
   =--started-tx= values for you to copy. (Tokenless still works on a task whose
   dispatches are all closed, which is only the historical worker-closed
   records; it can never act on a live one.) With =--started-tx= the named
   generation decides: re-running the same close is a clean no-op even while a
   successor dispatch is open, so a close interrupted mid-integration is safe to
   repeat. An unknown =--started-tx= is a hard error, never a fall-back to task
   matching.

   Note the ordering consequence: dispatching the reviewer for a task before
   closing its implementer is rejected as an overlapping open dispatch — close
   first.
5. *Reviewer pass.* After merge + close, dispatch a reviewer agent over the merged diff via the same CLI with =--kind reviewer=. (There is no =--worker= flag; earlier revisions said =--worker reviewer-codex-acp= and that flag has never existed. =--kind= selects the persona.) Reviewer findings → fix subtasks minted as =TASK-<parent>.N= per the ID rule above, with =:FIX_SUBTASK: t= marking the one-round fix semantics → fresh implementer. Do not set =:FIX_SUBTASK:= on polish or organizational subtasks; those still receive a reviewer pass.
6. *Brief discipline.* Keep write scope DISJOINT across parallel codex runs and name any OFF-LIMITS regions in each brief. Same file is OK only when workers are split by function or region — workers don't see each other's diffs, so make that boundary explicit in each brief ("do NOT modify =post_daemon_restart= — TASK-XC6RJ territory").
7. *Lockfile pitfall.* Pre-stage workspace deps before parallel rounds. If multiple codex runs need new =Cargo.toml= deps they will revert =Cargo.lock= to honour their stated write scope, leaving a stale lockfile on main. Add likely deps to the workspace =Cargo.toml= and commit =Cargo.lock= before the dispatch.

*Custom harness argv.* For `--harness custom`, pass the wrapped CLI as repeated
`--harness-arg` tokens (or `--harness-args-json`). Built-in harnesses ignore
arbitrary argv unless the adapter documents otherwise.

** Filing new nodes: mint IDs, never max+1
New task/decision/architecture/glossary nodes get SHORT-RANDOM ids — 5-char
Crockford base32 (0-9 A-Z minus I L O U, uppercase, at least one letter),
class-prefixed: =TASK-XXXXX= / =dec_XXXXX= / =arch_XXXXX= / =term_XXXXX=.
Mint with =orgasmic id mint --class task|decision|architecture|term= (no
daemon needed), or any local CSPRNG honouring the grammar. NEVER allocate
max+1-by-eye from the file — concurrent writers collide (two clones, two
sessions, same next number). Daemon creation routes auto-mint when =id= is
omitted and reject legacy sequential-numeric ids on create. Legacy ids
remain valid as references.

** Housekeeping while dispatching
- When you (or a dispatched implementer) encounter any pre-existing
  Pyright/TypeScript/clippy/other diagnostics or lints in files within the
  task's read scope — fix them, even if unrelated to the current task. Codex
  briefs should restate this rule so the implementer honours it inside the
  worktree.
- Code-level pitfalls live in =.orgasmic/gotchas.org=; read them before
  dispatching code work and point codex briefs there.

** Exit checklist
- Confirm `tasks/handoff.org` `:LIVENESS:` matches HEAD.
- Confirm `tasks/goal.org` stays thin: active goal plus optional reached
  criteria only.
- Confirm each touched task sits in the state file matching its heading keyword.
- Confirm every `manager.dispatch_started` tx you appended has a matching
  `implementer.done` / `reviewer.done` / `manager.dispatch_aborted` close tx;
  never leave orphan pre-flight tx for a non-running dispatch.
- Treat any `manager.dispatch_orphaned` tx as a worker that ended without
  calling `orgasmic dispatch finalize`: the daemon does not auto-continue.
  Read `rescue-policy` and choose reattach / resume-fork / fresh recovery /
  abandon from evidence — never assume the run completed.
