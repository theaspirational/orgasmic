How the manager delegates code work, closes every landing with review, and keeps
long-running dispatches recoverable. Read before dispatching code work.

** Always choose driver, harness, model and effort explicitly
Every dispatch is executed by a specific model at a specific reasoning effort,
and `--model` / `--effort` are optional flags. Omitting them does not mean "the
sensible default" — it means the harness picks, silently, and nothing in the run
record or tx says what it picked. `orgasmic run list` reports `driver` and
`harness` for a live run but carries no model or effort field, so an omitted
value is not recoverable afterwards from state: it is gone.

Choose all four deliberately per task — a P0 concurrency fix and a docs typo do
not deserve the same tier — and say why in the `--reason` when the choice is
unobvious. Review and risky-stage dispatches carry an explicit `--effort`;
ordinary and trivial work may run at the harness default, but only as a choice
you state, never as an omission you did not notice. Then carry all four into
every place you report that run: the launch message, the task's `** Evidence`,
and the handoff — reporting is not storage, and the record says what ran without
anything reading it back as a setting.

Two failures this rule exists to prevent, both observed 2026-07-26:
- a manager dispatched a review of a P1 concurrency fix and could not afterwards
  say what model was reviewing it;
- an implementer silently ran on a far more expensive model than the manager
  assumed, discovered only by reading a live process.

A worker claim whose author is unidentified cannot be weighed. If you find
yourself writing "the implementer reported", name the worker id, driver, harness,
model and effort instead.

** Where the four values come from
Harness and effort come from the operator, once per session. The router's
`** Agent selection` section (`shipped/entry/router.org`) is the single source
and this convention does not restate it: the manager asks its operator at the
first dispatch of a session which harness family to implement with and what
effort posture review and risky stages carry, carries both answers for the rest
of the session, and stores neither. Where no operator is there to answer,
dispatch anyway and put the reason in `--reason`.

*There is no stage table here, and there must not be one.* An earlier revision
of this section carried a per-stage matrix pinning `--model` and `--effort`
values, introduced as "use these unless the task gives you a reason to deviate".
That is a stored per-stage model preference, which dec_WDR5K item 9 (zero model
knowledge) removed from orgasmic deliberately so that a vendor model bump
requires no orgasmic change — and it went stale in shipped content, where every
manager reads it and nobody was looking. Model identifiers are harness
vocabulary: chosen per dispatch, passed through unvalidated, never written into
config, the graph, or this file. If you catch yourself adding a default model
back, you are rebuilding the surface that rule exists to remove.

What is durable, and stays here:

*Every dispatch runs in a TUI pane.* Not =stdio=. A pane is attachable, so the
operator can watch a live worker and intervene; a =stdio= worker is a black
box until it writes its report. A pane `--mode` with `--kind reviewer` still
selects the reviewer persona; there is no `--worker` flag.

*The reviewer runs a different harness family from the implementer.* Adversarial
review by the same model that wrote the code shares its priors and its blind
spots, which is most of what an independent pass buys. This is runtime policy,
not manager taste — the router states it — so do not "simplify" it by matching
them. Same-family review is allowed and states its reason on the dispatch.

*A fix pass may carry less effort than the pass that produced its findings.* A
fixer works from findings that already name the file, the line and the
direction; the expensive reasoning was spent producing them. Reserve the top
tier for the passes that have to discover something. Which tier that is, is the
operator's session answer, not a number this file pins.

*** Choosing a transport: ask for the properties, not the mode name
Two independent properties decide whether a pane transport is safe for long
work, and a mode name tells you neither. Ask for both, of the runtime you are
actually dispatching on.

**** Property one: a liveness channel the stall clock can see
The supervisor releases
a run after `stall_timeout_secs` (600 s by default) with no work evidence, and
on a pane transport there are exactly two channels that can supply it: the
driver's coalesced `pane_activity` event while the pane writes, and, at the
deadline when subtree CPU is below the work threshold, a capture of the pane
looking for the harness's open-turn statusline. A transport missing both kills
healthy workers in a long provider-bound think — ~0 % cpu, no tool calls,
nothing to see — at exactly ten minutes.

So the first question before a dispatch is not "which mode is current" but *does
the runtime I am dispatching on publish pane liveness for this transport* — and
the runtime is the installed daemon, not the source tree. A merged commit is not
an installed one; the daemon binary running the stall clock is what decides, and
it can be older than `HEAD` by any amount. `orgasmic --version` against the
installed binary, read next to when the channel landed, is the check; the source
tree cannot answer it.

**** Property two: a mux process that will outlive the dispatch
A liveness channel is necessary and it is not sufficient. The stall clock
protects a healthy worker from being released for looking idle; nothing protects
a healthy worker from the mux daemon underneath it exiting. When that happens
the panes go with it, the supervisor fails to release the drivers, flags the
runs `manager.dispatch_orphaned`, and every worker that had not committed loses
its work — there is no stall to detect, because from the daemon's side the runs
simply ended.

**** Reading both properties at once
Both properties must hold for the installed tmux runtime. A merged commit is
not an installed one, and a running mux is not evidence that the daemon has the
liveness implementation expected by the source tree. Check both before the
session's first pane dispatch.

What that means for a manager is:

- Read both properties against the installed runtime before each session's first
  dispatch, and say in `--reason` which one you accepted the risk on. Neither
  property is a standing fact about a mode; both move when the daemon is rebuilt
  or the mux is restarted.
- When property one is unmet, raise `stall_timeout_secs` and no more — dropping
  the guard entirely leaves only the four-hour ceiling. Drop the override once
  the channel is installed, and not before.
- When property two is the one you cannot guarantee, the mitigation is not in
  the flags. Tell the worker in its
  brief to commit as soon as it has anything worth keeping, because a commit is
  the only worker output that survives its pane disappearing. Prefer fewer
  concurrent dispatches on one mux for the same reason: a mux death is
  correlated across every pane it owns, so three parallel runs are one failure,
  not three independent ones.

Tmux is the supported pane transport. Dogfood it, but do not dispatch onto a
blind stall clock — pair it with the override until the installed runtime
carries the channel.

Before dispatching in pane mode, confirm the pane runtime responds (`tmux ls`)
and that the daemon's launchd PATH reaches
that binary; a dispatch that cannot find it fails at spawn rather than reporting
a missing tool. Note also that pane sessions are not currently reaped — check
`tmux ls` for accumulation and kill stale `orgasmic-*-run-*`
sessions during housekeeping.

What the stall detector can and cannot see on a pane: silence means silence, so a
harness parked on an interactive gate (trust prompt, login) or one that finished
without calling `dispatch finalize` is still released at 600 s. A harness that
hangs while its TUI keeps animating a spinner still looks alive — same blind spot
the =stdio= heartbeat has, and the one TASK-VZMZE is about. The `bytes` count on
each `pane_activity` event is diagnostic volume only — it is NOT a progress
classifier. The supervisor never interprets it; any `pane_activity` resets the
same clock. A full-screen renderer can repaint thousands of bytes for a
spinner-only frame, an SDK lag notice is counted as zero bytes of real activity,
and `PaneOutputStart::Oldest` can replay retained output after a reattach. Do not
read a healthy verdict out of that number.

The unit is raw pane output bytes, not lines (TASK-RWCRN.1). The first
implementation observed newline-terminated lines, so a TUI that redraws in place
with ANSI/CR and never emits LF produced no `pane_activity` at all and was still
released at 600 s — exactly the full-screen harnesses the event exists to
protect. The driver now drains `PaneOutputStream` and counts chunk lengths;
pane content is still never persisted. tmux emits the same event on the same
raw-byte contract (TASK-4CSMY, which superseded and cancelled TASK-XHP43) — in
the source; whether the runtime you are dispatching on carries it is the
installed-binary question above.

An orphaned dispatch also blocks re-dispatch: `manager.dispatch_orphaned` is not
in `scan_open_dispatches`'s terminal set, so the next attempt fails with
"dispatch already open for overlapping task(s)". Close it first with
`manager dispatch-close --task TASK-NNN --started-tx <started_tx> --status
aborted --reason <why>`.

** Typed stage authority
Prefer explicit stage transitions over implicit continuation. Implementer,
verifier, adversarial reviewer, fixer, lander, and housekeeping are distinct jobs
with distinct authority; do not ask one worker to quietly perform another
stage's responsibilities unless the task brief explicitly grants that authority.

Each dispatch brief must stand alone. Do not rely on hidden shared context between
workers; pass prior-stage summaries, changed-file lists, gates, findings, and
unresolved risks in the next brief as labeled claims for the worker to verify.

** Every code-landing pass closes with a reviewer
After an implementer merge:
1. Dispatch a reviewer agent (kind `reviewer`) over the merged diff.
2. Reviewer files findings as `reviewer.finding` tx entries linked to the
   original task.
3. Non-trivial findings → file a fix sprint task as a subtask, then dispatch a
   fresh implementer. Parentage lives in the ID, not in a property: mint the fix
   task as `TASK-<parent>.N` (`TASK-2BPWM.1`), because the schema derives
   `parent_task` from the id grammar via `derive_task_parent_id` and reads no
   `:PARENT_TASK:` drawer key. A `:PARENT_TASK:` property is accepted, stored and
   never read — verified 2026-07-26.
4. Trivial findings → note and roll into the next pass over the same area.

This applies even when the implementer's verification (tests, clippy, fmt)
is clean. Tests verify code correctness; reviewers verify design and
architectural fit.

** Pre-flight tx for long-running dispatches
Before launching any background work that outlives a single manager reply
(codex implementer, reviewer agent, watcher, daemon-side recovery):

Append a `manager.dispatch_started` tx with `:TASK:`, `:KIND:`
(implementer / reviewer / etc.), `:WORKTREE:` (if applicable),
`:BRIEF_PATH:` (harness-neutral; legacy `:CODEX_BRIEF_PATH:` still read),
`:STARTED_AT:`, `:OWNER_PID:` (your own PID if observable).

If you die before the dispatch finishes, the next manager:
1. Sees the pre-flight tx in recall.
2. Checks worktree state (`git -C <worktree> log`), brief, stdout log
   (`ls <project_root>/.orgasmic/tmp/dispatch/` — one subfolder per task, e.g. `task-NNN-impl/`), and live process (`ps -ef | grep codex`).
3. Decides: resume integration (merge + record `implementer.done`) if the
   codex finished, or abort (worktree cleanup + record
   `manager.dispatch_aborted`) if the brief is stale or the worktree
   diverged.

** Dispatching a worker via the =orgasmic manager dispatch= CLI
When code work needs implementing, dispatch a worker per task in an isolated git
worktree, through the daemon's dispatch endpoint. `--model` and `--effort` pass
through verbatim and are the operator's session answer, not a default this file
holds — see "Where the four values come from" above and the router's
`** Agent selection`. The example below shows the shape; every value in it is a
placeholder, not a choice.

For `--mode` and `--harness`, run `orgasmic manager drivers`. It prints every
supported pair, which of them run unattended, and what each one requires on this
host, sourced from `orgasmic_drivers::SUPPORTED` so it cannot drift from what
the daemon will accept.

An earlier revision of this paragraph said that verb did not exist and told you
to discover the pairs by submitting a bogus one and reading the rejection. It
does exist (TASK-JQARS); the rejection still names the whole set, but it is the
fallback, not the method. Pair a real dispatch with `--dry-run` when you want to
check the rest of the invocation too.

1. *Minimal self-contained brief.* Write the prompt to =<project_root>/.orgasmic/tmp/dispatch/task-NNN-brief.md=. The worker has no access to this chat, but the compiled bundle already injects the task heading (description, acceptance criteria, read/write scope, activity) and the worker persona — do not restate them. The brief carries only the delta: read-first anchors, target behaviour, non-negotiable invariants, verification gates, and the exact commit message. Shorter is better; never paste project conventions or file contents the worker can read from disk.
2. *Dispatch.* From the project root:
   #+begin_src bash
   orgasmic manager dispatch \
     --task TASK-NNN \
     --kind implementer \
     --mode <mode> \
     --harness <harness> \
     --model <model> \
     --effort <effort> \
     --brief <project_root>/.orgasmic/tmp/dispatch/task-NNN-brief.md \
     --reason "<one-line reason — surfaces in tx + run.created>"
   #+end_src
   The CLI atomically: creates the per-task git worktree at =~/.orgasmic/worktrees/<project-id>/task-NNN= on branch =task-NNN-impl= based on HEAD (defaults; override the branch via =--branch=, the worktree path via =--worktree=, the base commit via =--from=). The worktree lives OUTSIDE the project deliberately (TASK-M47E5): macOS pins a TCC grant for a freshly built, ad-hoc-signed binary to that binary's cdhash, so a worker building inside a =~/Documents=-hosted project re-prompts the operator on every rebuild, and =~/.orgasmic= is unguarded. Only the SCRATCH moved — the dispatch RECORD (brief, =last.txt=, stdout log) still lands under =<project_root>/.orgasmic/tmp/dispatch/<task-stem>/=, so every path in this convention stays valid; writes the =manager.dispatch_started= pre-flight tx; spawns the worker via the daemon's =/dispatch= endpoint; emits a =run.created= tx with the run_id, pid, brief path, last path, stdout path, session jsonl target. The worker runs as a =codex app-server= process talking codex's own JSON-RPC 2.0 app-server protocol over stdio to the daemon. That is not ACP: orgasmic's =stdio= mode names the wire only, and the harness decides the protocol (TASK-XCJYC; see the glossary term =term_YX8AG= transport mode). Use =--dry-run= to print the resolved plan without launching anything; useful before non-trivial dispatches.
3. *Wait.* Arm the blocking wait printed by =manager dispatch= immediately;
   background it when the harness needs a shell completion signal:
   =orgasmic manager dispatch-wait --started-tx <started_tx> &=. It exits 0
   only after the worker has written its =*.reported= terminal declaration;
   it exits 2 when the daemon no longer has that generation's run without a
   report, and 3 when =--timeout 30m= (or another explicit duration) elapses.
   Exit 1 means invalid/unknown generation or a daemon/API/transport failure;
   it is never a liveness classification. The command help prints the same
   stable 0/1/2/3 contract.
   It deliberately does *not* treat =[pid-gone]= as death: pane transports can
   have no worker PID, so that marker is not liveness evidence. Repeat
   =--started-tx= for one wait over a round. This command is the watcher
   mechanism; do not hand-roll a polling loop.

   When the manager itself lives in an app-created =custom= terminal, start
   Claude Code or Codex manually in that pane, then run plain =orgasmic manager
   register=. Its app-created terminal carries a daemon-minted, run-bound
   capability; registration never accepts a caller-supplied provider or target
   identity. =orgasmic manager wake= detects the foreground provider afresh
   and can inject only
   =: 'ORGASMIC_MANAGER_WAKE_V1'= followed by submit. The entry router treats
   that exact marker as =/orgasmic resume=; if the provider exits in tmux's
   final delivery gap, zsh/bash execute only the side-effect-free =:= builtin
   with one literal argument. Tmux still refuses a busy, shell, trust/login,
   unknown, or provider-mismatched foreground as a targeting gate.

   On =attention required=, inspect the preserved log/status artifacts and the
   concrete owned process/session once. Apply the shared
   =command_session_policy= from the worker prompt: do not launch duplicate
   verification, stop only a duplicate proven to be manager-owned, permit at
   most one non-restarting detached retry after a vanished subprocess, and
   close blocked with evidence after a second interruption. Escalation is a
   manager decision; it does not redefine supervisor heartbeat or stall-timeout
   semantics.
4. *Integrate.* Read =<project_root>/.orgasmic/tmp/dispatch/task-NNN-impl/task-NNN-impl-last.txt= for the worker summary *while the dispatch is still open*, then from your base branch — the branch HEAD was on at dispatch (=git branch --show-current=): =main= in the default upstream flow, or your feature branch when developing a feature via parallel worktrees for a PR — run =git merge --no-ff task-NNN-impl=, resolve any same-file conflicts (usually only =use= statements when two tasks added imports to the same crate), run =cargo test --workspace && cargo clippy --workspace --all-targets -- -D warnings=, record evidence in the sprint task's =** Evidence= section. *Do not remove the worktree or delete the branch by hand.* Success-path cleanup belongs to =dispatch-close --worktree-remove --branch-delete= and only to it: that path salvages uncommitted worker output to =refs/orgasmic/salvage/<sha>= first (TASK-2BPWM, TASK-D0GA3) and removes without =--force=, so git's own clean check gates the removal. =dispatch finalize --commit= is optional, so a worker may legitimately leave dirty or untracked output that never reached the merged branch; [DANGEROUS-EXAMPLE] =git worktree remove --force && git branch -D= destroys exactly that, which is the data-loss path those two tasks exist to close. The worker signals completion itself, as its terminal action, via =orgasmic dispatch finalize --summary-file <path> [--commit]= (dec_3M7M0) — the SOLE success signal: it writes the report verbatim, optionally commits the worktree, emits its =implementer.reported= completion tx (with =:REPORT_PATH:= naming the durable location close will promote into), and releases the lease in one call over the same worker→daemon channel used for every other write. The =implementer.done= close tx is yours, emitted by =dispatch-close= (see below). Every worker persona's contract ends with this call. Pane/process exit or stall/max-duration timeout without finalize is a failed/orphaned run (=manager.dispatch_orphaned=) — there is no scrollback-scrape or end-of-turn-marker fallback. If the worker never finalized (manager-rescued merge, aborted dispatch), record the close yourself via =orgasmic tx record= or =orgasmic manager dispatch-close=. Never leave orphan pre-flight tx — see the exit checklist.

   *=dispatch-close= is how you finish, including after a successful finalize*
   (TASK-6AYEJ). The worker's finalize emits =implementer.reported= — "I am
   finished", not "the dispatch is closed" — so the dispatch stays open, listed
   by =dispatch-status= as =[reported]=, until you run =orgasmic manager
   dispatch-close --task TASK-NNN --started-tx <started_tx> --status done
   --merge-sha <your merge sha> --worktree-remove --branch-delete=. That close
   emits =implementer.done=, records YOUR merge sha, runs worktree/branch
   cleanup with the salvage path, and flips the lifecycle stage.

   *After close, the worker report lives at
   =<project_root>/.orgasmic/dispatch-records/<started_tx>/last.txt=*
   (TASK-QGWK7, TASK-QGWK7.1). Close *promotes* =last.txt= and a bounded
   =stdout.log= out of gitignored =tmp/= into that tracked directory, keyed by
   the dispatch GENERATION (=started_tx=), not the task — so a chain of six
   dispatches keeps six distinct records. The close tx (and the worker's
   =*.reported= tx) carries =:REPORT_PATH:= naming that =last.txt=. Close also
   *commits* that directory, on its own, as =chore(orgasmic): dispatch record
   <started_tx>= (TASK-QGWK7.1.1). Durability then does not depend on which
   =git add= form a later state chore uses, nor on the manager remembering to
   commit: a fresh clone reads the record because it is in history. The commit
   is built through a throwaway index seeded from =HEAD=, so it contains the
   record directory and nothing else — whatever you have staged is neither
   committed nor disturbed, and when to commit YOUR change is still yours.
   *It is deliberately not just =git add=.* Staging alone breaks the very next
   step of this flow: a staged path — any staged path, not only one the merge
   touches — makes =git merge= refuse with "your local changes would be
   overwritten", and the review gate's own refusal message prescribes close
   first, merge second. Two consequences worth knowing: a close moves the
   branch you are on by one commit — *including a promote-only
   =--no-worktree-remove= close*, which persists the record the same way, so a
   round of N closes leaves N =chore(orgasmic): dispatch record= commits
   interleaved with your own work — and =orgasmic update= / =install.sh=
   (=git stash push --include-untracked= in the source repo, which for this
   project IS the orgasmic project) can no longer un-persist a record between a
   close and your next commit — a committed file is not stashed. *Record commits
   are UNSIGNED*: they are written with =git commit-tree=, which ignores
   =commit.gpgsign= (measured), so a repo whose push side enforces signatures
   will reject them. *A close does not persist while a sequencer operation owns
   HEAD* (rebase, am, merge, cherry-pick, revert, bisect, or an interrupted
   revert/cherry-pick sequence) or on a detached HEAD: it promotes the files,
   skips the commit, and says why through =CLEANUP_ERROR=. Only one of those
   aborts actually destroys a record — =rebase --abort= takes the commit and the
   promoted file with it (measured), and a rebase detaches HEAD, so the
   detached-HEAD refusal catches that case first. A record commit written inside
   a revert or cherry-pick is NOT destroyed: =git revert --abort= and
   =git cherry-pick --abort= exit 0 and the record survives in =HEAD= and on
   disk (measured) — for revert and cherry-pick because the abort rewinds to the
   CURRENT HEAD, which is the record commit itself; for =am= because git refuses
   to rewind past a HEAD that moved. The rewinding aborts (revert, cherry-pick,
   merge) discard the conflict resolution you had in the working tree; the =am=
   abort, having declined to rewind, leaves it in place (measured). Standing down is still the
   right move, for a different reason: the record would otherwise land in the
   middle of an operation you have not finished, on a branch whose shape you are
   still deciding — and one written on a detached HEAD is on no branch at all.
   Skipping the commit costs a promote plus a re-run, and buys a record that
   enters history once, cleanly, at a point you chose. A staged
   =git revert -n= counts: it leaves =REVERT_HEAD= just as a conflicted one does.
   So does a range with no pick currently stopped: resolve a conflict and
   =git commit= it by hand instead of =git revert --continue= and git clears
   =REVERT_HEAD= while leaving the =.git/sequencer= todo list, from which
   =git revert --continue= still resumes the range (measured). =git reset --hard=
   leaves that same todo list behind with nothing live to resume — =git status=
   does not show it and an ordinary commit does not clear it — and the two are
   indistinguishable on disk, so the close refuses both and its message names
   =git revert --quit=, the one command that clears the leftovers.
   Re-run the same close once the operation finishes or you are back on a
   branch; a re-run repairs any record its close promoted but could not commit,
   printing =re-persisted:=, and is otherwise still a no-op. *The repair lands on
   the branch you are standing on when you re-run*, not on the branch the failed
   close resolved (measured), and the =re-persisted:= line names that ref — so
   re-running a close from an unrelated branch is a known move, and if you care
   which branch carries the record, check it out before the re-run. The harness
   =stdout.log= sits beside the summary as falsifiable evidence: empty files
   promote no =stdout.log= (but still a =stdout.log.bytes= of =0=, so "printed
   nothing" is distinguishable from "never promoted"); larger files promote a
   64 KiB excerpt (plus ~180 bytes of banner, which ride on top of the cap),
   half from the head and half from the tail, with a banner line
   naming the truncation and the original byte count in =stdout.log.bytes=.
   =stdout.log.bytes= is therefore two statements, told apart by its VALUE: a
   =0= with no =stdout.log= means the harness printed nothing, while a NON-ZERO
   count with no =stdout.log= means the promote failed between the two renames
   — the excerpt is missing, and the close's =CLEANUP_ERROR= names it.
   =:REPORT_PATH:= always points at the summary, and is always
   project-relative — a =--property REPORT_PATH== outside the project root is
   refused rather than committed as a machine-specific path. *Retention: keep forever, with measured year-one growth.*
   At ~5,200–6,500 generations/year on this project: =last.txt= ≈ 24–30 MB/yr
   (mean ~4.6 KB); =stdout.log= ≈ 0 typical on tmux (empty panes skipped) and
   ≤ ~400 MB/yr worst case at the 64 KB cap. There is no silent age-out at
   close. Do not paste the raw report into =done.org= — the node keeps curated
   Evidence plus this pointer.

   *=--started-tx= is mandatory whenever a dispatch is live* (TASK-6AYEJ.1,
   TASK-6AYEJ.2). It is the =TX_ID= of the =manager.dispatch_started= this close
   belongs to — the dispatch GENERATION — printed by =manager dispatch= as
   =started_tx== and by =dispatch-status= as =TX_ID==. Close identity is a
   generation, not a task: a task outlives its dispatches, so closing the
   implementer flips the task to IN_REVIEW and a reviewer is then opened for the
   SAME task. A close bound only to the task would select whatever is open for
   it — at that point the live reviewer, which it would release, clean up and
   close under the wrong tx type. So a tokenless close is now REFUSED while any
   dispatch for the task is open, and the refusal prints the candidate
   =--started-tx= values for you to copy. (Tokenless still works on a task whose
   dispatches are all closed, which is only the historical worker-closed
   records; it can never act on a live one.) With =--started-tx= the named
   generation decides: re-running the same close is a clean no-op even while a
   successor dispatch is open, so a close interrupted mid-integration is safe to
   repeat. An unknown =--started-tx= is a hard error, never a fall-back to task
   matching.

   Note the ordering consequence: dispatching the reviewer for a task before
   closing its implementer is rejected as an overlapping open dispatch — close
   first.
5. *Reviewer pass.* After merge + close, dispatch a reviewer agent over the merged diff via the same CLI with =--kind reviewer=. (There is no =--worker= flag; earlier revisions said =--worker reviewer-codex-acp= and that flag has never existed. =--kind= selects the persona.) Reviewer findings → fix subtasks minted as =TASK-<parent>.N= per the ID rule above, with =:FIX_SUBTASK: t= marking them as fix rounds → fresh implementer. Do not set =:FIX_SUBTASK:= on polish or organizational subtasks. Either way the round is reviewed: since TASK-4WKNX a fix round's close lands =in_review= like every other implementer close (see below).

   *Close the reviewer with a verdict, and know which vocabulary your runtime
   speaks.* =dispatch-close --verdict <approve|approve-with-follow-ups|reject>=
   records the verdict as a first-class flag (TASK-YN5FJ.1). Any of those values
   clears the default-branch review gate, =reject= included: the gate asks whether
   an independent review happened, not whether it approved, and a bad verdict has
   its consequence in the task's next stage rather than in the merge. The legacy
   spelling =--property VERDICT=clean|ship|has-issues= still works and still maps
   the same way — which matters more than it sounds, because *a runtime older than
   TASK-YN5FJ.1 has no =--verdict= flag at all, and its stage mapping does not know
   the word =approve=*. On such a runtime an =approve= recorded through
   =--property= leaves the task =in_progress=; use =ship=. Check the installed
   binary, not the source tree, before assuming which vocabulary is available.

   *A fix round gets its own review by default.* Closing a =:FIX_SUBTASK: t=
   implementer dispatch as done lands the task in =in_review=, exactly like any
   other implementer close, so the reviewer dispatch that the active goal requires
   for a BLOCK SHIP fix round goes out with NO manual stage transition first
   (TASK-4WKNX). For a round genuinely too trivial to review, opt out explicitly:
   =orgasmic manager dispatch-close --task TASK-X.N --started-tx <tx> --status done
   --merge-sha <sha> --fix-round-final --reason <why>= closes it straight to =done=
   and stamps =FIX_ROUND_FINAL: true= on the close tx. The =--reason= is mandatory,
   same as on =--no-review-required=, so a skipped review is auditable rather than
   merely quiet.

   Do not reach for =--no-review-required= to get this: it waives the
   default-branch MERGE gate ("does a reviewer verdict exist for this merge"),
   while =--fix-round-final= waives the fix round's own REVIEW ROUND ("does this
   fix get reviewed at all"). Two flags because they are two questions.
6. *Brief discipline.* Keep write scope DISJOINT across parallel codex runs and name any OFF-LIMITS regions in each brief. Same file is OK only when workers are split by function or region — workers don't see each other's diffs, so make that boundary explicit in each brief ("do NOT modify =post_daemon_restart= — TASK-XC6RJ territory").
7. *Lockfile pitfall.* Pre-stage workspace deps before parallel rounds. If multiple codex runs need new =Cargo.toml= deps they will revert =Cargo.lock= to honour their stated write scope, leaving a stale lockfile on main. Add likely deps to the workspace =Cargo.toml= and commit =Cargo.lock= before the dispatch.

*Custom harness argv.* For `--harness custom`, pass the wrapped CLI as repeated
`--harness-arg` tokens (or `--harness-args-json`). Built-in harnesses ignore
arbitrary argv unless the adapter documents otherwise.

** Filing new nodes: mint IDs, never max+1
New task/decision/glossary/artifact nodes get SHORT-RANDOM ids — 5-char
Crockford base32 (0-9 A-Z minus I L O U, uppercase, at least one letter),
class-prefixed: =TASK-XXXXX= / =dec_XXXXX= / =term_XXXXX= / =ART-XXXXX=.
Mint with =orgasmic id mint --class task|decision|term|artifact= (no
daemon needed), or any local CSPRNG honouring the grammar. NEVER allocate
max+1-by-eye from the file — concurrent writers collide (two clones, two
sessions, same next number). Daemon creation routes auto-mint when =id= is
omitted and reject legacy sequential-numeric ids on create. Legacy ids
(including historical =arch_XXXXX= architecture nodes) remain valid as
references; the architecture class is no longer mintable (dec_HBK6A).

** Reclaiming managed worktrees
Managed worktrees live under =~/.orgasmic/worktrees/<project-id>/=, where
=git status= and =git worktree list= in the project no longer put them under
your nose. So the leak is reported for you and reclaimed only when you say so
(TASK-M47E5):

- *Detection is automatic.* Every =orgasmic manager dispatch-status= ends with
  a =RECLAIMABLE_WORKTREE= line per reclaimable tree — path, bytes, and WHY —
  plus a =RECLAIMABLE_TOTAL=, and a =HELD_WORKTREE= line for each one it will
  not touch.
- *Reclamation is an explicit verb.* =orgasmic manager worktree-prune=
  ( =--dry-run= to measure only, =--task TASK-NNN= to narrow). It salvages a
  dirty tree to =refs/orgasmic/salvage/<sha>= first and then removes it through
  its own anchored directory handle, refusing what a non-forced =git worktree
  remove= refuses — locked, still dirty after salvage, or containing an
  initialized submodule — and it runs =git worktree prune= so stale
  =.git/worktrees= metadata does not accumulate. =dispatch-close= still shells
  out to =git worktree remove=, so the two take the same decisions by different
  routes; do not read one as literally calling the other.
- *It never ends a dispatch.* A worktree an OPEN dispatch names is skipped
  whatever its run health, and an abandoned one is reported with the verb that
  releases it — =dispatch-close=, or =dispatch-status --cleanup-failed= for the
  orphan close. Nothing deletes a worktree on a timer or at daemon boot; a
  worker's uncommitted output is the most easily destroyed thing in the loop
  (TASK-2BPWM, TASK-D0GA3) and no unattended process gets that authority.
- A worktree whose REPO is gone is detected and removed directly, since
  =git worktree remove= has no repository to run from — and it says plainly
  that such a tree could not be salvaged.

** Exit checklist
- Confirm `tasks/handoff.org` `:LIVENESS:` matches HEAD.
- Confirm `tasks/goal.org` stays thin: active goal plus optional reached
  criteria only.
- Confirm each touched task sits in the state file matching its heading keyword.
- Confirm every `manager.dispatch_started` tx you appended has a matching
  `implementer.done` / `reviewer.done` / `manager.dispatch_aborted` close tx;
  never leave orphan pre-flight tx for a non-running dispatch.
- Treat any `manager.dispatch_orphaned` tx as a worker that ended without
  calling `orgasmic dispatch finalize`: the daemon does not auto-continue.
  Read `rescue-policy` and choose reattach / resume-fork / fresh recovery /
  abandon from evidence — never assume the run completed.
