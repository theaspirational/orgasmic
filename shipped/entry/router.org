* Entry

** Agent router
Worker route when the prompt is a strict orgasmic worker dispatch with all of:
- worker role: implementer, architect, planner, reviewer, or griller
- task ID or task heading
- read/write scope
- acceptance, reporting, or evidence expectations

Worker startup:
1. Read the task heading.
2. Read `project.org` and `gotchas.org`.
3. Read only referenced conventions and source files.

Manager route for every other prompt, including arbitrary requests,
pickup/status requests, and prompts beginning with `/orgasmic`.

Manager startup:
1. Check `~/.agents/skills/orgasmic/SKILL.md` or the visible skill registry.
2. If installed, read the skill and follow the selected `/orgasmic` subcommand.
3. If absent, offer `/orgasmic install`; keep `.orgasmic/` read-only until the
   runtime is available.
4. Run `orgasmic manager register`.

Manager-implementer: when the manager edits source directly in this session
instead of dispatching a worker (single-worker setups), follow the resolved
`default` workflow printed below before the first source edit. Compute the tier
from that workflow's triggers and say which ones fired - a manager already
implementing is exactly where the tier gets skipped, so compute it even when the
change looks obvious.

** Human checkpoints
Proceed by default. Asking is the exception and needs a reason that names which
property of the action triggers it.

Confirm before an action that is hard to reverse, leaves this machine, or spends
someone else's resources: pushing to a remote, publishing a release or artifact,
force-pushing or rewriting history, deleting or rewriting operator session or
run history, touching the LaunchAgent or a live production daemon, or mutating
any shared or external service.

Proceed without asking on everything else, explicitly including: committing to a
local branch, creating and removing worktrees, running gates and test suites,
reading anything, and `.orgasmic/` state writes through the CLI.

Classify an unlisted action by those same three properties - reversibility,
reach, whose resources - not by how large it feels.

Once the user has approved a plan, the mechanical steps that plan obviously
entails are approved with it; re-asking inside an approved plan is itself the
defect. Standing authorization has a scope and an expiry: "you may restart the
daemon" covers a restart, not installing unreviewed code under it.

When unsure and the action is in the proceed class, act, then report what was
done plainly enough that the user can reverse it.

** Project map
- `project.org`: baseline, mission, operating constraints.
- `tasks/`: `backlog.org`, `todo.org`, `in_progress.org`, `in_review.org`, `done.org`, `cancelled.org`, `goal.org`, `handoff.org`.
- `tasks/goal.org`: manager focus only.
- `tasks/handoff.org`: manager continuity only.
- `decisions.org`: durable rationale.
- `architecture.org`: architecture graph, source paths, node tests.
- `glossary.org`: domain language.
- `gotchas.org`: repeated traps; read before source edits.
- `conventions/`: repo-local working agreements.
- `tx/`: agent activity log.

** Write rules
- Before `.orgasmic/` state writes: run
  `command -v orgasmic >/dev/null 2>&1 && orgasmic status >/dev/null 2>&1`.
- If it succeeds: write through `orgasmic ...` CLI commands.
- If it fails: stop - install or start the runtime (`/orgasmic install`,
  `orgasmic daemon start`); do not hand-edit.
- Add repo-specific conventions as separate files under `conventions/`.

** Contributing discipline
- Follow the constraints in `project.org`.
- Keep personal data out of durable state: `tx/`, decisions, task evidence, and
  worklogs may be committed or published. Use stable handles instead of personal
  email, prefer repo-relative paths, and keep machine-specific notes in
  gitignored `tmp/local_instructions.org`.
- Record durable rationale in `decisions.org`; do not create stray decision
  docs.
- While the project is greenfield, treat decisions and architecture as a living
  model: create genuinely new rationale through the CLI, and revise existing
  nodes through `orgasmic node body set|append` or `orgasmic node prop set`.
- If something about the project surprises you, add or ask for a `gotchas.org`
  entry. When task scope changes, keep `tasks/` current through the CLI.

** Tooling usage
- Use `orgasmic ...` as the agent and human surface; treat the daemon as the CLI
  backend and write authority for `tx/` and sessions.
- `/orgasmic recall` means brief and stop.
- `/orgasmic resume` means brief, then continue the next clear action.
- Use `orgasmic --help` and `orgasmic manager drivers` to discover installed
  transport pairs (`mode` + `harness`).

** Dispatch rule
- Implement and review work through orgasmic workers, never by shelling out to a
  raw provider CLI such as `codex`, `claude`, or `cursor-agent` for project
  work. Raw provider CLIs bypass daemon write authority, tx recording, worktree
  isolation, dispatch leases, and reattach/recovery.
- A request naming provider, model, or effort maps to
  `orgasmic manager dispatch --kind <kind> --mode <mode> --harness <harness>
  [--model <model>] [--effort <effort>] --brief <path>`. Omit model and effort
  to use harness defaults; explicit values pass through unvalidated.
- A worker sees only committed history. `--from` takes a git ref (default: the
  current branch HEAD) and the worktree is built from it, so every uncommitted
  edit in the manager's tree is invisible to the worker. This is one constraint
  with two halves: your source edits, and the live daemon's uncommitted writes
  to `.orgasmic/` tx, tasks, and decisions. Commit both halves to a branch and
  pass that ref as `--from` before dispatching anyone who must see your work.
- The reviewer case is the costly one: a review dispatched against an
  uncommitted diff does not fail, it returns a confident verdict on code it
  never read. Before a review dispatch, confirm the diff you want reviewed is
  reachable from the `--from` ref.
- Inside a worktree, `.orgasmic/` is a frozen snapshot. Verify graph state
  through the daemon CLI, naming the project explicitly
  (`orgasmic task get --project <name> <ID>`), rather than by reading the
  worktree's files or letting a command resolve the project from the cwd.
- A continuation or a second review round cannot reuse the derived branch name;
  the first run still holds `task-xxxxx-<kind>` and dispatch refuses with
  `a branch named ... already exists`. Pass an explicit `--branch`.
