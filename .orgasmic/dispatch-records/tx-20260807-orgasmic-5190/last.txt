## Changed

**`crates/orgasmic-cli/src/manager.rs`**

- **F-1 (recovery).** `cmd_dispatch_close`'s `AlreadyClosed` no-op now calls a new
  `repersist_dispatch_record_best_effort`. It reads the close tx's recorded
  `CLEANUP_STATUS` (`closed_dispatch_cleanup_status`), and when that is non-`ok`,
  the promoted directory exists on disk, and `dispatch_record_is_in_history` says
  it is NOT in `HEAD`'s tree, it takes the cleanup lock and re-runs
  `commit_promoted_dispatch_record` — which needed only `dest_dir` all along;
  only its caller was gated on the unlinked tmp. Success prints
  `re-persisted: dispatch record <tx> committed (…)`; failure warns and names
  both the on-disk path and the cause. Cleanup itself is still a strict no-op.
- **F-1 (rollback).** The `git restore --staged` after a failed commit is no
  longer discarded behind `let _ =`. If the restore ALSO fails, the error says
  the record is left STAGED and prints the exact command to clear it — that
  state is M-0's symptom verbatim and would otherwise block the next merge with
  no clue why.
- **F-2.** `commit_promoted_dispatch_record` resolves `git symbolic-ref -q HEAD`
  alongside the OID and `write_dispatch_record_commit` compare-and-swaps THAT
  ref instead of `HEAD`. The CAS still refuses when the branch moved underneath
  (unchanged: same old-value argument, now on a named ref).
- **F-3.** New `sequencer_operation_in_progress` checks `rebase-merge`,
  `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `BISECT_LOG` under the
  per-worktree git dir, BEFORE the real `git add`, and returns an error naming
  the operation. Promotion still happens; only the commit stands down.
- **F-5.** A detached HEAD is refused by the same early gate (the
  `symbolic-ref` resolution above), before anything is staged — symmetric with
  the unborn-HEAD shape, which was already safe.
- **F-6.** `normalize_report_path_property` moved BELOW
  `reconcile_torn_closes_best_effort`.

**`shipped/prompt-studio/conventions/manager-dispatch.org`** (F-7, F-4) — four
additions to the close paragraph: a non-zero `stdout.log.bytes` with no

## What state a failed persist now leaves, and how it recovers

Unchanged, and deliberately: the close still SUCCEEDS, the promoted files stay
on disk, `CLEANUP_STATUS=partial`, `CLEANUP_ERROR` carries `report: commit
promoted dispatch record …`, and nothing is left staged (and if the rollback
that guarantees that fails, the error now says so and hands over the fix).

What changed is the way out. Re-running the same `dispatch-close --started-tx`
— the only command a manager has, and the one they already re-run — repairs it:
the no-op prints `already-closed`, then `re-persisted: dispatch record <tx>
committed`, and the record is in history on the branch the close resolved. A
third run finds it in `HEAD` and says nothing. No hand repair, no new verb.

### The F-2 test needs a real race, so it puts one on real git

`refs/heads/other` at the same OID is only reachable by a checkout landing
between the close's `rev-parse` and its `update-ref` — milliseconds, and a sleep
cannot hit it. The test installs a `git` shim on the child's `PATH` (the
`write_git_proxy` pattern already in this file) that, the first time the close
reaches `commit-tree`, runs `git branch -f sibling HEAD` +
`git symbolic-ref HEAD refs/heads/sibling` and then forwards to real git. That
is the reviewer's `p16` probe, deterministic, inside `cmd_dispatch_close`. The
record then lands on `main` (the ref the close resolved) and `sibling` is
byte-identical to its pre-close OID. With `update-ref HEAD` it is the reverse.

## Unmet Criteria

Every acceptance item is done. Two carry a limit worth a reviewer's attention:

1. **The `git restore` FAILURE branch is implemented but not pinned by a test.**
   Reporting it is done (and the brief asked for it "regardless"). Reaching it
   needs the commit to fail AND the index lock to be taken between the `git add`
   and the restore — a second, narrower injection point than the shim gives me.
   The `Ok(_) => Err(err)` half is exercised by every commit-failure test.
2. **F-3 is closed by refusal, not by making a close inside a rebase safe.** A
   close during a sequencer operation now leaves the record promoted-but-
   untracked and says so; putting it in history takes one re-run. `rebase
   --abort` losing an already-written record is pre-existing (the staged-only
   baseline loses it identically, measured by the reviewer) and is not made
   worse here.

## Residual Risk

- **A re-run of a close can now move the branch.** That is the point, and it
  prints `re-persisted:` when it does — but a manager who re-runs a close
  expecting a pure no-op gets one commit. It fires only when the close recorded
  a non-`ok` cleanup status AND the record is on disk AND it is not already in
  `HEAD`.
- **The re-persist reads the ledger** (`read_tx_entries`) on every already-closed
  re-run. Cheap, and already done several times on that path.
- **A refused persist leaves an untracked directory** under
  `.orgasmic/dispatch-records/`. A manager who runs `git add .` before re-running
  the close will sweep it into their own commit — the record is not lost, but it
  lands in the wrong commit. Naming it rather than weighting it.
- **Record commits remain unsigned.** F-4's mechanism is unchanged; only the
  convention now says so. Passing `-S` when `commit.gpgsign` is set would put a
  signing prompt inside every close, which invariant 3 forbids.
- **`BISECT_LOG` is checked but is close to unreachable on its own** — a bisect
  detaches HEAD, so the detached-HEAD refusal fires first.
