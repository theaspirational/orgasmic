# TASK-2QK4P.1.1 review

Verdict: **reject — BLOCK SHIP**.

Review tier: risky. Triggers: P0 priority, recovery-safety blast radius, breadth across more than one crate, and parent-task coupling.

## Findings

1. **P1 HIGH correctness — the completeness types stop before authority verification, so an observation failure can still become absence or invalid evidence.** `crates/orgasmic-daemon/src/recovery_claim.rs:304-371` makes `authority_key` fallible but collapses every `authority_tag` error inside `claim_has_valid_authority` to `false`. `index_recovery_origins_in_session` then uses that boolean at `:1297-1301` to `continue`, and the enumerator returns `AuthoritativeOriginLinks::Complete` at `:1542`. A transient key-file read failure while indexing one of two authenticated links therefore removes that link from a set labelled complete; if the other link matches the loaded claim, `:1635-1642` can return `Valid`. The same class remains after enumeration: `verify_committed_claim_against_session` returns a bare `bool` and maps replacement/origin session open/read/parse failures to `false` at `:2157-2179` and `:2262-2269`; the resolver reads that as invalid, quarantines at `:1644`, and can reach `Missing` at `:1699`, after which `POST /runs/:id/recover` plans a new replacement at `crates/orgasmic-daemon/src/api.rs:9264-9364`. This is the pre-authorised block-ship state: “could not authenticate/read” is still representable as “there was no authoritative link” or “the valid claim was invalid.” The structural pin is blind to it because it inspects only the two new enum declarations; it also merely checks that the `Unobserved { reason: ...` prefix exists (`recovery_claim.rs:4634-4643`), so adding a `links` field after the checked prefix would keep the pin green. No regression injects authority-key failure or a read failure between the cached complete enumeration and claim verification.

2. **P2 MEDIUM perf — one recover POST performs two complete project enumerations, so Acceptance 5 is not met on the production endpoint.** `post_run_recover` first calls `recovery_status_inner` at `crates/orgasmic-daemon/src/api.rs:9028`. That function creates its own `ProjectOriginAuthority` at `:10087` and resolves every failed-recoverable run at `:10092-10093`, which enumerates the project. The handler then discards that authority, creates another at `:9045`, and calls `links_for` at `:9055-9059`, enumerating the same files again in the same decision. `one_authority_serves_every_claim_in_a_project` (`recovery_claim.rs:4487-4556`) only proves reuse when callers already share one authority object; it does not exercise the endpoint’s inventory-then-recover composition. Using the manager-supplied 1.15 GiB / 340 ms single-pass measurement as context (not independently remeasured), POST pays roughly two full passes before action execution, and the second pass is not represented by the inventory metrics.

3. **P2 MEDIUM correctness/usability — the up-front 503 still preempts request errors that do not require authority.** The unresolved-enumeration refusal runs at `crates/orgasmic-daemon/src/api.rs:9054-9070`, before explicit action validation at `:9163-9171`, the “multiple actions; specify action” 409 at `:9209-9215`, and the failed-record `reattach_tmux` 400 at `:9233-9236`. Thus an invalid action against an otherwise valid failed record returns 503 whenever any unrelated session file is unreadable, then changes to the actionable 400/409 after that file is repaired. The symlinked-origin ordering fix covers `origin_authority.envelopes()` only; it does not cover these request validations. The safety refusal needs to precede minting or accepting authority, not input validation.

4. **P2 MEDIUM test/design — the torn-final inference is true of today’s writer but is not enforced at the scanner boundary.** All production session appends found in scope route through `append_session_inner` (`crates/orgasmic-daemon/src/writer.rs:1593-1626`) to `SessionWriter::append`, which serializes one valid envelope, writes the line, writes `\n`, flushes, and `sync_all`s (`crates/orgasmic-core/src/session.rs:257-270`). So the stated whole-line writer invariant is true today. However, `scan_session_lifecycle_complete_reader` defers any parse error at EOF without checking whether the malformed line was newline-terminated (`session.rs:1477-1510`), and its regression explicitly supplies a newline-terminated malformed final line (`:2420-2425`) — a shape the current writer cannot produce as a torn append, because the newline is written only after the serialized JSON write succeeds. The test therefore does not fail if a future writer starts persisting complete malformed lines or otherwise weakens the cross-module invariant. Preserve the liveness exception only for a non-newline-terminated EOF fragment, and make a newline-terminated malformed final lifecycle line unresolved.

## Open Questions

1. **C3 / full-scan cost:** the filesystem fallback is the correct safety source in the current tree; I would not replace it with a cache lacking a completeness generation merely to land this round. The supplied 1.15 GiB / 340 ms measurement is nevertheless an unbounded polling-path regression and warrants a follow-up completeness-generation design before release. The duplicate POST scan in finding 2 is not part of that redesign and should be fixed in this round.
2. **C6 / claim cleanup:** ruling `remove_recovery_claim` out of this round was reasonable. It still has no caller (`recovery_claim.rs:1716` is the only hit) and should get a cleanup/retention follow-up, but claim files are not what selects the slow path: any failed-recoverable tombstone reaches `resolve_authoritative_recovery_claim`, which enumerates before loading the claim. Removing committed claim files alone would not remove the repeated scan.

## Fix Directions

1. Replace `claim_has_valid_authority: bool` and `verify_committed_claim_against_session: bool` with typed three-way results: valid, invalid evidence, and unobserved/error. Propagate unobserved through `IndexedRecoveryOrigins`, `AuthoritativeOriginLinks`, `ResolvedRecoveryClaim`, and the API’s retryable 503 without quarantining. Add running regressions for an nth authority-key read failure and for a replacement/origin read failure after a cached complete enumeration; prove no `Valid`, no quarantine, no new replacement, then prove normal resolution after repair.
2. Share the authority built during POST’s inventory classification with the later claim/mint decision, and add an endpoint-level scan-count test. Report the full cost of every pass.
3. Move authority-independent action validation ahead of the 503 while preserving committed-claim idempotency; keep the completeness check immediately before any branch that can mint or accept recovery authority.
4. In the complete scanner, record whether EOF’s malformed line ended with `\n`; tolerate only a non-terminated final fragment. Update the regression to use the production tear shape and add a newline-terminated-corruption case that remains unresolved.
