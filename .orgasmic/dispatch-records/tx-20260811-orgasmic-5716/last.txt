## Findings

### LOW

**L1 — test, `index.rs:4442-4449`: the new test's barrier can in principle release the gate
before the later waiters have registered.**
The loop waits for `index.refresh_status().await.requests_total < 5`, but `requests_total` is
incremented *before* the coordinator lock is taken — `request_required_refresh` at
`index.rs:731-734` bumps it, then locks at `index.rs:738`; `schedule_watcher_refresh` at
`index.rs:674-676` bumps it, then locks at `index.rs:678`. A counter value of 5 therefore proves
five requests *entered*, not that five waiters are *registered*. If `first_gate.release` fired
in that window the exact-count assertions (`discarded_total == 1`, `scans_total == 2`,
`coalesced_total == 4`) would fail, or the `!newer.is_finished()` assertions would become
vacuous. Impact is test flakiness only, not product behaviour, and I could not make it happen:
30/30 consecutive runs of the test and 5×53 runs of the whole `index::` module at
`--test-threads=8` were green with byte-identical metrics. The idiom is pre-existing
(`index.rs:4392-4399`, `index.rs:4539-4545`), so this is a note rather than a regression. Fix
direction: gate on registered state (`pending_targets`/waiter counts) rather than on
`requests_total`, or move the counter bump inside the lock.

**L2 — docs, `verify/TASK-K9WWM/README.md:35` and `verify/TASK-K9WWM/hardening-round.md:15`:
"immediately scans again" / "triggers an immediate follow-up" contradicts the documented
coalescing floor.** After settling a superseded batch the worker re-enters the trailing-edge
loop at `index.rs:804-830`, so the follow-up scan is floored at 50 ms and bounded at 200 ms —
which the same README states at lines 27-29. An operator reading only the new paragraph will
expect a scan with no delay. Fix direction: say "schedules a follow-up scan through the same
50 ms trailing window".

**L3 — docs, `verify/TASK-K9WWM/README.md:148`: the runbook pre-arms a tooling waiver for the
final gate.** It instructs `ORGASMIC_ALLOW_MISSING_TOOLS=tmux scripts/run-tests.sh -p
orgasmic-cli`, while `hardening-round.md:84` records that `required_test_tooling_is_present`
passed with *no* missing-tool waiver. Given that this task exists precisely because a red must
not be excused, the runbook should not hand the manager a waiver it does not need. Fix
direction: drop the env prefix, or state the exact condition under which it is required.

**L4 — correctness (pre-existing in this task, not introduced by this round),
`index.rs:1178-1183`: a concurrent board-entry change turns a healthy mutation into a committed
503.** `publish_refresh` returns `Err("project {id} registration changed during refresh")` when
`snap.board`'s entry no longer equals the one the projection was seeded from. That `Err` flows
through `settle_captured_error` to `committed_refresh_error` (`api.rs:7832-7839`), so a caller
whose file and tx committed cleanly gets `503 index_status: refresh_failed` because an unrelated
registration edit landed mid-scan. It is reachable: `refresh_board()` runs on the registration
path (`api.rs:1329`) and on any watcher-observed `board.org` change (`watcher.rs:366`), both
concurrent with ordinary project mutations. Same *shape* as the H1 defect — a third party's
arrival becoming this caller's failure — but several orders of magnitude rarer, and the
follow-up scan does converge. Not a blocker; worth a manager-schedulable follow-up to retry the
build once instead of failing the batch.

**Still open from round 3, deliberately not taken this round** (recorded, not re-argued):
L3/L4 Git-probe dedup races at `index.rs:1380-1392` remain uncommented; the stray blank lines at
`.orgasmic/decisions.org:286-287` remain.

## Primary question: does `8672947..b8633cf` repair the H1 contract?

Yes. Each clause of the brief's contract, checked against the code:

| Contract clause | Status | Evidence |
|---|---|---|
| Successful publication acknowledges the batch captured before that scan | **Holds** | `index.rs:950-957` dispatches every `Ok(())` to `settle_captured_ok` with no stale gate in front of it. The old early `continue` at the stale branch is gone; `index.rs:937-948` now only bumps a metric and logs. |
| Duplicate waiter for the same captured `tx_id` may settle with that covered transaction | **Holds, and is sound** | `settle_captured_ok` (`index.rs:968-979`) `remove`s the whole `mutation_waiters` entry, so late duplicates settle too. Sound because a duplicate is only ever appended to an *existing* entry (`index.rs:749-756`), which means a waiter for that tx already existed at capture, which means the tx's bytes were durable before the scan began. |
| Distinct tx ids, explicit refreshes, and watcher requests arriving after capture stay pending and converge | **Holds** | Explicit/watcher drains are count-bounded from the front of the FIFO (`index.rs:980-991`); distinct tx ids are untouched because `settle_captured_ok` iterates only `captured.mutation_waiters`. Convergence is guaranteed by an invariant I checked exhaustively: `superseded == true` implies `has_required()` is still true after settling, because the only bump site is `index.rs:780`, which is reached only *after* the duplicate-tx short-circuit (`index.rs:758-763`) and the completed-tx short-circuit (`index.rs:742-748`) have returned. So the generation can never be bumped by a waiter that this settle removes, and `index.rs:959` always re-loops. No lost wakeup. |
| No healthy superseded generation returns the committed-refresh-failed 503 | **Holds** | `Err` now has exactly two producers — a `build_refresh` failure and a `publish_refresh` failure. Supersession is no longer one of them. (L4 above is a `publish_refresh` failure, i.e. a different arm.) |
| Real build/publication failures settle only the captured waiters, later arrivals converge | **Holds** | `settle_captured_error` (`index.rs:999-1033`) is unchanged: `drain(..captured_count.min(len))` per tx from the front, entry removed only when emptied. Proven live by `arrivals_during_failed_scan_survive_and_converge` (`index.rs:4516`), which I ran. |
| Read-after-write at every successful mutation acknowledgement | **Holds** | Capture takes the coordinator lock (`index.rs:832-850`) and `build_refresh` starts strictly after it is released (`index.rs:886`), so every captured waiter's write precedes the scan's filesystem read. Verified end-to-end on the production HTTP path by `project_task_mutation_is_immediately_visible_with_project_tx` / `..._with_home_tx`, both of which I ran. |

Other audited surfaces:

- **Generation handling.** `required_generation` is `u64` compared for inequality only; `wrapping_add` is a non-issue. `window_generation` (coalescing) and `required_generation` (supersession) remain separate, and `schedule_watcher_refresh` correctly bumps only the former (`index.rs:686-688`) so a watcher event cannot mark a mutation batch superseded.
- **Queue draining / FIFO counts.** `explicit_waiters` and `watcher_waiters` are `Vec`s pushed at the back and drained from the front by captured count in both settle paths — order-correct and over-drain-safe. The `.min(len)` clamps are defensive only: a single worker per target is enforced by `state.running`, so `len >= captured_count` always holds.
- **`watcher_pending`.** Cleared at capture (`index.rs:848`); a watcher arriving mid-scan re-sets it and survives the count-bounded drain, so `index.rs:959` re-loops for it. The `if watcher_waiters.is_empty()` re-clear at `index.rs:994-996` / `index.rs:1030-1032` is a no-op given that `schedule_*_refresh` always pushes a waiter when it sets the flag — harmless, and it makes the invariant explicit.
- **Completed-tx dedup.** `remember_completed` is called for each captured tx on the `Ok` path only, bounded at 1024 with FIFO eviction (`index.rs:408-418`). Eviction costs one extra scan, never a wrong answer.
- **Request cancellation.** `CapturedRefresh` holds `(tx_id, count)` and never senders (`index.rs:484-489`), so a dropped HTTP waiter cannot cancel convergence; sends into a closed oneshot are ignored. `cancelled_waiter_does_not_cancel_refresh_convergence` (`index.rs:4333`) passes.
- **Detached convergence.** The worker owns the loop; `drop(coordinator); continue` at `index.rs:960-961` is the only continuation and it is reached whenever anything is still queued.
- **Slow-log / `discarded_total` semantics.** `stale_discards_for_batch` is replaced by `published_generation_superseded` (`index.rs:931`), which is what the boolean actually means. `discarded_total` is incremented once per superseded successful publication (`index.rs:937-941`) and is documented as such at `README.md:83-85` and in the residual-risk section of the implementer report. Naming is historical but the docs are truthful.
- **Test quality.** `covered_batch_is_acknowledged_while_later_arrivals_converge` (`index.rs:4411`) is genuinely file-backed: TASK-002 is appended to `.orgasmic/tasks/backlog.org` *before* `tx-older` registers (`index.rs:4419-4424`), and the assertions at `index.rs:4478-4486` check the published projection contains TASK-002 and **not** TASK-003 at the moment the second scan is gated, while `newer`/`explicit`/`watcher` are asserted unfinished. It fails against the round-3 contract by construction (the older waiter is `expect`ed to be `Ok`). This is exactly the regression round 3 asked for.
- **Previously accepted fixes, re-verified intact at `b8633cf`.** Off-lock seed builds `tx: Vec::new()` / `parse_errors: Vec::new()` with `drop(seed)` immediately after the bounded reads (`index.rs:1079-1083`, `1104-1110`); failed non-forced Git probe removes only its own key so a later probe retries (`index.rs:1380-1387`); `build_refresh` contains no Git work, so ordinary mutation refresh has no Git delay; the writer's cached-`Transaction` arm sends the replay and falls through without `continue` (`writer.rs:1273-1289`), and `writer_accepts_a_command_after_cached_transaction_replay` passes; `DEFAULT_REQUEST_TIMEOUT_SECS = 10` is unchanged (`daemon_client.rs:48`) and the 30 s run-release timeout predates this task (`ab5cb07`).

  `verify/TASK-K9WWM/README.md`, `verify/TASK-K9WWM/hardening-round.md` — inside the declared
