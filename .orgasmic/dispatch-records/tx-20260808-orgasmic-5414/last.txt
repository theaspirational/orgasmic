## Changed

### `crates/orgasmic-cli/src/manager.rs`

**F-A — `walk_worktree` replaces `directory_bytes`.** One walk, two answers: the
recursive size it already produced, plus `nested_git` — the first NESTED entry
named `.git`, **of any type**, as a path relative to the worktree root. It
descends by `openat(O_NOFOLLOW|O_DIRECTORY)` from the worktree handle exactly as
before, so no `PathBuf` walk was introduced. `ManagedWorktree` carries the
result; `worktree_submodule_refusal` takes it as a third argument and consults it
**only in the `NoRepository` arm**. Depth 1 is excluded, so the worktree's own
dangling `.git` — always present on `RepoGone`, since that is what classified it
— is not its own refusal.

Type-agnostic per the reviewer's first correction: a submodule initialised inside
a linked worktree has a `.git` **file** naming an admin directory that, once the
repository is gone, is gone too. A directory-only predicate returns false on the
likeliest shape. `the_worktrees_own_dangling_git_link_is_not_a_nested_repository`
and `a_repo_gone_worktree_is_refused_over_a_nested_git_of_any_type` pin both
directions, the latter using the `.git`-as-FILE shape specifically.

**Ordering (acceptance 2) — nothing moved, and nothing needed to.** The
reviewer's statement that "the refusal currently sits ABOVE the size walk" is
inverted. The walk runs in `scan_managed_worktrees`, which is the *first* thing
`worktree_prune` does — before the cleanup lock, before the reservation, and long
before the refusal, which runs inside `reclaim_managed_worktree` under the guard
(`manager.rs`: walk at the classification loop, refusal at the top of
`reclaim_managed_worktree`). So the `NoRepository` leg consumes a result computed
*earlier*, not later, and no reordering of a destructive path was performed. What
that does cost is stated at the call site and under Residual Risk.

**F-B — the help sentence.** The false conjunction is split in two. The refusal
is still described as categorical and as running before every removal including
repo-gone; index-reading is now attributed only to the branch that has an index;
and the repo-gone branch states its own, explicitly **weaker**, check ("the
anchored walk of the tree's own contents refuses any NESTED `.git` entry, of any
type, and nothing else there is checked"). A closing sentence says there is no
`--force` on this verb.

**F-C — deleted, not rewritten.** "It is re-taken before EACH subprocess" is gone;
the comment now points at the three-window enumeration in the doc comment. No
third description was composed.

**F-D + correction 2 — `advice` split three ways.** `submodule_advice` (offers
`--force` conditionally, "while the repository is still there"), `record_advice`
for the record-unreadable refusals — split index, symlinked `.gitmodules`,
unparsed index — which now says plainly that nothing here claims a submodule
exists, and a third remedy inline in the `NoRepository` refusal that names the
offending path, says `git worktree remove --force` **cannot** run because the
repository it would run against is the one that is gone, and tells the operator
to delete the named path themselves.

**One change beyond the finding list, and it is not cleanup.** `entry_names`
now calls `rewinddir` on the stream. `dup` shares the *file description* — and
therefore the directory read offset — with the caller's handle, so a **second**
enumeration of the same handle resumed at EOF and returned an empty list, which
every caller here reads as "this directory is empty". In a destructive verb that
is a fail-open in both directions: no nested repository to refuse over, and
nothing left to remove. Found by the new unit test, which walks one handle twice.
I found no live path that enumerates the same handle twice today (production
opens a fresh child handle per walk), so I am reporting this as a **latent**
fail-open the new predicate would otherwise depend on, not a shipped defect.

## Residual Risk

1. **`nested_git` is a classification-time observation consumed under the
   guard.** It describes the same *identity* the handle was just re-proven to be,
   so it cannot have drifted onto another directory — but it can be stale about
   that directory's *contents*. A nested repository created between the scan and
   the reclaim is not seen. This is the price of the single-boolean approach the
   brief preferred over a second traversal; the reverse case (one deleted after
   the scan) only produces a spurious refusal, which costs a re-run. Closing it
   needs the walk repeated under the guard, which is the full descent this
   deliberately avoids.
2. **The walk skips unreadable entries**, inherited from the size walk, where an
   under-count was the honest choice. For this signal that is a fail-open: a
   `.git` under a directory that fails to open is not seen. It is why the signal
   only ever *adds* to the other refusals and replaces none.
3. **`MAX_DEPTH` is 64.** A nested repository deeper than that is not seen. Same
   bound the size number and the removal already carry.
4. **The heuristic is deliberately over-broad in the keep direction.** A
   repo-gone worktree holding a vendored `.git` that git would have let you
   delete is now kept, and the operator must delete it by hand. This is ruling 1
   plus the project's standing cost asymmetry, scoped to a state that only arises
   once the repository has already disappeared.
5. **On `RepoGone`, the new refusal shadows the `.gitmodules` branch** when a
   nested `.git` is present — both would refuse, but the operator now sees the
   nested-repository message. That is why
   `worktree_prune_refuses_a_repo_gone_worktree_containing_a_submodule` now
   passes through the new arm rather than the old one. Its assertions still hold
   unchanged (`vendor/sub` matches inside `vendor/sub/.git`), which I checked
   rather than assumed after it went red on the first wording.
6. **Not run, and therefore not claimed:** the full workspace suite (only
   `-p orgasmic-cli`, which is what the brief gated on), the `orgasmic-daemon`
   suite, and the UI checks. Nothing outside `orgasmic-cli` was touched, and
   `clippy --workspace --all-targets` compiled every crate and target.
7. **Non-Unix is untested.** Everything new is `#[cfg(unix)]`, consistent with the
   surrounding code.
8. **`rewinddir` (item under Changed) is the one change outside the finding
   list.** It is one line, it is a fail-open in a destructive verb's enumeration
   primitive, and the new predicate's soundness under repeated use depends on it.
   I could not find a live path that hits it today. If the reviewer would rather
   see it split out, it reverts cleanly on its own — but the unit test that found
   it goes red if it does.
9. **Same-family review is likely again** (TASK-52NJS). The strongest independent
   checks a reviewer can make here without re-running anything: the F-A red is
   quoted verbatim above and is reproducible by checking out `dc6a863` and
   cherry-picking only the new test; and the cli_parity pin's bite is reproducible
   by restoring the old help sentence, which is printed in full in the failure
   message.
