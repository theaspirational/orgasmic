## Findings

### P1 · MEDIUM · test — `PROBE_CHILD_DEADLINE < WORK_PROBE_TIMEOUT` is now load-bearing in the new docs and still enforced by nothing

Anchors: `crates/orgasmic-daemon/src/supervisor.rs:5449-5451` (the invariant, as
prose), `:5498-5507` (the new whole-call contract, which tells callers to bound
their *wait* instead — only sound while the child deadline is the smaller
number), `:5463` (the constant), `:86` (`WORK_PROBE_TIMEOUT`),
`:11287` (the one assertion with teeth).

`grep -n PROBE_CHILD_DEADLINE crates/orgasmic-daemon/src/supervisor.rs` returns
the definition at `:5463` and exactly three production call sites (`:5635`,
`:5651`, `:6019`). No test and no `const` assertion references it. Concrete
failure scenario: someone raises `PROBE_CHILD_DEADLINE` to 6 s to accommodate a
slower mux, inverting the documented relationship so the child deadline can no
longer fire before the sweep gives up. All five focused tests still pass —

- `a_probe_child_that_never_exits_...` (`:11023`) and
  `..._leaving_a_descendant_...` (`:11091`) use a **test-local** 2 s deadline;
- the new `probe_spawn_latency_is_additive_...` (`:11109`) uses a test-local
  200 ms deadline (`:11116`);
- `a_hung_mux_binary_...`'s `wait_for_pid_to_disappear(hung_child, 5s)`
  (`:11287`) only *starts* after the ~5 s outer await has returned, so it
  tolerates a child deadline of roughly 10 s.

So the brief's requirement "still catch a child-deadline regression before the
outer sweep timeout" is met for two of the three regression shapes — deadline
measured *before* spawn (caught by `post_spawn_wall >= child_deadline`,
`:11156`) and deadline removed entirely (caught by the pid assertions) — but not
for "deadline raised past the outer sweep timeout". This is the one item from
the prior review's fix direction 1b (`tx-20260812-orgasmic-5992/last.txt`,
"add a compile-time or unit assertion pinning
`PROBE_CHILD_DEADLINE < WORK_PROBE_TIMEOUT`") that was not delivered, and the
implementer's report declares "Unmet Criteria: None", so it was not consciously
declined either. Method: source reading plus the grep above; I did not mutate
the constant, as the role is read-only.

### P2 · MEDIUM · test — the rmux recovery test lost the only runtime proof that its fixture lands on the owned server, and a lost pin now leaks silently

Anchors: `crates/orgasmic-daemon/src/api.rs:32935-32943` (new body), old body at
`git show 2d89827:crates/orgasmic-daemon/src/api.rs:32936-32956` (the deleted
`server.session_names().contains(&session_name)` assertion),
`crates/orgasmic-drivers/src/modes/rmux.rs:679-684` (`owns_runs_on`), `:725-747`
(the reap on drop).

Reusing `claim_owned_rmux_endpoint` (`api.rs:36769-36785`) is the right call and
it does preserve both locks in workspace order (flock, then environment) — but
the helper hands back only the environment guard, so nothing in the test reads
the owned endpoint back any more. The dropped assertion was the detector for a
specific, reachable failure: `MuxMode::start_detached_session`'s rmux arm spawns
with no `-S` and relies entirely on the `RMUX_TMPDIR` pin, and
`LiveSessionGuard::owns_runs_on` reaps by `orgasmic-rmux-*` prefix **at the
owned endpoint only**. If the pin is ever lost or regressed, the fixture session
is created on the SHARED server that hosts live dispatch panes, the guard's drop
does not find it, and the test still reports green. The equivalent assertion
survives only for the artifact path (`api.rs:38569-38576`), which drives
`post_artifact_generate`, not `start_detached_session`, so it does not cover
this test's fixture. Fix: `own_rmux_server_for_tests()` is idempotent and is
re-fetched exactly this way at `api.rs:38569`; re-fetch it and reinstate the
containment assertion on the `Option<String>` the helper already returns.

### P3 · LOW · test — the new test's whole-call upper bound is ~10× the budget it guards, so only the lower half of the contract is really pinned

Anchor: `crates/orgasmic-daemon/src/supervisor.rs:11161`
(`total_wall < spawn_wall + child_deadline + Duration::from_secs(2)`) against
`child_deadline = 200ms` at `:11116`.

The lower-bound assertions (`spawn_wall >= injected_spawn_latency` `:11150`,
`post_spawn_wall >= child_deadline` `:11156`) are exact and deterministic — they
are what proves the remediation. The upper bound is not: a regression that
multiplied the post-spawn budget by anything up to ~11× (a second sequential
deadline chain, or the drain ceasing to share `expires_at`) passes it. Measured
on this host under load 6.5–10.2: spawn 1.4–3.5 ms, post-spawn fixture setup
3.9–10.9 ms, so cleanup has orders of magnitude of headroom and the tolerance
could be tightened substantially without reintroducing host sensitivity.

### P5 · LOW · design — the worst-case sweep overrun is now documented but still unmitigated

Anchors: `supervisor.rs:1601-1611` (new caller doc), `:5498-5507` (new callee
doc), `:86` (`WORK_PROBE_TIMEOUT` = 5 s), `:5463` (2 s), and the three chained
call sites `:5364-5365` (`work_probe_root_pid` → `pane_pid`), `:6019`
(`process_cpu_table`), `:5651` (`pane_content`).

One `observe` can chain three deadlined children, so the worst case is
`3 × (spawn + 2 s) ≥ 6 s` against a 5 s outer await — the blocking-pool thread
and its live child outlive the sweep, which is the leak shape TASK-JQ8AV.1
closed, reachable through latency rather than through a missing deadline. The
aggregate `3 × 2 s > 5 s` pre-dates this task; what this round changed is that
the docs now say so plainly instead of claiming the probe sits "well inside the
5 s". The prior review's option (a) — one shared budget threaded through all
three calls so the sweep stops depending on spawn latency at all — remains the
only change that would actually bound it. Recorded as the standing residual
because the dispatch brief explicitly accepted the documented-formula approach
for this round, not as a defect of this diff.

## What passed independent verification (no findings)

- **The child gets the complete post-spawn deadline, and nothing pretends spawn
  is cancellable.** `expires_at` is bound after `spawn` returns
  (`supervisor.rs:5526-5531`); the docs at `:5498-5507` and `:1601-1611` state
  the `spawn + child deadline + synchronous cleanup` contract and say outright
  that there is no finite whole-call bound independent of spawn latency. That is
  an accurate description of the code, not an overstatement.
- **The delayed-spawner test is deterministic and catches the regression it
  names.** The seam injects 350 ms against a 200 ms budget
  (`supervisor.rs:11116-11117`). Restoring the pre-`7ed905b` ordering
  (`expires_at` computed before `spawn`) makes the wait loop break on its first
  iteration, driving `post_spawn_wall` to ≈0 and failing `:11156`. All the
  timing terms it asserts are either `thread::sleep`-guaranteed or
  loop-guaranteed, so it does not depend on host scheduling for its verdict.
- **No detached or unowned threads.** The only thread is the pre-existing stdout
  reader, and it is `join`ed on all three exit paths
  (`supervisor.rs:5552-5558`, `:5564-5569`, `:5570`). The injected spawner runs
  inline on the blocking-pool thread that already owned the call. Group kill,
  `child.wait()` reap, the shared absolute drain deadline
  (`drain_finished_by`, `:5580-5593`) and the `status.success()` gate are
  byte-identical to `2d89827`.
- **Fail-closed evidence/release behaviour is unchanged.**
  `observe_work_evidence`'s body (`:1612-1626`) changed only in its doc comment;
  `Ok(Err(_)) | Err(_) => WorkEvidence::Unknown` is intact, and no release path
  was touched by the diff.
- **The pidfile tests no longer rely on a 400 ms post-spawn window.** Both are
  now 2 s (`supervisor.rs:10998`, `:11062`) and both keep their
  `elapsed < deadline + 3s` return assertion and their concrete
  process-group-disappearance check. Measured on this host at load 6.5–10.2
  (20 iterations of the same `/bin/sh -c "sleep 120 & echo $! > f; wait"`
  fixture): `spawn` 1.4/1.9/3.5 ms min/median/max, post-spawn setup
  3.9/5.2/10.9 ms. The change moves the `/bin/sh` exec — the Gatekeeper-priced
  term this task exists to handle — *out* of the budget and widens what is left
  5×, so the fixture now needs only the `/bin/sleep` exec to fit in 2 s where it
  previously needed both execs to fit in 400 ms. That is roughly a 10×
  improvement in tolerance; it is a widened budget, not an eliminated race, and
  the degraded-`syspolicyd` state was not recreated (see Verification Notes).
- **The rmux test's skip-before-pin is correct and safe.**
  `MuxMode::Rmux.availability()` (`api.rs:29271-29277`) is a pure
  `probe_rmux_binary().found` check with no endpoint dependency, so running it
  before the pin cannot touch the shared server. `skip_mux_mode_if_unavailable`
  is then called a second time inside the shared helper (`api.rs:32852`); that
  is harmless — `skip_test_if_missing` (`rmux.rs:440-453`) only `eprintln`s and
  returns a bool. Lock order (flock then environment) matches the family.
- **Scope is clean.** `git diff --name-only 2d89827..fa869cc` is exactly
  `crates/orgasmic-daemon/src/api.rs` and
  `crates/orgasmic-daemon/src/supervisor.rs`. `verify/` and
  `crates/orgasmic-drivers/` are untouched (0 files each), so no flake-registry
  entry was added and TASK-T7KSH's undeadlined `rmux -V` is not folded in. The
  merge `fa869cc` adds nothing beyond `164a005` except the empty dispatch-record
  file in P4.

## Fix Directions

1. **P1** — add the missing enforcement, ideally as a `const` assertion next to
   `PROBE_CHILD_DEADLINE` (`supervisor.rs:5463`) so it costs no runtime and
   cannot flake:
   `const _: () = assert!(PROBE_CHILD_DEADLINE.as_millis() < WORK_PROBE_TIMEOUT.as_millis());`
   That closes the third regression shape without reintroducing any wall-clock
   assertion on a loaded host.
2. **P2** — in `api.rs:32941-32943`, keep `claim_owned_rmux_endpoint` and add
   back the containment check by re-fetching the idempotent server exactly as
   `api.rs:38569` does, asserting on the `Option<String>` the helper already
   returns.
3. **P3** — tighten `supervisor.rs:11161` from `+ Duration::from_secs(2)` to
   something proportionate to the 200 ms budget (a few hundred ms is ~30× the
   measured cleanup cost on a loaded host).
4. **P4** — for the manager, not the implementer: fix or drop the
   `implementer.reported` `REPORT_PATH` so it names a record that exists, avoid
   committing 0-byte `last.txt` files, and copy this round's answers to

   `evidence`/`worklog` before the temp directory is swept.
5. **P5** — file the shared-probe-budget change (one clock across `pane_pid` +
   `process_cpu_table` + `pane_content`) as its own task if the sweep is ever
