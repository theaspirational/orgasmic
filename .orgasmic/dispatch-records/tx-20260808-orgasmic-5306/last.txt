# TASK-2QK4P — crash-recovery replay 409

## Headline

Fixed, and **the premise in the task heading is false**: this is not a TASK-RMA18
regression. It is a pre-existing, intermittent defect in the recovery-claim
resolver, and the bisect that named RMA18 sampled one run per commit on a test
that fails 40–50% of the time.

## Root cause (measured, not inferred)

`/api/runs/<id>/recover` answered 409 because
`resolve_authoritative_recovery_claim` (`crates/orgasmic-daemon/src/recovery_claim.rs:1248`)
required a Committed claim to be corroborated by exactly one link in
`indexed_origins` before it would accept it. `indexed_origins` comes from
`collect_recovery_origin_index` (`api.rs:11823`), whose candidate files come from
`RunCatalog::entries_for_project`. The catalog is a cache **with holes on
purpose**: `RunCatalog::invalidate_session` (`run_catalog.rs:1124`) *removes* the
record on every lifecycle append so the next refresh rebuilds it.

The replacement a replay is asked about is LIVE — the dead daemon spawned it, the
restarted daemon reattaches it — so it appends, its catalog record is dropped,
and the index carries no link for it until the next refresh. A replay landing in
that window read the silence as disproof, quarantined a claim it had *just*
verified against that replacement's own transcript, fell through to a fresh
acquire, and got `LeaseHeld` from the live replacement.

One captured run has the whole chain (`scratchpad/loop_4.log`):

```
TEMP invalidate-removed: .../recover-9b91e325-….jsonl replacement=Some("run-20260808T095404-1ba18a…")
TEMP index: dir=[recover-9b91e325-….jsonl, run-fault-origin.jsonl] candidates=[] catalog_all=[only the origin]
TEMP resolve: exists=true matching=0 claim_eq=None verify=true indexed_total=0
→ commit: replay status 409 {"error":"recovery blocked by an active lease",
                             "active_run_id":"run-20260808T095404-1ba18a…"}
```

`verify=true` and `matching=0` in the same line is the defect: the claim proved
itself and was destroyed by a cache miss. The `active_run_id` in the 409 is the
same run id the catalog had just forgotten.

The second observed symptom (`400 recovery action start_recovery_run is not valid
for run run-fault-origin`, at point `response`) is the same cause one call
earlier: `apply_recovery_claim_to_run` resolves first, gets
`InvalidQuarantined`, and clears `recovery_actions`.

## The fix

One condition, in `resolve_authoritative_recovery_claim`:

```rust
let contradicted = matching.len() > 1 || matching.iter().any(|link| link.claim != claim);
if !contradicted && verify_committed_claim_against_session(home, project_root, &claim) { … Valid }
```

An index that **contradicts** the claim (a disagreeing link, or two links for one
origin) still quarantines — `duplicate_authenticated_replacements_fail_closed`
still passes. An index that is merely **silent** no longer does.

What still guarantees replay idempotency: `verify_committed_claim_against_session`
re-derives the claim from the replacement transcript — daemon-keyed HMAC
authority tag, `RecoveryOrigin` envelope naming this origin *and* this
`request_id`, replacement run/runtime/boot identity, immutable-plan match, and
the origin session's own identity. Note the old rule made duplication *more*
likely, not less: quarantining the valid claim is precisely what let the handler
mint a second replacement beside the live one.

TASK-RMA18 implementer's "pre-existing / host load" call was right about *class*
and wrong only in giving up on it.

## Why the round went out green

Three separate things, none of which the gate itself got wrong:

1. **The test is intermittent, so one green run proves nothing.** `run-tests.sh`
   ran it and it passed that time. Nothing in the pipeline repeats a
   crash-recovery test, and nothing scores a pass-rate.
2. **A per-binary number was read as per-crate.** "738 passed" was the lib binary
   (`orgasmic_daemon-<hash>`). This crate has **23** test binaries;
   `recovery_fault_restart` is one of them. `run-tests.sh` already aggregates all
   of them and prints one `failures:`/`crashed:` verdict — the misreading came
   from quoting a raw `test result:` line instead of the verdict block.
   (My run: 23 binaries, `failures : 0`, lib now 739 with the new test.)
3. **The review ran no tests by brief.** Its residual-risk note named this gap
   exactly; that is the brief's cost, not the reviewer's.

Recommendation (outside my write scope, `scripts/**`): the fix for (2) is to
quote the VERDICT block, never a `test result:` line — the script already refuses
to let a crashed binary hide. For (1), a repeat-count for the crash-recovery
binary would have caught this in one round.

## Diagnostics kept

`recovery_fault_restart.rs` now prints the 409 **body** in the panic message.
`restarted.diagnostics()` was empty and the body carries the whole answer; this
one-line change is what turned an afternoon of reading into one run.

## Residual risk

- The same "cache silence read as absence" shape survives one step away: when the
  claim FILE is missing, `reconstruct_or_quarantine` uses the index to rebuild
  it, and a blind index yields `Missing`. No boundary in this fault matrix
  reaches that state with a live replacement, so it is not reachable today, but
  it is the same inference.
- `collect_recovery_origin_index` is left as-is: it is still catalog-derived and
  still incomplete during that window. This fix makes the incompleteness
  harmless for a claim that can prove itself, rather than making the index
  complete.
- 12/12 is not proof of zero rate; it is ~99.8% confidence against the measured
  ~45% rate. The new unit test, not the repetition, is what pins the mechanism.
