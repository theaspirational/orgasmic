NO — I would not reinstall the operator runtime on this tree.

# Verdict

`reject`

The Unix backend fixes for F1/F3/F4/F5 are substantially correct and the focused regressions are green, but two acceptance-critical gaps remain: the operator UI never receives/renders the failed-recoverable records carrying the new repair diagnostic, and F2's test never crosses the production boot decision that owns the irreversible `Reattach` write.

# Findings

## P1 HIGH bug/operability — the F3 operator notice is wired to buckets that can never carry it

`crates/orgasmic-daemon/src/api.rs:12084-12090` applies `recovery_unobserved*` only to `failed_recoverable` records, and `GET /runs` serializes those records under `failed_recoverable` at `api.rs:7552-7569`. But `ui/src/lib/types.ts:445-452` omits that bucket from `RecoveryInventoryResponse`, and `ui/src/components/RunsView.tsx:54-62` flattens only `interrupted`, `reattached`, `ambiguous`, and `terminal_noop`.

The new `recoveryUnobservedNotice` call therefore runs only on classifications that cannot carry the diagnostic. The permanently refused recoveries are absent from the table, so the operator still cannot see the named file or documented repair. This violates acceptance 5 and the pre-authorised operability blocker.

Recorded immediately as `tx-20260808-orgasmic-5522`.

Fix direction: add `failed_recoverable: RecoveredRun[]` to the TypeScript response contract, flatten/render it in `RunsView`, and add a component test whose mocked `failed_recoverable` record proves the reason cell visibly contains both the sanitized subject and remediation text.

## P1 HIGH test/acceptance — F2 never enters the production boot route or any writing code

`crates/orgasmic-daemon/src/recovery_claim.rs:6649-6715` calls `pending_recovery_claim_owns_session` directly, asserts the enum is not `Invalid`, and compares a session file that no exercised code can write. It never invokes `api::boot_reattach_ownership`, `reattach_live_runs_on_boot`, or `Supervisor::reattach` (`api.rs:10709-10790`).

Changing boot to reattach on `ClaimEvidence::Unobserved` would leave this regression green. The test therefore does not prove acceptance 4's production boot routing/no irreversible session write boundary, despite its comments claiming that path.

Recorded immediately as `tx-20260808-orgasmic-5519`.

Fix direction: make the nth-entry `readdir` seam available to an API boot test, route a real boot candidate through `reattach_live_runs_on_boot` (or an extracted decision that owns the reattach call), assert no supervisor reattach and byte-identical JSONL while faulted, then clear the fault and prove normal routing.

## P2 MEDIUM test — the non-UTF-8 regression has no teeth on the platform that runs it

`crates/orgasmic-daemon/src/recovery_claim.rs:6728-6790` accepts APFS/HFS+ `EILSEQ` and checks only that `names()` returns `Vec<OsString>`. My exact `--nocapture` run printed that the byte-preservation half did not run.

That type pin does not catch the old defect: `names()` could again call `to_str()`, silently drop `Err` entries, and still return `Vec<OsString>`. With no Linux gate here, the unsafe regression remains green on the configured platform.

Recorded immediately as `tx-20260808-orgasmic-5520`.

Fix direction: add a platform-independent raw-dirent/name-decoding seam that feeds invalid bytes through the production collection/filter logic, or require a Linux gate that executes the byte assertions. Prove the former drop/lossy-conversion implementation reds.

## P2 MEDIUM test/tooling — the derivation has no coverage self-check and incompletely reports its residual

`scripts/derive-observation-surface.py:195-243` searches for the next `{` after every `fn`, so semicolon-only trait/extern declarations acquire unrelated bodies; current examples are `WorkEvidenceProbe::observe` at `supervisor.rs:4834` and `setsid` at `modes/stdio.rs:584`. Its test-module regex misses `pub(crate) mod tests`, including the large API test module. `--report-dynamic` scans bodies only at `derive-observation-surface.py:362-370`, so it emits one row and omits the reachable `&dyn WorkerDriver` signature plus `driver.acquire(...)` call at `supervisor.rs:1735-1790`.

The reported 935 names / 96 leaves are therefore a test/macro-inflated superset, not a checked production call graph. I found the critical `ClaimDirectory::{open,read_regular,names}` and session leaves in the output and did not prove a current authority-decision leaf missing from the final superset, so this is not a second derivation block-ship finding. It does mean C2's requested self-check is needed.

Recorded immediately as `tx-20260808-orgasmic-5521`.

Fix direction: use a Rust parser/type-aware graph, or at minimum pin lexer EOF, declaration-vs-body ownership, `cfg(test)` exclusion including restricted visibility, indexed-item coverage, and dynamic call sites found in signatures. Keep the stated receiver-inference residual.

# Open Questions

No unresolved question changes the verdict.

- C3: the shipped Unix errno direction is sound. `EISDIR` and `ENAMETOOLONG` are observed disqualifying path facts; the default remains `Unobserved`. I did not re-open the ruled-out non-Unix policy.
- C4: treating an absent sessions directory as `Complete([])` is safe for the canonical path: `ENOENT` proves no directory entries/links exist there, while claims are loaded independently. Access/IO/resource failures still produce `Unobserved`.
- C5: the test-only `readdir` branch faithfully creates the syscall boundary's errno-bearing NULL and does not alter ordinary test-build calls. The missing proof is above it, at the production boot action boundary.
- C7: compile-time-only exhaustiveness is appropriate here. Every current unobserved resolver path is converted before the helper; the explicit arms plus structural wildcard pin prevent a future enum variant from silently becoming `NotAuthoritative`.
- C9: project-wide refusal should stay. Isolating an unreadable member and calling the remainder complete recreates the original uniqueness defect. The backend subject/remediation/repair design is sound; the UI fails to expose it.
- C10: raw `ClaimDirectory::{rename,remove,sync}`/`write_claim_atomic` errors are write-side and legitimate follow-ups. `SessionDirectory`/`SessionFile` reads are generally converted through `session_read_evidence`; the race-only `reconcile_pending_claim` direct 500 remains an operability follow-up, not a path that reports failed observation as authority or destroys evidence.
