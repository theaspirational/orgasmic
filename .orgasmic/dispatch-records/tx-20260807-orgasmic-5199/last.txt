# TASK-QGWK7.1.1.1 review — the guard is one marker short of total, and `git revert --abort` is the casualty

## Verdict: **REJECT**

One BLOCK SHIP, three LOW. The mechanism of every fix is right: F-1's repair
lives in exactly the correct place (`commit_promoted_dispatch_record` only ever
needed `dest_dir`), F-2's ref-named CAS is correct and its shim test is sound and
leak-free, F-5/F-6 are correct, and the convention prose is true where it speaks.
The reject is for one line: **F-3's sequencer guard omits `REVERT_HEAD`**, which
is the acceptance criterion "a close during *any* sequencer operation cannot lose
the record" left unmet — and the measured symptom is worse than the loss it was
meant to prevent.

---

## F-1 — BLOCK SHIP (bug, correctness) — the sequencer guard misses `git revert`, and a record commit written there WEDGES the operator's `git revert --abort`

`crates/orgasmic-cli/src/manager.rs:5760-5773` (`sequencer_operation_in_progress`),
convention at `shipped/prompt-studio/conventions/manager-dispatch.org:340`.

The guard checks `rebase-merge`, `rebase-apply`, `MERGE_HEAD`,
`CHERRY_PICK_HEAD`, `BISECT_LOG`. It does **not** check `REVERT_HEAD`. `git
revert` is the same sequencer machinery as `cherry-pick` — git writes both under
`.git/sequencer/` — and its `--abort` has the same HEAD-rewinding contract that
made `rebase --abort` the finding in the first place.

**Measured, three scratch repos, same fixture (conflicted revert of `c2` while at
`c3`), verbatim:**

| repo | what the close leaves | `git revert --abort` | record afterwards |
| --- | --- | --- | --- |
| **control A** — guard fires (what merge/rebase/cherry-pick/bisect get today) | promoted file on disk, untracked, nothing staged | **exit 0** | on disk, recoverable by the re-run |
| **control B** — staged-only, the pre-QGWK7.1.1 baseline | record staged | **exit 0** | **GONE** (the pre-existing loss) |
| **case C** — shipped behaviour today, `REVERT_HEAD` unguarded | record COMMITTED on `main` | **exit 128** — `error: Untracked working tree file '.orgasmic/dispatch-records/tx-1/last.txt' would be overwritten by merge` / `fatal: Could not reset index file to revision <record-commit>` | commit stuck at HEAD; `REVERT_HEAD` **still present**; index left `D .orgasmic/…/last.txt` + `UU f.txt` |

Case C is strictly worse than *both* controls. The operator typed `git revert
--abort`, got a fatal, and their revert is still in progress with a mangled
index — and nothing in the close's output warned them. That is not "a
pre-existing class not made worse"; it is a class the guard was written to close,
left open, with a failure mode the guarded operations do not have.

The window is wider than "a conflicted revert", too. **Measured:** a *clean*
`git revert -n --no-edit HEAD` — the ordinary way to stage a revert before
editing it — also leaves `REVERT_HEAD` present. Any manager who stages a revert
and then runs a close is in case C.

And the shipped convention documents the guarantee the code does not provide:
line 340 enumerates "(rebase, am, merge, cherry-pick, bisect)" — the same
incomplete set. `shipped_conventions.rs` pins the prose, so the prose is pinned
*wrong*.

**Fix:** add `("REVERT_HEAD", "revert")` to the array at `manager.rs:5761-5767`,
and — belt and braces for a multi-commit `revert`/`cherry-pick` range that is
between picks — `("sequencer", "revert or cherry-pick sequence")`. Add `revert`
to the convention's parenthesis. One line of code, one word of prose. Pin it with
the same shape as
`a_close_inside_a_conflicted_merge_keeps_the_record_and_persists_nothing`
(`manager.rs:9776`), swapping the conflicted merge for a conflicted revert.

## Answering the brief's central question: **is the persistence story total?**

No — one cell (revert) is undefined-and-harmful, and two more are defined but
surprising. State table, derived from source and checked against the probes:

### HEAD shape × first close (sequencer clean)

| HEAD | what happens | where the record ends up |
| --- | --- | --- |
| branch | `symbolic-ref -q HEAD` → `refs/heads/X`, CAS on that ref | in history on X ✓ |
| detached | `symbolic-ref -q` exits 1 → refused **before** the real `git add` | on disk, untracked, `partial` ✓ |
| unborn | **`symbolic-ref -q HEAD` SUCCEEDS** (measured: returns `refs/heads/main`); `rev-parse --verify HEAD^{commit}` then fails, still before the `git add` | on disk, untracked, `partial` ✓ |

The two unusual shapes are now symmetric, as claimed — but by two different
gates, not one. Worth knowing if someone later reorders those four lines.

### Sequencer × first close (HEAD on a branch)

| operation | marker | refused? |
| --- | --- | --- |
| rebase / rebase -i | `rebase-merge` | yes ✓ |
| `git am`, `rebase --apply` | `rebase-apply` | yes ✓ |
| conflicted merge | `MERGE_HEAD` | yes ✓ |
| conflicted cherry-pick | `CHERRY_PICK_HEAD` | yes ✓ |
| bisect | `BISECT_LOG` | yes ✓ |
| **conflicted revert, or any `git revert -n`** | **`REVERT_HEAD`** | **NO — F-1** |

### Commit outcome × re-run

| first close | re-run 1 | re-run 2 |
| --- | --- | --- |
| `ok`, committed | status `ok` → repersist skipped, silent ✓ | silent ✓ |
| commit failed (lock / ignore rule) | repairs and prints `re-persisted:` ✓ | in HEAD → silent ✓ (pinned by the test's third run) |
| refused (sequencer / detached), blocker still present | refuses again, warns, names the on-disk path ✓ | same ✓ |
| refused, blocker gone | repairs ✓ | silent ✓ |
| committed **but** status non-`ok` for an unrelated reason (worktree/branch failure) | `dispatch_record_is_in_history` → true → skipped ✓ **no duplicate** | ✓ |
| close died **before** its tx was appended | not `AlreadyClosed` → full cleanup re-runs → `promote_dispatch_artifacts_in_place` bails `last_path missing` → `partial`, tx now written | **third** run reaches `AlreadyClosed` and repairs. Recoverable, but it costs three runs and nothing says so. |

I chased the duplication cell the brief asked for specifically and could not
reach it: producing it needs status non-`ok` **and** record in history **and**
record on disk **and** absent from `HEAD`, and any `git checkout` that takes you
to a branch lacking the record commit deletes the tracked directory on the way,
which drops `dest_dir.is_dir()`. The trigger is tight enough (`recorded
CLEANUP_STATUS non-ok` AND `dest_dir` exists AND absent from `HEAD`).

I also checked the "gated behind a status some path does not set" question
(brief Q3). It holds up, via a non-obvious route:
`cleanup_status_reports_failure` (`manager.rs:7904`) excludes `ok` and
`cleanup_already_run`, and the staggered multi-task close that could stamp
`cleanup_already_run` over a `partial` cannot, because `close_tx_ran_cleanup`
(`manager.rs:7782`) only sets that flag for `ok`/`worktree_missing`. A
`worktree_failed` first leg still reports failure and still repairs. That is
load-bearing and undocumented — worth a comment, not a finding.

## F-2 — LOW (design) — the re-persist commits to whichever branch the manager is standing on, not the one the close resolved

`manager.rs:5806-5827` → `commit_promoted_dispatch_record:5686-5705`.

`repersist_dispatch_record_best_effort` calls straight into
`commit_promoted_dispatch_record`, which re-resolves `symbolic-ref -q HEAD` **at
re-run time**. The branch the original close resolved is recorded nowhere — I
grepped the close tx extras (`manager.rs:4941-4950`): `WORKTREE`, `BRANCH` (the
*dispatch* branch, not the manager's HEAD), no HEAD ref. So:

> close on `feature-x` fails to commit (index lock) → record on disk untracked →
> manager `git checkout main` (untracked files survive a checkout) → re-runs the
> close → the record lands on `main`.

Not lost, not duplicated, and arguably `main` is a fine home — but F-2 of the
parent round was filed precisely against "the record commit cannot land on a
branch the close did not resolve", and the re-persist path is exempt from that
property by construction. The new test
(`a_record_commit_cannot_land_on_a_branch_the_close_never_resolved`) pins the
first-close path only.

**Fix direction:** either stamp the resolved ref on the close tx and have the
re-persist refuse when it does not match (with the ref named in the refusal), or
say in the convention that the repair lands on your current branch, so re-running
a close from an unrelated branch is a known move. Source-derived; I did not
measure this one through the binary.

## F-3 — LOW (docs) — the stated `BISECT_LOG` residual is backwards, twice

Implementer report, "Residual Risk": *"`BISECT_LOG` is checked but is close to
unreachable on its own — a bisect detaches HEAD, so the detached-HEAD refusal
fires first."*

Both halves are wrong. **Measured:** after `git bisect start` alone, `BISECT_LOG`
and `BISECT_START` are present and `symbolic-ref -q HEAD` still returns
`refs/heads/main` — HEAD is **not** detached; it only detaches once you mark
good/bad. And even in the detached phase the ordering in
`commit_promoted_dispatch_record` puts `sequencer_operation_in_progress`
(`:5692`) **above** the `symbolic-ref` resolution (`:5706`), so the bisect
refusal fires *first*, not second. The check is fully reachable and correctly
named; only the residual is false. Same shape as last round's F-4 — drop it
rather than carry it.

## F-4 — LOW (test) — the `git restore` rollback is not merely unpinned; **no test reaches either arm**, and the report says otherwise

`manager.rs:5731-5748`. Implementer's stated limit 1: *"The `Ok(_) => Err(err)`
half is exercised by every commit-failure test."*

It is not. Every commit-failure fixture in the tree injects via `.git/index.lock`
— `tests/dispatch.rs:9788` (the new F-1 test) and `manager.rs:9700` (the M-1
unit test). A held `index.lock` makes the **real-index `git add` at
`manager.rs:5713` fail**, so `commit_promoted_dispatch_record` returns before
`write_dispatch_record_commit` is ever called, and the whole
`match git_capture(restore …)` block — both arms — is dead in the test suite.
The two verify artifacts replace the function body wholesale, so they do not
reach it either.

Risk is small (a broken pathspec in the restore would only surface on a path
that is already a failure path), but the claim in the report is what a future
round will trust. To actually reach it you need a failure at `commit-tree` or
`update-ref` with the index lock free — the `write_same_oid_sibling_git_shim`
pattern already in this file gets you there in about ten lines: have the shim
fail `update-ref` once instead of swapping branches.

## Also confirmed sound (no finding)

  lands in the per-worktree dir and **not** in `--git-common-dir`. The guard
  looks in the right place.
- **Q6 — the git shim.** Deterministic (a marker file under the per-repo gitdir

  (`manager.rs:6745`) reads the ledger and posts task-state transitions; it never

  the normalization below it cannot hand the reconcile an un-normalized path.
  The defect moved nowhere.
- **`dispatch_record_is_in_history`.** `git ls-tree --name-only HEAD -- <abs
  path>` works, including through the macOS `/tmp`→`/private/tmp` symlink alias

- **Q10 — convention prose.** True where it speaks: `commit-tree` genuinely

- The false `user.name`/`user.email` residual: I grepped `crates/`, `shipped/`
  and `verify/` too — it is not in the tree. Correctly handled by not restating
  it.

## Q8 / Q9 judgements the brief asked for

- **Q4 — is refusing a detached HEAD the right trade?** Yes. The alternative it
  replaces is a commit reachable from no ref, which the manager's next
  `git checkout` orphans while the close prints `ok` — silent loss. The refusal
  is loud, keeps the files, and the re-run repairs it. A manager working
  detached on purpose gets a warning per close and no records in history, which
  is the correct price: there is no durable place to put them.
- **Q8 — the untracked-record residual.** Acceptable as-is. A `git add .` sweeps
  the record into the manager's own commit, but the record is then *in history*,
  which is the property the whole chain exists to guarantee; the wrong commit is
  a cosmetic cost. The repersist warning already names `dest_dir`; the *initial*
  refusal does not, which is the cheap improvement if you want one.
- **Q9 — the unpinned restore branch.** See F-4: worse than stated, still LOW.

## One more edge, LOW, no separate finding

If `promote last.txt` fails after `create_dir_all` succeeds (`paths.rs:299-305`),
`dest_dir` exists but is **empty** and status is `partial`. Every re-run then
fires the repair, and **measured**: `git add -- <empty dir>` exits 0, the
throwaway index's `write-tree` equals `head_tree`, so
`write_dispatch_record_commit` takes its `tree == head_tree` early return,
`verify_dispatch_record_staged` sees no files and returns `Ok`, and the close
prints `re-persisted: dispatch record <tx> committed`. Nothing was committed;
`dispatch_record_is_in_history` stays false; **every future re-run repeats the
same false claim**. No commit spam (the tree guard holds) and no data at risk —
but the one line a manager would trust is wrong. Guard the print on the record
actually being in history afterwards.
