## Findings

### R1 (MEDIUM, docs) — the help still makes ONE unbounded universal claim about the walk, and it is the same class the pin now bans a single wording of

`crates/orgasmic-cli/src/manager.rs:386-388`:

> "…the anchored walk of the tree's own contents refuses any NESTED `.git`
> entry, of any type…"

The walk is bounded twice (`manager.rs:3833` returns at `depth >
anchored_dir::MAX_DEPTH` = 64, `:3836` returns on an `entry_names` error, `:3855`
skips an `open_child_dir` `Err`). So "refuses any NESTED `.git` entry" is, read
literally, an over-claim — the *dangerous* direction, and the one
`cli_parity.rs:156-161` now bans in the wording `"at any depth"` while the
shipped sentence makes the same universal claim more compactly and passes.

**Why this is MEDIUM and not HIGH, measured rather than argued from the previous
round's summary.** I re-derived round five's symmetry claim from source and it
holds exactly:

| fail-open in `walk_worktree` | matching limit in the removal |
|---|---|
| `:3833` `if depth > anchored_dir::MAX_DEPTH { return }`, entered as `walk(root, 1, …)` (`:3860`) | `:3180` `if depth > MAX_DEPTH { bail!(…) }`, entered as `remove_contents(&child, 1, …)` (`:3243`) — same constant, same start depth |
| `:3836` `let Ok(names) = entry_names(dir) else { return }` | `:3183` `for name in entry_names(dir)?` — propagates |
| `:3855` `Err(_) => continue` on `open_child_dir` | `:3184` `open_child_dir(dir, &name)?` — propagates |

`open_child_dir` (`:2977-2984`) only maps `ENOTDIR`/`ELOOP`/`EMLINK`/`ENOENT` to
a non-error; everything else (`EACCES` included) is `Err`. So a `.git` too deep
or too unreadable for the walk sits inside a directory too deep or too unreadable
for `remove_contents`, which turns into a `RemovalFailure`, never a silent clean
deletion.

**But the symmetry does not deliver what the help implies.** `RemovalFailure`
carries `touched` (`:3174-3177`), and `remove_contents` is readdir-ordered, so
siblings enumerated before the blocked directory are already gone. On the
repo-gone branch there is no salvage. So the operator's inference from this
sentence — "a nested `.git` anywhere means the worktree is KEPT untouched" — is
wrong in the fail-open shapes: they get a *reported partial removal*. The nested
repository itself survives (it is inside the thing that blocked the walk), which
is why this is a docs finding and not a data-loss one.

**Fix direction.** One clause, not a paragraph: bound the universal at the point
it is made — e.g. "…refuses any NESTED `.git` entry, of any type, as deep and as
far as it can read; a directory too deep or unreadable for that walk is also too
deep or unreadable for the removal, which then fails part-way rather than
completing." Cheaper alternative if the exact wording is not worth measuring
again: drop the bare "any" ("refuses a NESTED `.git` entry, of any type"), which
removes the over-claim without asserting anything new.

**This answers the brief's Q1 directly:** the implementer's omission is safe to
ship — no silent deletion is reachable through either fail-open — but it is not
*complete*, because the sentence's universal quantifier is what makes the
omission read as a promise. I would not hold the reinstall for it.

### R2 (MEDIUM, test) — the F5 shape-1 clause is a WORDING ban too, and the doc comment says otherwise

`crates/orgasmic-cli/tests/cli_parity.rs:112-115` says the first escape "is
closed below", and `:119-126` correctly says the second closes "THAT WORDING, not
the class". That asymmetry is not real: the new clause (`:228-241`) bans the
literals `"every branch"` and `"all branches"` inside a sentence containing
`"index"`, which is a wording ban of exactly the same kind.

**Measured.** I re-implemented the pin's logic verbatim against the shipped
`after_help` text (`manager.rs:370-391`) and ran candidate false helps through
it. Shipped help: PASS (matching the real `cli_parity` run, which is also green —
so the reimplementation is faithful). Then:

| appended false sentence | pin |
|---|---|
| "…reads the worktree's own INDEX for gitlinks on **every branch**." | CAUGHT |
| "…reads the worktree's own INDEX for gitlinks on **both branches**." | **PASSES** |
| "…reads the worktree's own INDEX for gitlinks, **whatever the branch**." | **PASSES** |
| "…reads the worktree's own INDEX for gitlinks. That is true of every branch this verb has." (split across two sentences — the `"index"` sentence has no quantifier, the quantifier sentence has no `"index"`) | **PASSES** |
| repo-gone sentence + "…**at any depth** and through unreadable directories" | CAUGHT |
| repo-gone sentence + "…**however deeply nested** and through every directory in the tree" | **PASSES** (matches the implementer's own table) |

`"both branches"` is not an exotic rewording: the help's own vocabulary is
"WHAT IT CAN CHECK DIFFERS BY BRANCH, so read both of the next two sentences"
(`manager.rs:378-379`). It is the phrasing the next author is most likely to
reach for.

**This answers Q2.** I agree with the stopping point — a clap-text pin cannot
decide truth, and chasing synonyms is a thesaurus, not a guarantee. But then the
doc comment must describe *both* clauses the same way. Fix direction: (a) add
`"both branches"`, `"either branch"`, `"whatever the branch"` to the ban list —
cheap, and it closes the phrasing an author of this particular help would
actually use; (b) change `:112-115` from "The first is closed below" to the same
honest framing `:119-126` already uses, and name the split-across-two-sentences
escape, which no per-sentence pin of this shape can see.

### R4 (LOW, docs) — the new repo-gone refusal states as observed fact something it only inferred

`manager.rs:4156-4167` says "…its own `.gitmodules` does survive inside the tree,
and names an initialized submodule at {module}". The condition that got here is
`nonempty_dir_under` (`:4635-4657`), which returns `true` both when the directory
lists non-empty AND when the listing *failed* (`:4655`, `Err(_) => true`, fail-
closed by design). In the second case the verb has not observed an initialized
submodule; it has observed that it could not look. The remedy it then offers
("remove {module} yourself") is still correct, and the direction is KEEP, so this
is cosmetic — but it is the same "say what you actually checked" discipline this
whole chain exists for, and the identical over-statement is pre-existing in the
sibling arm at `:4169-4173`.

## The reinstall call

**Yes — I would reinstall the runtime on this tree.**

The reasons, in the order they matter:

1. The destructive direction is covered by a fixture I ran, and by a red I
   reproduced myself rather than accepted. That is a stronger position than the
   verb has been in at any earlier round.
2. Every finding above runs in the KEEP direction or is operator text. R1 is the
   only over-promising clause left, and I traced its two failure shapes to a
   `RemovalFailure`, not a silent deletion.
3. The remaining risk is concentrated in things a reinstall does not change:
   the two unexercised fail-opens, and the fact that no cross-family reader has
   seen any of this.

What I would want *before the next destructive change to this verb* — not before
the reinstall: a fixture for at least one fail-open (the `chmod 000` one is far
cheaper to build than the 65-deep one and is the more reachable shape), and the
`verify/TASK-RMA18.1.1.1.1/` artifact from R3.
