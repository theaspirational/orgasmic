## Verdict

**approve-with-follow-ups.**

Both round-1 release blockers are fixed and I verified each independently, not from the
report. Every round-1 MEDIUM is addressed with a mechanism I could point at in the diff, and
most are backed by a test that would fail without the fix. The three findings below are real
but none of them blocks installation; they are follow-ups the manager can schedule.

Why the previously rejected semantics are now correct:

- **H1 (clippy red on `BuiltRefresh`)** — the enum's large arm is now
  `Project(Box<BuiltProjectRefresh>)` (`crates/orgasmic-daemon/src/index.rs:468-482`).
  `cargo clippy --workspace --all-targets -- -D warnings` runs **to completion**, including
  `orgasmic-cli`, with `CLIPPY_EXIT=0` and zero warning/error lines (`/tmp/k9r2-clippy.log`).
- **H2 (read-after-write broken when `tx.commit_to_project: false`)** — the authoritative
  refresh now follows the *mutation*, not the tx destination. `refresh_after_project_mutation`
  (`api.rs:7809-7830`) always refreshes the mutated project, and additionally refreshes the
  home ledger via `tokio::join!` when the tx routed home. Every project-file mutation site
  reaches it (`api.rs:2401, 13403, 13972, 15224, 15316, 15858, 15945, 16195, 16526, 16805`,
  plus the eight artifact paths at `17214…18498`, which legitimately pass `project_tx=true`
  because they compute a project-local `tx_path` unconditionally, e.g. `api.rs:18079-18082`,
  and never consult `tx_commit_to_project`). The regression that reproduces the round-1 defect
  is a real booted-daemon HTTP test parameterised over **both** routing modes
  (`api.rs:30422-30545`, `project_task_mutation_is_immediately_visible_with_{project,home}_tx`).
  I ran both: green.

## Findings

### MEDIUM

**M1 — `index.rs:1045-1061` and `index.rs:1084-1101`: the "bounded seed" clones the project's
entire tx and parse-error partition under the index read lock and then throws it away.**

```rust
let mut next = IndexSnapshot {
    board: vec![board_entry.clone()],
    projects: prior_project.map(...),
    tx: seed.tx.iter().filter(|r| r.project_id.as_deref() == Some(&project_id))
            .cloned().collect(),                                    // <- built
    parse_errors: seed.parse_errors.iter().filter(...).cloned().collect(),  // <- built
    rebuilt_at: seed.rebuilt_at,
};
drop(seed);
next.parse_errors.clear();                                          // <- discarded
next.tx.clear();                                                    // <- discarded
scan_index.load_project(&board_entry, &mut next, None);
```

Impact: this is pure dead work on the acknowledgement path whose cost this task exists to
reduce, and it is performed while holding `self.inner`'s read guard (acquired at
`index.rs:1027` as `read_owned()` and released only at the `drop(seed)` inside the blocking
closure). The filter iterates the whole `snap.tx` vector and clones every matching
`TxRecord`. For this repo's own project that partition is large — `.orgasmic/tx/2026-08.org`
alone holds 1656 tx headings and `2026-07.org` is ~1.7× its size — so a single project
acknowledgement allocates and drops several thousand records. Failure scenario: not a wrong
answer, a wasted allocation and a lengthened read-lock hold on the hot path, on a loaded host,
which is the precise condition this task was filed for.

The clears are *required* (`parse_error_already_recorded` and `collect_tx_dir` would otherwise
see stale state), so the correct fix is to stop seeding those two fields at all:
`tx: Vec::new(), parse_errors: Vec::new()`. `board`, `projects` (the last-good fallback at
`index.rs:1519-1525`), and `rebuilt_at` must stay. Behaviour-identical, verifiable by the
existing `parse_failure_keeps_last_good` and `refresh_keeps_last_good_indexed_task_body_*`
cases.

**M2 — `index.rs:1342-1350` vs `index.rs:1371-1373`: a failed Git probe is negative-cached
forever on the non-forced path.**

`refresh_repo_url` inserts the probe key into `repo_url_probed` *before* spawning Git
(line 1347), and the failure branch returns without removing it:

```rust
if !force {
    let mut probed = self.repo_url_probed.lock()...;
    if !probed.insert(probe_key.clone()) { return; }   // marked before the probe
}
...
let Some(repo_url) = repo_url else { return; };        // failure leaves the mark in place
```

Failure scenario: `orgasmic project init` (or the watcher's newly-registered-project branch at
`watcher.rs:383`) registers a Git-backed project while the machine is loaded enough that
`git remote get-url origin` exceeds its 3 s bound, or `git` transiently fails. Both callers use
the non-forced entry point (`spawn_repo_url_refresh_for`, `index.rs:1312-1314`, reached from
`api.rs:1340` and `watcher.rs:383`). `repo_url` stays empty and **nothing re-derives it** until
a daemon restart, `orgasmic reindex` (`post_reindex` → `rebuild` → `refresh_repo_urls(true)`),
or `reindex-project` (`api.rs:13325`, forced). This is a behaviour change: at baseline
`refresh_project` probed Git on *every* project refresh
(`4808f900:crates/orgasmic-daemon/src/index.rs:513-516`), so a failed probe self-healed on the
next task edit. Taking Git off the refresh path is correct and intended; permanently caching a
*failure* is not. The brief asked for exactly this scrutiny.

Fix: remove the key on the failure branch. The pre-insert can stay — it is what makes the
concurrent-registration dedup (`duplicate_registration_probe_requests_spawn_git_once`,
`index.rs:2808`) work while the probe is in flight — it just must not survive a failed probe.
The success path already re-inserts at `index.rs:1374-1377`.

**M3 — `index.rs:933-940`: the stale-generation discard has no retry bound, so acknowledgement
can be starved by a sustained same-target arrival stream.**

```rust
if result.is_ok() && state.required_generation != captured.required_generation {
    self.refresh.metrics.discarded_total.fetch_add(1, Ordering::Relaxed);
    drop(coordinator);
    continue;                       // nothing acknowledged, no cap, no deadline
}
```

The discard is *correct* — a mutation registering after capture may or may not be in the
projection, so republishing is the conservative choice — but on discard **no waiter is
completed**, including waiters whose mutations were unambiguously covered. Failure scenario: a
same-project mutation stream arriving faster than one `scan + publish` cycle keeps flipping
`required_generation`, and every waiter in the batch stays parked until the 10 s client budget
expires. There is no iteration cap, no deadline, and nothing in `IndexRefreshStatus` that
distinguishes "one discard" from "twenty consecutive discards" (`discarded_total` is a
monotonic counter, not a per-batch signal).

Practically this is unlikely — the staggered measurement recorded one discard across 30
arrivals, and the suite's dispatch tests each drive their own project — so I am not treating it
as a blocker. But the failure mode is a 10 s client timeout on a loaded host, i.e. the exact
symptom this task was opened for, and it is currently unbounded by construction. A max-discards
or an absolute deadline on the outer loop would close it; a per-batch discard count in the slow-
scan warning would at least make it visible when it happens.

### LOW

**L1 — `index.rs:804-830`: every mutation acknowledgement still pays an unconditional ≥50 ms
floor; the runbook does not say so.** The debounce always sleeps at least once before the first
scan, even for a single uncontended request. Round 1's M2 was half-addressed: the max-wait bound
was added (`REFRESH_COALESCE_MAX_WAIT`, `index.rs:372`, proven by
`staggered_arrivals_cannot_extend_coalescing_past_the_absolute_bound`), but the leading-edge
case was not. Against the baseline this is roughly a wash — the old path spent comparable time
spawning Git under the write lock — so I am not calling it a regression. It is, however, the
dominant term in an otherwise ~2 ms scan (`last_scan_duration_ms=2` in my own run below), and
`verify/TASK-K9WWM/README.md:20-27` presents the window only as a reduction, never as a cost.
Either scan immediately for the first arrival of an idle target, or record the floor in the
runbook so the next person measuring a 90 ms create knows where 50 ms of it went.

**L2 — `api.rs:9082-9110`: a release whose terminal tx landed durably still answers 503.** The
round-1 M6 ask was "decide explicitly", and the implementer did: the log line is now truthful
(`"released run and wrote its terminal tx, but projection refresh failed"`, `api.rs:9099`),
`ReleaseTaskTracker::spawn_release` correctly excludes a committed tx from lost-finalization
accounting (`api.rs:604`), and the CLI renders the reconciliation wording
(`daemon_client.rs:367-386`). That is a defensible decision and it is covered
(`release_terminal_tx_committed_refresh_failure_is_truthful_and_durable`, `api.rs:20109`).
The residual remains: `orgasmic dispatch finalize` exits non-zero for a dispatch that fully
completed, on a run whose lease is already gone, so the manager's `*.done` bookkeeping keys off
a failure for work that succeeded. Recording that consequence somewhere the manager reads would
be worth more than changing the status code.

**L3 — two new tests have less timing headroom than the failures they replace.**
`index.rs:4256` gives `staggered_arrivals_cannot_extend_coalescing_past_the_absolute_bound` a
450 ms budget to observe a bound that is 200 ms plus a scan; `index.rs:4410` gives
`snapshot_reads_remain_responsive_while_scan_is_gated` 25 ms. Both passed for me, but this task
exists because a 10 s budget proved load-sensitive on this host, and these are 450 ms and 25 ms.
If either reds under suite concurrency it must not be registered as a flake by reflex.

**L4 — `api.rs:7835` interpolates raw internal error text into a client-visible body while the
`ApiError` contract at `api.rs:18736-18738` still says unsafe details are "never included in the
body".** Today's strings are safe (`unknown project X`, `project X registration changed during
refresh`, `project X scan produced no projection`), but `"index refresh scan task failed:
{JoinError}"` (`index.rs:1118`) can carry a panic payload. Either narrow what
`committed_refresh_error` forwards, or amend the doc contract to name this exception.
Relatedly and unchanged from round 1: `/api/daemon/status` now returns
`writer.in_flight_operation.path`, i.e. absolute filesystem paths in an authenticated HTTP
body (`writer.rs` `WriterStatus`). Noted, not demanded.

**L5 — the writer-loop restructure fixes a latent termination bug that nothing tests.** At
baseline, `WriterCommand::Transaction`'s idempotent-replay and identity-conflict arms both did
`continue` (`4808f900:crates/orgasmic-daemon/src/writer.rs:1208-1218`), which returns to
`while let Some(current) = cmd.take()` with `cmd` already `None` — **terminating `writer_loop`
outright** and killing the daemon's only writer. The new `execute`-flag restructure
(`writer.rs:1273-1321`) removes that path. This is a genuine, unadvertised improvement worth
recording; it is latent because `transaction_mutation` pre-checks the cache at
`writer.rs:684` and `post_task_create`/`create_graph_heading` pre-check again at the API level,
so the writer-level arm only fires on a race. No regression asserts the writer is still alive
after a writer-level cached replay.

**L6 — `.orgasmic/decisions.org:285-286`: two stray blank lines** left where round 1's
misplaced paragraph was removed. Cosmetic; org parses fine.

## Brief checklist items not covered above

- **Per-target single flight** — structurally enforced by `TargetRefreshState::running` under
  the coordinator lock (`index.rs:764-785, 993-998`), and asserted by
  `index.max_same_target_scans() == 1` in three separate tests.
- **Cancellation detachment** — the coordinator owns the scan; the HTTP waiter is only a
  `oneshot`. `cancelled_waiter_does_not_cancel_refresh_convergence` (`index.rs:4279`) aborts the
  waiter mid-scan and then proves the *next* request for the same tx does not rescan, i.e. the
  detached scan really published.
- **Git off the mutation path** — `refresh_project`/`refresh_after_tx` no longer call
  `refresh_repo_url` at all; `stalled_git_probe_neither_delays_mutation_nor_counts_as_refresh_scan`
  (`index.rs:2779`) holds a probe open and acknowledges a mutation inside 500 ms with
  `scans_total == 1`.
- **Watcher convergence / event ordering** — `watcher.rs:399-423` awaits publication before
  publishing `ProjectIndexed`/`TaskUpdated`, so the event still trails the projection. Watcher
  waiters never join `required_generation` (`index.rs:665-696`), so an external edit arriving
  mid-scan schedules a follow-up instead of delaying a mutation ack.
- **Raw-tx / task / graph / goal / artifact coverage** — every `writer.transaction(_mutation)`
  site in `api.rs` below 18700 reaches `refresh_after_project_mutation`; the only surviving
  bare `refresh_project` calls are the two explicit reindex paths (`api.rs:1331`, `api.rs:13319`).
  The three `rewrite_file` sites that do not refresh (`api.rs:11369`, `11773`, `13217`) are the
  run-catalog snapshot and the restart drain marker — neither is indexed project state.
- **Do the tests prove the contract or merely exercise it?** Mostly prove. The single-flight,
  two-permit, home-permit-independence, cancellation, failed-scan-survival and Git-merge cases
  all assert a property that would flip without the fix. The 16-write HTTP case asserts the
  unchanged 10 s budget, exactly-once landing, and `scans_total` delta on the real router. The
  weakest is `snapshot_reads_remain_responsive_while_scan_is_gated`: its gate fires *after* the
  blocking scan, so it cannot observe the one window where a read guard is genuinely held
  (`index.rs:1027` → `drop(seed)` at `index.rs:1059`).

## Open questions

1. M3: is there an intended bound on discard retries, or is the 10 s client budget meant to be
   the only backstop? If the latter, say so in the runbook — it is the one place a future load
   red would be misdiagnosed.
2. L1: was 50 ms chosen by measurement? Neither the task record nor the runbook derives it, and
   it is still the dominant term in an uncontended acknowledgement (my run: `last_scan_duration_ms=2`
   against a 50 ms floor).
3. M2: should a failed registration probe be retried on any non-operator path, or is
   "empty until `orgasmic reindex`" the accepted contract? Either answer is fine; the current
   state is an accident of insert-ordering rather than a decision.

## Fix directions

1. **M1** — delete the `tx` / `parse_errors` seeding in `build_refresh` (both arms); use
   `Vec::new()` and keep only `board`, `projects`, `rebuilt_at`. Behaviour-identical, removes a
   multi-thousand-record clone from every project acknowledgement and shortens the read-lock
   hold.
2. **M2** — in `refresh_repo_url`, remove `probe_key` from `repo_url_probed` on the
   `let Some(repo_url) = repo_url else { return; }` branch, so a failed probe is retried by the
   next non-forced request instead of being cached until restart. Add a case that fails a probe
   and asserts a second registration-path request re-spawns Git.
3. **M3** — bound the outer worker loop: either a max consecutive-discard count or an absolute
   deadline measured from the first captured waiter, and surface the per-batch discard count in
   the `slow index refresh scan` warning so a starving target is legible in the log.
4. **L1** — scan immediately on the first arrival to an idle target (leading edge, then trailing
   coalesce), or record the unconditional 50 ms floor in `verify/TASK-K9WWM/README.md` next to
   the coalescing numbers.
5. **L2** — record, where the manager reads it, that a committed-refresh failure on
   `/api/runs/:id/release` yields a non-zero `dispatch finalize` for a dispatch that actually
   completed, and how to reconcile it from the ledger.
6. **L5** — add a writer regression that drives a writer-level cached `Transaction` replay and
   then asserts the writer still accepts a subsequent command, so the termination bug this
   restructure removed cannot come back unnoticed.
