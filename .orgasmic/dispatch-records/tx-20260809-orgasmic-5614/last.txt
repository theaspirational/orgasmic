# Verdict

REJECT / BLOCK SHIP. Candidate `fcf082532ca65de9ebf30e04811fac5c94d168b6..53d9fc453951f48b24c3f450ad0f62dbbde92657` correctly adopts the revised fixed shell-no-op wake marker and moves claim promotion onto the supervisor lease, but it still does not authenticate claim authority, breaks plain registration for already-supervised app managers, loses claims on reattach, and leaves two independent false-death paths in `dispatch-wait`. Busy-pane targeting, UI representation, typed failure coverage, and the required P1 test matrix are also incomplete.

# Findings

1. **HIGH / security — claim authority is still caller-supplied JSON, not an authenticated calling runtime.** `crates/orgasmic-cli/src/manager.rs:1522-1533` builds `RuntimeIdentity` entirely from inherited environment, and `:1599-1607` sends that identity plus the process-name-derived provider in the request body. `crates/orgasmic-daemon/src/api.rs:2921-2939` deserializes both fields and `:2982-2993` passes them straight to the supervisor; request middleware authenticates only the shared admin bearer (`api.rs:807-855`), not a run-scoped identity. Worse, `GET /manager/state` returns the supervisor snapshot (`api.rs:3406-3409`), including the full identity, so an ordinary bearer-authenticated shell can copy another terminal's run/runtime/boot tuple and POST `provider=codex` without any provider ancestry at all. The supervisor's tuple equality then validates the forged assertion against itself. Minimal fix: authenticate a run-scoped capability/credential at the HTTP boundary, populate the calling runtime as a trusted request extension, derive provider/target daemon-side, and remove `caller_identity`/`provider` from public JSON. Add negative tests proving copied request fields and inherited env cannot claim, release, or unclaim another run.

2. **HIGH / bug — plain `manager register` now fails for a normally app-launched Claude/Codex manager.** The shipped router unconditionally runs plain registration on manager startup (`shipped/entry/router.org:23-31`). Every app-launched manager has `ORGASMIC_RUN_ID`, so `cmd_manager_register` always takes the claim branch (`crates/orgasmic-cli/src/manager.rs:1586-1608`). But app launch creates non-custom providers with role `manager` (`crates/orgasmic-daemon/src/api.rs:2873-2879`), while `claim_manager_terminal` accepts only role `terminal` (`crates/orgasmic-daemon/src/supervisor.rs:2982-2997`). Therefore the existing supervised-manager startup path returns `manager terminal claim refused` instead of its previous no-op. Minimal fix: have the authenticated daemon endpoint distinguish “exact caller already owns the stable manager lease” and return an idempotent success; only promote an exact custom-terminal caller. Cover app launch -> plain register and repeated register.

3. **HIGH / correctness — a claimed manager is forgotten on daemon restart/reattach.** Promotion mutates only the in-memory `RunRecord` (`crates/orgasmic-daemon/src/supervisor.rs:3029-3038`); it writes no durable lifecycle event or RunMeta update. Reattach always constructs `manager_terminal_claim: None` (`supervisor.rs:2649-2655`) and boot restores only the originally persisted task/role/harness contract (`crates/orgasmic-daemon/src/api.rs:11107-11141`). A claimed custom terminal therefore reattaches as the old unique `terminal` run, drops the stable project manager lease and provider claim, disappears as a wake target, and permits a second manager. Minimal fix: persist promotion/demotion as lifecycle state and restore original task id, claimed provider, manager role, and stable lease atomically during boot/manual reattach; add restart tests for wake, singleton conflict, release, and generic terminal release.

4. **HIGH / correctness — the new daemon endpoint retains a release/report false-death race.** `post_manager_dispatch_wait` reads/parses the tx ledger first and only then snapshots live runs (`crates/orgasmic-daemon/src/api.rs:3198-3212`). A finalize can append its terminal tx and settle/remove the release admission after that parse (`api.rs:8716-8739`, release settlement at `api.rs:500-512`) but before the snapshot. The handler then has the stale `reported=false` view, sees neither live run nor in-flight release, and returns `died` at `api.rs:3258-3271` for a successful report. This is the same cross-source race moved behind one HTTP route. Minimal fix: maintain one versioned generation state under daemon synchronization, or use an observation order/epoch that proves either pre-release liveness/in-flight state or the post-release terminal tx; add a deterministic hook test for the exact parse -> append/settle -> snapshot interleaving and repeated waits.

5. **HIGH / correctness — `dispatch-wait` ignores recovery replacement run lineage and can kill a healthy recovered generation.** The endpoint attaches only `run.created ORIGIN=cli_dispatch` (`crates/orgasmic-daemon/src/api.rs:3223-3230`) and matches reports only to that single stored run id (`:3232-3238`). The established dispatch scanner explicitly folds `run.created ORIGIN=recovery` into the same generation (`crates/orgasmic-cli/src/manager.rs:9400-9424`) because resume/recovery may replace the run id. Once the origin disappears, a live or reported replacement is invisible to the endpoint and the generation returns `died`. Minimal fix: fold the complete origin -> replacement lineage into the daemon-owned generation state and treat any live/in-flight/reported member as the generation's authority; test reattach-in-place and new-id recovery before and after report.

6. **HIGH / correctness — a busy provider can still pass the composer gate through an output-history glyph.** `provider_composer_ready` scans `pane.lines().any(...)` for any visible `›`/`❯` line (`crates/orgasmic-drivers/src/modes/tmux.rs:2621-2636`), and `tmux_provider_ready` accepts that after proving only that the provider process is foreground (`:2642-2699`). During a busy turn the provider remains foreground, so a visible model/tool output line beginning with the glyph authorizes the fixed marker even though the actual composer is absent. The marker is shell-safe, but this violates the required typed busy refusal and can queue or inject a resume turn into an active provider. Minimal fix: bind readiness to the provider's actual current input component/bottom-frame shape, not any viewport line, and test busy output/history glyphs for both Claude and Codex.

7. **HIGH / test — the P1 lifecycle/concurrency and real wait matrix is still absent.** This range adds only the sequential `claimed_terminal_moves_the_real_manager_lease_and_release_demotes_it` test (`crates/orgasmic-daemon/src/api.rs:20481-20588`) and the direct `bash`/`zsh -c` marker test (`crates/orgasmic-drivers/src/trait.rs:929-949`); there are no endpoint tests for authenticated caller spoofing, app-manager idempotence, claim-vs-launch/register races, boot reattach persistence, generic release, UI regrouping, pane-exit/unavailable mapping, recovery lineage, or the release/report race. The shell test does not exercise a real tmux pane before provider start and after provider exit, and no Claude/Codex compiled-router test proves marker -> resume. The live task records that the implementer aborted specifically because reattach persistence and the full wait matrix remained. Minimal fix: add the isolated-daemon concurrency/restart matrix, actual tmux bash/zsh and router fixtures, and a non-billed real `dispatch-wait` proof including `[pid-gone]`, report, abort/close, timeout, repeat wait, multi-generation, recovery, restart, and the `tx-20260809-orgasmic-5609` fixture.

8. **MEDIUM / correctness — claimed manager state is still represented as a terminal in the UI.** The backend changes the run's task/role to manager and exposes `claimed_manager_provider` (`crates/orgasmic-daemon/src/supervisor.rs:3033-3038`, `:3479-3482`), but the candidate changes no UI code. `ui/src/lib/types.ts:385-402` does not model the field, and `ui/src/components/manager/runDockLabels.ts:19-24` classifies every `manager.*` run with harness `custom` as a terminal. Because promotion does not change the harness, the claimed run remains in the terminal group and excluded from Running Agents. Minimal fix: carry the claim field (or authoritative role) into the UI classifier and add promotion/demotion grouping tests.

9. **MEDIUM / correctness/docs — typed wake failures and wait help are incomplete.** Tmux pane capture/paste failures are `DriverError::Transport` (`crates/orgasmic-drivers/src/modes/tmux.rs:2603-2616`, `:2118-2169`), but `post_manager_wake` maps only the dedicated unavailable/mismatch/unsupported variants and sends every other error through the generic API error path (`crates/orgasmic-daemon/src/api.rs:3104-3130`). A pane that vanishes during capture or delivery therefore produces generic CLI exit 1, not stable `unavailable=5`. Independently, the source-built `manager dispatch-wait --help` lists arguments but not the implemented 0/2/3 exit contract because `DispatchWaitArgs` has no `after_help` (`crates/orgasmic-cli/src/manager.rs:362-370`); wake help does document 0/4/5/6/7. Minimal fix: normalize target-loss transport failures to the closed wake status enum, add CLI exit tests, and document/test dispatch-wait exits in generated help.
