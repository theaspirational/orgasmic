#+title: TASK-AJP4A independent review — lazy project index loading

* Verdict
approve-with-follow-ups

The core architecture is correct and verified from code: boot publishes only the
board catalog plus home-owned tx state, watches attach for every registered root
pre-bind, and every project-scoped route funnels through one single-flight
=ensure_project_loaded= boundary. Acceptance criteria 1-8 are met in structure.
The findings below are load-path bounding, one cross-project filter regression,
and UI/contract drift — none of them invalidate the design, but F1/F2 reintroduce
a variant of the very stall the task set out to remove.

* Findings

** F1 HIGH (bug, availability) — project loading is now completely unbounded, and markers/artifacts share the 2-permit scan pool
=crates/orgasmic-daemon/src/index.rs:515= (=project_scans: Semaphore::new(2)=),
=crates/orgasmic-daemon/src/index.rs:1161= (permit now taken by every non-HomeTx
target, i.e. Project *and* Markers *and* Artifacts).

The diff deletes =rebuild_with_timeout=, the per-project =tokio::time::timeout=,
and =warn_macos_files_access_timeout= / =macos_files_access_hint= entirely
(index.rs, removed at old lines ~2751-2790 and ~555-600). Nothing in the new path
bounds a scan: =ensure_project_loaded= → =request_project_load= → =rx.await= has
no deadline, and =spawn_blocking= cannot be cancelled.

Failure scenario: one registered root sits on a stalled mount or is blocked by
macOS Files-and-Folders TCC (the exact condition the deleted hint was written
for). Its =spawn_blocking= scan never returns, so it holds one of the two permits
forever and its HTTP handler hangs forever. A second such root takes the last
permit. From that moment every =GET /api/projects/:id=, every graph route, every
marker/artifact projection, and every mutation refresh for *every healthy*
project blocks indefinitely at =index.rs:1162=, with no log line naming the
cause. Before this change the same root cost 5 s once at boot and produced an
actionable macOS hint.

Fix direction: bound =ensure_project_loaded= (and marker/artifact loads) with a
timeout that records =Failed= + the macOS hint rather than parking a permit, and
either give markers/artifacts their own permit pool or exclude them from the
project-scan cap.

** F2 HIGH (bug, regression) — `orgasmic status --errors` now forces a whole-board recursive source scan under a 10 s client timeout
=crates/orgasmic-cli/src/main.rs:2402= (=client.get("/graph/markers/__coverage__")=)
→ =crates/orgasmic-daemon/src/api.rs:13733-13768= (=get_graph_markers= with no
=?project= ensures markers for every authorized board entry) →
=crates/orgasmic-daemon/src/index.rs:2758= (=scan_project_markers=, full recursive
repo walk), serialized behind the 2-permit semaphore.
Client timeout: =crates/orgasmic-cli/src/daemon_client.rs:48= (=DEFAULT_REQUEST_TIMEOUT_SECS = 10=).

Failure scenario: after a restart on this operator's board (orgasmic, ddd,
vscode-orsl, …), the first =orgasmic status --errors= must complete N recursive
source-tree walks in ≤10 s. The task's own measured datum is 12.785 s for a
single vscode-orsl scan. The command returns a transport timeout instead of parse
errors. The detached coordinator keeps scanning, so a retry a minute later
succeeds — which makes this read as intermittent rather than as a known cost.

Related and worth confirming: the same 10 s budget now covers the *first*
project-scoped CLI call after any restart (=orgasmic task list=, =graph=, =entry=
all go through =ensure_loaded_snapshot=). Core =.orgasmic=-only loads should be
well under 10 s now that markers/artifacts are split out, so this is likely fine
— but it is untested, and F2's marker path definitively is not.

Fix direction: raise the timeout for the explicit full-coverage request, or have
=status --errors= request per-project marker coverage and stream/report progress,
or expose a cheaper coverage-forcing endpoint.

** F3 MEDIUM (correctness) — `GET /tx?project=X` now returns home-scoped tx records too
=crates/orgasmic-daemon/src/api.rs:2571-2576=:

#+begin_src rust
r.project_id.as_ref().is_some_and(|pid| covered_projects.contains(pid))
    || (r.project_id.is_none() && matches!(identity, Identity::Admin))
#+end_src

The second clause is unconditional on =q.project=. Home-ledger records carry
=project_id: None= by construction (=index.rs:2089=, =collect_tx_dir(&dir, None, snap)=).
Previously the filter was =r.project_id.as_deref() == Some(p)=.

Failure scenario: =ui/src/components/TaskView.tsx:17= calls =fetchTx(projectId, 30)=
and =ui/src/components/ActivityView.tsx:138= calls =fetchTx(projectId, limit)=. An
admin viewing project X's Activity tab now sees home/daemon-level ledger rows
interleaved, and because the =limit= truncation at =api.rs:2579-2584= runs *after*
the merge, those rows displace X's own newest entries. On this machine
=~/.orgasmic/state/tx/= holds 8 such records today, so the effect is small but
real and grows with the home ledger. =orgasmic tx list --project X= is affected
identically.

Fix direction: gate the =project_id.is_none()= clause on =q.project.is_none()=.

** F4 MEDIUM (design, contract drift) — the UI ignores `x-orgasmic-project-coverage` and never forces marker coverage
=crates/orgasmic-daemon/src/api.rs:13413-13435= adds the coverage header, and the
CLI reads it (=main.rs:2404-2408=). No UI consumer does:
=ui/src/components/StatusView.tsx:20= and
=ui/src/components/notifications/NotificationBell.tsx:85= both call
=fetchParseErrors()= and render the raw array.

Because =lint_project_identity_state= moved out of core loading into the marker
projection (=index.rs= diff: removed from =load_project=, now only in the
=Markers= build arm), identity-lint parse errors — duplicate ID, malformed ID,
heading/token mismatch — are now *permanently invisible* in the UI: nothing in
the web app ever hits =/graph/markers/…=. Every daemon test for those lints had to
add an explicit marker fetch to keep passing
(=tests/identity_lint.rs:42-53=, =tests/id_mint.rs:419=,
=tests/dispatch_worktree_layout.rs:101=, =tests/body_write_guard.rs:561=), which is
the evidence that the surface changed.

This is the acceptance criterion "global endpoints … never return silently
incomplete cross-project results" satisfied at the HTTP layer but not at the
surface the operator actually reads. The notification badge silently reads 0.

Fix direction: surface the coverage header in StatusView/NotificationBell (a
"partial coverage" note plus a "load full coverage" action), or have the
notification poll force marker coverage the way the CLI does.

** F5 MEDIUM (bug) — whole-board reindex aborts on the first failing project
=crates/orgasmic-daemon/src/api.rs:13453-13466=: =post_reindex= loops the board and
=force_reindex_project(&state, &project_id).await?= — the =?= returns 503 on the
first failure. =force_reindex_project= (=13469-13498=) additionally does core +
markers + artifacts serially per project.

Failure scenario: three registered projects, the second one's root is
temporarily unreadable. =orgasmic reindex= returns
=503 project B reindex failed: …= and project C is never reindexed. The old
=Index::rebuild()= visited every project and recorded the failure without
aborting the pass. This also makes =reindex= a much longer operation (it now
forces every recursive marker/artifact scan) against the same 10 s CLI timeout as
F2.

Fix direction: collect per-project outcomes, always visit all of them, return a
partial-success body naming the failures.

** F6 LOW (design regression) — board cards lost the "blocked" count
=ui/src/components/BoardView.tsx=: =projectStats=/=hasBlockedBy= and the
=N blocked= destructive badge were deleted, and =ProjectTaskStats=
(=index.rs:47-52=) has only =total/active/done=. Ready projects that previously
showed blocked-task pressure on the board no longer do. This is a feature drop,
not a lazy-loading consequence — the field could be computed alongside the others
in =Index::catalog()=.

** F7 LOW (observability) — a failed refresh of an already-loaded project leaves the catalog stuck on `loading`
=crates/orgasmic-daemon/src/index.rs:903-914=: =record_project_load_failure= returns
early when =snap.projects.contains_key(project_id)=. But
=mark_loading_if_unready= / =ensure_project_loaded= have already set
=state = Loading=. So when a refresh fails for a project that has a last-good
projection, nothing ever moves it off =Loading=.

Failure scenario: =/daemon/status= and StatusView report the project under
=loading_projects= indefinitely with no error, contradicting AC #8's "failed
loads retain the actionable error until retry". Also =record_project_load_failure=
never sets =last_attempt_at=, so the failed-state timestamp in the catalog stays
whatever the pre-check wrote.

** F8 LOW (bug) — parse-errors handler can panic on a hand-edited board id
=crates/orgasmic-daemon/src/api.rs:13432=:
=HeaderValue::from_str(&coverage).expect("catalog project ids form a valid header")=.
The string interpolates raw board ids. A board file edited by hand with a
non-visible-ASCII byte in an =:ID:= makes =GET /api/graph/parse-errors= panic the
handler task (500 / dropped connection) instead of returning errors. Prefer
=from_str(...).unwrap_or(HeaderValue::from_static("unavailable"))= or sanitize.

** F9 LOW (docs) — `Index::rebuild` doc comment is stale
=crates/orgasmic-daemon/src/index.rs= — the new comment says "Explicit whole-board
rebuild used by the reindex surface and tests", but =post_reindex= no longer calls
it (F5); the only remaining callers are tests and the api.rs test helper. Either
restore it as the reindex implementation or say it is test-only.

** F10 LOW (observability) — legitimate board path changes leave a transient "Failed" catalog entry
A =Project(X)= scan in flight when the board's =:PATH:= for X changes is rejected at
publication (=api-adjacent= =index.rs= =publish_refresh=: "registration changed
during refresh"), and =record_project_load_failure= then stamps X =Failed= with
that message. The next access retries and succeeds, but =orgasmic status= / the
Board card show a red "failed" state for a correct operation in the meantime.

* Open Questions
1. Is the =get_tx= home-record inclusion (F3) intentional — i.e. was the intent
   "a project view should also show daemon-level ledger entries"? If so it needs
   its own opt-in flag and must not be subject to the shared =limit=.
2. Should =ProjectTaskStats= carry =blocked= (F6), or was dropping the badge a
   deliberate simplification?
3. What is the intended bound on a first load (F1)? The task removed the 5 s cap
   as a boot-path bound, but the replacement path has no bound at any layer.

* Fix Directions (ordered)
1. F1 — reintroduce a bound on every coordinator scan (Project, Markers,
   Artifacts): timeout → =Failed= + restored macOS Files-and-Folders hint, and
   release the permit. Separate the marker/artifact pool from the project pool.
2. F2 — raise or override =DEFAULT_REQUEST_TIMEOUT_SECS= for the explicit
   full-coverage request in =cmd_status_errors=, and/or do per-project marker
   coverage with progress output.
3. F3 — one-line fix at =api.rs:2575=: require =q.project.is_none()= for the
   home-record clause.
4. F5 — make =post_reindex= accumulate per-project results instead of =?=.
5. F4 — render coverage state in StatusView and NotificationBell; decide whether
   the UI should force marker coverage on demand.
6. F7/F8/F9/F10/F6 — small, independent, safe to batch.

* Test Gaps (residual)
- No test asserts a bound on a blocked *first access* — the surviving blocked-FIFO
  test only proves boot does not scan. The hang described in F1 has no coverage.
- No test covers =GET /tx?project=X= filtering at all, which is why F3 shipped.
- No test covers =post_reindex= with one failing project among several (F5).
- No UI test covers the =x-orgasmic-project-coverage= header (F4) — the coverage
  contract is asserted only in a daemon integration test and the CLI.
- No test drives a project-scoped route against a >10 s first load, so the CLI
  timeout interaction (F2) is unmodelled.
