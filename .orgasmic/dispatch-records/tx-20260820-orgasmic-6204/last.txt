## Per-finding outcome

### MEDIUM (tx-…-6190) — write-side case check applied to the removal direction. FIXED.

One line in the shared guard, after the empty-key and identity refusals:

```rust
let Some(value) = value else { return Ok(()) };
```

`value` is now the DIRECTION. Only empty-key and `ID` are direction-free;
everything below (canonical case, ledger shape) is a write-side argument and is
skipped on removals. This is the root-cause fix: it covers *every* removal route
through the guard at once — the task arm (`api.rs:15525`) and the
decision/glossary/project/handoff arm (`api.rs:15549`, the "node prop unset on
non-task layers" the brief asked me to sweep for) — instead of one call site.

Two dead `None` arms inside the function (`tail`, `shape_sentence`) collapsed as a
consequence; they were unreachable after the split.

Contract now: `node prop unset <task> priority` removes the `:priority:` line it
names; `PRIORITY` removes `:PRIORITY:`; the STATE refusal table still guards both
directions; an absent key refuses via `PropertyNotFound` naming the node and the
drawer's real keys, with no path disclosure (that ZKZBF.1 pin is untouched and
still green).

## THE SWEEP

### 1. Write-side arguments applied to a REMOVAL or READ direction

Enumerated every caller of the shared guard and every removal route:

```
grep -rn "validate_drawer_property_key_case" crates/     # 4 call sites
grep -rn "RemoveProperty|remove_property|unset" crates/ --include=*.rs
```

- **`api.rs:15525` (task unset) and `api.rs:15549` (other layers, unset)** — the
  defect. Both fixed by the single split. `graph revise`/`graph create`
  (`api.rs:14664`, `:14849`) pass `Some(value)` unconditionally: write-only by
  construction, nothing to split.
- **`NodeEditOp::RemoveProperty` wire op** — the only removal op; it routes through
  the fixed guard. Covered.
- **Decision `PARENT` special cases** (`api.rs:14644`, `:14831`, `:14868`,
  `:15568`, `:15922`, `:15931`) — all reachable and all deliberate. The
  set/remove pair in `validate_decision_parent_ops` is symmetric (set validates the
  new tree, remove recomputes it with `None`), and `graph revise --property PARENT=`
  (empty value) is a *set*-shaped pseudo-removal keyed on byte-exact `PARENT`, so
  the case check there is correctly a write-side rule. **Left, with a residual noted
  below.**
- **`parse_close_property` (`manager.rs:9946`) and `tx.rs:337`** — record/append
  only; no removal direction exists on the ledger. Left.
- **`artifacts.rs:404`, `api.rs:14874`** — `remove_property` with hardcoded
  canonical keys, no user input. Left.
- **CLI** (`crates/orgasmic-cli/src/node.rs`) — passes the key through verbatim in
  both directions; no client-side guard. But its `--help` for `Unset` still said
  "UPPERCASE org drawer spelling — the reader compares keys byte for byte", which
  now contradicts shipped behaviour. **Fixed** (see scope note).
- **UI** (`ui/src/components/orgdoc/NodeDocEditor.tsx:126`) — emits
  `remove_property` only for descriptor-declared canonical keys; no user-typed key
  reaches it. Nothing to split. Not edited.
- **Read direction** — no route applies a key-shape or case rule to a read.
  `node prop` has only `Set`/`Unset`; reads go through the typed node document.

## Residual Risk

- **Scope**: `crates/orgasmic-cli/src/node.rs` is outside the declared write scope
  (`crates/orgasmic-daemon/src/api.rs,crates/orgasmic-cli/tests`), as is `verify/`
  (which the brief explicitly requires). The `node.rs` edit is a doc-comment only —
  no behaviour, no signature — and it removes user-facing `--help` text that this
  change makes false. Naming it rather than leaving it: a reviewer would file it
  otherwise. Revert it in one hunk if the boundary matters more.
- **`graph revise --property parent=` (empty) on a decision** cannot remove a legacy
  lowercase `:parent:` line — the removal branch is keyed on byte-exact `PARENT`, so
  a miscased key upserts instead. Not a regression and not widened here; the door
  that now works for it is `orgasmic node prop unset <dec> parent`. Filing-worthy if
  the manager wants graph revise to have parity.
- **Deleting `render_new_task_heading`'s drop list** relies on
  `validate_task_property_keys` running first on the only caller. Verified by
  reading (`api.rs:16859` precedes `:16898`) and by the green daemon-lib leg, but no
  test pins "the guard runs before the renderer" — if a future route calls the
  renderer without validating, a refused key would land in the drawer instead of
  vanishing. That is the intended trade (visible over mute) but it is a trade.
- **Non-task layers' unset direction has no refusal table of its own.** After the
  split, decision/glossary/project/handoff removals are guarded only by the identity
  check. There is no per-layer door-owned key on those layers today (STATE is
  task-only), so nothing is unguarded in practice — but if one is ever introduced it
  needs its own `*_unset_refusal_reason`, not the write table.
- I did not run the full workspace suite, only the two focused CLI suites plus the
  daemon-lib leg. `validate_drawer_property_key_case` is shared by graph
  create/revise, node prop, task create/update — the set direction is byte-identical
  to before this change, so the blast radius is removals only.
