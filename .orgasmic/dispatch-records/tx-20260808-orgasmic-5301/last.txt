### F1 — BLOCK SHIP. Closed.

Premise reproduced independently before writing code, git 2.52.0, in a scratch
fixture (not the reviewer's or the manager's):

- clean worktree + initialized submodule → `git status --porcelain` EMPTY, no
  `locked` line, `git worktree remove` **EXIT=128** `fatal: working trees
  containing submodules cannot be moved or removed`;
- committed `submodule.vendor/sub.ignore = all` + untracked file in the
  submodule → `git status --porcelain` EMPTY, `--ignore-submodules=none` shows
  ` M vendor/sub`. Both divergences real.

`git_would_remove_worktree` now reproduces **all three** of git's non-forced
refusals in git's order — locked, **submodule**, unclean — and passes
`--ignore-submodules=none` on the clean check, as `remove_cmd` does.

Per manager ruling 1, the refusal is computed **from the anchored handle**, no
new subprocess: `worktree_submodule_refusal(&child.dir, path)` reproduces both
branches of git's `validate_no_submodules`:

1. the worktree's own admin dir holds `modules/` — measured: a
   `git submodule update --init` inside a **linked** worktree creates
   `.git/worktrees/<id>/modules/<path>`, so this is the branch that actually
   fires, and it survives a later `deinit` or an edit to `.gitmodules`;
2. a `.gitmodules` `path =` entry whose directory is **non-empty** (git's
   `!is_empty_dir`, walked with `openat(O_NOFOLLOW)` per component, so a
   `.gitmodules` naming `../..` or routing through a symlink cannot look
   outside the tree). An *uninitialized* submodule is an empty placeholder and
   is **not** a refusal — matching git, verified in the fixture.

It is also checked **before the salvage**, not only inside
`git_would_remove_worktree` after it: salvage cannot capture anything inside a
submodule, so running it first would stage the index and detach HEAD of a tree
that is kept anyway.

Divergence from git, stated: git reads the worktree's **index** for gitlinks;
this reads `.gitmodules`, because the index is a binary format no handle-based
read can parse. Branch 1 covers the gitlink whose `.gitmodules` entry was edited
away. A gitlink that was never in `.gitmodules` **and** whose worktree admin dir
has no `modules/` is not refused — residual, below.

## Residual Risk

1. **F2's subprocess window is open.** Bounded and now documented at
   `reclaim_managed_worktree`. Closing it needs the clean decision computed from
   the handle the way the submodule refusal now is.
2. **F1's index-vs-`.gitmodules` divergence.** A gitlink that was never in
   `.gitmodules` **and** whose worktree admin dir holds no `modules/` is not
   refused by us but is by git. No path in this repo produces one
   (`git submodule add` always writes `.gitmodules`, and `submodule update
   --init` always creates the admin `modules/`). Closing it means parsing git's
   binary index or spending a `git ls-files --stage` subprocess — the latter
   would re-open F2 for this decision.
3. **`dispatch-close` still shells out to `git worktree remove`.** So prune and
   close now take the same decisions by different routes. They agree on the
   three refusals; they are not the same code. The org convention now says this
   out loud rather than implying they are one mechanism.
