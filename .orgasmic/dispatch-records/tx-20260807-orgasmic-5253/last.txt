## Measured by me vs inherited

**Measured myself, git 2.52.0, scratch repos:**

- The D-1 counterexample. `git revert --no-edit HEAD~1 HEAD~2` → `REVERT_HEAD` +
  `sequencer`; `git add` + `git commit` → **`sequencer` alone**, `git status`
  clean, todo still `revert 7cdfd59 v2` / `revert 9627dfc v1`, and
  `git revert --continue` resumes (stops again, re-creating `REVERT_HEAD`).
- The latch: after `reset --hard`, `.git/sequencer` survives; an ordinary commit
  does not clear it; `git revert --quit` does (exit 0, dir gone).
- **New, and load-bearing for the artifact:** a *single-pick* conflicted revert
  and a clean `git revert -n` create **no `.git/sequencer` at all**. That is why
  restoring the entry does not disturb `verify/TASK-QGWK7.1.1.1.1` — its fixture
  is a single pick, so the injection's missing `REVERT_HEAD` is still the only
  thing standing between the close and `ok`.
- D-3, production shape (real-index `git add` first, then throwaway index,
  `commit-tree`, `update-ref`): `git revert --abort` → **exit 0**, record on disk
  and in `HEAD`, `REVERT_HEAD` gone, and `f.txt` back to `v3` — i.e. the abort
  **rewound to the current HEAD and discarded my conflict resolution**. Skipping
  the real-index `git add` reproduces the old exit-128 wedge, confirming C-1's
  account of why the original symptom was wrong.

**Inherited from the review, not re-measured:** that `merge --abort` is likewise
`reset --merge` to HEAD, and that `am --abort` is the only one that declines
outright. Both appear in the corrected prose. Residual risk noted below.

## What I disagreed with / decided differently

1. **Three patches re-authored, not two.** D-2 asked for the array as an exported
   `const`, and `orgasmic-cli` has no lib target, so the array had to leave
   `manager.rs` — which staled `verify/TASK-QGWK7.1.1.1.1/injection.patch` as
   well. I judged that acceptable rather than abandoning D-2: the re-authored
   patch deletes the same row, produces the same five-marker set, and the artifact
   still goes red on the same first assertion. Called out loudly here and in
   the artifact's README, since a reviewer will see a third artifact in the diff.
2. **The abandoned range is now REFUSED, not persisted.** C-2's trap was real, and
   the previous round's `a_close_after_an_abandoned_pick_range_persists_the_record`
   pinned the opposite of what this round pins. There is no way to distinguish an
   abandoned range from a live hand-committed one on disk — both are `sequencer`
   with no `*_HEAD` — so the guard must refuse both and the message must carry the
   difference. That is exit (a) as instructed; I renamed the test rather than
   leaving a name that asserts the reverse of its body. No `cmd`/`expect-red`
   pinned that name (checked).
3. **`rebase-apply` maps to the convention's `am`.** The array's refusal name is
   `"rebase or am"` but the prose lists `rebase` and `am` separately, so the
   third field carries the prose spelling and the mapping is documented at the
   const. If a future reader thinks that mapping is a fudge, the fix is to make
   the prose say `rebase or am` — but that reads worse to a manager.

## Residual Risk

- **`merge --abort` and `am --abort` mechanisms are inherited.** I re-measured
  the revert/cherry-pick row and the "abort discards your resolution" claim
  myself; the reviewer measured the other two and I did not re-run them. If
  either is wrong the corrected prose has a wrong clause again — though the
  *outcome* half (exit 0, record intact) is what the code depends on, and that
  row is covered by `a_close_inside_a_conflicted_revert_…`.
- **The `.org` list parser is anchored on a sentence.** Reword
  `"A close does not persist while a sequencer operation owns HEAD* ("` and the
  new test panics with a message naming the anchor rather than silently passing.
  I chose a loud failure over a fuzzy match; it does mean a legitimate reword
  costs a one-line test edit.
- **Order sensitivity is deliberate.** The pin compares as an ordered Vec, so
  reordering the prose list without reordering the array fails. That is intended
  (the array's order is load-bearing — `sequencer` must be last) but it is
  stricter than "same set".
- **`verify/TASK-QGWK7`** is stale and is TASK-8Q92K's, not touched here.
