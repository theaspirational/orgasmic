# The answer to your one most important question

> which adjacent branch did round 5 leave wrong?

**The B2 arm's `FAIL_COUNT -eq 0` guard, for the population it still owns.**

I enumerated the nine arms and drove each population through both modes. Round 5
correctly removed the crashed-*target* population from behind that guard by
deriving it from the log. What it did not do is ask *why the guard is there*.
The comment at `:1257` answers it exactly: **"cargo exits 101 whenever any test
fails."** That justifies exempting **101** — it does not justify exempting
**every** non-zero code. `FAIL_COUNT -eq 0` is a proxy for "the exit is 101", and
it is a leaky one.

So the arm still swallows every anomalous exit code the moment a registered flake
lifts `FAIL_COUNT` off zero — and this chain exists because registered flakes
fire. r3 missed the flake path; r4 missed the crash-plus-flake path; **r5 missed
the anomalous-exit-plus-flake path.** Same guard, third time.

# Findings

## F-1 — HIGH — BLOCK SHIP — a non-101 non-zero cargo exit is swallowed whenever any failure classifies

`scripts/run-tests.sh:1254`.

**LIVE PATH, stub cargo, verbatim.** Stub emits one registered-flake failure
(green in isolation, signature matched) and exits **137**:

```
  failures : 1
  crashed  : none — every failing target reported a failure list
  host     : calm (threshold syspolicyd_rate>=1.50; load corroborating only)
verdict: GREEN modulo 1 registered flake(s). No unexplained red.      exit 0
```

and the log the live run wrote, in the same work dir:

```
# orgasmic-suite-exit: 137
```

Drop the flake from the same log and the same exit is caught:

```
  failures : 0
verdict: RED — cargo exited 137 with no per-test failure list.        exit 1
```

Identical exit code, identical arm, opposite verdict — decided entirely by
whether a *registered flake* happened to fire. `--classify` on the stamped log
agrees with the live path in both cases, so R-2's parity holds; both modes are
wrong together.

**Why this is not R-1 re-filed.** R-1 was a crashed *target*: cargo survived,
printed `error: test failed, to rerun pass`, exited 101, and the log named the
casualty. F-1 is a crashed *suite*: cargo itself died, so there is no failing
target to diff and no cause line to name — `CRASH_COUNT` is 0 by construction and
round 5's log-derived detector cannot see it. The only witness is the exit code,
and that is precisely the witness `FAIL_COUNT -eq 0` gags.

**Why it reaches CI.** `ci.yml:197` runs the live path and `exit $status`. Exit 0
merges. The verdict block a human might read says `crashed  : none` and
`No unexplained red.` over a suite that never finished — the truncation is
mentioned nowhere.

**Reachability.** Signals to `cargo` on this board: jetsam/OOM under exactly the
memory pressure this chain documents, or an operator `^C`/`kill` mid-run. Note
the tension with your claim 3: you were right that host pressure can present as a
crash — it just presents one level higher than where round 5 looked.

**Fix direction.** Replace the proxy with the fact the comment already states.
Guard on the *code*, not on `FAIL_COUNT`:

- `SUITE_EXIT` ∈ {0, 101} → ordinary; classify as today (this is what preserves
  M-1: 101 is the flake path, and it stays green modulo N).
- `SUITE_EXIT` anything else, and not `?` → its own RED arm with its own summary
  line, **whatever else classified**, placed beside the crash arm. Name it: the
  run did not finish, so nothing in it is a trusted green — the same argument
  F4 made for `REAL_COUNT` and R-1 made for `CRASH_COUNT`.
- `?` (pre-stamp `--classify`) → skip, as B2 already does.

This does **not** re-drop the `FAIL_COUNT` guard and does not recreate M-1 — M-1
was caused by treating **101** as a red, and 101 stays exempt. Pin it with a
live-path case: registered flake + stub exit 137 → RED exit 1, and the existing
flake+101 case passing in the same run.

## F-2 — MEDIUM — a target that *did* report is reported as having crashed (your claim 2)

`scripts/run-tests.sh:841`.

The exclusion is `(exit status: 101)` **only**, and `NAMED` never asks whether
the target was accounted for. Any other exit status on a target that printed its
full failure list is counted as a crash.

**Reproduced.** The p1 log (one registered flake, full `failures:` list, correct
`Caused by`), with the cause changed from `(exit status: 101)` to
`(exit status: 1)` and nothing else:

| cause | verdict | exit |
|---|---|---|
| `(exit status: 101)` | `GREEN modulo 1 registered flake(s).` | 0 |
| `(exit status: 1)` | `RED — 1 crashed test target(s).` | 1 |

The CRASHED section then prints, about a target whose failures are listed three
lines above it in the same log:

```
      note     : libtest dies with the process, so this target reported NO
                 failures. It cannot be classified, registered, or excused.
```

That is a **false RED on the flake path** — M-1's shape by the third route, and
the statement in the report is false on its face.

**Answering your question directly:** no, 101 is not the only ordinary-red exit
code, and non-101 exits do **not** merely land in UNACCOUNTED — they land in
**NAMED**, which is the wrong home, because NAMED has no accounted-for test.
UNACCOUNTED *is* the right home: the cardinality diff excludes reporting targets
by construction, which is exactly the discrimination NAMED lacks.

**Not currently live in this repo** — I grepped every `Cargo.toml` for
`harness = false` and there are none, so every target here exits 101 through
libtest. It is latent, and it is latent on the one branch whose whole job is not
to invent reds.

**Fix:** require a NAMED target to also be unaccounted (`cause` then only
*explains* the crash rather than *deciding* it). One condition, and it fixes F-3
in the same edit.

## F-3 — MEDIUM — `max()` unions two *disjoint* sets by cardinality, so it names the wrong target (your claim 1)

`scripts/run-tests.sh:858`.

`max` is safe as a *gate*: `max(N,U) = 0` iff both are 0, so it can never
under-count to zero and can never produce a false green. If the count only gated
a boolean you would be right to downgrade this. **It does not** — `CRASH_COUNT`
is printed in the summary line, in the section header, and in the verdict line,
and it decides whether the unnamed-remainder block prints at all (`:1199`).

NAMED and UNACCOUNTED are not two derivations of one set; they can describe
**different targets**. Reproduced with a two-target log — `--lib` reported its
failures and exited 1 (NAMED, accounted), `--bin crashdemo` genuinely vanished
(unaccounted, no cause line):

```
  crashed  : 1 target(s) died without reporting a failure list
CRASHED (1) — target died without reporting a failure list:
  -p orgasmic-daemon --lib          <-- the target that DID report
      why      : process did not exit successfully (exit status: 1)
```

`--bin crashdemo`, the target that actually died, **appears nowhere in the
output**: the remainder block at `:1199` is suppressed because
`CRASH_UNACCOUNTED (1) > CRASH_NAMED (1)` is false. The operator is handed the
wrong binary to re-run, told a falsehood about it, and never told about the real
one.

**Fix:** union by target identity, not by cardinality — keep the NAMED
target→cause map, mark unaccounted targets, and report the union. Requiring
NAMED ⊆ unaccounted (F-2's fix) collapses this case correctly on its own.

## F-4 — MEDIUM — test — the `(exit status: 101)` exclusion has zero coverage

`scripts/run-tests-selftest.sh` (all 50 cases).

```
$ grep -n "exit status" scripts/run-tests-selftest.sh
$ echo $?

```

**Not one fixture log in the entire self-test contains a `(exit status: …)`
cause line.** The 50 cases model cargo as emitting `Caused by:` for the *crashed*
target and nothing at all for the ordinary red — see
`install_stub_cargo_crash_plus_flake` at `:227` of the diff, whose `--lib` target
gets a bare `error: test failed, to rerun pass` with no cause block.

That single regex at `:841` is the only thing standing between every ordinary red
on the real suite and a false CRASH verdict, and it is exercised by nothing. I
verified by hand that it is **correct** for the canonical shape (probe p1 above:
GREEN modulo 1, exit 0) — so this is coverage, not a live defect. But this chain
has now shipped four rounds whose defect was an unexercised adjacent branch, and
this is the round's largest one.

Compounding it: the whole crash detector is calibrated against a log shape nobody
has re-measured. The implementer says so plainly (Residual Risk 5). If real cargo
*does* emit `Caused by: … (exit status: 101)` for ordinary reds — which I could
not confirm inside the zero-cargo budget — then on the real suite that regex runs
on every red, untested. If it does *not*, the exclusion is dead code and F-2's
false RED is unreachable by that route. Either way the fixture corpus should
carry both shapes.

**Fix:** add two cases — an ordinary registered-flake red *with* the
`(exit status: 101)` cause block (must stay GREEN modulo 1, exit 0), and the same
with a non-101 status (asserting whatever F-2's fix decides). Both are three-line

## F-5 — LOW — design, follow-up not block — the crash arm outranks `HOST_DEGRADED` (your claim 3)

`scripts/run-tests.sh:1229` vs `:1268`. Confirmed empirically: `(signal: 9,
SIGKILL: kill)` on a stamped-DEGRADED log returns `RED — 1 crashed test
target(s)`, exit 1, not INCONCLUSIVE exit 4.

**The ordering is right. Ship it.** Your split is the correct one, and it lands
almost entirely on the code side:

- **Cannot plausibly be host-caused:** SIGABRT(6), SIGSEGV(11), SIGILL(4),
  SIGFPE(8). A process does not receive these because the machine is busy. RED is
  correct and F4's argument applies unchanged.
- **SIGBUS(10)** is a code fact far more often than not (misaligned access,
  truncated mmap); the host-caused reading needs a full disk, which is its own
  red anyway.
- **SIGKILL(9)** is the only genuinely misfiled one — a test binary essentially
  never SIGKILLs itself, so on this board it means jetsam.

Even for SIGKILL, RED-over-INCONCLUSIVE is the conservative direction: it fails
loudly rather than merging, which is the right default for a gate, and exit 4
also fails CI (`ci.yml:197`) so the merge outcome is identical — only the
diagnosis differs. Carve SIGKILL out to INCONCLUSIVE **only if** the false-red
cost is ever measured, and note it interacts with F-1: a SIGKILLed *cargo* lands
in the same place by the same argument.

# Your claims, by number

**1. Is `max` right?** No — see **F-3**. It is safe as a gate (never
under-counts to zero, so no false green) but it does *not* only gate a boolean:
it drives the count in three printed places and gates the remainder block, and I
built a log where it names the target that reported and silently drops the one
that died. Do not downgrade.

**2. The `(exit status: 101)` exclusion.** 101 is not the only ordinary-red exit,
and the others land in **NAMED**, not UNACCOUNTED — wrong home, false RED on the
flake path. Reproduced. See **F-2**. Latent only: no `harness = false` targets in
this workspace.

**3. Crash outranks `HOST_DEGRADED`.** Ordering is **right**; SIGKILL is the only
signal in the misfiled subset, and even there the merge outcome is unchanged.
Follow-up at most, **not** BLOCK SHIP. See **F-5**.

**4. Is anything that used to reach B2 now reaching nothing?** **No.** B2's
condition is byte-identical; only the crash arm was inserted above it. The moved
population is exactly `FAIL_COUNT==0 ∧ exit≠0 ∧ CRASH_COUNT>0`, which now lands
on a strictly louder RED at the same exit 1. B2 is still live and now pinned —
probe p8 (`exit 137`, no failures, no targets named) reaches it and prints
`RED — cargo exited 137 with no per-test failure list`. The narrowing is sound.
The hole is not in what left B2, it is in what B2 still fails to catch (**F-1**).

**5. `open_owner()` in the fixture.** **Keep it.** You are trading a loud break
for a *louder* one, not a rarer one, and I checked the predicate rather than the
intent:

- `open_owner` accepts id X iff X's `:ID:` appears in a top-level non-done,
  non-cancelled `*.org` **and** X is not in `done.org`/`cancelled.org`.
- `check_owner_lifecycle` (`:301`) accepts X iff X is not in
  `done.org`/`cancelled.org` **and** X appears anywhere under `.orgasmic/tasks`.

The first strictly implies the second, so **there is no board state in which the
resolver picks an owner the gate then rejects.** That is the confusing-break
scenario you feared, and it cannot occur.
- No open task at all → `FAIL setup: no open task in … to own the fixture
  registry entries`, `exit 1`. Loud and named.
- First open task renamed/closed → picks the next one; assertions interpolate
  `$FIXTURE_OWNER`, so they follow. Self-healing.

The measured cost of the hardcoded id was **36 of 44 cases failing** for a reason
with nothing to do with the classifier — the gate you assigned was unrunnable.
Residual (LOW, accept): the fixture prints a real unrelated task id
(`TASK-P19ZM` on today's board) as a flake owner, and self-test output is no
longer reproducible across boards.

**6. `EXPECTED_CASES=50`.** **It does not fail open.** Proven, not reasoned — I
ran a scratch copy with the constant bumped to 51:

```
50 passed, 0 failed
FAIL case count: ran 50, expected 51 — a case was added or vanished     exit 1
```

`TOTAL = PASSED + FAILED`, so a case that `start`s and never `check`s is counted
by neither and trips the assertion; `take_live_log` failing counts as a FAIL, so
the R-5 path is covered from both sides. Your friction concern is **real and
unmitigated**: adding a case requires touching a constant 900 lines away, and the
failure message — *"a case was added or vanished"* — literally offers bumping the
number as one of two readings. LOW; if you want it closed, derive the count from
the `start` calls rather than declaring it.

**7. Ordinary cases byte-identical.** **Verified independently**, not taken on
report: I extracted `scripts/run-tests.sh` at `4136972` and diffed its output
against HEAD's on the same clean log and the same registered-flake log.

- **Verdict lines and exit codes: identical.** `GREEN — no failures.` exit 0 and
  `GREEN modulo 1 registered flake(s).` exit 0 on both.
- The only content delta, both cases, is **one added summary line**:
  `crashed  : none — every failing target reported a failure list`. Deliberate,
  documented, and the CI step-summary publisher (`ci.yml:210`) copies the block
  wholesale, so nothing parses around it.

So the *substance* of the claim holds. The word **"byte-identical" in the
implementer's report is wrong** — the output did change by one line. Minor, but
worth correcting in a chain where a report's precision is load-bearing. (Also
cosmetic: that line reads `every failing target reported a failure list` on a
clean run where no target failed at all.)

**8. Your commit `a8edf93`.** **Legitimate. I attacked it and it holds.**

Mechanically clean — I diffed the registry excluding `owner =` and comment lines
and the result is **empty**: signatures, evidence and `filed` dates are byte-
untouched. `bash scripts/run-tests.sh --check` → `registry: OK — 7 entries in
verify/flake-registry.toml, every owner open`.

On intent: transfer would defeat *"a registry that only grows is a graveyard"* if
`TASK-X0PV1` were a parking lot. It is not — I read its acceptance criteria
(`backlog.org:4195+`), and they close the loophole explicitly:

> Either each registered mode is FIXED and its entry deleted, or the entry is
> re-evidenced with a fresh dated measurement and stays owned by an open task.
> No entry is deleted merely to make `--check` green while the flake still fires.
> If a mode proves unreproducible on current HEAD, say so with the measurement
> and delete it on that evidence.

That is a fix obligation with a dated re-evidencing requirement and an explicit
ban on the graveyard route — a stricter home than the entries had under
TASK-STWVB, which closed while still owning them. Deleting them would have
converted four measured flakes into unexplained REAL failures, and the transfer
preserves the one thing the registry exists to preserve: a named human-scale
owner. The only defect is documentary — **F-6**.

**9. Doctest exclusion.** **Internally complete and consistent — conditionally
correct.** Verified, not accepted: `TARGETS_FAILED` (`:852`) counts only
`^error: test failed, to rerun pass`, and `TARGETS_ACCOUNTED` (`:854`) skips
`$2 == "doctests"`. Both sides drop doctests, so the cardinality diff is balanced.
A doctest-only failure log through `--classify` gives `crashed  : none` and
`RED — 1 real failure(s)` — correct.

I could **not** verify cargo's literal string inside the zero-cargo budget. The
exclusion's correctness rests entirely on it: if cargo ever printed
`error: test failed` (not `doctest failed`) for a doctest target,
`TARGETS_FAILED` would count it while `TARGETS_ACCOUNTED` excludes it, and
**every doctest failure would become a false CRASH**. Note the asymmetry that
already exists: the NAMED awk matches `^error: [a-z]+ failed` and so *does* see
doctests, while `TARGETS_FAILED` does not. That is defensible (a signalled
rustdoc is a real crash) but it means the two derivations disagree about what a
doctest is. Keying the diff on target names instead of cardinality removes the
dependence on that string entirely.
