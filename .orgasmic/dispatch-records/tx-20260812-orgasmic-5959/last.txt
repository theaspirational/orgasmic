## Verdict

**PASS.** All four acceptance criteria are met and independently verified, including the one the task

## Findings

### LOW (test) — `test_hooks::reset()` does not clear the new armed-rename list

`crates/orgasmic-daemon/src/writer.rs:87` resets `SYNC_COUNT`, `SYNC_ATTEMPT_COUNT`, `SCAN_COUNT`, and
`FAIL_NEXT_SYNC`, but not `RENAME_BEFORE_SYNC` (`writer.rs:56`). Every other injectable hook is cleared
there; this one is not, and nothing else consumes an entry that never reaches a sync.

Nothing breaks today: no unit test in the lib-test binary calls `reset()`, and armed entries are keyed by
absolute `tempfile` paths, so they cannot be matched or clobbered by another test. The concrete future
symptom is a stale entry surviving a test that arms a rename and then fails before `sync_tx_writer` runs
— e.g. a test that also arms `fail_next_sync(1)` for the same path, since the injected-failure `bail!`
at `writer.rs:130-134` returns *before* the rename block at `writer.rs:137-157`. The leaked entry then
makes the `assert!` at `writer.rs:113` panic with "a tx path rename before sync is already armed" in
whatever later test reuses that path, pointing at the wrong test.

Fix direction: clear `RENAME_BEFORE_SYNC` in `reset()` under `#[cfg(test)]`, or have
`rename_tx_path_before_next_sync` return a drop guard that disarms.

Not a data race: the list is a `std::sync::Mutex<Vec<_>>` (not a `static mut`), the guard is dropped
before `std::fs::rename` runs (`writer.rs:139-147`), and poisoning is absorbed via `into_inner`.
Parallel-test isolation is sound because arming and matching both key on the full tempdir path.

### LOW (test) — the malformed-transaction regression cannot distinguish "rejected" from "executed with nothing to write"

`writer.rs:2537` (`malformed_transaction_is_request_local_and_writer_stays_live`) sends
`rewrites: Vec::new()`. It proves the reply arrives, the message text, and that the writer accepts the
next command — the stated acceptance criterion — but with an empty rewrite set it would pass equally if
the branch had executed the transaction. Reading `writer.rs:1330-1341` confirms the branch sets
`execute = false`, so no write can occur; this is a coverage nit, not a bug. One non-empty `FileRewrite`
plus an assertion that the target file is byte-identical afterwards would close it.

### LOW (test/design note) — the seam expresses rename-away only, not unlink or atomic replacement

The task text asks for a seam that "renames/unlinks/replaces the ledger pathname". The hook matches on
`rename.source == path` (`writer.rs:143`), i.e. the pathname being synced is always the rename *source*,
so a decoy renamed *onto* `tx_path` (atomic replacement) is structurally not expressible.

This is a fair trade rather than a defect, and worth recording so a future reader does not "fix" it:
* Unlink is behaviorally identical to rename-away for the negative control — a restored reopen gets
  `ENOENT` either way.
* Atomic replacement is precisely the variant a reopen-based ack gets **silently** wrong: the reopen
  succeeds and fsyncs the wrong inode, returning `Ok`. No error-propagating test can catch it, so adding
  that variant would weaken, not strengthen, the guard. The retained-descriptor fix satisfies the
  "invariant under atomic replacement" constraint by construction, since the ack path never touches the
  pathname again.

### Observation (not attributable to this change) — unrelated flaky test under parallel load

`api::tests::post_artifact_regenerate_cold_changed_address_replaces_whole_launch_record`
(`crates/orgasmic-daemon/src/api.rs:37904`) failed once in a full `--lib` run (828 passed / 1 failed),
asserting `model: Some("old-model"), effort: Some("high")` where `model: Some("new-model"), effort: None`
was expected. It passes in isolation (`1 passed`, 0.87s). Classified **flaky, pre-existing**: the commit
touches `writer.rs` only, the failure is in the artifact launch-record path, and the observed
old-vs-new-record content is a state/ordering symptom, not a durability one. Worth a separate task; it
should not gate this one.

## Verification against the brief's five questions

1. **Seam placement / production behavior.** `before_sync(path)` is called at the top of
   `sync_tx_writer` (`writer.rs:1782`), which runs after every append in `process_tx_batch`
   (`writer.rs:1633`) and after `append_tx_inner` in `transaction_inner` (`writer.rs:1796`) — so the seam
   is exactly between append and the real fsync. Under `cfg(not(test))` the body is byte-for-byte the
   prior logic plus `let _ = path;` (`writer.rs:126-136`); the rename block is `#[cfg(test)]`-only.
   Existing hook order is preserved: attempt-counter increment, then `FAIL_NEXT_SYNC`, then (test-only)
   rename — the injected-failure path is unchanged and still wins.
2. **Negative-control claim: CONFIRMED, twice.** See Verification Notes; both new tests fail under a
   restored reopen, and also fail if the seam itself is disarmed.
3. **Hook isolation.** Sound as written; see LOW finding 1 for the one missing symmetry.
4. **`unreachable!` → request-local error.** `writer.rs:1320`. The `Err` arm (`writer.rs:1330-1336`)
   takes the reply exactly once, sends the error, sets `execute = false`, and never reaches
   `transaction_inner`, the idempotency-cache insert, or the `TxAppended` publish — so no duplicate
   write, no missing reply, no writer death. `command_failed = true` only increments
   `metrics.failed_total` (`writer.rs:1500-1503`); there is no sticky degraded state.
   The branch remains unreachable from production: the only two `WriterCommand::Transaction`
   constructors (`writer.rs:707`, `writer.rs:739`) both pass `mutation: Some(..)`. I checked the two
   `mutation: None` sites in `api.rs` (`14575`, `14721`) — those are `GraphWriteRequest.mutation`, which
   routes to `WriterHandle::transaction()` at `api.rs:15671`, which itself sets `Some(mutation)`. No
   remaining `unreachable!`/`panic!`/`todo!` exists in `writer.rs` outside `mod tests` (starts line 2244).
5. **Existing durability behavior.** Unchanged and still proven — all 6 `writer_durability` integration
   tests pass, covering fsync-before-ack, one-sync-per-batch, sync-failure denial, and rewrite rollback.

**Not verified.** No crash-consistency test (power-loss durability of the synced bytes) — out of scope
and not claimed. No production daemon probe: install/restart was prohibited by the brief, and the
regressions already run the real serialized writer task via `spawn()` + `WriterHandle`, which is the
daemon's actual routing rather than a direct `TxWriter` call. Both negative controls compile and run
the same daemon routing, so the production path is exercised in test configuration only.
