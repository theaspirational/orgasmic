## Verdict

**approve-with-follow-ups**

The lazy-catalog boundary is genuinely hardened. Timeouts, the core/optional
semaphore split, generation/registration guards, scoped-tx filtering, header
sanitization, and the partial-coverage UX are all real, correct closures of the
first review's findings. Two HIGH follow-ups remain: a coordinator budget that

## Findings

### H1 — HIGH (bug, availability + wrong operator diagnosis)
`crates/orgasmic-daemon/src/index.rs:432`, `:530`, `:943`, `:1287`

`FIRST_LOAD_COORDINATOR_TIMEOUT` is 8s. It is measured from waiter registration
(`request_project_load`, index.rs:943) and therefore covers the coalescing
window (≤200ms, index.rs:430), the wait for a `core_project_scans` permit
(2 permits, index.rs:530), *and* the project's own 5s scan (index.rs:431/1287).

With N projects stalled on the same dead mount, a queued healthy project waits
`ceil(N/2) × 5s` before it even starts. At N ≥ 4 that is ≥10s > 8s, so the
healthy project's first load fails before its own scan can run. It also fails at
N = 2 whenever its own scan needs more than ~2.8s.

The failure text is actively wrong. `refresh_timeout_message` (index.rs:1406)
emits `"... coordinator wait timed out after 8.0s at <path>; check that the
project path is mounted and readable, then retry"` and, for anything under
`~/Documents`, appends the macOS Files-and-Folders guidance (index.rs:2961).
The project is mounted, readable, and correctly permissioned; it was queued.
API callers see a 503 blaming the wrong project.

Concrete scenario: board with 5 projects, 4 on a hung SMB/NFS mount, 1 healthy
local. `GET /api/tx` (api.rs:2559) ensures all five. The healthy project 503s
with `project healthy failed to load: project coordinator wait timed out after
8.0s at /Users/aspirational/Documents/code/healthy; check that the project path
is mounted and readable ... grant the orgasmic daemon Files and Folders access
for Documents`. An operator following that guidance changes TCC settings for a
project that never had a permission problem.

The new test does not catch this: `bounded_first_loads_release_capacity_for_a_
healthy_project` (index.rs, added in this diff) calls
`set_refresh_timeout(Duration::from_millis(150))`, which shrinks the *scan*
budget but leaves the 8s coordinator budget untouched — so the ratio under test
(150ms scan : 8s coordinator ≈ 53×) is nothing like production (5s : 8s = 1.6×).
The shipped constants are unexercised.

Fix direction: either start the coordinator clock after the permit is acquired,
or size it as `permit_queue_depth × PROJECT_REFRESH_SCAN_TIMEOUT + margin`
(≥16s), or — cheapest and most honest — give the queued case its own message
that says "waiting behind N slow project scans" and never appends the
Files-and-Folders hint on a coordinator-wait timeout. Add a test that drives the
production constants rather than a rescaled pair.

### H2 — HIGH (bug, availability)
`crates/orgasmic-daemon/src/api.rs:13779-13789`; `crates/orgasmic-cli/src/main.rs:2402`

`get_graph_markers` loops every authorized project and `?`s on the first
failure. One project that cannot load markers makes the whole request 503, and
every project ordered after it is never attempted.

This is the designated full-coverage path for both new operator surfaces:
- `orgasmic status --errors` (main.rs:2402) `?`s on it, so the command aborts
  with an error and prints **no parse errors at all** — worse than the partial
  output it used to give.
- The StatusView "Load full coverage" button and the NotificationBell
  "Load full coverage" row both call `loadFullParseErrorCoverage`
  (ui/src/lib/api.ts), which does `get('/graph/markers/__coverage__')`. It
  toasts "Full coverage failed" and the coverage badge stays `partial` forever.

AC #5 required exactly this partial-outcome discipline and `post_reindex`
(api.rs:13482-13492) implements it correctly with a `failures` map. The same
treatment was not applied to the marker path that AC #2 and AC #4 depend on, so
a single permanently-failing project makes full coverage permanently
unreachable — the state the fix was supposed to make escapable.

Fix direction: mirror `post_reindex`. Collect per-project marker failures,
continue the loop, and return 200 with the partial file set plus a failures map;
let `status --errors` and the UI report which projects were skipped.

### M3 — MEDIUM (correctness)
`crates/orgasmic-daemon/src/index.rs:636-645`; `ui/src/components/BoardView.tsx:147-151`

`blocked` counts every non-Done/non-Cancelled task with a non-empty
`depends_on`, without checking whether those dependencies are themselves done.
A project whose dependency chain is fully satisfied still renders a red
`destructive` "N blocked" badge on its board card.

Two related notes:
- This is not a restoration of prior behavior. The pre-lazy `BoardView`
  computed `blocked` from `t.blocked_by`, but `TaskSummary` (index.rs:57-79) has
  no `blocked_by` field and never serialized one — `BLOCKED_BY` is only an alias
  onto `depends_on` in the graph-edge router (api.rs:13739). The old badge was
  dead code that always rendered 0. This is new visible behavior.
- The new test asserts only `stats.blocked == 1` on a fixture where the
  dependencies are still `BACKLOG` (index.rs:4317-4330), so the
  satisfied-dependency case is untested.

Fix direction: exclude tasks whose `depends_on` targets all resolve to
Done/Cancelled, or relabel the badge so it does not claim blockage.

### M4 — MEDIUM (design, availability)
`crates/orgasmic-daemon/src/index.rs:1287-1301`

The scan timeout drops the `spawn_blocking` JoinHandle; the OS thread keeps
running to completion. The in-code comment is correct that late work cannot
publish (`drop(seed)` happens before the expensive scan in every arm of
`build_refresh`, so no read guard is held either — good), but nothing bounds how
many such threads accumulate.

After the timeout settles, `state.running = false`, so the next request for the
same target spawns a fresh worker and a fresh `spawn_blocking` while the
previous one is still wedged. The daemon runs on a default `Runtime` (no
`max_blocking_threads` override anywhere in `crates/`), so the pool caps at 512.
A truly hung mount plus any polling caller — `GET /tx` at api.rs:2559 ensures
every board project on every NotificationBell poll — leaks one thread per
project per poll until the pool is exhausted, at which point *every*
`spawn_blocking` in the daemon queues behind dead threads. That is a global
wedge, not a per-project one.

Fix direction: a per-target in-flight guard that refuses to start a new scan
while the prior one has not returned, and a leaked-scan gauge in
`refresh_status` so the condition is observable before it becomes fatal.

### M5 — MEDIUM (availability, parent-scope but aggravated here)
`crates/orgasmic-daemon/src/api.rs:2559-2566`

`GET /tx` with no `project` ensures every board project loads and `?`s on the
first failure, so one unloadable project 503s the entire notification feed for
every project. The loop predates this diff (present at `9ef8ae5`, absent before
TASK-AJP4A), so it is parent scope — but this fix's new 5s/8s budgets convert
"eventually slow" into "hard 503", which is what makes it worth a follow-up now.

### L6 — LOW (contract)
`crates/orgasmic-daemon/src/api.rs:13482-13492`

`POST /reindex` returns 200 even when `failures` is non-empty, so
`orgasmic reindex` exits 0 after a partially failed whole-board reindex. The
JSON body is honest; the exit status is not. Any script gating on exit code
treats a half-failed reindex as success. Consider 207-style semantics or a
non-zero CLI exit when `failures` is populated.

### L7 — LOW (design)
`crates/orgasmic-daemon/src/index.rs:431`, `:2997-3031`

`PROJECT_REFRESH_SCAN_TIMEOUT` is a hard-coded 5s with no env override.
`scan_project_markers` reads the contents of every `.rs/.ts/.tsx/.js/.jsx/.py/
.sh/.bash/.zsh/.yaml/.yml/.toml` file in the tree. Measured on the orgasmic repo
itself: 11.4 MB across the scannable extensions, 0.155s warm — so the constant
is comfortable here. A large monorepo or a cold network mount has no escape
hatch and would lose marker coverage permanently with no way to grant it more
time.

## Things I checked that are correct

- **Timeout releases capacity.** `drop(project_permit)` (index.rs:1310) runs on
  the timeout path, and `drop(seed)` precedes the expensive scan in all four
  arms of `build_refresh` (index.rs:1583, 1624, 1642, 1657), so a stalled scan
  holds neither a semaphore permit nor an `inner` read guard past its budget.
  This kills the obvious "one stall wedges the RwLock and starves every reader"
  failure mode.
- **Late work cannot publish.** Publication is outside the `spawn_blocking`
  closure; the abandoned handle's result is discarded.
- **Core/optional lane separation** is real (index.rs:1241-1261) and the marker/
  artifact test proves the core lane stays free.
- **Path-change race.** `record_project_load_failure` (index.rs:958) correctly
  refuses to overwrite a fresh `Unloaded` entry installed by `refresh_board`,
  and the `old_root_refresh_racing_path_change...` test exercises the real
  ordering.
- **Ready-with-last-good on failed refresh.** `mark_project_refresh_attempt`
  and `record_project_load_failure` both keep a project `Ready` when a last-good
  projection exists, set `error`, and preserve `generation`/`last_loaded_at` —
  the "stranded in loading" defect is closed.
- **Scoped `GET /tx`.** `include_home_tx` (api.rs:2542) is correct;
  `TxRecord.project_id` is assigned from the tx *directory*
  (`collect_tx_dir`, index.rs:2667-2681), so home rows carry `None` and are now
  excluded before the limit is applied. The new test's fixture deliberately sets
  a `:PROJECT:` property on the home row and still expects exclusion, which is
  the right assertion.
- **Header panic.** The old `.expect("catalog project ids form a valid header")`
  is gone; `coverage_project_ids` percent-encodes, and the `from_str` fallback
  is a belt-and-braces `partial;` value. AC #8 met.
- **CORS.** `expose_headers` is now set (api.rs:856) and asserted from a real
  request with an `Origin` header — without it the browser could never read the
  coverage header, so this was load-bearing.
- **Notification polling does not scan.** The bell polls
  `fetchParseErrorsWithCoverage` → plain `GET /graph/parse-errors`, no
  materialization. Recursive scanning is only on the explicit action. Asserted.
- **`getWithHeader`** lives inside `transport.ts` and `transport.request` is
  never reassigned anywhere in `ui/` or the Tauri shell, so bypassing the
  `transport` indirection is safe today (it does not handle 204, but the one
  endpoint it serves always returns a body).

## Aggregate-failure causality assessment

**The two supervisor process-probe failures are not caused by this fix.**

- `supervisor::tests::a_probe_child_that_never_exits_is_killed_and_reaped_at_the_deadline`
  (supervisor.rs:10951) and its sibling both fail on
  `.expect("the stub recorded its \`sleep\` pid")` (supervisor.rs:10987).
- The stub is `/bin/sh -c "sleep 120 & echo $! > <pidfile>; wait"` killed at a
  **400ms** deadline (supervisor.rs:10964). Under aggregate-run load the shell
  can be killed before it flushes the pidfile, leaving the read empty. That is a
  host-load race in the fixture, not an assertion about supervisor behavior.
- `git diff --stat 9ef8ae5..57d658b` touches no supervisor code: only
  `index.rs`, `api.rs`, `orgasmic-cli/{main,daemon_client}.rs`, `ui/src`, and
  `.orgasmic` records. There is no call path from any changed line into
  `probe_command_stdout` or the process-group reaper.
- Classification: **environment / host-load flake**, not a regression. The gate
  policy marking it REAL because it is unregistered is a flake-registry gap, not
  evidence of causation. The implementer correctly declined to edit the registry
  (outside declared write scope); registering these two is the right follow-up
  and belongs to whoever owns supervisor.rs.
- The tmux reattach failure matching TASK-X0PV1 is a known registered flake and
  is likewise unrelated to this diff.
- The TASK-QCG6J close-guard premise did not reproduce (both tests green in the
  final aggregate), which I accept as reported — this diff touches nothing on
  that path either.

## Open Questions

1. On H1 — is the intended contract that a first-load request may fail while the
   underlying scan later succeeds? Today the waiter 503s at 8s and the worker
   publishes `Ready` moments later, so a retry succeeds. If that is intended,
   the message should say "still loading, retry shortly", not "check that the
   path is mounted".
2. On M4 — is there an existing daemon-wide policy for bounding leaked
   `spawn_blocking` work? `supervisor.rs` solved the same class of problem with
   process-group kill; the index has no equivalent, and I could not find a
   shared helper.
3. On M3 — was the `depends_on`-based count a deliberate choice over
   unmet-dependency semantics, or an assumption that `depends_on` implies
   unsatisfied? The acceptance wording ("existing dependency semantics") is
   ambiguous and the repo has no other server-side readiness computation to
   anchor on.

## Fix Directions (ranked)

1. **H2 first** — smallest change, biggest operator win. Make
   `get_graph_markers` collect per-project failures instead of `?`, exactly as
   `post_reindex` already does, and surface them in `status --errors` and the
   coverage UI.
2. **H1** — decouple the queue wait from the scan budget, or raise
   `FIRST_LOAD_COORDINATOR_TIMEOUT` to cover `ceil(N/permits) × scan + margin`,
   and split the queued-behind message from the path-unreadable message so the
   macOS hint only appears when a path is actually implicated. Add a test at
   production constants.
3. **M4** — per-target in-flight guard plus a leaked-scan counter in
   `refresh_status`.
4. **M3** — resolve dependency state before counting, or relabel the badge.
5. **M5 / L6 / L7** — partial-outcome `GET /tx`, non-zero exit on reindex
   failures, and an env override for the scan budget.
6. Register the two `supervisor::tests` probe races in the flake registry
   (separate owner, separate task).
