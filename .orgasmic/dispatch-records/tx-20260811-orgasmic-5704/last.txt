## Verdict

**reject.**

Two of my three round-2 MEDIUMs (M1 seed clone, M2 negative-cached Git probe) are closed
correctly and cleanly, and the two LOW follow-ups the round took on (L1 documentation, L5
writer regression) are closed properly too. The third, M3, is closed with a mechanism that
introduces a new correctness defect: **at the five-discard bound the coordinator reports
failure for a refresh that provably succeeded.** It sends the committed-but-refresh-failed
error to a batch of waiters whose mutations were published to the index by the first of those
five scans and have been readable ever since. That is a regression in the exact load regime
this task exists to fix, and it is now written into the verification artifact as intended
contract, so it will be hard to revisit later.

The fix is small and local (settle the saved batch with `Ok` instead of `Err`, or drop the
discard for covered waiters entirely). Everything else in this round should be kept as landed.

## Findings

### HIGH

**H1 — `index.rs:952-967`: the stale-discard bound fails waiters whose mutation was already
published, turning a successful refresh into a `503 index_status: refresh_failed`.**

```rust
let stale = result.is_ok() && state.required_generation != captured.required_generation;   // :925
...
if stale {
    ...
    if consecutive_stale_discards >= MAX_CONSECUTIVE_STALE_DISCARDS {
        let captured = stale_batch.take().expect(...);
        let error = format!("index refresh remained stale for {consecutive_stale_discards} consecutive scans");
        Self::settle_captured_error(state, captured, &error);            // :959  -> Err to every covered waiter
```

The batch being failed is provably covered by a published projection. The chain, each link
verified in the tree:

1. `stale` is only reachable when `result.is_ok()` (`index.rs:925`), and `result` is the return
   of `publish_refresh` (`index.rs:910-913`), which installs the projection into `self.inner`
   under the write lock (`index.rs:1167-1216`). A stale iteration therefore *published*.
2. That projection was built by `load_project` reading the filesystem inside
   `build_refresh` (`index.rs:1092`), which starts strictly **after** the capture at
   `index.rs:835-853`.
3. Every waiter in that capture registered through `request_required_refresh`
   (`index.rs:727-790`) only after the serialized writer returned — e.g. `transaction_mutation`
   is awaited at `api.rs:15930-15942` and only then does `refresh_after_project_mutation` run at
   `api.rs:15945`. The bytes are on disk before the waiter exists.
4. `settle_captured_error` (`index.rs:1007-1041`) nonetheless sends `Err`, and
   `committed_refresh_error` (`api.rs:7831-7839`) turns that into
   `503 {"error":"mutation committed but index refresh failed: …","committed":true,
   "index_status":"refresh_failed"}`.

The codebase already agrees with points 1-3 everywhere else: the non-stale success branch at
`index.rs:972-989` acknowledges *this same captured batch* with `Ok(())` under an identical
`publish_refresh` success. The only difference at the bound is that an **unrelated later**
mutation bumped `required_generation`. A third party's arrival is being converted into this
caller's failure.

Concrete failure scenario. Sustained same-project writes keep bumping `required_generation`
during each scan, so every outer iteration burns the full `REFRESH_COALESCE_MAX_WAIT`
(`index.rs:817-833`) plus one scan: the bound fires after roughly 5 x (200 ms + scan)
≈ **1.0-1.3 s**, about an eighth of the 10 s client budget. A caller whose task write landed and
became readable at ~200 ms receives a 503 at ~1.2 s. Before this round the same caller got
`Ok` as soon as the stream quieted; the regression window is every stream that would have
quieted between ~1.2 s and the 10 s budget. For `orgasmic dispatch finalize` that is a non-zero
exit for a dispatch that fully completed — the round-2 L2 residual, previously reachable only
through an injected failure, now reachable from ordinary load.

Second impact, same root cause: the saved batch's `explicit_count` and `watcher_count` are
failed too (`index.rs:1024-1035`). A failed watcher waiter makes `watcher.rs:405-407` `continue`
and **suppress the `ProjectIndexed` / `TaskUpdated` wildcard events** for a projection that was
in fact published, so TUI/SSE clients miss the invalidation. A failed explicit waiter on the
newly-registered-project path (`watcher.rs:379-382`) additionally skips
`spawn_repo_url_refresh_for` and the same events for a project that did load.

Fix direction, in increasing order of how much it removes:

- Minimal: at the bound, settle the saved batch with `Ok(())` and `state.remember_completed(tx_id)`
  (a `settle_captured_ok` mirroring `settle_captured_error`'s count-bounded draining, so later
  duplicate waiters for the same tx are not over-drained). The bound then means "stop *waiting*
  for a quiet generation", not "fail".
- Better: acknowledge the captured batch on **every** successful publish and re-loop only for
  the newer generation. `state.has_required()` is already true in that case (a
  `required_generation` bump always leaves a fresh waiter — the duplicate-tx and
  `completed_tx_ids` short-circuits at `index.rs:742-764` return *before* the bump), so
  convergence for the newer arrivals is unchanged. `MAX_CONSECUTIVE_STALE_DISCARDS`, `stale_batch`
  and the bound then become unnecessary and `discarded_total` reduces to a pure metric.

Test and docs encode the wrong contract and must move with the fix:
`sustained_stale_generations_fail_older_batch_but_newer_waiters_converge`
(`index.rs:4419`) asserts `expect_err` on the older waiter; `verify/TASK-K9WWM/README.md:31-34`
and `verify/TASK-K9WWM/hardening-round.md:16-20` state the 503 as the intended outcome. Note the
existing test cannot detect the defect because its older waiter is `refresh_after_tx("project",
"tx-older")` with **no file mutation behind it** — there is no data whose visibility could be
asserted. A corrected regression should mutate a file for the older tx and assert the projection
contains it at the moment the bound fires.

### LOW

**L1 — `index.rs:960-965`: the bound's warning labels the settled batch with the wrong `cause`.**
`cause` is computed from the *current* (discarded) capture at `index.rs:855-861`, but the batch
being settled is the saved oldest one. A bound fired on a batch of mutations can log
`cause="watcher"` if the most recent capture happened to be watcher-driven. Cosmetic, but this
warn line is the only operator-visible signal that the bound fired.

**L2 — `index.rs:926-930`: `stale_discards_for_batch` is non-zero on a scan that was not stale.**
On a successful non-stale iteration the field carries the count of the *preceding* discard run,
which is only cleared afterwards at `index.rs:975`. The `slow index refresh scan` warn therefore
reports a stale count for a batch that was acknowledged. Defensible as "this batch waited through
N discards", but it is not what the field name says.

**L3 — `index.rs:1388-1394`: a failing non-forced probe can remove a dedup key a concurrent
forced probe just installed.** The failure branch removes `probe_key` unconditionally when
`!force`; a forced probe that succeeded and inserted at `index.rs:1396-1399` in the interim loses
its key. Consequence is one redundant later Git spawn, not a wrong URL. Worth a comment rather
than a change.

**L4 — residual on the same path: a probe deduped against an in-flight probe that later fails is
itself dropped.** `refresh_repo_url` returns early at `index.rs:1364` for the second caller; if
the in-flight probe then fails and clears the key, no retry is scheduled for the caller that was
deduped away. Since registration and watch-path probes are event-driven, a project registered
exactly once can stay `repo_url: ""` until the next registration/watch event or an operator
reindex. `failed_registration_git_probe_can_retry_later` (`index.rs:2859`) covers only the
sequential fail-then-retry case. This is strictly better than the round-2 permanent negative
cache; recording it is enough.

## Open questions

1. **H1**: was failing the saved batch a deliberate choice over acknowledging it, and if so on
   what grounds? I can find no case where a waiter present at capture is absent from a projection
   published by a scan that started after that capture — and if such a case existed, the non-stale
   success branch at `index.rs:972-989` would already be unsound. If there is a reason, it belongs
   in a comment at `index.rs:952`, because the code currently reads as an oversight.
2. Was `MAX_CONSECUTIVE_STALE_DISCARDS = 5` derived from a measurement? Under a sustained stream
   each iteration costs the full 200 ms max-wait, so five discards is ~1.2 s — chosen against a
   10 s budget with no recorded derivation. If H1 is fixed as "acknowledge on publish", the
   constant disappears; if it is fixed as "settle `Ok` at the bound", the value still wants a
   stated basis.

## Fix directions

1. **H1 (blocker)** — stop failing the saved batch. Preferred: delete the stale-discard gate for
   the captured batch entirely and acknowledge it on every successful publish, re-looping for the
   newer generation (which `state.has_required()` already guarantees); `MAX_CONSECUTIVE_STALE_DISCARDS`,
   `stale_batch` and the bound warn then go away and `discarded_total` becomes a pure metric.
   Minimal alternative: at the bound call a `settle_captured_ok` that mirrors
   `settle_captured_error`'s count-bounded FIFO draining, sends `Ok(())`, and calls
   `state.remember_completed(tx_id)` for each captured tx. Either way, rewrite
   `index.rs:4419` to give the older waiter a real file mutation and assert its data is visible at
   the moment the bound fires, and correct `verify/TASK-K9WWM/README.md:31-34` and
   `verify/TASK-K9WWM/hardening-round.md:16-20`.
2. **L1** — pass the saved batch's own `cause` (store it alongside `stale_batch`) into the bound
   warn at `index.rs:960`.
3. **L2** — either zero `stale_discards_for_batch` on a non-stale iteration or rename it to say it
   counts the preceding discard run.
4. **L3/L4** — add a comment at `index.rs:1388` noting that a forced probe's key may be removed by
   a concurrent failing non-forced probe (benign, costs one respawn), and record that a probe
   deduped against an in-flight probe which subsequently fails is not itself retried.
5. Keep M1, M2, L1(50 ms doc) and L5 exactly as landed — they are correct and independently
   verified above.
