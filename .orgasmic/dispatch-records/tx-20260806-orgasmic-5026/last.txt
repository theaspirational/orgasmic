# TASK-QGWK7.1 review — approve-with-follow-ups

**Not a block ship.** The parent's own acceptance criterion 2 is now met: a
promoted report lands in the git index by construction, not by habit. Eight
findings, all follow-up; one MEDIUM is a real behaviour bug this change
introduced (a staging failure mis-reports the close *and* silently skips
`--branch-delete`).

## Verdict on the six claims, by number

**1. Is durability guaranteed now, or just usually true? — YES, by construction,
for `last.txt`.** Every close path that promotes also stages: `--worktree-remove`
via `remove_worktree_required_with_hook` (`manager.rs:5209`) and
`--no-worktree-remove` via `promote_dispatch_artifacts_in_place`
(`manager.rs:5527`), both through the single
`promote_and_stage_dispatch_record`. There is no third promote caller —
`post_dispatch_cleanup` (the dispatch-*create* rollback at `manager.rs:874`)
prunes and never promoted. What I checked and ruled out:

- `.orgasmic/.gitignore` is exactly `tmp/`; `git check-ignore` exits 1 for both
  `.orgasmic/dispatch-records/<tx>/stdout.log` and `.../stdout.log.bytes`.
  Nothing about a `dispatch-records/` path is ignored here.
- Measured `git add --` semantics in a scratch repo: fully-ignored directory →
  exit 1 with the "paths are ignored" message (**visible**, folds into
  `CLEANUP_ERROR`); missing directory → exit 128; not a git repo → exit 128.
  Only the *inner-file* ignore case is silent (finding 2).
- Nothing between `git add` and the manager's commit un-stages it. The close
  after promote does `git worktree remove` and `git branch -d`, neither of which
  touches the main index (a linked worktree has its own index, so salvage cannot
  clobber it). `orgasmic verify` uses `git apply`/`git apply -R`, not the index.
  Staging is in fact *stronger* than the old state against the two things that
  actually threatened the file: a staged path survives `git checkout -- .`
  (restored from the index) and is skipped by `git clean -fdx`.
- Mid-rebase/merge, detached HEAD: `git add` is unaffected.

The residual is honest and small: "in the index" still needs the manager to
commit eventually, and `git reset`/`git stash push` in the interim would unstage
it (leaving the file present but untracked again). That is a much narrower
dependency than "which `add` form the manager happens to type."

**2. Does the bounded tail preserve what stdout.log was for? — Mostly.**
Arithmetic holds: 6,500 × 64 KiB = 406 MiB, matching the convention's "≤ ~400
MB/yr worst case"; `last.txt` 5,200–6,500 × ~4.6 KB = 24–30 MB/yr. The
convention does state the two separately with numbers
(`manager-dispatch.org:311-330`), and `shipped_conventions.rs:398` pins both
strings. Two gaps: the tail is the wrong end for the early-death transcript
(finding 4), and truncation is only discoverable out-of-band (finding 3). I do
**not** think either is worth a reject — the tail is the right default and the
sidecar plus the convention makes it recoverable.

**3. F-3's fence — the construction is right, with one hole.** The predicate
`close_needs_artifact_fence` (`manager.rs:4285`) is
`remove_worktree || (open.last_path.is_some() && open.stdout_path.is_some())`,
and the promote arm fires on exactly the same pair after
`resolve_project_path`, which is an `Option::map` and cannot change Some-ness —
so predicate and destructive branch agree by construction, not by luck. The
cleanup lock is taken as the **first statement** of
`promote_dispatch_artifacts_in_place` (`manager.rs:5527`), before the
`last_path.exists()` probe, before validation, and therefore before the unlink;
`no_worktree_remove_promote_takes_cleanup_lock` proves it blocks. No double
acquire: the remove path takes the lock in `remove_worktree_required_with_hook`
and calls `promote_and_stage_dispatch_record` directly, never the in-place
wrapper. The hole is finding 6: a record with LAST_PATH+STDOUT_PATH but no
WORKTREE makes the predicate true while `reserve_close_guard` returns `Ok(None)`
(`manager.rs:4294`) — the fence is requested and silently absent, and unlike the
remove path (which reports `worktree_missing` and destroys nothing) the promote
arm still unlinks. The live race itself remains prevented by argument; the
implementer says so, and I agree that is acceptable given the syspolicyd budget.

**4. Did the ordering invariant survive? — Yes.** Traced all four cases in
`paths.rs:272-340`:
- failed `last.txt` copy → `Ok(report_path: None, error)`, **no unlink**, tmp
  intact, `.promoting` scrubbed.
- failed stdout tail copy → `Ok(report_path: Some, error)`, **no unlink** — this
  is F-8 closed: the record names what it kept and tmp still holds both.
- failed `stdout.log.bytes` write → the closure fails before either rename, both
  `.promoting` temps removed, no dest written, no unlink.
- crash between the copies → tmp intact (unlink is last), `last.txt` promoted;
  the only residue is an in-flight `.promoting`, which the in-process scrub
  cannot cover on a hard kill.
`.promoting` names do not collide: `last.txt`→`last.promoting`,
`stdout.log`→`stdout.promoting`, `stdout.log.bytes`→`stdout.log.promoting`.
One narrow ordering nit: if the *second* rename (sidecar) fails, `stdout.log` is
already at the dest with no byte count — truncated evidence with no marker. Rare
enough to fold into finding 3.

**5. Is REPORT_PATH project-relative everywhere? — No, one site remains.** Three
of four emitters are clean: `manager.rs:1913` (`dispatch_record_report_rel`),
`manager.rs:1919` (the new relativizing fallback, returns `None` rather than an
absolute path), `manager.rs:5595` (cleanup's promoted rel path). The fourth,
`manager.rs:4863`, lets a manager-supplied `--property REPORT_PATH=` win
unvalidated, and `tests/dispatch.rs:988,1001` currently *pin* an absolute
`/tmp/...` landing in the tx. F-6 named the finalize fallback and that is fixed;
the acceptance sentence says "always". Finding 5.

**6. Do the tests pin the acceptance? — Five of nine pin; two accompany.**
Genuinely pinning (would fail on the parent tree, and enter production
functions): `dispatch_close_stages_promoted_record_in_git_index` (plus the
`verify/TASK-QGWK7.1` red run),
`no_worktree_remove_promote_against_missing_worktree_is_ok` (asserts
`CleanupStatus::Ok` through real `cleanup_dispatch`),
`no_worktree_remove_promote_takes_cleanup_lock` (real cross-thread lock
contention), and the two `paths::tests` promote tests. Merely accompanying:
`no_worktree_remove_with_artifacts_needs_close_guard` and
`finalize_report_path_fallback_is_project_relative` both assert on the new
helper in isolation and never enter `cmd_dispatch_close` /
`cmd_dispatch_finalize` — they cannot fail on the parent tree because the
functions did not exist there, so they pin the predicate, not the wiring
(finding 8). That matters because those two are the only coverage F-3 and F-6
have.

**F-5 deferral: the reasoning holds.** `manager.rs:369` and `:3643` confirm
`worktree-prune` refuses every invocation by construction (TASK-M47E5.3) and
`:3373` marks the reclaim path unreachable, owned by TASK-RMA18. Promote-on-
reclaim would be unreachable code today. Stated deferral accepted.

## Findings

Filed as eight `reviewer.finding` tx entries on TASK-QGWK7.1.

**MEDIUM — `manager.rs:5423` — a `git add` failure reports `worktree_failed` and
silently retains the branch.** `promote_and_stage_dispatch_record` folds a
staging error (and now a stdout-tail error, which returns `Ok`+error rather than
`Err`) into `WorktreeRemovalOutcome.error`. `cleanup_dispatch` sets
`worktree_failed = true` for *any* such error even when `removed: true`. Two
consequences: the close reports `CLEANUP_STATUS=worktree_failed` when the
worktree was removed and the report was promoted, staged and named; and the
`branch_delete` chain at `:5460-5481` requires `!worktree_failed`, so with
`--branch-delete` no arm fires — the branch is silently kept, `branch_failed`
stays `false`, and no error names it. Concrete trigger: a concurrent state chore
holding `.git/index.lock` → `git add` exits 128. This contradicts the stated
design ("staging failure … does not fail the close" — it doesn't fail it, it
mis-classifies it). *Fix:* push promote/stage errors into `errors` without
setting `worktree_failed`, exactly as the `--no-worktree-remove` arm already does
at `:5452`.

**LOW — `manager.rs:5566` — inner-file ignores are silent.** Measured: `git add
-- <dir>` exits 0 and stages only the non-ignored entries. A project rule as
common as `*.log` would drop `stdout.log` from the record while the close reports
success. Not triggered in this repo (verified). *Fix:* confirm the expected
entries with `git ls-files --stage`/`--error-unmatch` after adding and report the
delta.

**LOW — `paths.rs:388` — truncation visible only out-of-band.**
`stdout.log.bytes` is written for *every* non-empty stdout, so its presence does
not mean truncated; a reader must know the 64 KB cap and compare. The tail itself
starts mid-line with no banner. A skipped 0-byte stdout writes no sidecar, so
"empty" and "not promoted" are indistinguishable. *Fix:* one banner line at the
head of a truncated tail.

**LOW — `paths.rs:130` — the tail keeps the wrong end for early failures.** See
claim 2. *Fix:* 32 KB head + 32 KB tail with an elision marker; identical
year-one arithmetic.

**LOW — `manager.rs:4863` — `--property REPORT_PATH=<abs>` still lands absolute**
in a committed tx, pinned by `tests/dispatch.rs:988,1001`.

**LOW — `manager.rs:4294` — fence requested, silently absent with no WORKTREE.**
See claim 3.

**LOW (docs) — `manager.rs:4280`** — the new predicate was inserted between
`reserve_close_guard`'s doc comment and its signature, so "`Ok(None)` means there
is no worktree to reserve" now documents a `-> bool` function and
`reserve_close_guard` is undocumented.

**LOW (test) — `manager.rs:9142`** — see claim 6.

## Open questions

1. Should a promote/stage error downgrade `CLEANUP_STATUS` at all, or only
   populate `CLEANUP_ERROR`? The `--worktree-remove` and `--no-worktree-remove`
   arms currently disagree (`worktree_failed` vs `partial`) for the same class of
   failure. Picking one is the cheap version of finding 1.
2. `--no-worktree-remove` is no longer an escape hatch for a daemon without the
   close-guard route — both forms now require it, and the updated message says
   "restart the daemon". Intentional per F-3, but it means a close is impossible
   until the daemon is restarted. Worth stating in the convention.
3. `orgasmic update` / `install.sh` use `git stash push --include-untracked` in
   the source repo (`update.rs:979`, `install.sh:505`). For *this* project the
   source repo and the orgasmic project are the same tree, so an update run
   between a close and the manager's commit would unstage the record. Not
   introduced here; flagging because it is the one realistic un-stage path.

## Fix directions

Ranked. All follow-up; a fix round is warranted for the first two, the rest are
opportunistic.

1. `manager.rs:5419-5431` — separate the promote/stage error channel from
   `worktree_failed` so a staged-record failure cannot mis-report the close or
   suppress `--branch-delete`. Test: staging fails (e.g. a pre-created
   `.git/index.lock` in the fixture) → `removed` still true, branch deleted,
   status `partial`, `CLEANUP_ERROR` names the staging failure.
2. `manager.rs:5566` — verify what actually landed in the index after `git add`
   and report the difference, closing the silent inner-ignore case.
3. `paths.rs:388` — prepend a one-line truncation banner; consider a
   head+tail split.
4. `manager.rs:1123` / `:1911` — add wiring tests that enter `cmd_dispatch_close`
   and `cmd_dispatch_finalize`, so F-3 and F-6 are pinned at the call site rather
   than at the helper.
5. `manager.rs:4863` — relativize or refuse an absolute `--property REPORT_PATH`,
   and update `tests/dispatch.rs:988,1001` which currently pin the absolute form.
6. `manager.rs:4280` — move the orphaned doc comment back onto
   `reserve_close_guard`.
