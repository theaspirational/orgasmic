# TASK-STWVB.1.1 (host degradation judged on a rate) — REJECT

**REJECT.** Two BLOCK SHIP, two MEDIUM, two LOW.

B1 is genuinely fixed and the rate is the right shape — I attacked it empirically
and could not break it. B2 is not fixed; it is over-fixed. Moving
`SUITE_EXIT != 0` above the FLAKE/LOAD/HOST arms dropped the implicit
`FAIL_COUNT == 0` guard it used to sit behind, so **every live run that
classifies any failure now prints `RED — cargo exited 101 with no per-test
failure list` while listing that failure list three lines above it.**
`GREEN modulo N registered flakes` and `LOAD-SENSITIVE → INCONCLUSIVE` — the C
interlock this whole chain exists to build — are now unreachable on the live
path. They survive only under `--classify`, so the two modes disagree about the
same log.

The chain has been chasing "the gate returns no verdict." Round 3 fixed the
exit-4-on-a-calm-host half and broke the exit-0-on-a-flake half. Both
demonstrations in the brief dodged it by construction: the workspace run had a
REAL (earlier branch wins) and the scoped run had zero failures (cargo exited 0).

## Findings

Filed as `reviewer.finding` tx entries on TASK-STWVB.1.1 (tx-…-5065 onward).

### M-1 — HIGH — BLOCK SHIP — a registered flake now reddens the live gate
`scripts/run-tests.sh:1048`

The B2 move put

```sh
elif [ "$SUITE_EXIT" != "?" ] && [ "$SUITE_EXIT" != 0 ]; then
```

above the `HOST_DEGRADED` arm **and above the `FAIL_COUNT > 0` arm**. In the
pre-change ladder (`4788e1f:scripts/run-tests.sh`) this branch sat *after*
`FAIL_COUNT > 0`, which is what made its message true: it could only fire when
there was no per-test failure list. There is now no `FAIL_COUNT` guard at all,
and `cargo test` exits 101 whenever any test fails. So on the live path:

Reproduced with a stub `cargo` on PATH emitting one failing test whose signature
matches a fixture registry entry, isolation-green:

```
  failures : 1
  host     : calm (threshold syspolicyd_rate>=1.50; …)
FLAKE (1) — green in isolation, registered signature matched:
  tests::recovery_inventory_waits_for_atomic_claim_commit
      signature: "waited for the atomic claim commit" — matched
      isolation: passed
verdict: RED — cargo exited 101 with no per-test failure list.   exit 1
```

The same log through `--classify` (where `SUITE_EXIT` is `?`):

```
verdict: GREEN modulo 1 registered flake(s). No unexplained red.   exit 0
```

Two modes, one log, opposite verdicts. And the sentence is false on its face —
the failure list is printed immediately above it.

Second reproduction, degraded host + unregistered isolation-green failure:

```
  host     : DEGRADED (threshold syspolicyd_rate>=1.50; …)
LOAD-SENSITIVE (1) — isolation-green, unregistered, host was degraded:
verdict: RED — cargo exited 101 with no per-test failure list.   exit 1
```

So `EXIT_INCONCLUSIVE` is dead on the live path. Every artifact of TASK-STWVB
(LOAD-SENSITIVE, the C interlock, exit 4) is now `--classify`-only.

The selftest cannot see this: all thirteen flake/load/host cases drive
`--classify`, where `SUITE_EXIT="?"` short-circuits the branch, and the two new
live-path cases use a stub cargo that either exits 0 or exits 101 *with no
failure list*.

**Fix.** Guard the branch with the condition its own message states, keeping the
position B2 chose:

```sh
elif [ "$FAIL_COUNT" -eq 0 ] && [ "$SUITE_EXIT" != "?" ] && [ "$SUITE_EXIT" != 0 ]; then
```

and pin it with a live-path case: stub cargo emitting a registered flake and
exiting 101 → `GREEN modulo 1 registered flake`, exit 0; and the degraded
variant → `INCONCLUSIVE`, exit 4. Neither case exists today.

### M-2 — HIGH — BLOCK SHIP — `host : calm` when the primary signal was never measured
`scripts/run-tests.sh:496-507` and `:988`

`host_judgment_measured` ORs `load | cpu | wall`. Load essentially always
parses, so the word is `calm` whenever the *gating* signal is unmeasurable.
Probed via the injector on the live path:

| injected sample | printed |
|---|---|
| `load=4.0,syspolicyd_cpu=?,wall_s=300` | `host : calm`, `rate ?`, exit 0 |
| `load=4.0,syspolicyd_cpu=250.0` (no `wall_s`) | `host : calm`, `rate ?`, exit 0 |
| `load=4.0,syspolicyd_cpu=250.0,wall_s=0` | `host : calm`, `rate ?`, exit 0 |
| `load=4.0,syspolicyd_cpu=250.0,wall_s=-5` | `host : calm`, `rate ?`, exit 0 |

Row 2 is a regression against STWVB.1/F3, not just an F-E residual: the stamp
format gained `wall_s` in this commit with no compat path, so **every suite log
written by any earlier version now reclassifies as `calm`** where F3
deliberately made it `unknown`. Rows 1, 3 and 4 cover Linux, a `pgrep -x
syspolicyd` miss, and a sub-second window.

The reach that matters is CI. `ci.yml:200-206` fails the lane on exit 4 on the
authority of the rate threshold; if `syspolicyd` is not visible on the
`macos-15` runner, the gate is inert and the summary still prints
`host : calm (threshold syspolicyd_rate>=1.50; …)` — asserting a threshold was
applied to a measurement that never happened. Same class as the original F2
phantom `0.0`, one level up, which is exactly what F-E was filed about.

The two new F-E cases pass because they set *every* field to `?`/junk. They pin
the all-unknown corner and miss the common one.

**Fix.** Derive the word from the rate, not from any-field: `calm` only when the
rate parsed as a number and is below threshold; `unknown` otherwise, with the
reason named (`no syspolicyd signal` / `window unknown`). Keep load as display.

### M-3 — MEDIUM — the rate has no minimum window
`scripts/run-tests.sh:465-493`, `:636-638`

`local_wall` is `date +%s` arithmetic — integer, ±1 s quantisation — clamped to a
floor of 1, and `host_is_degraded` gates at any wall. Probed:

- `wall_s=1, syspolicyd_cpu=2.0` → `rate 2.0000` → DEGRADED, exit 4
- `wall_s=3, syspolicyd_cpu=4.5` → `rate 1.5000` → DEGRADED, exit 4

So a 1–3 s scoped run judges the whole host on 1–3 samples of a bursty quantity.
See the direct answer to claim 1 below for what I measured.

**Fix.** Require `wall_s >= ` a floor (10–30 s) for the rate to gate at all;
below the floor report `host : unknown (window too short to judge)` — neither
calm nor DEGRADED. That also disposes of `wall_s=0` and the sub-second clamp,
which currently *under*-report (a 0.3 s window's delta divided by 1).

### M-4 — MEDIUM — the summary advertises a load threshold that does not exist
`scripts/run-tests.sh:88`, `:986-990`

`LOAD_DEGRADED_THRESHOLD=8.0` is referenced only inside the two summary strings
(`load corroborating only, display>=8.0`). `grep -n LOAD_DEGRADED_THRESHOLD`
returns exactly three lines: the assignment and those two `printf` arguments.
Nothing compares load to it; load is printed unconditionally in the
`before`/`after` fields at any value. The operator is told a display threshold is
in play that is not implemented.

**Fix.** Either annotate the load field when it clears 8.0 (which is what
"corroborating" would mean in the output) or drop the constant and the clause.

### M-5 — LOW — F-F's replacement assertion is narrower than its headline
`scripts/run-tests-selftest.sh:396`

`grep -Eq 'syspolicyd_time=0(\.0)?($| )'` cannot match the format the field
actually carries. Verified directly: `syspolicyd_time=0:00.00` does **not**
match; only a bare `0` or `0.0` would. It is no longer vacuous — a regression
that printed a bare `0` default would fire it — but the realistic phantom-zero
shape (the F2 defect re-expressed as a cumulative `ps` time) escapes.

**Fix.** Also reject `syspolicyd_time=0:00(\.0+)?`.

### M-6 — LOW — note, not a defect: the stamp format is still duplicated
`scripts/run-tests-selftest.sh:110-116`

`stamp_host` still hand-writes the stamp, so the acceptance clause "the stamp
format is not duplicated in the test" is not literally met. In practice the
duplication now works in the right direction — the hand-written fixtures pin the
*reader* while the new e2e case pins the *writer*. I mutation-tested it (see
Verification Notes); all three renames were caught. Recording it so the clause is
not silently dropped, not asking for a change.

## Ruling on the six claims

**1. Is a rate the right shape, or does it just move the failure to short
windows? Is there a window short enough to make this gate misfire — yes or no?**

**Structurally yes; empirically no.** Both halves matter.

*Yes, structurally:* there is no floor. `wall_s=1` with a 2.0 s delta returns
DEGRADED and exit 4 today (M-3). The estimator's variance scales as 1/wall and
nothing in the code notices.

*No, empirically — I tried hard to break it and could not.* Read-only 1 Hz
sampling of `syspolicyd` cumulative CPU on this Mac:

- **Ambient, 83 s at load 3.7–4.6:** mean 0.087 s/s, **peak 1 s-window 0.17 s/s.**
- **Induced Gatekeeper scan storm** — 300 freshly compiled, uniquely-hashed
  Mach-Os first-exec'd (40 serial, 80 parallel, 180 parallel): mean 0.12 s/s,
  **peak 1 s-window 0.25 s/s.** Cost per fresh binary: **0.043 CPU-s**, at
  **0.32–0.35 s of wall each** even when 80 ran concurrently.

That last row is the important one and it is new evidence for this chain:
syspolicyd under scan pressure is **serialisation-bound, not CPU-bound**. It
burns ~0.04 CPU-s per binary while making each exec wait a third of a second.
Crossing 1.50 s/s over a 3 s window needs 4.5 CPU-s ≈ 105 fresh-binary
evaluations inside those 3 seconds; the queue physically will not deliver them —
105 evaluations took 34 s of wall in my probe. **The suite's own scan storm
cannot spike this gate at any window length.** It also independently confirms
part A's mechanism (queue wait, not CPU), which is the settled question — I am
not reopening it, only noting the instrument agrees.

The residual is that the chain's historical thrash figure is ~5.6 s/s, ~22×
anything I could induce, so some *other* syspolicyd workload does go multicore.
Under that regime a short window would read DEGRADED — but so would a long one,
and it would arguably be right. So the honest answer: the rate does **not**
move the failure to short windows for the suite's own load, and the residual
short-window risk is a variance problem worth a floor (M-3), not the mirror of
B1.

**2. Is 1.50 defensible, or is it the third arbitrary number?**

Defensible — and it is the first number in this chain with a *mechanism-level
upper bound* under it rather than a single calibration point over it.

The brief's worry was a 1.6× margin over the 0.96 scoped peak. My measurements
say the real margin is bigger than that, because 0.6045 and 0.96 are not the
suite's own contribution — both were measured with live dispatch workers on the
box. The suite's own worst case is the scan storm, and that tops out at
0.25 s/s. That is a **6× margin**, with the historical thrash at 5.6 s/s giving
**3.7× on the other side**. Roughly an order of magnitude of separation each
way, which is a different situation from the previous two thresholds.

The comment at `:91-97` should be amended to say what 0.6045 actually was
(a whole-workspace run *with concurrent dispatches*), since it currently reads
as the suite's own rate and that is the number a future round would re-derive
from.

On CI: the concern inverts. A 3-vCPU `macos-15` runner caps the rate at 3.0 s/s
by construction, and the cold workspace build sits inside the window, inflating
the denominator by minutes. The rate goes *down* on slower hardware, not up —
1.50 will not trip CI by construction. The real CI exposure is the opposite one
and it is M-2: if `syspolicyd` is not visible there, the gate is inert while the
summary claims `calm`.

**3. Did demoting load change behaviour, or only the display?**

Behaviour, genuinely. `host_is_degraded` (`:484-493`) reads only
`host_syspolicyd_rate`; load is not in the function. I traced every
`HOST_DEGRADED=1` assignment (`:594`, `:617`, `:642`) — all three are guarded by
`host_is_degraded` alone. Load cannot trigger by any path. The new selftest case
"high BEFORE load alone stays calm" fails against the pre-change runner
(verified), so it pins the change.

But it is *reported* as a threshold that fired, not as corroboration — that is
M-4. The line names `display>=8.0` and nothing implements it.

On Linux: correct, and the gate has no degradation signal there at all. That is
the intended "correct, not a gap" — and **no, the output does not say so.** It
prints `host : calm (threshold syspolicyd_rate>=1.50; …)` with `rate ?`, which
reads as measured-and-under-threshold. That is M-2.

**4. Do the six new selftest cases close F-D honestly?**

Yes, and better than I expected.

*Would they have failed before?* I ran the new selftest verbatim against
`4788e1f:scripts/run-tests.sh` in a throwaway repo. **All six new cases fail**
(25 passed, 8 failed — the other two are pre-existing cases whose stamp fixtures
were re-expressed as rates). Nothing was added that could not have failed.

*Does a case run the live path and reclassify the log that run wrote?* Yes —
`:632-…` runs the real runner with a stub cargo, then feeds `work/suite.log`
back through `--classify` and asserts the reclassified `delta` string equals the
one the writer emitted. That is a true round trip, not a copy.

*Is the F-D failure mode actually caught now?* I mutation-tested it — three
renames applied to a scratch copy of the current script, full selftest run
against each:

| mutation | result |
|---|---|
| writer stamp key `delta=` → `judgment=` | 31 passed, **2 failed** |
| judgment field `syspolicyd_cpu` → `syspolicyd_burn`, producer *and* reader | 25 passed, **8 failed** |
| `wall_s` dropped from the judgment sample | 29 passed, **4 failed** |

F-D's exact scenario — "rename a field and the selftest stays green while
`--classify` silently falls back to unknown" — is closed. The format duplication
in `stamp_host` remains (M-6) but is now what makes the reader-side rename fail.

**5. Is the gate's verdict on the QGWK7.1 regression correct — and would the old
bound have buried it?**

The verdict is correct: the test fails alone, so `classify_one` reaches
`REAL_COUNT` regardless of host state, and the ladder puts `REAL_COUNT` ahead of
`HOST_DEGRADED`. The gate did its job.

**But the "would have been buried under exit 4" framing is not right, and I
should say so since the brief asked someone other than the manager to check it.**
Round 2 already moved `REAL_COUNT` above `HOST_DEGRADED` (confirmed in
`4788e1f:scripts/run-tests.sh` — `REAL_COUNT` at the third arm, `HOST_DEGRADED`
at the sixth). Under the old absolute bound that run would have stamped
`host : DEGRADED` (215.2 > 100 on a calm host) but still printed
`verdict: RED — 1 real failure(s)` and exited 1. The REAL survives either way.

What the old bound *would* have done to that run: mislabel a calm host as
degraded, and — this is the part worth keeping — convert any *isolation-green*
unregistered failure in the same run into a LOAD-SENSITIVE excuse it did not
earn, because `classify_one:794` keys that label off `HOST_DEGRADED`. That is
the strongest true statement available: the old bound did not bury REALs, it
**minted excuses** on calm hosts. Plus the exit-4-on-green case, which is B1
proper.

**6. F-E and F-F.**

F-E: three-state for the all-unknown corner only. `delta=load=? syspolicyd_cpu=?
wall_s=?` and `load=abc syspolicyd_cpu=xyz wall_s=qqq` both print
`host : unknown (no numeric host signal…)` — the two new cases pass, and both
fail against the pre-change runner. But the mixed case, which is the common one,
still prints `calm` (M-2). Acceptance partially met.

F-F: replaced, and no longer vacuous — but narrower than its headline (M-5). It
asserts a value shape the field cannot take; only a bare-`0` regression fires it.
