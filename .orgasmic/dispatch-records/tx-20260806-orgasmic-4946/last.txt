# APPROVE WITH FOLLOW-UPS

TASK-QGWK7 (promote the worker report instead of deleting it). Read-only review of
merged `0df25d0` / `da88c19`.

**No close path destroys a worker report any more.** The two remaining deleting
call sites are failed-dispatch rollback, where no worker ever ran. Criterion 4 of
the brief finds no BLOCK SHIP. Verified end-to-end on the production path, not
just in unit tests.

**But acceptance criterion 2 — "the path is tracked in git, so a fresh clone or
another machine can read it" — is not met as written.** The destination is
*trackable* (outside `.orgasmic/.gitignore`'s `tmp/`), and nothing tracks it.
That is F-1, and it is the finding I would fix first.

Answering the two direct questions up front:

- **After a close, can the report be read from the path the tx names?**
  On disk, on every close path that promotes: **yes** — and the paths that do not
  promote leave the file in `tmp/` rather than deleting it, so nothing is lost.
  **From a fresh clone: no**, today, on any path. Nothing stages or commits the
  promoted directory, and no observed manager habit would sweep it in (F-1).
- **Did this change create a new unbounded-growth surface?**
  **Yes — `stdout.log`, and it is the TASK-ZBYH3 → TASK-G64ZH shape aimed at git
  history.** Numbers in F-2. It is invisible today only because this project runs
  tmux, where 47 of 51 measured `stdout.log` files are 0 bytes. It is
  transport-dependent, not bounded.

---

## Findings

### F-1 · HIGH · correctness (non-blocking) — nothing ever stages the promoted directory, so criterion 2 is unmet
`shipped/prompt-studio/conventions/manager-dispatch.org:312-323` —
*"Commit the promoted directory with the rest of the change so a fresh clone can
read it."*

Nothing in `crates/` runs `git add`. The promoted files land as **untracked**
paths under `.orgasmic/dispatch-records/`, and the durability guarantee is a
sentence in a convention.

The brief asks me to rule on whether that is acceptable. **It is not, and the
evidence is the repo's own commit history.** Since 2026-07-01 there are **468
commits touching `.orgasmic`** out of 997 total — the manager commits state
constantly. Every one I sampled stages only *already-tracked, modified* files:

```
6e8eee6  .orgasmic/tasks/{backlog,handoff,in_progress}.org
059cff9  .orgasmic/tx/2026-08.org
ae32fd2  .orgasmic/tasks/in_progress.org  .orgasmic/tx/2026-08.org
6e266fd  .orgasmic/tasks/*.org            .orgasmic/tx/2026-08.org
c03dc66  .orgasmic/tasks/backlog.org      .orgasmic/tx/2026-08.org
```

Not one adds a new untracked path under `.orgasmic/`. A `git add -u` or a
file-named `git add` — which is what all five of those look like — **skips
`dispatch-records/` forever**. So in 468 opportunities, the habit this convention
now depends on has zero precedent. The predicted steady state is: reports on the
manager's disk, absent from every clone, and a `git status` that accumulates
untracked directories at ~5,000/year until someone runs `git clean -fd` and
destroys the lot in one command.

This is the task's own thesis one layer out: *"it silently punishes the correct
workflow"* became *"it silently depends on a step nobody has ever taken."* The
brief calls it "strictly better — mechanical rather than interpretive," and that
is true and worth keeping; a missed commit leaves the file on disk instead of
destroying it. But strictly-better is not the bar the acceptance criterion set.

**Ruling: close should stage the directory itself.** `git add -- <dest_dir>` after
a successful promote, in `remove_worktree_required_with_hook` (manager.rs:5163)
and `promote_dispatch_artifacts_in_place` (manager.rs:5462). Staging, not
committing:
- It satisfies "tracked" — a path in the index is in git, and *every* subsequent
  state chore, including `git add -u` and `git commit -a`, then carries it
  automatically. One mechanical step converts 468 existing habits into 468
  working ones.
- It leaves *when to commit* with the manager, which is the part that genuinely
  needs judgment.
- It is less invasive than what close already does unasked — it removes worktrees
  and deletes branches. `entry.org`'s human-checkpoint rule puts `.orgasmic/`
  state writes explicitly in the proceed-without-asking class.
- A failure to stage is reportable through the `CLEANUP_ERROR` channel that
  already exists, so it degrades the same way promotion already does.

Non-blocking only because the failure mode is "file on disk, not in the clone,"
not data loss — and because this diff is already merged, so blocking means a
revert of a change that is a clear net improvement.

### F-2 · MEDIUM · perf/design — `stdout.log` promoted unconditionally into permanent git history
`crates/orgasmic-core/src/paths.rs:234`, retention stated as *"keep forever"* at
`manager-dispatch.org:319`.

The brief asked for a number for a year of realistic dispatch volume. Measured on
this project:

**Volume** — `manager.dispatch_started` tx in `.orgasmic/tx/`:
| month | generations |
|---|---|
| 2026-06 | 202 |
| 2026-07 | 556 |
| 2026-08 (6 days) | 191 |

949 in ~67 days = **14.2/day**; July alone ran 17.9/day. Annualized:
**5,200–6,500 dispatch generations/year**, one promoted directory each.

**Size** — surviving artifacts under `.orgasmic/tmp/dispatch/` (603 stem dirs):
| artifact | n | mean | max |
|---|---|---|---|
| `last.txt` | 114 | 4,580 B | 15,562 B |
| `stdout.log` | 51 | — | 478,920 B |

47 of those 51 `stdout.log` are **0 bytes** (tmux never persists pane content).
The 4 non-zero ones — from stdio/ws dispatches — average **157,703 B**.

**Year one, committed permanently:**
- `last.txt` alone: 5,200–6,500 × 4.58 KB = **24–30 MB/yr** raw. Text, packs
  well. Acceptable. This is the file the task is about and it should be promoted.
- `stdout.log` on today's tmux transport: **~0 bytes of content, and 5,200–6,500
  empty blobs plus tree entries** — pure noise, one useless tracked file per
  dispatch.
- `stdout.log` if the project runs stdio/ws at the observed mean:
  5,200–6,500 × 157.7 KB = **820 MB – 1.03 GB/yr uncompressed**, perhaps
  80–200 MB/yr packed.

For scale, this repository's entire history is **`size-pack: 8.71 MiB`**. One
stdio-heavy year of `stdout.log` promotion is **10–25× the whole repo, packed**;
raw, ~100×. And unlike `daemon.err.log`, you cannot rotate it — pruning git
history is a rewrite of every downstream clone.

The implementer's stated reason for including it — it *"can falsify a curated
close reason"* (paths.rs:218-220) — is genuinely good, and it is the strongest
argument in the whole change. The curated `REASON` being unfalsifiable is
explicitly what the task exists to fix. **Weigh, don't dismiss:** the
falsification job is served by a bounded tail. A curated reason is falsified by
what the worker actually said near the end, not by 478 KB of harness chatter.

**Ruling: `last.txt` yes, `stdout.log` not as-is.** Pick one:
1. **Bounded tail** (preferred): promote the last 64 KB of `stdout.log` and record
   the original byte count beside it. Caps the year at ~400 MB worst case and
   ~0 typical, keeps falsifiability, and makes truncation *visible* rather than
   silent — the task's own rule that a policy needs a number.
2. **Promote only on non-success** (`--status aborted`, or a finalize that was
   `blocked`) — that is when the transcript is worth more than the summary.
3. Skip a 0-byte `stdout.log` entirely at minimum, whichever of the above lands.

Also: `manager-dispatch.org:320-322` states the retention policy but gives no
number and no age-out. The task's own text says *"if old records should age out,
that is a policy with a number, not a silent delete at close."* "Keep forever" is
a legitimate answer, but it is only defensible for `last.txt` at 24–30 MB/yr —
it was chosen without the `stdout.log` arithmetic above.

### F-3 · MEDIUM · correctness — the `--no-worktree-remove` promote runs with no cleanup lock and no close guard
`crates/orgasmic-cli/src/manager.rs:5401-5413` → `5462-5479`.

Every other artifact-touching path takes `acquire_dispatch_cleanup_lock`
(manager.rs:5107, api.rs:5766) and, for a destructive close, a daemon-owned
close guard. `promote_dispatch_artifacts_in_place` takes **neither**:

- `cmd_dispatch_close:1120` — `let mut close_guard = if remove_worktree { … } else { None };`
- `promote_dispatch_artifacts_in_place:5462` — no `acquire_dispatch_cleanup_lock` call.

And it is destructive: `promote_validated_dispatch_attempt` **unlinks** both tmp
artifacts (paths.rs:235).

Before this change `--no-worktree-remove` touched no files at all, so the missing
fence cost nothing. It costs something now. The hole is named in the code's own
comment at manager.rs:1147-1152: a 404 from `release_dispatch_run` is filtered as
"not live by that id," and the thing it fails to rule out — *"a recovery
replacement whose origin→replacement association never reached the ledger, live
in this very worktree"* — is, per that comment, refused by the guard. Which is
not taken here.

Concrete failure: a recovery replacement is streaming into `last.txt`; the close
copies a partial report, unlinks the inode, and every subsequent worker write goes
to an unlinked file. The promoted report is silently truncated at the close
instant — a quieter version of the defect this task closes.

Sharpest form: `reserve_close_guard`'s own failure message
(manager.rs:4278-4283) tells the operator *"or close without `--worktree-remove`"*
when the daemon is too old to fence. That escape hatch is now the one path that
mutates artifacts with no fence at all — advertised, by this code, to operators on
exactly the daemons that cannot fence.

**Fix:** take `acquire_dispatch_cleanup_lock(project_root)` inside
`promote_dispatch_artifacts_in_place`, and reserve the close guard whenever the
record names promotable artifacts, not only when `remove_worktree`.

### F-4 · MEDIUM · correctness — `--no-worktree-remove` close of an already-reclaimed worktree flips `CLEANUP_STATUS` from `ok` to `partial`
`manager.rs:5401-5413`, `5438-5440`; `paths.rs:302`.

`promote_dispatch_artifacts_in_place` calls `validate_dispatch_cleanup_targets`,
which calls `validate_dispatch_worktree` → `std::fs::symlink_metadata(worktree)`
(paths.rs:302). If the worktree is gone, that errors, the error is pushed, and the
new arm at 5438-5440 downgrades `Ok` → `Partial`:

```rust
(false, false, false) if errors.is_empty() => CleanupStatus::Ok,
(false, false, false) => CleanupStatus::Partial,
```

This is reachable and not exotic. `manager worktree prune` reclaims an orphan's
worktree (`reclaim_managed_worktree:3454`); the manager then closes the dispatch
record. `--worktree-remove` is not an option — `remove_worktree_required:5108`
bails `"worktree path missing"` → `WorktreeFailed` — so the correct flag *is*
`--no-worktree-remove`. That close now emits `CLEANUP_STATUS=partial` and
`CLEANUP_ERROR=report: last_path missing…` where it used to emit `ok`.

Consequences, all permanent (tx entries are append-only):
- `cleanup_status_reports_warning:5504` prints a warning on every such close.
- `scan_cleanup_failures:7322` + `cleanup_status_reports_failure:7353` list it in
  `dispatch-status --cleanup-failed` **forever** — poisoning the audit surface a
  manager uses to find real cleanup failures.
- `close_tx_ran_cleanup:7232` accepts only `ok`/`worktree-missing`, so
  `cleanup_already_run` no longer gets set by these closes.

**Fix:** a failed promote is not a cleanup failure. Report it on its own key
(`REPORT_PROMOTE_ERROR`) and leave `CLEANUP_STATUS` reflecting worktree/branch
disposition only; or skip the branch when the recorded worktree does not exist.

### F-5 · LOW · design (gap, not blocking) — orphan reclaim never promotes
`reclaim_managed_worktree:3454-3585` hardcodes `report_path: None` at six exit
points and never calls `validate_dispatch_cleanup_targets` at all. `manager
worktree prune` removes the worktree and leaves `last.txt`/`stdout.log` in `tmp/`
indefinitely, with no tx naming them.

Nothing is destroyed, so per the brief this is a gap worth naming, not a block.
But it is the *rescued-dispatch* case — the one the task text says matters most —
and it is the one path where a report never becomes resolvable.

### F-6 · LOW · correctness — the finalize `REPORT_PATH` fallback writes an absolute, user-specific path into a committed tx
`manager.rs:1911-1913`:

```rust
} else if let Some(last) = run.last_path.as_ref() {
    extra.push(("REPORT_PATH".to_string(), last.display().to_string()));
}
```

`run.last_path` is absolute (manager.rs:1957 writes the summary through it from
the worker's cwd, so it must be). This contradicts the invariant stated at
manager.rs:6978-6980 — *"Tx records store project-relative paths (no
user-specific prefixes in committed files)"* — which `:LAST_PATH:` itself honors
in the live ledger:

```
:LAST_PATH:    .orgasmic/tmp/dispatch/task-qgwk7-review/…-last.txt
```

It also names a path close then unlinks, so on the fallback the `*.reported` tx
points at a file guaranteed not to exist after close.

**On claim 5 of the brief — when can the generation not be resolved?** Better than
feared. `attach_recovery_run_to_dispatch:7093-7106` inserts the replacement
`run_id` into `record.run_ids`, so a **recovered/rescued run resolves correctly**
— the case the task was filed for is covered. `durable_report_path_for_finalize`
returns `None` only when `read_project_id` fails or the project is absent from the
board. And the close tx always carries the correct value regardless, because
`cleanup_dispatch` uses `open.tx_id` directly (5382, 5411). So the audit trail is
never body-less; it is only, in a rare case, pointed at the wrong copy.

**Fix:** make the fallback project-relative, or drop it — no `REPORT_PATH` beats a
`REPORT_PATH` that is wrong after close.

### F-7 · LOW · perf — the promote copy buffers the whole artifact in memory
`paths.rs:268-290`. `copy_validated_artifact_to` accumulates the entire file into
a `Vec<u8>` before writing a single byte — for a file the task text itself
describes as *"a streaming sink for unbounded untrusted bytes."* The chunked
`read_at` loop is already there; writing each chunk as it is read is a two-line
change and removes the only place where a hostile or runaway worker's output size
becomes the manager's RSS.

### F-8 · LOW · correctness — a half-succeeded promote leaves an unnamed file
`paths.rs:233-236`. If `last.txt` copies and `stdout.log` fails, the function
returns `Err`, so `report_path` is `None` and **no `REPORT_PATH` lands on the close
tx** — even though `last.txt` was promoted successfully and is sitting at the
canonical path. The fd-anchored ordering the brief flags is correct (unlink runs
only after both copies succeed, so a partial failure duplicates rather than
loses — confirmed at paths.rs:235); this is the mirror gap on the tx side.
Also, a mid-flight failure leaves `last.promoting` / `stdout.promoting`
(paths.rs:285) in the tracked directory.

### F-9 · LOW · test — the `--no-worktree-remove` promotion branch has no test
Three tests pass `--no-worktree-remove` (`dispatch.rs:2070`, `8211`, `8296`) and
now traverse the new branch at manager.rs:5401, but none asserts on promotion or
on `CLEANUP_STATUS`. So F-3 and F-4 are both invisible to the suite.

## Answers to the brief's five claims

**1. Does the fix reproduce its own defect shape?** Partly — see F-2. `last.txt`
at 24–30 MB/yr is fine and should be kept forever. `stdout.log` at up to
1 GB/yr into unrewritable history is the same unbounded-unrotated shape, and the
implementer's falsification argument is good enough to keep a *bounded* form of
it rather than drop it.

**2. Is a manual commit enough?** No — F-1. Rule: **close should stage the
directory.** 468 state commits, zero precedent for adding an untracked path.

**3. Windows.** Not a regression, and quieter than the brief feared: **the
`#[cfg(not(unix))]` arm at paths.rs:238-241 is unreachable on Windows.**
Validation fails first — `open_dispatch_dir` (paths.rs:369-372) returns
`"no-follow dispatch cleanup requires unix"`, and both
`validate_dispatch_worktree:315` and `validate_dispatch_artifact_pair:325` go
through it. So a Windows close has *always* failed at
`validate_dispatch_cleanup_targets` with `CLEANUP_ERROR`, before this change and
after, with the same message. No new noise, no new failure path — but the new
error string is dead code, and worth a comment saying so rather than reading as
live coverage.

**4. The paths that do not promote.** Full enumeration:

| close path | report | `REPORT_PATH` |
|---|---|---|
| `--status done --worktree-remove`, removal OK | **promoted** | yes |
| `--status aborted --worktree-remove`, removal OK | **promoted** (same `cleanup_dispatch`; abort differs only in tx type) | yes |
| `--worktree-remove`, `git worktree remove` fails (5148-5160) | left in `tmp/` | no |
| `--worktree-remove`, worktree already gone (5108) | left in `tmp/` | no |
| `--no-worktree-remove`, worktree present | **promoted** (unfenced — F-3) | yes |
| `--no-worktree-remove`, worktree gone | left in `tmp/`; status → `partial` (F-4) | no |
| record missing LAST_PATH/STDOUT_PATH/WORKTREE | left in `tmp/` | no |
| re-close / `cleanup_already_run` (1176) | left in `tmp/` | no |
| orphan reclaim, `worktree prune` (3454) | left in `tmp/` forever (F-5) | no |
| `dispatch-status --cleanup-failed` (2558) | read-only listing, touches nothing | n/a |
| Windows, any close | left in `tmp/`, unchanged from before | no |
| failed-dispatch rollback, local (`cleanup_created_resources:5276`, `started_tx: None`) | **DELETED** — deliberate | n/a |
| failed-dispatch rollback, daemon (`api.rs:5805`, reachable only from `manager.rs:874`) | **DELETED** — same rollback semantics | n/a |

`--status blocked` is not a close status: `DispatchCloseStatus` is `Done |
Aborted` only (manager.rs:1097-1236). `blocked` is a *finalize* status that maps
to `manager.dispatch_aborted` (manager.rs:1889). A tokenless close cannot reach a
live record at all since TASK-6AYEJ.2 (manager.rs:1092-1096).

**Both deleting paths are failed-dispatch rollback, where no worker report exists
— there is nothing to keep. No BLOCK SHIP.**

**5. `REPORT_PATH` on `*.reported`.** Covered — see F-6. Recovered runs resolve;
the close tx is always correct regardless.

## Open Questions

1. **Is "keep forever" still the answer for `last.txt` alone?** At 24–30 MB/yr I
   think yes and would not add an age-out. Confirm that the number, not just the
   principle, is what was intended.
2. **Should promotion be skipped when `last.txt` is 0 bytes?** A dispatch whose
   worker never finalized pre-creates both artifacts empty (observed live: this
   review's own stem dir has two 0-byte files). Promoting those creates a tracked
   directory with nothing in it, per aborted dispatch.
3. **Should the manager see the path?** `cmd_dispatch_close` prints only
   `closed: <task> <type> tx=<id>`. Printing the promoted `REPORT_PATH` would make
   the new durable location discoverable without reading the ledger — and would
   make a *missing* one obvious at the moment it matters.

## Fix Directions

Ordered as I would land them.

1. **F-1** — `git add -- <dest_dir>` after a successful promote, at
   `manager.rs:5163` and `manager.rs:5462`. Report a staging failure through
   `CLEANUP_ERROR`. Update `manager-dispatch.org:319-321` from "commit the
   directory" to "close stages it; commit it with your next state chore." Add a
   test asserting the promoted path is in the index after close.
2. **F-2** — truncate `stdout.log` to a bounded tail (64 KB) and record the
   original byte count beside it, or promote it only on a non-`done` close. Skip
   0-byte files either way. Put the chosen number in the convention next to
   "Retention: keep forever," which should then read as a policy with an
   arithmetic justification.
3. **F-3** — `acquire_dispatch_cleanup_lock` inside
   `promote_dispatch_artifacts_in_place`; reserve the close guard whenever the
   record names promotable artifacts, not only when `remove_worktree`.
   *Repro:* close with `--no-worktree-remove` while a second process holds the
   cleanup lock and appends to `last.txt`; observe the promoted copy truncated at
   the close instant and the writer's fd orphaned.
4. **F-4** — separate the promote error from `CLEANUP_STATUS`; add
   `REPORT_PROMOTE_ERROR` and leave `CLEANUP_STATUS` about worktree/branch only.
   *Repro:* build the `dispatch_cleanup_fixture`, `fs::remove_dir_all` the
   worktree, call `cleanup_dispatch(root, &open, false, false)`, assert the
   status. Expect `Partial` today, `Ok` before this diff.
5. **F-9** — cover both branches: a `--no-worktree-remove` close that promotes,
   and one whose worktree is gone (pinning whichever status rule wins in F-4).
6. **F-6** — make the finalize fallback project-relative, or emit nothing.
7. **F-7** — write each 64 KB chunk as it is read instead of accumulating a `Vec`.
8. **F-8** — return the partial success so a promoted `last.txt` still gets a
   `REPORT_PATH`; clean up `*.promoting` on failure.
9. **F-5** — promote from `reclaim_managed_worktree`, or state in the convention
   that a pruned orphan's report stays in `tmp/` and how to find it.
