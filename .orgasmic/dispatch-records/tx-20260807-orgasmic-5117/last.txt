# TASK-QGWK7.1.1 — the promoted record is committed, not left staged

## M-0 — which option, and why

**Option 2: the close commits the record.** Options 1 and 4 are not judgement
calls — I measured them dead.

- **Option 1 ("stage only when the index is otherwise clean for that path")
  does not fix anything.** Measured in a scratch repo: on `main` with the path
  absent from HEAD, from the index and from the merged tree, `git add`ing one
  new file and then `git merge --no-ff side` fails with
  `Your local changes to the following files would be overwritten by merge`.
  The index *was* clean for that path — that is the failing case, not the safe
  one. **Any** staged addition blocks **any** merge; the merge does not have to
  touch the path.
- **Option 4 ("a staging mechanism that does not participate in merge conflict
  detection") — I looked, and there is none.** `git add -N` (intent-to-add) is
  the only candidate: measured, it *still* blocks the merge, **and** a later
  plain `git commit` does not capture it (`git ls-tree -r HEAD` shows the path
  absent). Doubly disqualified. Anything else that "stages" is by definition an
  index entry, and an index entry that differs from HEAD is exactly what the
  merge refuses on.
- **Option 3 (keep staging, document merge-before-close)** is what the manager
  ruling's candidate 2 asks me to weigh honestly. I rejected it: it moves the
  guarantee from construction to a documented step, which is what F-1 existed to
  remove, and it also does not fully work — staging still leaves the record
  un-clonable until the manager remembers to commit, which is the residual the
  review itself named ("in the index still needs the manager to commit
  eventually").
- **Option 2 is the only one where the acceptance holds.** Committing is
  strictly more than staging: a fresh clone reads the record (parent criterion
  2, `manager-dispatch.org`'s "so a fresh clone can read it"), and the index is
  clean afterwards so the merge that the review gate prescribes next still runs.

**What breaks, stated plainly** (the ruling asked for reasons, not precedent):

- A close now moves the branch the manager is on by one commit. That is real
  and is now stated in the convention.
- The old objection was "when to commit needs manager judgement". That objection
  is about committing *the manager's change*. This commit cannot contain it: the
  tree is built through a **throwaway index seeded from `HEAD`**
  (`GIT_INDEX_FILE` + `read-tree HEAD` + `git add -- <record dir>` +
  `write-tree` + `commit-tree -p HEAD` + `update-ref HEAD <new> <old>`), so it
  holds `.orgasmic/dispatch-records/<started_tx>/` and nothing else. Whatever
  the manager has staged is neither committed nor disturbed — measured. The
  path is per-generation and fresh, so a record commit can never conflict.
- `update-ref` is given the old HEAD, so a HEAD that moved underneath the close
  refuses rather than clobbers.
- This is **not** the rejected salvage: the commit lands on the branch
  (`refs/heads/...` via `HEAD`), not on `refs/orgasmic/*`. A fresh clone reads
  it — pinned by `dispatch_close_commits_promoted_record_so_the_next_merge_still_runs`
  via `git cat-file -e HEAD:<report_path>`.
- Plumbing rather than `git commit` for three reasons: it can be scoped to one
  directory without touching the manager's index; `git commit --only` refuses
  during a merge; and no porcelain/hook path runs inside a close. Nothing is
  bypassed that was previously running — the close never committed before.

**What the durability guarantee now rests on:** the record being in a commit
reachable from the branch the close ran on, written by the close itself. Not on
a manager habit, not on a documented step, not on a custom ref.

**Failure behaviour** (a failed persist must never fail the close, and must
never leave the merge blocked): if the commit fails at any step, the index is
restored to HEAD for that path (`git restore --staged --`), so the record ends
up untracked-but-present — the pre-TASK-QGWK7.1 state, which does not block a
merge — and `CLEANUP_ERROR` says why. The promoted files are never the casualty.

## M-1 — which cleanup arm is authoritative

**The `--no-worktree-remove` arm.** Promote/persist failures go into `errors`
prefixed `report:` with **no** failure flag, so the status is `partial`; the
`--worktree-remove` arm now does the same. The two arms agree, and
`--branch-delete` is free to fire on a worktree that really was removed.

Mechanically: `WorktreeRemovalOutcome` gained `report_error`, separate from
`error`. `error` now means "the removal itself failed" and is the only thing
`cleanup_dispatch` classifies as `worktree_failed`.

Answering the review's open question 1: a promote/stage error **does** downgrade
`CLEANUP_STATUS`, but only to `partial` — never to `worktree_failed`. `partial`
is honest (something did not complete) and it is the status that leaves every
branch arm reachable.

## The parent's verify artifact was re-authored — say so out loud

`verify/TASK-QGWK7.1/injection.patch` targeted `stage_promoted_dispatch_record`,
which no longer exists. Per `verify/README.md` a stale artifact is a failure,
not a skip, so it is re-authored to no-op the persistence step that replaced it
(`commit_promoted_dispatch_record`). **`expect-red` and the pinned assertion are
byte-unchanged**, and the F-1 test
(`dispatch_close_stages_promoted_record_in_git_index`) is untouched — it asserts
`git ls-files --stage`, which is true of a committed path too. The property F-1
claims did not move; only the mechanism the injection removes did. This is the
opposite of the salvage, which rewrote the test and the artifact to match a
weakened property.

## One deviation from the brief, stated

The brief prescribed the final commit subject
`fix(dispatch): keep the promoted record staged without breaking the merge`.
It was written before the M-0 option was chosen, and the fix does not keep the
record staged — it commits it. Committing under a subject that says the opposite
would be a false record, so the subject reads
`fix(dispatch): commit the promoted record instead of leaving it staged`. The
body and the `TASK-QGWK7.1.1` trailer are the brief's.

## Residual risk

- A close now writes a commit. If `user.name`/`user.email` are unset, or HEAD is
  unborn, or HEAD moves concurrently, the commit fails — reported through
  `CLEANUP_ERROR`, index rolled back, record still on disk. No close fails, no
  report is lost, no merge is blocked.
- A close during an in-progress merge/rebase will advance HEAD under the
  sequencer. The record commit is a real ancestor and the index is untouched
  apart from the record path, so the pending operation still completes, but this
  is an interleaving no test covers.
- The record commit is unsigned and hook-free (plumbing). A repo that requires
  signed commits will have unsigned record commits in its history.
