## BLOCK SHIP

### B1 — HIGH — `SYSPOLICYD_CPU_DEGRADED=100.0` is a fixed threshold on a quantity that grows with run duration

`scripts/run-tests.sh:95`, window at `:591`–`:599`.

The implementer's own F9 numbers settle this. The **daemon `--lib` subset alone**,
51.4 s of wall, on a **calm** host (BEFORE 4.13), burned **+49.33 s** of syspolicyd
CPU. That is 49 % of the threshold in under a minute of a scoped run. The
threshold was then calibrated on that one run — the only run whose delta happened
to land under it — and applied to a gate whose default `CARGO_ARGS` is
`--workspace`.

Three compounding facts, all read from the source:

1. **`cargo build` is inside the sampled window.** `HOST_BEFORE` at `:591`, then
   `cargo test` at `:595` (which builds), then `HOST_AFTER` at `:598`. Every
   freshly linked rustc output is a new Mach-O that Gatekeeper evaluates — the
   mechanism this repo documents in `test_fixtures.rs:3-7`. A cold build is
   itself a scan storm, and it is charged to the run's degradation score.
2. **The delta accrues from ambient background too.** I measured it: over 60 s of
   an otherwise-idle host at load 4.01, syspolicyd accrued **+4.52 s
   (0.0753 s/s)** with nothing running. That alone caps a trustworthy run at
   ~22 minutes before any contention exists.
3. **The in-run rate is 0.35–0.96 s/s** (F9 run 1 and run 2 normalized by wall).
   At that rate the 100 s line is crossed in **~2 minutes of suite execution.**

So: `scripts/run-tests.sh` with no arguments — the invocation `.orgasmic/project.org:23`
tells every worker to run — reports `host : DEGRADED` and exit 4 on a calm host,
because the workspace suite plus its build runs several times longer than two
minutes. That is the original F4 failure verbatim: *the suite trips its own gate,
and exit 0 becomes unreachable.* It arrives via the syspolicyd signal instead of
the load signal, and it was missed because only the scoped `-p orgasmic-daemon
--lib` case was ever validated.

CI makes it worse rather than better. The Suite job (`ci.yml:128-206`) is
`macos-15`, has **no separate build step** — the cold workspace build happens
inside `cargo test`, inside the sampled window — is budgeted `timeout-minutes: 90`,
and `ci.yml:200-206` now *deliberately* fails the lane on exit 4. The comment
there justifies that decision with "exit 4 means host state **not attributable to
this run**". After B1 that premise is false: the delta is dominated by this run's
own build and duration. The lane becomes red for a reason nobody is expected to
fix, which is the exact thing `ci.yml`'s own header argues against.

I cannot measure a GitHub runner, so I state the CI consequence as near-certain
rather than proven; the local consequence needs no hedging.

**Fix direction.** Normalize the signal to the window. Judge on a *rate*
(syspolicyd CPU seconds per wall second of the sampled window) rather than an
absolute — calibration data already exists: 0.075 s/s ambient, 0.35–0.96 s/s
in-run on this Mac, and the historical +281/+32 pair can be re-expressed the same
way. Or exclude the build from the window by sampling around `cargo test --no-run`
and the run separately. Either way, measure the *workspace* delta once before
picking a number; every measurement so far is of the scoped subset.

### B2 — HIGH — a crashed test binary is reported as "suite looked green"

`scripts/run-tests.sh:1002-1013` vs `:1016-1019`.

Reproduced with a `cargo` stub on `PATH` emitting a `signal: 6, SIGABRT` tail and
exit 101, no per-test failure list:

- calm host → `verdict: RED — cargo exited 101 with no per-test failure list.` exit 1 ✅
- same run, `ORGASMIC_HOST_STATE_SAMPLE=load=11.41,syspolicyd_cpu=250.0` →
  `failures : 0` … `verdict: INCONCLUSIVE — re-run when calm. Host was degraded
  (suite looked green; that green is not trusted).` **exit 4**

Two defects in one branch. The ordering residual the manager flagged is real —
`SUITE_EXIT != 0` still sits after `HOST_DEGRADED`, and only `BUILD_BROKE` is
caught earlier. But the sharper problem is the *text*: because `FAIL_COUNT` is 0,
the INCONCLUSIVE message says **the suite looked green** about a run whose log
literally contains `SIGABRT: process abort signal`. That is not a downgrade, it
is a misreport, and it survives into the CI step summary as the lane's
deliverable.

On the ordering itself I'll rule rather than leave it open: a binary that died was
never re-run in isolation, so it is not "alone-red" in the sense F4 protected, and
a host excuse for it is arguably defensible. The misreport is not. Move
`SUITE_EXIT != 0` above `HOST_DEGRADED` (the same one-line move F4 made for
`REAL_COUNT`) — a process that aborted is a code fact — or at absolute minimum
make the INCONCLUSIVE text name the non-zero cargo exit instead of claiming green.

**I traced the rest of the ladder for other downgrades.** `BILLED_RAN` `:985`,
`BUILD_BROKE` `:988`, `REAL_COUNT` `:991` and the interlock tripwire `:996` all
precede `HOST_DEGRADED` `:1002`. `SUITE_EXIT != 0` is the only remaining code fact
behind it. `FAIL_COUNT == REAL + LOAD + FLAKE` holds (`classify_one` increments
exactly one per row, and the read loop is not a subshell), so the
"GREEN modulo flake" branch cannot swallow a REAL.

## Follow-ups

### F-C — MEDIUM — the BEFORE-load threshold moved the number, not the justification

`scripts/run-tests.sh:83-90`, `:469-470`.

The cited baseline — mid-run 7.35, post-run 4.13 → 7.87 — is the **suite's own
contribution**, which the BEFORE sample excludes by construction. It justifies a
threshold for a during/after sample. It is applied to BEFORE. Nobody measured the
distribution of BEFORE on this board; three values exist (4.13, 8.94, 12.95) and I
measured 7.20 with a single dispatch running and 4.01 two minutes later. 8.0 sits
inside that band, so GREEN vs INCONCLUSIVE is decided by ambient dispatch
activity within one load unit.

Worse, BEFORE is not unattributable to this run in the workflow the project
prescribes: `.orgasmic/project.org:23` says `cargo build`, then
`scripts/run-tests.sh`. The 1-minute load average carries that build straight into
the BEFORE sample, and a build is at least as parallel as the test run whose own
contribution was measured at +3.74.

Fix: `host_is_degraded` ORs the two signals at `:469-470`. Make load a
*corroborating* signal instead of an independent trigger and leave the (normalized,
per B1) syspolicyd delta primary. It is the mechanism this task actually
documented, and it has far better separation (~50 s normal vs 281 s thrash) than
a load number straddling ambient noise. On Linux there is no Gatekeeper scan storm
to excuse, so losing the trigger there is correct, not a gap.

### F-D — MEDIUM — the live sampler path still has no test, and the stamp format is duplicated

`scripts/run-tests-selftest.sh:107-112`, `:377-398`.

The new "live sampler path" case calls `--sample-host`, which prints one snapshot
and exits at `:530-534`. `host_judgment_from_snapshots`, `write_host_stamp`, and
the live BEFORE/AFTER wiring are untouched by any test. F3's acceptance —
"at least one selftest case drives the live sampler path" — is met in letter only.

And `stamp_host` hand-writes the stamp format rather than calling the writer, so
the eight stamp-driven cases assert the reader against a *copy* of the writer's
format. Rename a field in `write_host_stamp` and the selftest stays 27/27 while
`--classify` silently stops reading real logs and falls back to `host : unknown` —
which fails safe, so nothing goes red. A test that passes without exercising the
contract.

I closed the coverage gap by hand for this review (see Verification) and the round
trip is correct **today**. Nothing pins it. Fix: one case that runs the runner with
a stubbed `cargo` on `PATH`, then reclassifies the log that same run wrote. Covers
live sampling, stamp write, and round-trip in about a second, no cargo.

### F-E — LOW — an all-unknown or unparseable judgment prints `host : calm`

`scripts/run-tests.sh:940-948`. Reproduced:

- `delta=load=? syspolicyd_cpu=?` → `host : calm`, exit 0
- `delta=load=abc syspolicyd_cpu=xyz` → `host : calm`, exit 0
- truncated stamp with no `delta=` → `host : unknown` ✅ (fails safe)

Only the no-stamp path reaches "unknown". The *fields* correctly print `?` — the
acceptance criterion is met at field level — but the summary word is derived from
`host_is_degraded` returning false, which conflates "measured calm" with "measured
nothing". Same class as F2's phantom `0.0`, one level up. Derive the word from
whether any signal parsed as a number.

### F-F — LOW — a vacuous assertion in the new sampler case

`scripts/run-tests-selftest.sh:386` greps for `syspolicyd_cpu=0\.0` against a
snapshot that emits `load=` and `syspolicyd_time=` only (`:413-415`). The
assertion can never fire, so the case's headline "never a measured 0.0" is
unchecked. Assert on `syspolicyd_time=`, or move it to the judgment sample where
the field exists.

## Rulings on the six claims

**1. Is the calibration sound, or did it just move the arbitrary number?**
It moved the number. Both thresholds are still uncalibrated, and the syspolicyd
one is wrong in kind (B1): a fixed bound on a duration-proportional quantity,
calibrated on a 51-second scoped run and applied to a whole-workspace run with a
cold build inside the sampled window. The BEFORE-load threshold is a category
error (F-C): the measurement justifies a during/after bound and is applied to
BEFORE. To answer the manager's sub-questions directly — BEFORE is *not*
unattributable to this run, because `project.org` prescribes a `cargo build`
immediately before it and the average is 1-minute; a second concurrent dispatch
does push BEFORE past 8.0 (the implementer's own run 1 had BEFORE 8.94 from
nothing but sibling workers); and `SYSPOLICYD_CPU_DEGRADED=100.0` is the
*better*-separated of the two thresholds in isolation (50 normal vs 281 thrash is
a real 5.6× gap, and 100 is near their geometric mean) — its defect is not n=2, it
is that the quantity is not comparable across runs of different length.

**2. The F9 probe came back negative — what should follow? Does part A stay?**
**Part A stays. Keep it. Do not revert, and do not run a third probe as a gate.**

The probe is **uninformative, not negative** — the implementer's "leans against it"
over-reads it. Three reasons: the arms differ in wall time by 3× (155.7 s vs
51.4 s) because run 1 hit a hung-mux failure, so comparing raw *cumulative* deltas
is not a comparison at all; the arms differ in starting load (8.94 vs 4.13) and
cache warmth in a fixed order; and the instrument measures the wrong quantity. A
avoids *serialized Gatekeeper queue wait* — the measured 196 ms fresh vs 4 ms
linked is dominated by blocking, not by syspolicyd CPU burn — so 136 avoided
scans could be tens of seconds of wall latency and only noise-level CPU. Both
normalizations I tried (raw, and per-wall-second with the hang attributed) land on
"no detectable difference", which is what an instrument blind to the effect
returns.

What actually supports keeping A: the mechanism is directly measured (196 ms →
4 ms per site, 136 sites converted); the previous review verified the
link-vs-fresh boundary call correct at all eight sites, so the risk of keeping it
is zero; and reverting re-adds 136 Gatekeeper evaluations to buy nothing. Record
it as **mechanism-justified, effect size unmeasured on this suite** and close it.

If anyone does want the effect size later, the sound design is: the already-built
binary, filtered to *only* the tests that touch converted fixtures, A-on and A-off
alternated ≥3 times each and interleaved to cancel drift, any run with a failure
discarded, measuring **wall time of that subset** — not syspolicyd CPU. That is a
curiosity, not a gate. Two rounds have died on this question; it should not take a
third.

**3. Did F4 actually close, or only mostly?**
Mostly. The headline closed — `REAL_COUNT` at `:991` genuinely precedes
`HOST_DEGRADED` at `:1002`, the selftest case that encoded the wrong ruling was
*changed* rather than deleted, and `verify/TASK-STWVB.1` pins it. The named
residual is real and I found it is worse than an ordering problem: the verdict
text calls a SIGABRTed binary green (B2). No *other* case in the ladder downgrades
a code fact — I traced all eight branches.

But F4's underlying complaint — *the suite trips its own gate* — is **not** closed.
It was closed for the load signal and reopened for the syspolicyd signal (B1).

**4. Is the `--classify` stamp trustworthy, and is it forgeable?**
Substantially yes, with one gap. An older log with no stamp → `host : unknown`,
LOAD-SENSITIVE unavailable, alone-red and unregistered stay REAL — fails safe,
covered by a selftest, and I reproduced it. A *truncated* stamp (prefix present,
no `delta=`) also fails safe to unknown. The stamp round-trips exactly: I fed a
live-written stamp back through `--classify` and got byte-identical before/after/
delta lines and the same verdict. Forgeable in the trivial sense that the log is a
plain file the operator owns — not worth hardening. The gap is F-E: a stamp whose
values are unknown or unparseable reads as `calm` rather than `unknown`.

One thing worth naming even though it is not a defect in the gate: the round's
headline GREEN verdict block was produced by `--classify` over the **F9 run 2**
log — the run with `ORGASMIC_DISABLE_SHARED_FIXTURE_LINKS=1`, i.e. **part A turned
off** — plus a hand-appended stamp. So the shipped demonstration of a green
verdict does not exercise the shipped configuration, and it never went through
`run-tests.sh`'s live path at all. The reclassify path is sound, so the
demonstration is not *wrong*; it is just not a demonstration of the live gate.
I closed that by running the live path myself (Verification).

**5. Do the new selftest cases test the right thing?**
Partly. 27/27 reproduced independently. The case that encoded the wrong behaviour
was **changed, not deleted** — `degraded host + fails alone too -> REAL exit 1,
host stamp alongside`, now asserting exit 1 and `host : DEGRADED` together. Good.
The reordered ladder is exercised. The **live sampler is not** (F-D): the one
"live" case drives `--sample-host`, a snapshot printer, and one of its four
assertions is vacuous (F-F). The write→read stamp contract is covered only by a
hand-duplicated copy of the writer's format.

**6. F6–F8 and the fixture machinery.**
All three closed, and the positive control is a real one, not a weaker assertion.
`malicious_claude_shim_writes_log_and_exits_cleanly` links the shim, execs it with
real argv, asserts `status.success()` (which is what `/usr/bin/true` at
`test_fixtures.rs:137` now delivers) *and* asserts the side-channel log contains
`--resume`. That is exactly the assertion whose absence made the arm dead code.
The exit-97 sentinel is now unconditional by construction — the block moved to the
top of `FIXTURE_SCRIPT` ahead of the argv prelude, guarded only by the
`.orgasmic-pinned-wrapper` marker — and `pinned_wrapper_sentinel_fires_for_prelude_argv`
drives `config`, the hang-risk shape. F8's in-place `std::fs::write` is gone,
replaced by temp-file + `persist` rename with both failures named in the panic.
The `ORGASMIC_DISABLE_SHARED_FIXTURE_LINKS` kill switch does **not** leak: it lives
in `test_fixtures.rs`, which `lib.rs:36-37` gates behind `#[cfg(test)]`, and it has
no reference anywhere outside that file.
