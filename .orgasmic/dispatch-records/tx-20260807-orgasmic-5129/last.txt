# TASK-QGWK7.1.1 review — `dispatch-close` now writes a commit

## Verdict

**APPROVE WITH FOLLOW-UPS.**

The M-0 mechanism is correct and I could not break its happy path. I attacked
claims 1–5 with scratch-repo git probes rather than reading git's docs, and the
three load-bearing safety claims — the real-index `git add` is required, the
`update-ref` old-value check really is a compare-and-swap on the *branch*
through the symref, and a fully-ignored record cannot report success — all hold
under measurement.

The brief pre-committed to **BLOCK SHIP if a close corrupts a rebase**. It does
not. `git rebase --continue` completes correctly and keeps the record commit;
`git merge` completes with both parents intact; `git cherry-pick --abort`
restores cleanly. `git rebase --abort` *does* destroy the promoted record — but
I measured the pre-change staged-only baseline and it loses the record
identically, so that is pre-existing from TASK-QGWK7.1, not introduced here.
Details in F-3.

What keeps this off SHIP is one MEDIUM: **a record commit that fails has no
recovery path at all**, and the code has more failure modes than the old `git
add` did.

## Findings

### F-1 · MEDIUM · correctness — a failed record persist is unrecoverable, and re-running the close refuses

`crates/orgasmic-core/src/paths.rs:317` (tmp unlink) →
`crates/orgasmic-cli/src/manager.rs:5636` (`promote_and_persist_dispatch_record`).

`promote_validated_dispatch_attempt` unlinks the tmp artifacts as soon as the
*copies* succeed — **before** `commit_promoted_dispatch_record` is ever called.
So when the commit fails, the state is: record on disk untracked, tmp gone,
`CLEANUP_ERROR` = `report: commit promoted dispatch record …`, status `partial`.

There is then no way back into git:

- `promote_dispatch_artifacts_in_place` (`manager.rs:5605`) bails on
  `last_path missing`, because tmp is gone.
- Re-running `orgasmic manager dispatch-close` does not even get that far: the
  close tx was appended, so `resolve_close_target` returns
  `CloseTarget::AlreadyClosed` and `cmd_dispatch_close` prints
  `already-closed … (no-op)` and returns (`manager.rs:958–982`) — deliberately
  *not* re-running cleanup.
- There is no `dispatch-record commit` / `--repersist` verb.

So the one path where the guarantee fails is also the one path with no repair,
and the only signal is a `warning:` line on stderr. That is precisely the
regression back to "manager habit" that F-1 of the parent existed to remove —
narrowed to the error path, but silent there.

Two concrete ways in, both measured:

1. **Process death between the real `git add` and the `update-ref`.** I
   reproduced the resulting state directly: with the record staged and
   uncommitted, `git merge --no-ff side` fails with
   `error: Your local changes to the following files would be overwritten by
   merge: rec/tx1/last.txt`. That is the M-0 symptom, back verbatim, and no
   later close clears it — each close only ever touches its own
   `dispatch-records/<started_tx>/`.
2. **The rollback is best-effort and its failure is dropped.**
   `manager.rs:5691` runs `git restore --staged --` behind `let _ =`. If the
   index lock is held at *that* moment (the same class of event as the M-1
   trigger, just a few milliseconds later), the restore fails, nothing is
   reported, and the record is left staged — merge blocked again.

I confirmed the rollback works when it *can* run: after
`git restore --staged -- <dir>`, `git status --short` shows only `?? rec/`, the
subsequent `git merge --no-ff` exits 0, and the record file is still on disk.
The mechanism is right; it is the unguarded-ness that is the finding.

**Fix direction:** make persistence idempotent and re-entrant — a
`commit_promoted_dispatch_record` that works from `dest_dir` alone (it already
does; only its *caller* is gated on tmp), reachable either from the
already-closed no-op when `CLEANUP_STATUS` was non-ok, or as an explicit verb.
Cheapest partial: report the `git restore` failure instead of discarding it, so
a left-staged record is at least named.

### F-2 · MEDIUM · correctness — the `update-ref` CAS can pass on the wrong branch

`crates/orgasmic-cli/src/manager.rs:5800–5812`.

Claim 2 is **confirmed** in the case that matters. Measured: branch moved
between `rev-parse` and `update-ref` →

```
fatal: update_ref failed for ref 'HEAD': cannot lock ref 'HEAD':
  is at 224158a… but expected 4e82d0f…   (exit 128)
```

and `refs/heads/main` was untouched. `update-ref` dereferences the symref and
does a real compare-and-swap on the branch. Two racing closes cannot clobber
each other; the loser reports through `CLEANUP_ERROR`.

The hole is narrow but real: the CAS compares **OIDs, not ref identity**. If
HEAD is repointed to a *different* branch that happens to sit at the same OID
between the `rev-parse --verify HEAD^{commit}` and the `update-ref`, the check
passes and the record commit lands on the wrong branch. Measured in `p16`:
`git branch other && git checkout other` (both at `OLD`), then
`update-ref HEAD <new> <OLD>` → exit 0, and `other` advanced while `main` did
not. Millisecond window, requires a concurrent checkout; naming it rather than
weighting it.

**Fix direction:** resolve `git symbolic-ref -q HEAD` alongside the OID and CAS
that specific ref instead of `HEAD`, falling back to `HEAD` when detached.

### F-3 · MEDIUM (pre-existing, not a regression) · data loss — a close inside a conflicted rebase is discarded by `git rebase --abort`

Claim 3, measured in four scratch repos rather than read from docs.

| interleaving | result |
| --- | --- |
| conflicted `merge` → close → resolve → `git commit` | **safe.** `MERGE_HEAD` survives, the merge commit keeps both parents (`716a3b9 3049cb3`), the record is in `HEAD`'s tree, and the record commit is an ancestor. |
| conflicted `rebase` → close → `rebase --continue` | **safe.** Exit 0, lands back on `main`, `git cat-file -e HEAD:rec/tx1/last.txt` succeeds. The record commit is embedded in the rebased chain (`cmain / record / cside / c1`) — odd-looking history, not corruption. |
| conflicted `cherry-pick` → close → `cherry-pick --abort` | **safe.** Working tree restored (`f.txt = main`, 0 conflict markers), sequencer state and `CHERRY_PICK_HEAD` cleared, **and the record survives on disk** — better than the baseline. |
| conflicted `rebase` → close → `rebase --abort` | **record destroyed.** HEAD resets to `.git/rebase-merge/orig-head`, the record commit is unreferenced, and `rec/tx1/last.txt` is **gone from the working tree**. |

The last row is why I checked the baseline before grading it. With the *old*
staging-only behaviour, `git add` + `rebase --abort` also deletes the file
(`record file on disk after abort: GONE`). **Identical loss, so this is
pre-existing from TASK-QGWK7.1, not introduced by `960caea`** — which is why
this is not the BLOCK SHIP the brief pre-authorised. The object is still
reflog-recoverable in both cases; the working-tree file is not.

**Fix direction:** cheap and complete — refuse the close (or skip persistence
and say so) when `.git/rebase-merge`, `.git/rebase-apply`, `.git/MERGE_HEAD`,
`.git/CHERRY_PICK_HEAD` or `.git/BISECT_LOG` exists. Only the rebase case
actually needs it, but a single sequencer-state check is simpler than four.

### F-4 · LOW · correctness — `commit-tree` ignores `commit.gpgsign`, and the report's stated residual is wrong in the other direction

Measured: in a repo with `commit.gpgsign=true` and `user.signingkey` set to
garbage, `git commit-tree` exits **0** and produces an unsigned commit. So a
project that requires signed commits gets unsigned `chore(orgasmic): dispatch
record …` commits in its history with no warning, and a push-side signature
policy will reject the push. The worker names this residual correctly.

The worker also states "if `user.name`/`user.email` are unset … the commit
fails". Measured: it does **not** — `commit-tree` succeeds with git's derived
`user@host` ident. Harmless in effect, but the stated residual risk is
inaccurate and shouldn't be carried forward as a known failure mode.

### F-5 · LOW · correctness — detached HEAD persists to no branch

Measured: with a detached HEAD, `update-ref HEAD <new> <old>` moves the detached
HEAD only; `refs/heads/main` is untouched. The record commit is then on no
branch, and the manager's next `git checkout <branch>` removes the file from the
working tree and orphans the commit. The close reports `ok`.

Unborn HEAD, by contrast, is **safe**: `rev-parse --verify HEAD^{commit}` fails
first (`fatal: Needed a single revision`), before the real `git add`, so nothing
is staged and the close reports the failure. Worth stating that the two unusual
shapes are not symmetric — one is guarded, one is not.

### F-6 · LOW · correctness — M-5's refusal is now ahead of the torn-close recovery

`crates/orgasmic-cli/src/manager.rs:951` vs `:955`.

`normalize_report_path_property` was inserted *above*
`reconcile_torn_closes_best_effort`, whose own comment says it must run "before
anything else". So re-running a torn close with the same command line that
carried an absolute `REPORT_PATH` now bails before the stranded transition is
reconciled. Trivially recoverable (drop the property and re-run), and refusing
*is* the right call for the normal case — but the ordering silently demoted a
path that was explicitly ordered first.

### F-7 · LOW (docs) — the sidecar now has two meanings and the convention documents one

`crates/orgasmic-core/src/paths.rs:394–460`, convention at
`manager-dispatch.org:334–340`.

Re-tracing the flipped rename order (claim 7): the invariant **holds**. Sidecar
create/write failure, excerpt write failure, and sidecar rename failure all
return `Err` with both `.promoting` files scrubbed and tmp left intact (tmp is
unlinked only on `Ok`, `paths.rs:317`), so a retry recovers. The one asymmetric
state is the intended one — sidecar landed, `stdout.log` rename failed → a byte
count with no excerpt, never a truncated excerpt with no count.

The gap is readability, not safety. That state is distinguishable from "the
harness printed nothing" **only by reading the sidecar's value** (`0` vs
non-zero), and the convention prose documents only the `0` case. A reader who
finds `stdout.log.bytes: 51234` and no `stdout.log` has no documented way to
know that means a failed promote. One sentence in
`manager-dispatch.org` fixes it.

Also folded in: the promoted excerpt is now `64 KiB + ~180` bytes (the two
banner lines ride on top of the cap; the test pins `< 200`). The convention
still says "64 KB excerpt". 0.3% — worth a word, not a change.

## Claims that are fine, one line each

- **Claim 1 — the real-index `git add` IS load-bearing. Confirmed, measured.**
  With the real add skipped, `git status --short` reports `D  rec/tx1/last.txt`
  + `?? rec/`, and the manager's very next `git commit` **deletes the record
  from history** (`git cat-file -e HEAD:rec/tx1/last.txt` fails). With it, the
  index is clean and `git merge --no-ff` exits 0. The process-death half of this
  claim is F-1.
- **Claim 4 — the `tree == head_tree` early return cannot report a false
  success.** Two reachable shapes, both measured: a record dir under an ignored
  *directory* rule fails at the real `git add` (exit 1, `The following paths are
  ignored`) before the scratch index is ever built; a dir whose every *file* is
  ignored (`*.log`,`*.txt`,`*.bytes`) does reach `tree == head_tree` and return
  `Ok(())` — but `verify_dispatch_record_staged` ran against the real index
  first and returns `Err` naming all three files, and that `Err` is what
  `commit_promoted_dispatch_record` returns. Replay of the same generation is
  the only *silent* path, and it is correct.
- **Claim 6 — `partial` costs nothing downstream.** All three consumers treat it
  exactly as they treated `worktree_failed`: `cleanup_status_reports_warning`
  (`manager.rs:5882`, non-`Ok` → warn), `cleanup_status_reports_failure`
  (`:7731`, non-`Ok` → listed by `--cleanup-failed`), and `close_tx_ran_cleanup`
  (`:7610`, only `ok`/`worktree_missing` count as "cleanup ran"). No transition,
  gate or re-dispatch reads it. The M-1 fix is behaviourally clean.
- **Claim 5, subdirectory project root — safe.** `git ls-files -- <abs dir>` run
  with `cwd = project_root` emits paths relative to the cwd, so they match
  `strip_prefix(project_root)` exactly. Measured with a project root nested one
  level inside the repo: both sides produce
  `.orgasmic/dispatch-records/tx1/last.txt`.
- **Claim 8 — the tests do enter the production path.** The tx-log sweep exists
  and asserts what was claimed (`tests/dispatch.rs:1041–1050`: every
  `:REPORT_PATH:` line in the ledger this run produced must not start with `/`),
  and it is preceded by a `run_orgasmic_failure` that drives the real binary
  through `cmd_dispatch_close` with an outside-the-project absolute path
  (`:969–1000`). The fence's companion is likewise real: the extension at
  `:4527–4568` runs an actual `--no-worktree-remove` close through the CLI
  against a live run and asserts the tmp report **survives** the refusal.
  `manager_supplied_report_path_property_is_project_relative` is still
  helper-only, but it is no longer the *only* coverage — which is what the
  parent's M-8 asked for.
- **Claim 9 — refusing is right and is not a trap.** The `bail!` is at the top of
  `cmd_dispatch_close`, before any destruction, and the offending value is a
  command-line property the manager controls; drop or fix it and re-run. The
  only cost is the ordering in F-6. The `/var` vs `/private/var` fallback works:
  `normalize_path` (`manager.rs:6864`) canonicalizes, and its
  nearest-existing-ancestor fallback matters here because a curated
  `REPORT_PATH` may name a file that does not exist yet.
- **Claim 10, the rest of it.** `--merge-sha` verification runs at
  `manager.rs:1047`, well before `cleanup_dispatch` at `:1199`, so the HEAD
  advance cannot invalidate it. `git stash push --include-untracked`
  (`update.rs:979`, `install.sh:505`) genuinely can no longer un-persist a
  record — the parent review's open question 3 is closed by construction, not
  worked around. The one consequence nobody has stated: **every** close now
  advances the branch, including promote-only `--no-worktree-remove` closes
  (`promote_dispatch_artifacts_in_place` → `promote_and_persist_…`), so a
  manager closing N dispatches in a round gets N `chore(orgasmic): dispatch
  record` commits interleaved with their own work. The convention says "a close
  moves the branch you are on by one commit"; it does not say it applies to
  promote-only closes too.

## Open questions

1. **Should the close refuse to persist while a sequencer operation is in
   flight?** F-3 says only `rebase --abort` loses anything and that loss is
   pre-existing — but the check is four `exists()` calls and it closes the whole
   class. Cheap enough that not doing it should be a decision, not an omission.
2. **Is an unrecoverable persist failure acceptable if it is loud enough?** F-1
   can be answered either by making persistence re-entrant or by escalating the
   report (the manager currently gets one `warning:` line). The second is much
   cheaper; the first is what "by construction" means.
3. **Do record commits need to be signable?** If any consuming repo enforces
   signatures on push, the close silently produces unpushable history. A
   `-S`-when-`commit.gpgsign` pass-through, or an explicit "record commits are
   unsigned" line in the convention.

## Fix directions (ordered)

1. **F-1** — make `commit_promoted_dispatch_record` reachable when tmp is
   already gone (it needs only `dest_dir`), and route the already-closed no-op
   into it when the recorded `CLEANUP_STATUS` was non-`ok`. Minimum viable:
   stop discarding the `git restore --staged` result.
2. **F-3** — refuse or skip persistence when `.git/rebase-merge`,
   `.git/rebase-apply`, `.git/MERGE_HEAD`, `.git/CHERRY_PICK_HEAD` or
   `.git/BISECT_LOG` exists; report through `CLEANUP_ERROR`.
3. **F-2** — CAS the branch ref resolved by `git symbolic-ref -q HEAD` rather
   than `HEAD` itself, falling back to `HEAD` when detached (which also gives
   F-5 a place to refuse).
4. **F-6** — move `normalize_report_path_property` below
   `reconcile_torn_closes_best_effort`.
5. **F-7 / F-4** — two sentences in `manager-dispatch.org`: what a non-zero
   `stdout.log.bytes` with no `stdout.log` means, that record commits are
   unsigned, and that promote-only closes advance the branch too.
