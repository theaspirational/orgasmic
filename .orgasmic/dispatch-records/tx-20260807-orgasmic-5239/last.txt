# TASK-QGWK7.1.1.1.1.1 review — the replacement claim is true; the *removal's* justification is not

# Verdict

**REJECT — BLOCK SHIP on F-1.**

The C-1 correction is right. I re-measured the production shape myself and the
new prose's *conclusion* holds: `revert --abort`, `cherry-pick --abort`,
`merge --abort` and `am --abort` all exit 0 with the record alive on disk and in
`HEAD`; `rebase --abort` is genuinely the only destroyer, and it genuinely
detaches HEAD. C-3 and C-4 are correct and accurate. `expect-red` is
byte-unchanged (I checked independently), and the re-authored injection restores
the identical five-marker set.

But this round removed a guard entry on the strength of a universal — *"a
revert/cherry-pick range stopped between picks ALWAYS carries its own `*_HEAD`
marker"* — and that universal is **false**. I built the counterexample by an
ordinary route (resolve the conflict, `git commit` instead of
`git revert --continue`): `.git/sequencer` with a two-entry pending todo and **no
`*_HEAD` marker at all**. Before this round the guard refused that state. Now it
persists into it. Your dispatch brief set exactly this test — *"if such a state
exists and is harmful, the removal was wrong"* — so I am returning the answer
rather than waving it through.

Worse, the shipped convention still promises coverage of *"an interrupted
revert/cherry-pick sequence"*, and `shipped_conventions.rs:444` still pins that
phrase while the entry that implemented it is gone. That is the **exact
prose/code drift TASK-QGWK7.1.1.1.1 B-2 existed to kill**, recreated in the round
whose purpose was prose accuracy. The pin did not catch it because it only reads
the prose (F-2).

Second-order: the *mechanism* the new prose gives — "git declines to rewind a
HEAD that moved" — is false for three of the four operations it is asserted over
(F-3), and it is stamped "(measured)". A false explanation for a true conclusion
is the same defect class this round was convened to fix, one layer down.

I agree with your ruling on the test name; see Open Questions.

# Findings

## F-1 — BLOCK SHIP — correctness/regression — a stopped pick range with NO `*_HEAD` marker is reachable, and the guard no longer refuses it

`crates/orgasmic-cli/src/manager.rs:5793-5801` (the array), doc comment
`:5808-5816`, `verify/TASK-QGWK7.1.1.1.1/README.md:98-102`, test doc
`:10047-10059`.

The removal rests on a universal asserted in three shipped places:

> "a revert/cherry-pick range stopped between picks **always** carries its own
> `*_HEAD` marker alongside the todo list, so the marker above already refuses
> it" — `manager.rs:5810-5812`

**Measured, git 2.52.0, counterexample by an ordinary route:**

```sh
git init -q -b main . && git config user.email t@t && git config user.name t
echo base > f.txt && git add f.txt && git commit -qm base
for i in 1 2 3; do echo v$i > f.txt; git commit -qam v$i; done
git revert --no-edit HEAD~1 HEAD~2          # stops between picks
#   .git markers -> [REVERT_HEAD sequencer]     <- refused, correctly
echo resolved > f.txt && git add f.txt && git commit -qm "resolved by hand"
#   .git markers -> [sequencer]                 <- NO *_HEAD marker
#   .git/sequencer/todo -> "revert bdc0857 v2" ; "revert 6b57078 v1"
```

`git commit` clears `REVERT_HEAD` and leaves the todo list. The range is *not*
abandoned — I confirmed it resumes: `git revert --continue` from this state picks
the remaining reverts on top of the manual resolution commit (it stopped again on
the next conflict, re-creating `REVERT_HEAD`, with `resolved by hand` in the log).
This is a documented git workflow, not a fabricated state.

In that state `sequencer_operation_in_progress` sees none of `rebase-merge`,
`rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, so
it returns `None` and the close commits the record. The manager's next
`git revert --continue` then stacks the rest of the range on top of it.

**Why that is the harm this guard exists to prevent**, in the corrected
convention's own words: the record "would otherwise land in the middle of an
operation you have not finished, on a branch whose shape you are still deciding."
Here it lands mid-range, at a point the manager did not choose — and if they later
abandon the range with `git reset --hard <pre-range>`, the record dies with it.
**Before this round, this state was refused.** So the round is a coverage
regression, and the acceptance item *"a stopped range is still refused via its
`*_HEAD` marker"* is falsified.

**I am not arguing the entry must come back as it was.** Your latch measurement
is correct and I reproduced it: after `git reset --hard`, `.git/sequencer`
survives, `git status` says nothing, an ordinary commit does not clear it, and
only `git revert --quit` does — a permanent, unexplained refusal. That is a real
trap and worth removing. What cannot ship is the *reason given*: "it adds no
coverage" is measurably wrong, in the same document set this round exists to make
truthful. Fix directions below offer both exits.

## F-3 — MEDIUM — docs — the corrected prose asserts a MECHANISM, "(measured)", that is false for three of the four operations

Three sites: `shipped/prompt-studio/conventions/manager-dispatch.org:346-349`;
`crates/orgasmic-cli/src/manager.rs:5765-5767`;
`verify/TASK-QGWK7.1.1.1.1/README.md:75-78`.

> "git declines to rewind a HEAD that moved, so `git revert --abort` and
> `git cherry-pick --abort` exit 0 and the record survives in `HEAD` and on disk
> (measured)" … "`merge --abort`, `cherry-pick --abort` and `am --abort` behave
> the same way: git declines to rewind a HEAD that moved."

Measured in the production shape (real-index `git add`, throwaway index,
`commit-tree`, `update-ref`), git 2.52.0 — **the conclusion is right in every
row, the mechanism is right in exactly one**:

| operation | abort exit | record on disk / in HEAD | git printed |
|---|---|---|---|
| single-commit conflicted `revert` | 0 | YES / YES | *(nothing)* |
| single-commit conflicted `cherry-pick` | 0 | YES / YES | *(nothing)* |
| conflicted `merge` | 0 | YES / YES | *(nothing)* |
| conflicted `am` | 0 | YES / YES | `warning: You seem to have moved HEAD since the last 'am' failure. Not rewinding to ORIG_HEAD` |
| conflicted `rebase` | 0 | **NO / NO** | *(nothing)* — and HEAD was detached |

Only `am` declines. For a single-commit revert/cherry-pick, git's
`rollback_single_pick` path does `reset --merge` **to the current HEAD** — it
rewinds, silently, and the record survives only because it is already *at* HEAD.
I confirmed the rewind happened: `f.txt` after `git revert --abort` was `two`,
the pre-revert tip content, so the conflicted state was discarded. `merge --abort`
is likewise `git reset --merge` to HEAD.

The "declines to rewind" wording is the *multi*-pick path: with a stopped range
plus a record commit, `git revert --abort` did print
`warning: You seem to have moved HEAD. Not rewinding, check your HEAD!` — a
different code path from the one the correction actually measured.

Impact is bounded (no behaviour rests on it) but it is an explanation stamped
"(measured)" that the measurement does not support, shipped to managers, in the
round convened because that happened last time. A manager reasoning forward from
"git declines to rewind a moved HEAD" will predict wrongly about their own
conflict resolution surviving an abort — it does not.

**The rest of the C-1 correction is sound.** The two rows the implementer
inherited without re-measuring (`merge --abort`, `am --abort`) I measured myself:
both hold. `rebase --abort` destroying the record and detaching HEAD: measured,
holds.

# Fix Directions

1. **F-1, exit (a) — restore the entry without the latch.** The failure mode was
   never the entry, it was the *message*: it told the manager to wait for a
   sequence that cannot finish. Restore
   `("sequencer", "revert or cherry-pick sequence")` and special-case the advice —
   when the marker that fired is `sequencer` with no `*_HEAD` beside it, say
   *"finish it with `git revert --continue`, or — if you already abandoned this
   range with `git reset --hard` — clear the leftover todo list with
   `git revert --quit`"*. That converts a permanent unexplained refusal into a
   one-command self-serve fix and keeps the F-1 state covered. Pin both: the
   abandoned-range close must name `--quit`, and the manual-commit state must be
   refused.

2. **F-1, exit (b) — keep the removal, correct the claim.** Strike "adds no
   coverage" and "always carries its own `*_HEAD` marker" from
   `manager.rs:5808-5816`, `README.md:98-102` and the test doc at `:10047-10059`;
   say instead that the entry was dropped because its latch outweighed the one
   unmarked state it covered, and *name that state*. Then drop "or an interrupted
   revert/cherry-pick sequence" from `manager-dispatch.org:341-342` and the
   `"revert/cherry-pick sequence"` phrase from `shipped_conventions.rs:444` —
   leaving them is F-2.

3. **F-2 — make the pin bidirectional.** Have `shipped_conventions` read the
   operation names out of `sequencer_operation_in_progress` (export the array as a
   `const`) and assert each is nameable off the prose, instead of hard-coding the
   phrase list. Then dropping an entry from either side really does fail there.
   Until that exists, the comment at `:436-438` should not claim it does.

4. **F-3 — say what was measured, not why.** Replace "git declines to rewind a
   HEAD that moved" with the outcome alone: *"the abort exits 0 and the record
   survives in `HEAD` and on disk — for `revert` and `cherry-pick` because the
   abort rewinds to the current HEAD, which is the record commit; for `am` because
   git refuses to rewind past a moved HEAD."* Or drop the mechanism clause
   entirely; the conclusion stands without it. Also worth a line: the abort
   discards the manager's conflict resolution either way.

5. **F-4 — fix the string and re-author the two patches.**
   `manager.rs:5695-5697` should not promise a discard that only `rebase` performs.
   Something like *"the record was promoted to disk but not committed, so it does
   not land mid-{operation}"*, and refresh the deleted-context lines in
   `verify/TASK-QGWK7.1/injection.patch:23` and
   `verify/TASK-QGWK7.1.1/injection.patch:24` in the same commit. If you overrule
   me and leave it, put the reason in a comment at the site — the next reader will
   otherwise file it as a sixth site.

6. **F-5 — recover or re-request `tx-20260807-orgasmic-5232/last.txt`** before it
   is needed for the next round's provenance.
