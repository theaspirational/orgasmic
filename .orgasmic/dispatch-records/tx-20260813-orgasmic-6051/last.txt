# TASK-P9T4N (atomic dispatch close) — final independent review of `639a955`

## Verdict

**approve** — with one MEDIUM to fix on the next touch of this path.

All four required checks pass. The post-append sync rollback P0 is genuinely
closed, the two former P1/P2 classes I could reach are handled, and the writer
core is proven by its own tests. The one new defect I found is in the CLI's
legacy-recovery loop, not in the writer or the atomic commit itself, and it is
recoverable by a manual transition — not data loss, so it does not block.

## Findings

### P2 (MEDIUM, correctness) `crates/orgasmic-cli/src/manager.rs:1403`

The new already-closed lifecycle replay loop posts `transition.to` for every
requested task in `open.closed_tasks` **unconditionally**, with no check that
the task is still where the close left it.

`transition.to` is derived at `manager.rs:8320-8333` from `open.kind` +
`args.status`/`args.fix_round_final` — never from what actually happened — and
`update_task_state` (`crates/orgasmic-daemon/src/api.rs:17302-17352`) has no
legality gate: any from→to move is applied. Contrast `reconcile_torn_closes`,
whose guard is explicit and documented as the property that "never drags a
deliberately moved task back" (`manager.rs:8594`:
`if current != transition.from || transition.from == transition.to { continue }`).

Failure scenario: a two-task dispatch (A, B). A's close lands, B's fails. A
reviewer dispatch or an operator then moves A from `in_review` to `done`. The
operator re-runs the identical command line — which is how a partial close is
re-run — `manager dispatch-close --task A --task B --started-tx … --status done`.
A is in `open.closed_tasks`, so the loop posts `state=in_review` for A and drags
it back out of `done`. With `--status aborted` on the re-run it lands A in
`todo` instead. `reconcile_torn_closes_best_effort` at `manager.rs:1065` cannot
prevent this: it correctly skips A (current ≠ recorded `LIFECYCLE_FROM`), and
then the new loop fires anyway.

No test covers this. `bundled_partial_close_retry_is_idempotent_and_visible`
(`crates/orgasmic-cli/tests/dispatch.rs:3039`) exercises only the benign
direction — the old-format partial close where the stranded task is still at its
pre-close stage — and passes.

### P3 (LOW, usability) `crates/orgasmic-cli/src/daemon_client.rs:422`

`daemon_http_error_message` has a humanized branch for
`committed:true, index_status:"refresh_failed"` but none for the new
`committed:true, durability:"uncertain"` body emitted at `api.rs:1724-1728`. The
operator therefore gets a polished sentence for the *less* dangerous outcome and
a raw JSON blob for the more dangerous one:

```
daemon returned 503 Service Unavailable: {"committed":true,"durability":"uncertain","error":"multi transaction committed but durability is uncertain; retry the same request_id …"}
```

It is honest and it does not claim success, so check #4 is met — but the advice
("re-read state, do not blindly retry") is exactly what a committed-but-unsynced
close needs and is absent.

### P3 (LOW, design) `crates/orgasmic-daemon/src/api.rs:1720-1722`

`dispatch_close_writer_error` distinguishes the committed-but-uncertain case by
substring-matching two writer message literals. Nothing pins the producer
(`writer.rs:1686`, `writer.rs:1724`) to the consumer. Rewording either message
silently downgrades a committed close to a `500 "failed to apply changes"` — an
error that asserts nothing was written when both ledger entries are on disk.
A typed error variant (or a shared `const`) removes the coupling; no test
currently fails if the strings drift apart.

### P3 (LOW, correctness — narrow) `crates/orgasmic-daemon/src/api.rs:17118-17147`

In the `current_state == to_state` replay branch, `from_path` is rebuilt as
`task_file_path(root, lifecycle_stage_file_name(from_state))`, whereas the
original commit used `task.source_file`. If a task's heading does not live in
the canonical stage file for its stage, the replay reconstructs a different
rewrite set, the writer's identity check fails closed
(`writer.rs:691-696`), and the caller gets a 500 instead of the intended
idempotent replay — or a 404 from `read_artifact` if that stage file does not
exist. Reachability is low: `DaemonClient::post_json` does not retry
(`daemon_client.rs:109-116`), so no CLI path re-POSTs a close, and the new test
only covers the canonical-file case.

### Residual (not blocking)

- **SyncUncertain does not seed the per-tx request-id cache.** The
  `SyncUncertain` arm (`writer.rs:1711-1726`) inserts only the multi cache key;
  `cache_durable_multi` (`writer.rs:2019-2046`) is what seeds each tx's own
  `request_id`. So after an uncertain close, a caller that replays only the
  lifecycle leg by its own `request_id` will not be recognized as
  `already_applied`. The CLI does not do this today.
- **Partial `write_all` inside `append_many`.** `TxWriter::append_many`
  (`crates/orgasmic-core/src/tx.rs:420-438`) validates everything before writing,
  but an `ENOSPC`/`EIO` mid-`write_all` still leaves bytes; the `Err` arm at
  `writer.rs:2767-2773` then rolls the rewrites back, i.e. a tear in the other
  direction. Pre-existing and shared with the single-tx path; outside this
  remediation's P0.

## Required checks — result

1. **P0, no rollback after append.** Closed. `retain_rewrites_after_append` is
   `true` only for the multi path (`writer.rs:1702`); the sync-failure branch
   returns `Ok(MultiTransactionCommit::SyncUncertain)` *before* any
   `rollback_renamed_rewrites` (`writer.rs:2774-2783`), and because that is an
   `Ok`, `cleanup_committed_backups` (`writer.rs:2789`) deletes the `.bak`
   sidecars — nothing survives that could restore the pre-close bytes.
   - *Repeated* sync failure: the cache entry stays `SyncUncertain`, and the
     retry re-syncs the retained descriptor only (`writer.rs:1672-1689`) — it
     never re-enters `transaction_multi_inner`.
   - Response contract: first failure and re-sync failure return distinct
     messages, both routed to a 503 carrying `committed:true`.
   - Events: `publish_multi_events` fires only on a durable outcome
     (`writer.rs:1680`, `1708`) — no `TxAppended` is published for bytes that
     were never acknowledged.
   - Identical retry converges on the same two tx ids with no duplicate pair;
     changed request under the same id fails closed. Both proven by
     `post_append_sync_failure_keeps_rewrites_and_retry_syncs_without_duplicate_pair`
     (asserts `sync_attempt_count()==3`, `sync_count()==1`, ledger stays at 2
     entries) and
     `multi_transaction_request_id_collisions_fail_closed_on_semantic_changes`.
2. **Single-rewrite rollback preserved.** `transaction_inner` and
   `transaction_locked_inner` both pass `retain=false`
   (`writer.rs:2550`, `writer.rs:2685`) and turn an impossible `SyncUncertain`
   into an error rather than a silent success. `rewrite_transaction_rolls_back_when_tx_sync_fails`
   passes in my run.
3. **Former P1/P2s.**
   - Partial old-format bundled close recovery: implemented at
     `manager.rs:1403-1418`, covered by
     `bundled_partial_close_retry_is_idempotent_and_visible` (passes). See the
     MEDIUM above for what it does *not* guard.
   - Legacy torn-close-before-`REPORT_PATH` ordering:
     `a_torn_close_is_reconciled_before_an_absolute_report_path_is_refused` now
     seeds the torn ledger directly instead of manufacturing a tear through a
     rejecting proxy — necessary, since the tear is no longer producible. Passes.
   - Home-routed close read-after-write: `refresh_after_project_mutation`
     (`api.rs:7996-8017`) now refreshes the project *and* the home ledger.
     Confirmed non-stalling: the `tx_id` is only a coalescing key in
     `request_required_refresh` (`index.rs:1486-1502`), not a content
     requirement, so passing a home tx id to a project refresh is safe.
     `dispatch_close_home_ledger_refreshes_project_for_read_after_write` passes.
   - Stale-ready index: `state.index.refresh_project` before the snapshot read
     (`api.rs:17075-17083`);
     `dispatch_close_revalidates_a_ready_but_stale_task_index` passes.
   - Parse guard: every rewrite is UTF-8-checked and `OrgFile::parse`d before
     the writer is touched (`api.rs:17185-17194`), including in the replay
     branch.
   - Labelled no-op replay: `cache_durable_multi` seeds each leg's own
     `request_id`, so a later `post_task_state` with
     `close_lifecycle_request_id` resolves through `cached_tx_id` to
     `already_applied` (`api.rs:17337-17344`).
     `resubmitted_close_and_transition_are_labelled_no_ops` passes.
4. **API error semantics.** Met. A durability-uncertain close is a 503 with
   `{"committed":true,"durability":"uncertain"}` (`api.rs:1724-1728`); a normal
   write failure is a 500 `"failed to apply changes"` (`api.rs:1713-1716`). The
   CLI surfaces the 503 body verbatim and fails the command — it never reports
   success. See the two LOWs above for the polish gaps.
5. **Scope.** Reviewed only `639a955` vs `42f0b10`. The one broad-suite failure
   is classified as environment, not regression — see below.

## Open questions

1. Was the unconditional already-closed replay loop meant to carry
   `reconcile_torn_closes`' current-state guard, or was it deliberately
   unguarded on the theory that a partially-closed dispatch's tasks cannot have
   moved? If deliberate, it should say so and cite why the reviewer-dispatch
   case cannot move them.
2. Is the `current_state == to_state` replay branch in
   `post_task_dispatch_close_commit` intended for any caller other than an
   HTTP-layer retry? Nothing in the CLI reaches it today, which is why its
   `from_path` reconstruction is untested against a non-canonical
   `source_file`.

## Fix directions

1. **MEDIUM.** Gate the loop at `manager.rs:1403` the way
   `reconcile_torn_closes` gates itself: skip the task unless it is still
   stranded. Cheapest correct predicate — replay only when the close tx for that
   task carries no `LIFECYCLE_TO` (i.e. it is genuinely old-format, which is the
   loop's stated reason to exist) **or** the ledger shows no
   `task.state_transitioned` for it after that close tx; that is exactly
   `torn_close_candidates`' decision procedure. Add a test: partial close, then
   move the closed task forward by hand, then re-run the same command line and
   assert the task stayed put.
2. **LOW.** Add a `committed == Some(true) && durability == Some("uncertain")`
   branch to `daemon_http_error_message` (`daemon_client.rs:422`) that says the
   close *did* land, that only durability is unconfirmed, and that the safe
   action is to re-read state and retry the same `request_id`.
3. **LOW.** Replace the substring match in `dispatch_close_writer_error` with a
   typed error the writer returns (or at minimum shared `const` message
   fragments referenced from both sides), and add a test that a
   `SyncUncertain` reply maps to 503 with `committed:true`.
4. **LOW.** In the replay branch, prefer `task.source_file` for `from_path` when
   the task is findable, falling back to the canonical stage file only when it
   is not — so a replay reconstructs the same rewrite set the original commit
   used.
