## Verdict

**APPROVE.**

No HIGH or MEDIUM findings. The correction is a *strict narrowing* of a
mutating path — the new eligibility set is provably a subset of the old
`open.closed_tasks` filter — so it cannot introduce a new unwanted lifecycle
write. All four review objectives check out against the code, and the four
LOW findings below are coverage/observability items, not ship blockers.

## Findings

### L1 — LOW (test) `crates/orgasmic-cli/src/manager.rs:8733-8739`
`legacy_close_active_stage` has no direct unit test, and the only end-to-end
exercise (`legacy_partial_close_retry_does_not_move_an_advanced_sibling_backwards`,
`tests/dispatch.rs:3199`) covers exactly one arm: implementer / `--status done`.
The `reviewer` and legacy `architector` arms, and the `manager.dispatch_aborted`
close type, are untested.

I verified the mappings by hand rather than by test:
- `implementer -> InProgress`, `reviewer -> InReview` match
  `dispatch_lifecycle_transitions` (`manager.rs:8283-8292`) exactly.
- `architector -> InProgress` matches the pre-excision arm at
  `96dfa8a^:crates/orgasmic-cli/src/manager.rs:4001`
  (`DispatchKind::Architector => LifecycleStage::InProgress`). Correct.
- Aborted closes: `manager.dispatch_aborted` is in the tx-type match
  (`manager.rs:8712-8716`); `close_lifecycle_transitions` maps aborted
  implementer/architector -> `Todo` (from `InProgress`) and aborted reviewer
  -> `InReview` (from `InReview`, i.e. a `from == to` no-op). Both are safe.

No plausible lifecycle regression found in any of the four mappings. Fix
direction: a table-driven unit test over
`(kind, status) -> active_stage` so a future kind cannot be added silently.

### L2 — LOW (test) `crates/orgasmic-daemon/src/api.rs:20811`, `writer.rs:1734`/`1771`, `daemon_client.rs:651`
The typed-error contract is tested on both ends but the two ends are never
joined, and the *production construction* is not the one under test:

- `api.rs:20812` builds the error with `anyhow::Error::new(...)`, while
  `writer.rs:1734`/`1771` build it with `anyhow!(CommittedSyncUncertainError…)`.
  If `anyhow!` had selected the Display-only (`AdhocKind`) path, the
  `downcast_ref` at `api.rs:1720` would silently fail and every
  committed-but-uncertain close would degrade to a 500
  `"failed to apply changes"` — i.e. exactly the "must not be reported as an
  ordinary failure" requirement breaking with all tests green.
  I proved out-of-band that it does not: with anyhow 1.0.102 (the locked
  version), `anyhow!(TypedError)` selects `TraitKind` and preserves
  `downcast_ref` (`downcast_ok=true` for both the `initial` and `retry`
  variants). **No live bug** — but nothing in the repo pins it.
- The daemon's 503 body and `daemon_http_error_message`'s parser are both
  fed hand-written JSON in their own tests; a rename of the `durability` key
  on one side leaves both green.

Fix direction: assert `downcast_ref::<CommittedSyncUncertainError>()` on the
error returned by `WriterHandle::transaction_multi` inside
`tests/writer_durability.rs:240` (which already drives both uncertain
branches), and add one endpoint-level test that feeds the real serialized 503
body through `daemon_http_error_message`.

### L3 — LOW (design/observability) `crates/orgasmic-cli/src/manager.rs:8706-8718`, `9694-9724`
Requiring an exact `CLOSED_TX == open.tx_id` match is correct per the brief,
but it silently drops legacy replay for close txs written before `CLOSED_TX`
existed. Those closes still land in `open.closed_tasks` through the
task-overlap fallback in `close_matching_dispatch` (`manager.rs:9711-9718`),
so the two sides now disagree about what "closed by this generation" means.

Measured against the production ledger at
`/Users/aspirational/Documents/code/tools/orgasmic/.orgasmic/tx/*.org`:
132 of 600 close txs carry no `CLOSED_TX` (107 of them in 2026-07). **Live
exposure is nonetheless 0**: replaying a full `scan_dispatches` over the real
ledger yields 2 still-open records and **0 partially-closed still-open
records**, and a fully-closed record never reaches this code
(`resolve_close_target` returns early on the already-closed branch,
`manager.rs:1073-1102`). So this can only bite a future multi-task generation
whose partial close predates `CLOSED_TX`, which cannot now be created.

Secondary, and the part I would actually fix: when a task is skipped because
its stage no longer matches, nothing is printed. The operator sees
`closed: … tx=already_closed` and has no signal that a legacy lifecycle leg
was deliberately not replayed. Fix direction: one `eprintln!` naming the
task, its current stage, and the stage the old close expected.

### L4 — LOW (usability) `crates/orgasmic-cli/src/daemon_client.rs:438-443`
The new branch returns a fixed string and discards the 503 body's `error`
field. That field is the only carrier of the writer's actionable remedy —
`"retry the same request_id to sync the retained ledger descriptor without
appending again"` (`writer.rs:74-80`) — plus the ledger path and underlying
sync failure. Note the sibling `refresh_failed` branch two lines above does
append `tx_id`. The brief's requirements are met (it says re-read exact state,
it does not call this success), so this is polish: append the daemon's
`error` text to the message.

### L5 — LOW (perf) `crates/orgasmic-cli/src/manager.rs:8698-8702`
`legacy_close_replay_tasks` calls `read_tx_entries` — a full read+parse of
every `.orgasmic/tx/*.org` — before checking whether `open.closed_tasks` is
even non-empty. On the normal close (nothing pre-closed) this is a second
full ledger parse after `scan_dispatches`, on a path that already holds the
close guard. Fix direction: return early when no task in `tasks` is in
`open.closed_tasks`, before `read_tx_entries`.

### L6 — LOW (residual, pre-existing) `crates/orgasmic-cli/src/manager.rs:8550-8567`
`post_task_state` sends only `to`, with no expected-`from` precondition, so
the new stage check is advisory: a deliberate move landing between the
`read_task_lifecycle` check and the POST is still clobbered. Identical in
shape to `reconcile_torn_closes` (`manager.rs:8582-8630`), which shipped in
EP3H1 — not introduced here. Real fix would be an `if_from` field on the task
state endpoint; out of scope for this correction.

## Objective-by-objective

1. **`legacy_close_replay_tasks` (`manager.rs:8693-8731`)** — all five
   required properties confirmed:
   - reads parsed ledger entries via `read_tx_entries` and matches on
     `extra(entry, "CLOSED_TX") == open.tx_id` **and**
     `entry.task == task`, newest-first (`.iter().rev().find`) — 8706-8718;
   - skips on `LIFECYCLE_FROM` **or** `LIFECYCLE_TO` present — 8720-8722.
     This reliably separates atomic from legacy because `push_lifecycle_extra`
     (`manager.rs:6607-6618`) writes *both* keys unconditionally whenever a
     transition exists, and `cmd_dispatch_close` always passes
     `Some(transition)` (1352, 1362) after `ok_or_else`-bailing when absent;
   - gates on `read_task_lifecycle(...).stage == active_stage` — 8724-8728;
   - sibling behaviour proven by the new test: advanced `TASK-BUNDLE-A` stays
     `DONE`, still-open `TASK-BUNDLE-B` closes to `IN_REVIEW`, and
     `implementer.done` count is 2 (no duplicate legacy close);
   - the separate reconciler (`torn_close_candidates` /
     `reconcile_torn_closes`, `manager.rs:8582-8679`) is untouched by the
     diff and its tests pass (see below).

   Note the eligible set is a strict subset of the old
   `open.closed_tasks.contains(task)` filter, so no close that was previously
   skipped can now fire.

2. **Committed-but-durability-uncertain path** — typed, not text-matched:
   `dispatch_close_writer_error` now takes `anyhow::Error` and branches on
   `downcast_ref::<CommittedSyncUncertainError>()` (`api.rs:1719-1732`). The
   negative half of the test (`api.rs:20820-20826`) proves an untyped
   `anyhow!` with the *same human text* now yields 500, not 503 — the
   impostor path is genuinely closed. The JSON contract is byte-identical
   (`{"error", "committed": true, "durability": "uncertain"}`, `api.rs:1726-1730`),
   and `ApiError::service_unavailable` (`api.rs:19547-19558`) passes `body`
   through verbatim. CLI-side, the 503 is surfaced as a hard `bail!`
   (`daemon_client.rs:418`), so `dispatch-close` fails non-zero and the
   operator is told to re-read exact state before retrying — it is never
   reported as success. Both `CommittedSyncUncertainError` variants
   (`initial`, `retry`) classify identically. Only one production call site
   (`api.rs:17232`) and it passes `anyhow::Error`.

3. **Does the new test represent the regression, and would it fail before?**
   Yes — proven statically, and the proof is tight:
   - `append_partial_close_tx` (`tests/dispatch.rs:721-734`) writes an
     old-format `implementer.done` with `:CLOSED_TX: <start_tx>` and no
     `LIFECYCLE_*`, so `TASK-BUNDLE-A` lands in `open.closed_tasks`.
   - The test then advances A to `done` and asserts it stays `DONE`.
   - Under the old filter, A passes, and `transition_for(A)` is
     `from = Done`, `to = implementer_done_stage(false, false) = InReview`
     (`manager.rs:8329`, `8364-8370`), so `post_task_state` posts
     `state=in_review`.
   - `update_task_state` (`api.rs:17304-17400`) has **no** legality guard —
     any stage to any stage is written — so A would actually be pulled
     `DONE -> IN_REVIEW` and `assert_task_stage(…, "DONE", …)` fails.
     (Even had the daemon refused, the `?` would fail the command and the
     test would still fail.)
   The pre-existing sibling test `bundled_partial_close_retry_is_idempotent_and_visible`
   (`tests/dispatch.rs:3039`) is the positive control: there A is still at
   `IN_PROGRESS` and the legacy replay *does* advance it to `IN_REVIEW`, so
   the recovery path is demonstrably still live, not disabled.
   Focused coverage for the typed API and CLI transport exists but is not
   joined end-to-end — see L2.

4. **Neither weakens the original fix nor expands scope.** The `writer.rs`
   diff is purely the string-error -> typed-error swap;
   `transaction_multi_inner`, `retain_rewrites_after_append`,
   `sync_tx_writer`, and the SyncUncertain caching are all untouched, and the
   two existing durability tests still assert on the same substrings the new
   `Display` impl emits. Diff is 5 source files, no task files, decisions,
   docs, or daemon/install state. The known noncanonical task source-file
   replay observation is out of scope and **does not block shipping** —
   nothing in this diff touches task-file path resolution.

## Open Questions

1. L3: is the `close_matching_dispatch` task-overlap fallback
   (`manager.rs:9711-9718`) still wanted at all, now that the replay path
   requires an exact `CLOSED_TX`? Two definitions of "closed by this
   generation" now coexist. Not blocking (measured exposure 0), but it is the
   kind of divergence that becomes a bug when someone widens one side.
2. L4: was dropping the daemon's `error` text from the operator message
   deliberate (to keep the message terse) or incidental? The retry remedy it
   carries is the one thing an operator most needs at that moment.

## Fix Directions

   `(kind, status)` pairs, so adding a kind cannot silently disable or

   `WriterHandle::transaction_multi` in `tests/writer_durability.rs:240`,

5. Early-return before `read_tx_entries` when nothing is pre-closed (L5).
