* Findings

** HIGH-1 (bug, regression, blocking) — seed-capture errors leak the blocking-scan registration and permanently poison the refresh target

=crates/orgasmic-daemon/src/index.rs:1911-1974= (the new =let scan_seed = { ... }=
block) versus =crates/orgasmic-daemon/src/index.rs:1976= (=let completion =
BlockingScanCompletion { ... }=).

The refactor moved four error exits out of the blocking closure and into the
seed-capture scope, which now runs *before* =BlockingScanCompletion= is
constructed:

- =index.rs:1920= — =unknown project {project_id}= (Project arm)
- =index.rs:1948= / =index.rs:1950= — =unknown project= / =project {id} is not loaded= (Markers arm)
- =index.rs:1960= / =index.rs:1962= — same pair (Artifacts arm)

The worker loop registers the target with =begin_blocking_scan= at
=index.rs:1621=, before calling =build_refresh=. The *only* code path that ever
calls =finish_blocking_scan= (=index.rs:706=) is =Drop for
BlockingScanCompletion= (=index.rs:738-741=). =mark_blocking_scan_timed_out=
(=index.rs:689=) only flips a flag; it never removes the entry, and there is no
reaper. So when =build_refresh= returns via one of the six early exits above, the
=BlockingScanRegistry= entry for that target is never removed.

Every later scan of that same target then fails permanently at
=begin_blocking_scan= (=index.rs:665-671=) with:

: markers:project has a in-flight filesystem scan still running; retry after that stale scan exits

Before this diff those same errors were raised *inside* the closure, i.e. after
the completion guard existed, so the registration always released.

*Impact.* A target that hits one of these exits once can never be scanned again
for the lifetime of the daemon process. For the Markers/Artifacts arms that means
markers, artifacts and their parse errors silently stop loading for that project;
for the Project arm the whole project projection stops loading. The user-facing
symptom is a project stuck with a confusing "scan still running" error that no
retry, reindex or watcher event clears — only a daemon restart does.

*Production reachability.* Both arms are reachable through the existing
board-reload path. =bootstrap_catalog= replaces the board wholesale at
=index.rs:2524= and then evicts by id at =index.rs:2531-2536=:

#+begin_src rust
snap.projects.retain(|id, _| registered.contains_key(id) && !changed.contains(id));
#+end_src

=changed= holds every id whose =BoardEntry= differs from the prior one (path,
branch or status). So a board entry edit — the exact race the existing test
=old_root_refresh_racing_path_change_stays_unloaded_then_loads_new_root= already
models — drops the id from =snap.projects= while a Markers/Artifacts refresh for
it is queued, and the queued scan then takes the =is not loaded= exit and poisons
=markers:<id>= forever. Deregistering and re-registering the same project id
poisons the Project arm the same way via the =unknown project= exit.

*Proof (deterministic, base-vs-HEAD).* Probe test added in a disposable worktree
at =/…/scratchpad/probe= (the reviewed worktree was never modified):

#+begin_src rust
let first = index
    .request_project_load(RefreshTarget::Markers("project".to_string()))
    .await.unwrap_err().into_message();
assert_eq!(first, "project project is not loaded");
index.ensure_project_loaded("project").await.unwrap();   // now genuinely loaded
let second = index
    .request_project_load(RefreshTarget::Markers("project".to_string()))
    .await.map_err(ProjectLoadRequestError::into_message);
assert!(second.is_ok(), "…: {second:?}");
#+end_src

- On =245f202= (HEAD): *FAILED* —
  =markers target was poisoned by the leaked registration: Err("markers:project has a in-flight filesystem scan still running; retry after that stale scan exits")=
- On =e010cf8= (base), same probe adapted to the base signature: *ok*

Classification: regression, introduced by this diff.

** MEDIUM-2 (correctness / UI contract) — a coordinator-only Delayed project is still reported as =failed= on the wire the UI actually consumes

=crates/orgasmic-daemon/src/api.rs:2580-2583= and =crates/orgasmic-daemon/src/api.rs:2602-2612=.

=get_tx= puts every =Err= from the load call into =failures= and renders it as
=failed=[…]= in =x-orgasmic-project-coverage=. A coordinator-only queue timeout
returns =Err= just like a real path failure, so a project whose *load state* is
correctly =Delayed= is nonetheless published to the UI as a failed project.

The new =delayed=[…]= segment was added only to the =/parse-errors= coverage
header (=api.rs:13464-13485=) and =delayed_projects= only to =/daemon/status=
(=api.rs:8080=). =/tx= — the endpoint the NotificationBell polls
(=NotificationBell.tsx:101=) — has no delayed concept.

Two concrete consequences:

1. Acceptance criterion "queue-only delay is represented honestly without marking
   an unscanned project as path-failed" holds for =ProjectLoadState= and
   =/daemon/status=, but not for =/tx=. Under queue pressure the notification
   reads "Activity coverage is partial … failed=[proj]" for a project that was
   never scanned and has no diagnosed path problem.
2. It interacts badly with the new dismissal. =txCoverageDismissalKey=
   (=NotificationBell.tsx:68-74=) keys dismissal on the normalized *failed* set.
   A user who dismisses a transient queue-delay notification for =failed=[a,b]=
   has thereby permanently dismissed the notification for a *genuine* load
   failure of exactly =[a,b]= later on. The user is never told again.

** MEDIUM-3 (a11y / design, UI honesty) — the board paints the new Delayed state as a red failure with a neutral badge

=ui/src/components/BoardView.tsx:43-47= and =ui/src/components/BoardView.tsx:157-161=.

=loadVariant= has no =delayed= arm, so a Delayed project falls through to
=outline= — the same badge tone as =ready= and =unloaded=. Meanwhile
=BoardView.tsx:157= renders =p.load.error= unconditionally, for any state, in
=text-destructive=. =record_project_load_delay= (=index.rs:1330-1333=) always
stores the coordinator message in =load.error=.

Symptom: under queue pressure the board shows a project with a calm neutral
"Delayed" badge next to red error text reading

: project:<id> coordinator wait timed out after 8.0s while queued behind slow scans; this does not diagnose the project path or macOS permissions

which is precisely the "this is not a path failure" message rendered in failure
red. =StatusView.tsx:94-101= got the honest treatment; =BoardView= did not.

Same code path also repaints a genuinely *Ready* project red: when
=record_project_load_delay= sees =has_last_good= it sets state =Ready= but still
assigns =load.error= (=index.rs:1326-1333=). That half is inherited from
=record_project_load_failure=, but this diff adds a new, non-failure source for it.

** LOW-4 (perf) — the bounded seed clone moved from the blocking pool onto the async executor

=crates/orgasmic-daemon/src/index.rs:1921= (=seed.projects.get(project_id).cloned().map(Box::new)=)
and =index.rs:1935= (=seed.repo_urls.clone()=).

Previously the =ProjectIndex= clone happened inside =spawn_blocking=. It now runs
on a Tokio worker thread while holding the index read guard. This is still a large
net win over the old =read_owned= guard held across the whole scan, and it is the
correct shape for the lock-drop requirement, but it does put an O(project-size)
memcpy on the runtime and extends the read-guard hold (which blocks publication's
write lock) by that amount. Worth measuring on the largest real project before
this is considered settled. No test covers the cost.

** LOW-5 (test) — the new late-waiter test has a 250 ms margin against its own scan timeout

=crates/orgasmic-daemon/src/index.rs:3932-3988=
(=late_waiter_after_batch_capture_joins_the_in_flight_scan=).

The test sets =set_refresh_timeout(800ms)= and then sleeps 550 ms while the gate
is held. The test gate lives *inside* =build_refresh= (after =built_rx.await=),
and =build_refresh= is wrapped in =tokio::time::timeout(scan_timeout, …)= at
=index.rs:1634-1638=, so the gated sleep is charged against the 800 ms scan
timeout. The margin is 250 ms. On a loaded aggregate run this can trip the scan
timeout and fail the =generation == 1= assertions.

I ran it 15/15 green in isolation on this machine, so this is a robustness note,
not an observed failure. Widening the timeout (or shortening the sleep) removes
the coupling.

** LOW-6 (test gap) — the "normalized" claim in the dismissal key is not tested

=ui/src/components/notifications/NotificationBell.tsx:69-72= sorts the failed ids
so that =failed=[b,a]= and =failed=[a,b]= collapse to one dismissal key. The new
test =ui/src/components/__tests__/ParseErrorCoverage.test.tsx:189-228= only
covers identical-string and different-set cases. The reordering case — the whole
reason =.sort()= is there — is unexercised.

** LOW-7 (security, low impact) — the captured timeout value is not newline-safe in the systemd unit

=crates/orgasmic-cli/src/daemon_service.rs:1041-1047=. =systemd_quote_env= escapes
=\= and ="= but not newlines. =captured_project_scan_timeout=
(=daemon_service.rs:385-387=) deliberately captures the value raw, so
=ORGASMIC_PROJECT_SCAN_TIMEOUT_SECS=$'5\nExecStartPre=/bin/sh -c …'= writes extra
directives into the generated unit. This is self-inflicted (the user's own env,
the user's own unit) and the same helper already handles machine-derived =PATH=,
but this diff is the first to route arbitrary user-supplied text through it.
The launchd renderer is fine — =xml_escape= plus XML's newline tolerance.

** LOW-8 (design) — dismissal keys accumulate without bound in localStorage

=ui/src/components/notifications/NotificationBell.tsx:110-116=. Each distinct
failed-project set writes a new permanent key under
=orgasmic.notifications.dismissed.v2=. Same class as the existing
=question:=/=parse:= keys, so not a new defect, but the new key is set-shaped and
therefore combinatorial rather than entity-shaped.

* Open Questions

1. HIGH-1: should the fix construct =BlockingScanCompletion= immediately after
   =begin_blocking_scan= succeeds in the worker loop (=index.rs:1621=) and pass
   it into =build_refresh=, or keep it in =build_refresh= but hoist it above the
   =scan_seed= block? The former also covers any future early exit added between
   the two points, and is what I would pick.
2. MEDIUM-2: is a =delayed=[…]= segment on the =/tx= coverage header acceptable
   for this task's scope, or is that a follow-up? Note the dismissal-key
   suppression consequence is the sharper half of the finding and needs a
   decision either way — keying dismissal on "failed ∪ delayed" would not fix it.
3. LOW-4: is there a measured upper bound on =ProjectIndex= clone cost for the
   largest registered project? If it is milliseconds, this is closed; if it is
   tens of milliseconds, the read-guard hold is worth a second look.

* Aggregate-failure causality

Classified evidence for this HEAD, per the manager: the =XjEmKh= aggregate ran
1,897 passed / 3 failed / 15 ignored / 1 billed filtered, with all four
=index::=-git tests green, and only the two known unregistered supervisor
process-probe races
(=a_probe_child_that_exits_leaving_a_descendant_on_stdout_is_bounded_and_killed=,
=a_probe_child_that_never_exits_is_killed_and_reaped_at_the_deadline=) plus the
registered TASK-QCG6J (tmux close-guard) flake
=explicit_reattach_tmux_is_fenced_out_of_a_worktree_a_close_guard_holds= failing
in-suite and passing in isolation.

Tracing causality rather than dismissing by path:

- All three live in the same =orgasmic-daemon= lib test binary as the changed
  =index.rs= and =api.rs=, so a shared-binary load argument is admissible and I
  did consider it. All three are *deadline* tests — process-probe reap deadlines
  and a tmux close-guard fence — i.e. wall-clock sensitive, and their failure mode
  is a missed deadline, not a wrong value.
- The diff does add in-binary wall-clock and thread pressure: the new
  =late_waiter_after_batch_capture_joins_the_in_flight_scan= is
  =multi_thread(worker_threads = 2)= and holds a gate for 550 ms. That is a
  plausible marginal aggravator for deadline tests running concurrently, and it is
  the only mechanism by which this diff could touch them.
- It is not a *cause*: none of the three reads the index, the load-state machine,
  the coverage headers, the service renderers or the UI. There is no data or
  control-flow edge from the changed code into =supervisor.rs='s process probe or
  =api.rs='s tmux close guard. Both supervisor tests fork real child processes and
  assert on reap timing; the tmux test is gated on a session fence.
- Classification: *flaky (pre-existing, load-sensitive)*, with this diff a possible
  marginal load contributor and not a logical cause. Evidence: they pass in
  isolation; two are unregistered and one is registered to TASK-QCG6J; the changed
  code has no reachable edge into either subsystem.

* Fix Directions

1. *HIGH-1 (blocking).* Make the completion guard cover the seed capture. Simplest
   correct shape: construct =BlockingScanCompletion= in the worker loop the moment
   =begin_blocking_scan= returns =Ok(token)= (=index.rs:1621-1623=) and move it
   into =build_refresh=, so any early exit — present or future — releases the
   registration on drop. If it must stay inside =build_refresh=, hoist the
   =let completion = …= binding above the =let scan_seed = { … }= block
   (=index.rs:1911=) and =drop(completion)= is then handled by the closure move as
   today. Add a regression test per arm asserting that a rejected seed capture
   leaves the target immediately re-scannable — the probe in this report is a
   ready-made template. Also worth considering: make the registry entry's lifetime
   a value the caller cannot forget, e.g. have =begin_blocking_scan= return the
   guard itself rather than a bare token.
2. *MEDIUM-2.* Split the coordinator-delay case out of =get_tx='s =failures= map
   into a separate =delayed= map and emit a conditional, percent-encoded
   =; delayed=[…]= segment on the =/tx= coverage header, mirroring
   =api.rs:13465-13470=. Then key =txCoverageDismissalKey= on the failed set only
   and render delay as its own non-dismissible informational row, so dismissing a
   queue delay can never suppress a later real failure for the same project set.
3. *MEDIUM-3.* Give =loadVariant= (=BoardView.tsx:43=) an explicit =delayed= arm
   (=secondary=, matching =loading=, reads as "in progress" not "broken"), and gate
   the red =load.error= text at =BoardView.tsx:157= on
   =p.load.state === 'failed'=, rendering the message in =text-muted-foreground=
   for =delayed= and for the last-good =Ready=-with-error case.
4. *LOW-5.* Raise the test's =set_refresh_timeout= well above the gated sleep (e.g.
   3 s) so the assertion depends on coordinator behavior rather than on beating a
   scan timeout.
5. *LOW-6.* Add one case to the dismissal test where the second response lists the
   same ids in a different order and asserts the row stays dismissed.
6. *LOW-7.* Reject or strip control characters in =captured_project_scan_timeout=
   before rendering, or escape newlines in =systemd_quote_env=.
7. *LOW-4 / LOW-8.* Measure, then decide. Neither blocks.
