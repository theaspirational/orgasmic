    (new). Reads `project_sessions_dir(project_root)` and indexes every `*.jsonl`
    through the existing `index_recovery_origins_in_session`. `None` is a THIRD
    answer, not "nothing found": a sessions directory that will not open, or a
    directory entry that will not read, leaves completeness unresolved.
  - `matching_origin_links(...)` (new, extracted). The link filter that
    `resolve_authoritative_recovery_claim` and `reconstruct_or_quarantine` both
    already had inline, verbatim.
  - `resolve_authoritative_recovery_claim`, committed branch: no longer consults
    `indexed_origins` **at all**. It enumerates, then accepts only `[only] if

    the authoritative set.

## The reproduction, and what it turned up

Driving `RunCatalog` + `collect_recovery_origin_index` with two
daemon-HMAC-authenticated replacements for one origin and **both** live records
invalidated: the collector returns an empty slice, and at the 724973d predicate
the resolver returns `Valid(...)` naming one of the two. Captured in full in the
red log — `origin_run_id: "run-hidden-origin"`, `replacement_run_id:
"run-20260808T122822-57acc21225f040cbb686a897156c1f14"`, with
`run-hidden-second` equally authenticated and never discovered.

**The finding I did not expect, and it changes the fix.** A **one**-element
index states no more about completeness than an empty one. The catalog can hold
the record for the replacement this claim names while a *second* authenticated
replacement's record sits invalidated — that needs one live appender rather than
two, so it is the **likelier** arrangement, not the rarer. Enumerating only on a
zero match, as acceptance 1(a) literally reads, would have closed the hole at
zero links and left it open at one.

This is pinned as its own test and its own red:
`a_partially_loaded_index_does_not_confirm_uniqueness`. It is the reason the
committed branch ignores `indexed_origins` entirely rather than treating a
non-empty fast index as a shortcut. Ruling 2 governs it — *unknown is not
permission* — and a fast index of any size is unknown about what it was not
holding.

**Traded knowingly (ruling 3):** one bounded lifecycle scan
(`SessionScanBudget::DEFAULT`, ≤192 KiB) per session file under the ONE project,
per committed-claim resolution on the `apply_recovery_claim_to_run` inventory
path — where before it was zero. Scoped to one project, never the board. A
committed claim exists only for a failed-recoverable run mid-rescue, and the
non-Valid outcome quarantines the claim, so a claim that cannot be confirmed
pays the enumeration once and then resolves through the `Ok(None)` path. The
repeated cost is the *Valid* case, which is the narrow post-append pre-refresh
window measured last round. I did not take the cheaper option (b) — making
catalog dirty-generation observable — because it couples the resolver to the
catalog and the safety argument then rests on that coupling being right.

## Residual Risk

- **Bounded-scan truncation, pre-existing and unchanged.** The enumeration uses
  `index_recovery_origins_in_session`, a `SessionScanBudget::DEFAULT` scan
  (128 KiB head + 64 KiB tail), while `verify_committed_claim_against_session`
  does a full `read_path`. A `RecoveryOrigin` envelope sitting outside both
  windows of a huge replacement transcript would not index, and the claim would
  now quarantine where before the fix it was accepted on silence. This is the
  pre-724973d predicate's exposure, not a new one — the same indexer fed the
  same uniqueness test before this task — and `RecoveryOrigin` is written near
  the head of the replacement's own session. Not measured against a >192 KiB
  replacement transcript.
- **Inventory latency**, quantified above. Not measured against the real
  198-file board; the estimate is ~198 × ≤192 KiB per committed-claim
  resolution. If that proves material, route (b) is the follow-up, not a
  reversal of the safety property.
- **`reconstruct_or_quarantine` reached from `Ok(None)` / `CorruptClaim` still
  decides from the passed `indexed_origins`.** A silent catalog there returns
  `Missing` and the caller mints a fresh claim. Out of scope: the task and the
  review both concern the committed branch, and I did not want to change
  reconstruction semantics unasked. Worth a look by whoever owns the next round.
- **Not run:** workspace-wide tests, MSRV, non-Unix. `cfg(not(unix))` paths in
  the touched code are unexercised on this host; the new enumeration itself is
  cfg-independent.
- The suite ran on a host the run-tests gate judged **calm** (rate 0.7012), but
  the watchdog recorded a genuine 20-second syspolicyd burst peaking at **796.3%**
  as test execution began, decaying to 167% and then to single digits. Hot
  streak reached 2 of the 6 samples required to kill. Consistent with the
  gotchas' "sustained-load precursor" model; no action taken, recorded because
  the peak is well above the 400% line and only its duration kept it under the
  guard.
