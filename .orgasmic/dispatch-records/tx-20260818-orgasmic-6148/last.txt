# TASK-ZKZBF (remaining --property surfaces) — reviewer report

## Verdict

**REJECT (changes requested), scoped.** The fix is correct, the tests are real,
and the injection proof replays PASS on my own run. But the task is an *audit*,
and the audit missed one instance of the audited class on a surface it was
explicitly assigned (`node prop set`, key `ID` on the non-task layers) — and
the diff ships a new per-layer key table that lists `ID` as a legal Project /
Handoff schema key, actively advertising it. One MEDIUM in-scope gap, one
MEDIUM scope-adjacent gap, three LOWs. No regression found; every acceptance
gate I re-ran independently is green.

Manager's audit: claims 1, 2, 3(mechanically true, see LOW-1), 5, 6, 7 all hold
under attack. **Claim 4 is false** — create and revise DO diverge, on `ID`.

## Findings

### MEDIUM-1 (correctness) — `node prop set` writes `:ID:` on every non-task layer; the key set diverges by layer
`crates/orgasmic-daemon/src/api.rs:15476` (validation loop), `:15637` (apply)

The new loop routes `NodeLayer::Task` through `validate_task_property_keys`,
which refuses `ID` by name ("task identity is immutable…", `:16365`). Every
other layer falls to the `other =>` arm, which runs only
`validate_drawer_property_key_case` — a case check with no refusal table. `ID`
is already uppercase, so it passes, and `:15638` upserts it.

`crates/orgasmic-core/src/org.rs:284`: `find_by_id` matches on `property("ID")`.
So the write re-keys the node.

    orgasmic node prop set term_XXXXX ID term_YYYYY     # 200, identity rewritten
    orgasmic node prop set dec_XXXXX  ID dec_YYYYY      # 200, identity rewritten

Every `RELATES_TO` / `GLOSSARY_REFS` / `PARENT` / task `IMPLEMENTS` reference to
the old id dangles afterwards, and `--force` is not required — the check is
unconditional but the arm has nothing to check.

Worse for the audit's own stated goal: `node_layer_schema_property_keys`
(`:16412`) *lists* `"ID"` as a Project key and a Goal/Handoff key, so the
refusal text for a miscased key on those layers ends with "Project keys the
schema reads: BRANCH, DEFAULT_BRANCH, **ID**, LOCAL_PATH, PATH, STATUS" — the
new code names `ID` as something to pass.

Same divergence one route over: `create_graph_heading` refuses `ID` by name
(`:14652`), `mutate_graph_heading` (decision/glossary revise, `:14837`) got only
the case check. This is exactly what manager claim 4 says cannot happen
("create/revise cannot diverge").

Fix direction: hoist an `ID`-is-derived refusal to `validate_drawer_property_key_case`
(or a sibling called from all three sites), and drop `"ID"` from the
Project/Goal/Handoff key lists. One guard, three callers — the same shape the
task already used for the case check.

### MEDIUM-2 (correctness, scope-adjacent) — `tx record --extra` is the same defect, on the same drawer `dispatch-close --property` now guards
`crates/orgasmic-core/src/tx.rs:292`, `crates/orgasmic-cli/src/manager.rs:9783`, `:9562`

The worker's decided rule for tx metadata — "open key vocabulary, CLOSED case
rule, refused at parse" — was implemented on `dispatch-close --property`
(`parse_close_property`, `manager.rs:9942`) and nowhere else.
`tx record --extra` writes the same ledger through `validate_property_key`,
which bans only empty / reserved / colon / whitespace / control. Case is not
checked.

`extra()` (`manager.rs:9783`) is a byte-exact `got == key`. So:

    orgasmic tx record --type manager.dispatch_started --task TASK-X --extra kind=implementer

writes `:kind: implementer`, `dispatch_record_from_entry` (`:9562`) hits
`extra(entry, "KIND")?` and returns `None`, and the dispatch is **invisible to
`dispatch-close` entirely** — not "closes wrong", *unfindable*. The task's own
new test stages a dispatch with exactly this command
(`node_property_silent_drop_cli.rs:519-533`, uppercase), so the miscased form is
one keystroke away from a documented workflow.

I accept this sits just outside the five named surfaces. I file it MEDIUM
anyway because the task's per-surface question is "does the key set diverge
from a sibling verb", the answer here is yes, and the worker had to *invent* the
tx-metadata rule to close the dispatch-close surface — applying it to one of the
two verbs that write that drawer is the divergence the task exists to find.

### LOW-1 (design/disclosure) — `PropertyNotFound` 400 returns the absolute on-disk path and omits what the drawer actually has
`crates/orgasmic-daemon/src/api.rs:15649`

`OrgRewriter::new(&file, path.to_string_lossy())` (`:15568`) carries the
absolute path, and `OrgError::PropertyNotFound`'s Display is
`"{file}: property {key} not found on heading {heading}"` (`org.rs:176`). So the
new body is e.g. `/Users/…/proj/.orgasmic/tasks/todo.org: property PRODUCES not
found on heading TASK-X`.

That contradicts this file's own convention twice:
- `org_parse_bad_request` (`api.rs:1658`) deliberately `tracing::warn!`s the
  path and returns a path-free body.
- `crates/orgasmic-core/src/tx.rs:226`: *"Never a path: this string can reach an
  API client inside a parse error."*

And it is weaker than its own sibling. `unknown_section_error` (`api.rs:15169`)
— the not-found error for sections — names the node and lists what it *does*
have. Since miscased keys are now refused earlier, this message only fires for a
genuinely absent canonical key, which is precisely the case where "the drawer
has: PRIORITY, DEPENDS_ON" is the useful answer. Mirror `unknown_section_error`
and the path disclosure goes away with it.

### LOW-2 (design) — unset refusals talk about a flag the command doesn't have
`crates/orgasmic-daemon/src/api.rs:15505`

The `RemoveProperty` / Task branch calls `task_property_key_refusal`, whose
sentences are all phrased `` `--property KEY=…` is refused: … ``. So
`orgasmic node prop unset TASK-X STATE` answers with a message about
`--property STATE=…`. `node prop unset` has no `--property` flag.

### LOW-3 (design) — the case refusal steers into a second refusal
`crates/orgasmic-daemon/src/api.rs:14652` vs `:14663`

`glossary create --property id=x`: the `ID` guard checks the exact key `"ID"`,
misses `"id"`, so the case check fires and says "Use `ID`" — and `ID` is then
hard-refused by name. Two round trips to learn one rule. Checking the guard
case-insensitively (or listing `ID` in the refusal-worthy set before the case
check) collapses it to one.

Also dead, while you are in there: `api.rs:15521`'s inner
`NodeLayer::Task | NodeLayer::Goal => "Task"` is unreachable — `Task` is handled
by the arm above and `Goal` is rejected at `:15479`. Were `Goal` ever reachable
it would print the label "Task" beside Goal's key list.

## Open Questions

   yes, MEDIUM-1's fix is "state the rule and route it through a verb", not a
   flat refusal — but the audit stated nothing either way, which is the gap.
2. `--status aborted` + `--property` is now a hard error. I found no doc, script
   or historical invocation that used it (grepped `shipped/`, `.orgasmic/`,
   `dispatch-records/*/last.txt`), and `close_aborted_request` (`manager.rs:6763`)
   provably never recorded them, so nothing is lost. Confirming there is no
   out-of-repo manager habit is a manager call, not mine.

## Fix Directions

1. **MEDIUM-1** — put the `ID`-is-derived refusal in
   `validate_drawer_property_key_case` (it already receives the layer label and
   key list) so `create_graph_heading`, `mutate_graph_heading` and
   `post_org_node_edit` inherit it from one place; delete `"ID"` from the
   Project and Goal/Handoff entries of `node_layer_schema_property_keys`. Then
   the create-side special case at `api.rs:14652` collapses into the shared
   check and LOW-3 disappears with it. Test: `node prop set term_… ID term_…`
   refused by name, `glossary.org` byte-identical afterwards.
2. **MEDIUM-2** — either apply the closed-case rule in `validate_property_key`
   (`core/tx.rs:292`) so every tx writer inherits it, or state explicitly on the
   task record why `dispatch-close` is fenced and `tx record` is not. My
   preference is the former: it is one `if` in the function both verbs already
   call, and it makes the rule the worker decided actually true of the ledger.
3. **LOW-1** — mirror `unknown_section_error`: name the node, list the drawer
   keys it has, drop the path from the body and keep it in the `tracing::warn!`
   that is already there.
4. **LOW-2** — thread a verb noun into `task_property_key_refusal`, or give the
   unset path its own one-line phrasing.
