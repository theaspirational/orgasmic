Reviewed: implementer commit `c233a1c` (merged `7943072`) against base `67873a3`,

# Findings

## M1 (MEDIUM, bug/usability) — the documented scan-timeout override cannot reach the managed daemon

`crates/orgasmic-cli/src/main.rs:157-159` documents
`ORGASMIC_PROJECT_SCAN_TIMEOUT_SECS` on `orgasmic serve`, and
`crates/orgasmic-daemon/src/index.rs:497-511` reads it once at `Index::new`.
But the service units hardcode a closed env dict:

- `crates/orgasmic-cli/src/daemon_service.rs:846` (macOS LaunchAgent
  `EnvironmentVariables`) emits only `ORGASMIC_HOME`, `PATH`, and the log-mirror
  key.
- `crates/orgasmic-cli/src/daemon_service.rs:934-936` (systemd) emits the same
  three `Environment=` lines.
- `ServiceSpec` (`daemon_service.rs:73-80`) has no field that could carry it.

launchd and systemd do not inherit the invoking shell's environment. Failure
scenario: an operator with a large cold monorepo reads `orgasmic serve --help`,
sets `export ORGASMIC_PROJECT_SCAN_TIMEOUT_SECS=60`, runs `orgasmic daemon
restart`, and the daemon still uses 5 s — with no diagnostic, because the
warn-on-invalid path never fires for an absent variable. The only paths that do
honor it are a hand-run `orgasmic serve` and the ad-hoc auto-start in
`crates/orgasmic-cli/src/daemon_lifecycle.rs:454-465`, which inherits the parent
env but only when no daemon is already running.

Acceptance criterion 7 ("explicit supported override for legitimately large or
cold repositories") is therefore met for `serve` but not for the normal
installed deployment.

Fix direction: add the variable to `ServiceSpec` and to both unit renderers,
sourced from the environment at `daemon start`/`install` time (or from a
persisted `~/.orgasmic/user` setting), and state in `--help` that the value is
captured when the service is installed.

## M2 (MEDIUM, correctness/availability) — an OS `stat` runs while the owned index read guard is held

`crates/orgasmic-daemon/src/index.rs:1769` takes
`self.inner.clone().read_owned().await` and moves the guard into the blocking
closure. In the `RefreshTarget::Project` arm, `orgasmic_dir.is_dir()`
(`index.rs:1790`) executes **before** `drop(seed)` (`index.rs:1819`). `is_dir()`
is a `stat(2)`; on a hung network mount or a wedged FUSE path it blocks
indefinitely.

`tokio::sync::RwLock` is fair: one pending writer blocks all subsequent readers.
Failure scenario: project `X` points at a stale SMB mount. Its scan thread parks
in `is_dir()` holding a read guard. The next `publish_refresh` for any healthy
project takes `inner.write()`, queues behind that reader, and every later
`ensure_project_loaded` read then queues behind the writer — the whole index
stalls on one bad path, and the new stale-scan guard makes the stall persist for
the full duration of the hung syscall.

This is pre-existing (the diff moved the guard into the closure but did not
introduce the `is_dir()` ordering), yet audit requirement 1 explicitly demands
"no index read/write lock is held across OS work", so it is not closed.

Fix direction: hoist the board lookup and `.orgasmic` existence check to plain
cloned data and drop `seed` before any filesystem call, i.e. move `drop(seed)`
above the `orgasmic_dir.is_dir()` check in the Project arm (the Markers,
Artifacts, and HomeTx arms already do OS work only after the drop).

## M3 (MEDIUM, correctness) — the coordinator budget covers lane depth but not the coordinator's own second settlement round

`request_project_load` (`index.rs:1137-1147`) sizes the budget from lane depth
only. But `spawn_refresh_worker` settles only the batch captured at
`index.rs:1408-1427` and then loops when `state.has_work()`
(`index.rs:1599-1601`). A waiter that registers **after** `captured` is taken is
not settled by the in-flight scan; it waits for the remainder of that scan plus
a whole second scan.

Failure scenario, default settings: scan A for project `P` starts and runs 4.9 s
(slow but successful). A waiter arrives at t=4.8 s; `lane_depth` is 1, so its
budget is 8.2 s. Scan B then runs another 4.9 s. Total wait ≈ 9.9 s > 8.2 s, and
the waiter gets `coordinator wait timed out ... queued behind slow scans` and is
recorded `ProjectLoadState::Failed` even though nothing was queued behind
anything. This is strictly better than the old flat 8 s, so it is not a
regression — but acceptance criterion 1's "cannot exhaust a fixed coordinator
budget before its own bounded scan runs" is only fully true for the lane
dimension.

Fix direction: add one wave (`waves + 1`) to cover the round-boundary case, or
have `request_project_load` recompute/extend its deadline when it observes that
its own generation was not the captured one.

## M4 (MEDIUM, perf) — unscoped `/tx` now retries every failing project on every request, and the UI polls it

Before this change, unscoped `GET /tx` aborted on the first project that failed
to load. Now `api.rs:2559-2575` continues, and `ensure_project_loaded`
(`index.rs:1011-1029`) short-circuits only for `Ready` projects — a `Failed`
project starts a fresh bounded scan on **every** call, with no negative caching
or backoff.

`ui/src/components/notifications/NotificationBell.tsx:86-93` now calls
`fetchTxWithCoverage(200)` (unscoped `/tx`) and refreshes it from
`useEventStream` on every `graph`, `manager`, and non-`run_event` `run` event
(`NotificationBell.tsx:110-126`).

Failure scenario: a board with three permanently broken project paths. Each
daemon graph event makes the bell re-request `/tx`; the handler serially retries
all three, each costing up to the 5 s scan timeout, so a single request occupies
~15 s and the core scan permits, while an event burst queues several of them.
Requirement 8's "routine notification polling must stay scan-free" holds only
once every project is `Ready`.

Fix direction: give `ProjectLoad` a cooldown so a recently failed project is
skipped (reported straight into `failures`) for a short interval, and/or give
the unscoped aggregation one overall deadline rather than N sequential
per-project budgets.

## M5 (MEDIUM, test) — the coordinator budget's wiring is untested; only its arithmetic is

`index::tests::production_first_load_budget_covers_every_queued_scan_wave`
(`index.rs:3741-3772`) calls `first_load_coordinator_timeout` directly with
literal arguments. Nothing exercises the `lane_depth` computation at
`index.rs:1137-1141` — the `state.running && shares_scan_lane` filter, the
inclusion of the requesting target itself, or `HomeTx` falling through
`shares_scan_lane` to depth 0. A regression that passed the wrong depth (e.g.
counting only *other* targets, or dropping the `running` filter) would keep this
test green while reintroducing exactly the starvation the task exists to fix.

Fix direction: add a multi-threaded tokio test that seeds N projects, gates
several project scans open, and asserts a later healthy project's waiter still
resolves — i.e. asserts the observed budget, not the formula.

## L1 (LOW, usability/a11y) — the partial-coverage notification is permanent and non-dismissible

`NotificationBell.tsx:131-142` pushes the `tx-coverage-partial` row without the
`!dismissed.has(...)` filter every other row uses
(`NotificationBell.tsx:145-147`), and `total()`/`sectionTotal()` now count it
(`NotificationBell.tsx:69`, `NotificationPopover.tsx:29-30`).

Failure scenario: one project on the board is permanently unreadable. The bell
shows "1 unread" forever, the row cannot be dismissed, and the badge stops being
a signal that something new happened.

Fix direction: give the row a dismiss action keyed by the failed-project set, so
it returns when the set changes but not while it is unchanged.

## L2 (LOW, correctness/observability) — a pure queue delay marks the project `Failed`

`ensure_project_loaded` routes the new queue-delay string through
`record_project_load_failure` (`index.rs:1043-1047`), which sets
`ProjectLoadState::Failed` (`index.rs:1185-1190`) for a project that was never
actually scanned. The message itself is honest and no longer blames the path or
macOS permissions (`index.rs:528-538`), which is what criterion 1 required — but
the *state* still reads as a project defect in the catalog and UI.

Fix direction: keep the honest error string but leave the state `Loading` (or
add a distinct `Delayed`) when the failure came from the coordinator queue
rather than from a scan.

## Non-findings, checked and clean

- Async timeout is genuinely independent of OS work: the blocking closure now
  reports through a `oneshot` (`index.rs:1911-1917`) and the `JoinHandle` is
  detached, so `tokio::time::timeout` at `index.rs:1491` fires on schedule.
- At most one stale blocking scan per `RefreshTarget`: `begin_blocking_scan`
  refuses a second registration (`index.rs:632-662`).
- The guard cannot leak or release early: `BlockingScanCompletion`
  (`index.rs:707-720`) is constructed outside and moved *inside* the closure, so
  it drops only when the OS work returns; `finish_blocking_scan` is
  token-matched (`index.rs:681-704`), so a late completion cannot clear a newer
  registration.
- Late results cannot publish: the closure only `send`s; publication happens in
  the awaiting task (`index.rs:1543-1549`), which is gone after a timeout.
- Authorization precedes every load in both aggregators: `api.rs:2544-2557` and
  `api.rs:13793-13803`.
- Scoped requests stay exact and fail-fast: `api.rs:2566-2570` and
  `api.rs:13810-13814`.
- Wire compatibility: `/tx` keeps its bare array body; the coverage header is
  percent-encoded per id by `coverage_project_ids` (`api.rs:13464-13480`), so
  `loaded=[a,b]` is unambiguous, and it is already CORS-exposed at
  `api.rs:857`. `MarkerFilesResponse` gains only additive `projects`/`failures`
  (`api.rs:13777-13781`).
- `reindex` honesty: `post_reindex` already aggregated `failures`
  (`api.rs:13500-13516`); the CLI prints the JSON then bails only for the
  unscoped form (`main.rs:2459-2466`), so scoped behavior is unchanged.
- Blocked counts: resolution is Done/Cancelled by project-local task id
  (`index.rs:809-845`), with no cross-project load.
- Timeout-test fidelity: `apply_blocking_refresh_delay` is invoked inside the
  blocking closure *after* `drop(seed)` in every arm (`index.rs:1819-1821`,
  `1853-1854`, `1877-1878`, `1893-1894`), so it delays real OS-phase work with
  no lock held, and the test asserts scans_total stays 1 across the retry and
  that the late result never publishes (`index.rs:3763-3849`).
- Eager/lazy boundary: no recursive or eager full-board discovery returned.
  Full-board marker coverage remains behind the explicit `__coverage__` action
  in both CLI (`main.rs:2412`) and UI (`api.ts:277-282`).

# Open Questions

1. Is the intended supported channel for the scan-timeout override the service
   unit (M1), a `~/.orgasmic/user` setting, or `launchctl setenv`? The answer
   changes whether M1 is a code fix or a docs fix.
2. Should a project whose scan permanently hangs stay guarded indefinitely, or
   should the guard expire after some multiple of the scan timeout and allow one
   fresh attempt? The current choice is deliberate and documented in the
   implementer's residual-risk note, but it is a policy decision.
3. Should `x-orgasmic-project-coverage` carry failure *reasons* for `/tx` (the
   UI currently receives only ids in the detail string and hardcodes
   `failures: {}` at `ui/src/lib/api.ts:314`), or is the ledger's id list
   sufficient?

# Aggregate-Failure Causality Assessment

The implementer reported 1,892 passed / 3 failed / 15 ignored / 1 filtered.

- `api::tests::recovery_reattaches_tmux_session_when_handle_exists` — matches
  registered TASK-X0PV1 (tmux reattach). Not touched by this diff.
  Classification: **known registered flake**.
- `supervisor::tests::a_probe_child_that_never_exits_is_killed_and_reaped_at_the_deadline`
  and
  `supervisor::tests::a_probe_child_that_exits_leaving_a_descendant_on_stdout_is_bounded_and_killed`
  — both live in `crates/orgasmic-daemon/src/supervisor.rs:10951` and `:11011`.
  `git diff --name-only 67873a3 c233a1c` does not include `supervisor.rs`; the
  diff touches only `index.rs`, `api.rs`, the CLI, and the UI. Both assert wall-
  clock bounds (a 400 ms deadline with 3 s slack, and a 5 s pid-disappearance
  wait), which is a host-contention failure signature. I reran both on this tree
  and **both passed** (0.49 s, above). Classification: **pre-existing,
  timing-sensitive, not caused by this diff.**

  One honest caveat, stated because it is a real mechanism rather than a
  dismissal: this diff does add contention pressure to a full-suite run. The new
  `timed_out_blocking_scan_guards_retries_until_os_work_exits` test parks a real
  OS thread in `std::thread::sleep(3s)` (`index.rs:2185-2195` via the test hook),
  and `build_refresh` now *detaches* its `spawn_blocking` handle
  (`index.rs:1911-1915`), so a timed-out scan's pool thread outlives the test
  that started it. Each `#[tokio::test]` owns its own runtime and blocking pool,
  so there is no shared-pool starvation path — the coupling is only host CPU and
  thread pressure under `cargo test`'s default parallelism. That is enough to
  make an already-marginal 400 ms deadline flakier, but it is not a correctness
  link, and the two tests fail on hosts under load independently of this change.

  Recommendation: register both supervisor tests in the flake registry with the
  timing rationale rather than leaving the aggregate gate red and unexplained.
  They are outside this task's write scope, so that is a separate ticket.

# Fix Directions

Ordered as I would sequence them:

1. **M1** — thread `ORGASMIC_PROJECT_SCAN_TIMEOUT_SECS` through `ServiceSpec`
   and both unit renderers (`daemon_service.rs:73-80`, `:846`, `:934-936`), or
   persist it as a daemon setting; update `serve --help` to say when the value is
   captured. Without this, criterion 7 is unmet for the installed daemon.
2. **M2** — move `drop(seed)` above `orgasmic_dir.is_dir()` in the Project arm
   of `build_refresh` (`index.rs:1790` vs `:1819`) so no index lock spans a
   syscall.
3. **M3** — widen the wave count by one in `first_load_coordinator_timeout`
   (`index.rs:514-524`) to cover a waiter that arrives after the batch capture.
4. **M4** — add a short failure cooldown to `ensure_project_loaded`
   (`index.rs:1011-1029`) so unscoped `/tx` stops rescanning known-broken
   projects on every notification refresh.
5. **M5** — add an integration test that asserts the observed coordinator budget
   with real queued targets, not the formula.
6. **L1/L2** — make the coverage notification dismissible; stop marking a
   queue-delayed project `Failed`.
