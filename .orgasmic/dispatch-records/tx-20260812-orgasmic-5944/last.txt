# Independent review — TASK-GRCWC (worktree-prune unsafe traversal proof)

Commit reviewed: `c3c7b058ec039b7cad96c687d1f8f6214acfb4fb` (3 files, +418/-42), reviewed

## Verdict

**PASS.** No HIGH findings. The safety claim under review holds: every depth, readdir,
and openat failure in `walk_worktree` now becomes a `WorktreeDisposition::UnsafeTraversal`
that fails `disposition_is_reclaimable`, so the worktree is dropped out of `reclaimable`
before the cleanup lock, before the daemon reservation, and before any removal — proven on
the production verb, not only on the helper. Acceptance 1, 2 and 4 are met. Acceptance 3
("make the help true about a partial removal") is met in substance but the new help
sentence is ambiguous in the dangerous direction, and the new refusal itself is the one
refusal in this verb that names neither the cause nor a remedy. Those are the three MEDIUM
items below; none blocks ship.

## Findings

### MEDIUM — bug/usability. `crates/orgasmic-cli/src/manager.rs:3843` — the traversal refusal swallows the OS error, contradicting the contract an existing fixture already asserts

```rust
disposition = WorktreeDisposition::UnsafeTraversal { detail: err.to_string() };
```

`anyhow::Error`'s non-alternate `Display` writes only the outermost context and drops the
cause chain (verified in `anyhow-*/src/fmt.rs`, `ErrorImpl::display`: the chain is walked
only `if f.alternate()`). The chain built here is
`"could not open worktree descendant z-unreadable"` → `"openat \"z-unreadable\""` →
`"Permission denied"`, so `to_string()` yields only the first link. The operator-facing
line is therefore:

```
SKIP PATH=<wt> WHY=worktree traversal incomplete (could not open worktree descendant z-unreadable); kept before deletion
```

with no errno — the operator cannot tell EACCES from EMFILE from a mid-stream `readdir`
failure, which are three different remedies.

This is not a style preference; it is a stated contract of this verb. The sibling refusal
`WorktreeDisposition::Undetermined` is pinned by
`crates/orgasmic-cli/tests/dispatch.rs:9985-9989`:

```rust
assert!(
    stdout.contains("Permission denied") || stdout.contains("permission denied"),
    "the underlying I/O error must be printed, not swallowed\nstdout={stdout}"
);
```

The new fixture (`tests/dispatch.rs:10666-10671`) asserts only
`"worktree traversal incomplete"` and `"z-unreadable"`, so nothing catches the regression
in behaviour between the two refusals. Note also that the two new unit fixtures print
`{:#}` in their own assert messages (`manager.rs:12947, 12997`) — the tests see the chain
the operator does not.

*Fix direction:* `detail: format!("{err:#}")`, and extend
`worktree_prune_refuses_an_unreadable_descendant_before_deletion` with the same
`"Permission denied"` assertion the `Undetermined` fixture already carries.

### MEDIUM — docs. `crates/orgasmic-cli/src/manager.rs:426-429` — the new help sentence's grammatical subject is the descendant, not the worktree, which reads as the fail-open this task removed

```
Before deletion begins, the anchored walk must completely traverse the worktree: an
unreadable descendant or one deeper than 64 directory levels is SKIPPED and
left untouched.
```

"an unreadable descendant … is SKIPPED and left untouched" says the *descendant* is
skipped and left alone — the natural completion of which is "and the rest is deleted",
i.e. precisely the pre-commit behaviour. What actually happens is that the *whole
worktree* is skipped and nothing in it is deleted. Acceptance 3 is specifically "make the
help true"; this sentence is true only on a charitable reading and false on the reading an
operator reaches for when deciding whether a destructive verb is safe.

`crates/orgasmic-cli/tests/cli_parity.rs:182-189` cannot catch this: it asserts the
lowercased help *contains* `"unreadable descendant"`, `"skipped"`, `"left untouched"`.
Substring presence is insensitive to which noun the verb attaches to, so the parity gate
is green on either wording. This is a test that passes without exercising its acceptance
criterion.

*Fix direction:* make the worktree the subject, e.g. "…: a worktree containing an
unreadable descendant, or one nested deeper than 64 directory levels, is SKIPPED WHOLE and
nothing in it is deleted." Then assert the new phrase in `cli_parity.rs` so the wording is
pinned rather than the keywords.

### MEDIUM — usability. `crates/orgasmic-cli/src/manager.rs:3738` — the traversal refusal names no remedy, breaking the help's own promise about refusals

```rust
format!("worktree traversal incomplete ({detail}); kept before deletion")
```

`manager.rs:425-426` states the verb's contract: *"There is no `--force` on this verb, so a
refusal names what to clear by hand instead of offering an override."* Every other refusal
honours it — `worktree_submodule_refusal` says "rescue what you need, then delete {nested}
yourself and re-run" (`:4390`) and "Repair or remove what did not read and re-run"
(`:4364`). The new one stops at "kept before deletion". Because this disposition is
sticky — `UnsafeTraversal` is never reclaimable, and the verb has no `--force` — an
operator who hits it has no stated path out of it at all; the worktree becomes permanently
unprunable through this verb with no instruction.

*Fix direction:* append a remedy to the `UnsafeTraversal` arm, e.g. "make it readable
(`chmod`) or remove the offending descendant by hand, then re-run — this verb has no
`--force` of its own", matching the three existing remedy strings.

### LOW — test. `crates/orgasmic-cli/tests/dispatch.rs:10802-10807` — the summary assertions this commit added are the one piece of new coverage that false-greens under privilege

The commit extended `a_removal_that_stops_part_way_reports_partial_and_never_kept` with
the new `PARTIAL=1 KEPT=0` summary assertions, but that pre-existing fixture silently
`return`s when the mode-0o500 directory does not actually block:

```rust
if std::fs::remove_file(blocked.join("inner.txt")).is_ok() {
    std::fs::set_permissions(&blocked, ...0o755).unwrap();
    return;                     // running as root: passes green, proves nothing
}
```

Both *new* fixtures get this right — they `assert!(File::open(&blocked).is_err(), ...)` and
fail loudly under root (`manager.rs:12936-12941`, `tests/dispatch.rs:10641-10646`). The
new `PARTIAL=`/`KEPT=` split is the only summary change in this commit and it is verified
only by the fixture that skips. On a privileged CI host, `PRUNE_SUMMARY PARTIAL=…` has no
coverage.

*Fix direction:* replace the `return` with the same assert-and-fail guard the two new
fixtures use.

### LOW — correctness. `crates/orgasmic-cli/src/manager.rs:4113` — one fail-open remains in the walk

```rust
Ok(_) => { if let Ok(kind) = anchored_dir::stat_at(dir, &name) { found.bytes = ...; } }
```

An `fstatat` failure on a non-directory entry is still swallowed, so the walk can complete
"successfully" having under-counted the tree. The consequence is confined to reporting —
`bytes` feeds only `RECLAIMABLE_WORKTREE`, `WOULD_RECLAIM`, and `RECLAIMED …
BYTES=/SIZE=`; it informs no deletion decision, and `.git` detection is by entry NAME, not
by stat. So this does not reopen the safety hole. It is called out because the new help
now asserts the walk "must completely traverse the worktree", which this makes slightly
untrue in the size dimension.

*Fix direction:* either propagate it for symmetry with the other three branches, or state
the exception in the `walk_worktree` doc comment.

### LOW — docs/test. `crates/orgasmic-cli/src/manager.rs:428` and `tests/cli_parity.rs:183` — the depth bound is hardcoded in help and in the gate, so raising `MAX_DEPTH` leaves the help lying while the gate stays green

The help says "64 directory levels" and `cli_parity` asserts the help contains
`"deeper than 64 directory levels"`. If `anchored_dir::MAX_DEPTH` (`manager.rs:3091`) is
raised and the help is not updated, the assertion still passes on the stale string. (The
integration fixture's `MAX_DEPTH_UNDER_TEST = 64` at `tests/dispatch.rs:10692` fails loudly
in that scenario, so the risk is bounded — but the *help* silently stops being true.)

*Fix direction:* have `cli_parity` assert against a value derived from the constant, or add
a comment at `MAX_DEPTH` naming the two literals that must move with it.

### LOW — correctness. `crates/orgasmic-cli/src/manager.rs:5599-5602` — `PRUNE_SUMMARY KEPT=` counts a non-worktree

```rust
Err(err) => { kept += 1; println!("KEPT PATH={} WHY={err}", project_root.display()); }
```

A `git worktree prune` metadata failure increments the same `kept` counter as a kept
worktree and prints `KEPT PATH=<project_root>`, which is not a managed worktree. The
counter conflation is pre-existing (it was `failed` before), but this commit re-specified
KEPT in the help as a per-worktree removal outcome ("KEPT means no content was deleted"),
so the summary field is now marginally untrue for that one branch.

*Fix direction:* leave the `KEPT PATH=` line (nothing was destroyed, which is accurate) but
do not fold it into the worktree `KEPT=` count.

## Open Questions

1. `UnsafeTraversal` is permanently non-reclaimable and this verb has no `--force`. Was a
   deliberate escape hatch considered and rejected, or is the intended answer "the operator
   fixes the permissions / deletes the subtree by hand"? Whichever it is, it should be the
   text of the refusal (MEDIUM #3).
2. Acceptance 3 says "decide and state what a partial removal *means to the operator*". The
   help now states what PARTIAL *is*; it does not say what to do next (re-run? inspect? the
   tree is a ruin). Is that considered discharged?
3. No `verify/TASK-GRCWC/` red/green spec exists, unlike `verify/TASK-RMA18*` and
   `verify/TASK-M47E5.2`. Intentional, or an omission for this chain's closure?

## Residual Limits

1. **The walk proves readability, not writability, and a successful walk does not imply a
   complete removal.** A directory at mode 0o500 lists and opens fine, so the walk returns
   `Ok`, and `remove_contents` then fails at `unlink_at` after removing earlier siblings —
   a genuine destructive PARTIAL. This is exactly what
   `a_removal_that_stops_part_way_reports_partial_and_never_kept` fixtures at
   `tests/dispatch.rs:10802`. The help's "the anchored walk must completely traverse the
   worktree" is a necessary but not sufficient condition for a clean removal; the following
   PARTIAL sentence covers it, but no fixture pins the boundary *as a stated limit*.
2. **Classification-to-removal TOCTOU is unchanged.** The walk runs before the cleanup lock
   and the reservation; a descendant that becomes unreadable inside that window still
   reaches `remove_contents` and yields PARTIAL/KEPT. Correctly reported, not eliminated.
3. **The `entry_names` failure branch has no fixture.** Of the three fail-opens the task
   names, two now have fixtures; a mid-stream `readdir` failure is not reproducible without
   a fault-injecting filesystem. Both sides propagate it identically by inspection
   (`:3417` and `:4092`), which is the same "derived, not executed" status the task opened
   over — narrowed from three branches to one.
4. **`dispatch-close` is the other destructive surface and is untouched.** It removes
   through `git worktree remove` (`manager.rs:6955, 6970`), not through the anchored walk,
   so `UnsafeTraversal` does not cover it. Out of this task's scope; noted because
   `manager.rs:398` names both verbs as the removers.
5. **A worktree root that is itself unreadable aborts the whole verb.** `open_child` at
   `:3787` propagates with `?`, so `scan_managed_worktrees` returns `Err` and
   `worktree_prune` exits at `:5400` — no other worktree is reclaimed and no `SKIP` line
   names the offender. Pre-existing (untouched by this diff) and fail-closed, but it is a
   different shape from the new per-worktree refusal.
6. **Non-Unix.** `walk_worktree` and `scan_managed_worktrees` are `#[cfg(unix)]`; the
   non-Unix scan returns an empty vector (`:3864-3871`). Unchanged.
