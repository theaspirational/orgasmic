# TASK-RMA18 review — fd-anchored worktree reclamation (`3a36858..db2edb6`)

## Verdict

**REJECT — BLOCK SHIP on F1.** The verb must not become reachable in its current
form.

The six findings this task was filed for **are closed**, and closed well. The
ancestor-symlink walk (finding 4), the `(dev, ino)` identity carried from
enumeration to `unlinkat` (finding 5), the daemon-side pending-admission fence
(finding 6), the `errno`-checked `readdir` and the PARTIAL/KEPT split all hold
under reading, and the three destructive-path regressions in `verify/TASK-RMA18`
are real regressions with real victims. **C2 is the strongest part of this
change** — the manager's read was right.

The manager's other read was also right: **C3 is the sharpest risk**, and it is
worse than the manager suspected. `git_would_remove_worktree` is not a faithful
reproduction of `git worktree remove`'s non-forced refusals. It omits a
**categorical** refusal — not an edge case — and the omission is on the path that
recursively deletes. Measured, not argued (git 2.52.0, three probes below).

To be explicit about the pre-authorised trigger: F1 is **not** "a directory whose
identity was never proved" — the identity work is sound. It is a HIGH-severity
data-loss divergence from a safety contract the code, the `--help` text and the
manager convention all state in writing. Restoring the gate is one remedy; the
smaller one is F1's fix landing in a `TASK-RMA18.1` round before the reinstall.
Either is fine — what must not happen is un-gating as it stands.

**On the manager's objection: you are not wrong, on either half.** Branch 2 of
the disjunction ("prove the exact child inode at the destructive syscall") is
**not** reachable through a subprocess — `git worktree remove` accepts only a
pathname, re-resolves it inside a process this one cannot fence, and offers no
`AT_`-style handle option; even running it with cwd set to the anchored fd leaves
git resolving a path of its own. Taking branch 1 was correct and necessary. What
was not correct was reproducing *part* of git's decision procedure while the code
comment, the `after_help` and the convention doc all claim parity with the whole
of it.

### F1 — HIGH / correctness, data loss. `git_would_remove_worktree` omits git's categorical submodule refusal; prune recursively deletes worktrees a non-forced `git worktree remove` refuses outright

`crates/orgasmic-cli/src/manager.rs:3915-3979`

The reproduction implements exactly two refusals: *locked* (from `git worktree
list --porcelain`) and *unclean* (from `git status --porcelain`). Real
`git worktree remove` refuses a third state **before it ever considers
cleanliness**: any worktree containing an initialized submodule.

Measured, git 2.52.0, on a **clean** worktree containing one initialized
submodule:

```
status --porcelain:                          []      <- reproduction says "clean"
status --porcelain --ignore-submodules=none: []
worktree list --porcelain:                   no `locked` line
git worktree remove ../wt
  fatal: working trees containing submodules cannot be moved or removed
  EXIT=128
git worktree remove --force ../wt
  EXIT=0
```

So `git_would_remove_worktree` returns `Ok(())` and
`AnchoredManagedRoot::remove_child` recursively deletes a tree that git refuses
to touch without `--force`. **The data-loss variant is one committed config line
away.** With `submodule.<name>.ignore = all` in `.gitmodules` — committed, so
every clone inherits it — a submodule holding uncommitted work reports clean to
the parent:

```
# sub/ holds an untracked precious.txt and a modified tracked f
status --porcelain: []                       <- prune proceeds, no salvage
git worktree remove ../wt
  fatal: working trees containing submodules cannot be moved or removed
```

Salvage cannot rescue it either way: the parent's `git add -A` records a
submodule only as a gitlink, so `sub/precious.txt` is never captured. Note also
that git passes `--ignore-submodules=none` in its own check
(`builtin/worktree.c` `remove_cmd`) and the reproduction does not, which is a
second, independent divergence in the same call.

Why this is reachable rather than theoretical:
- `git worktree add` does **not** init submodules, so a fresh dispatch worktree
  is clean — but a worker that must *build* runs `git submodule update --init`,
  which is the normal case in a submodule project.
- `dispatch-close` still shells out to `git worktree remove`
  (`manager.rs:5775-5779`), so in exactly those projects the close **fails** and
  managed worktrees accumulate — which is the state that makes an operator reach
  for `worktree-prune`. This change therefore makes prune strictly more
  destructive than the close whose semantics it claims to match.
- `grep -rn submodule crates/ shipped/ .orgasmic/*.org` → **zero hits**. There is
  no handling and no documented exclusion; before this change git enforced the
  boundary for free.

The claim of parity is stated in three places and is now false in all three:
`manager.rs:3431` ("refusing the same states a non-forced `git worktree remove`
refuses"), `manager.rs:3912` ("Both refusals git makes are reproduced"), and the
operator-facing `after_help` at `manager.rs:369-374`.

**Fix direction.** In `git_would_remove_worktree`, after the `registered`/`locked`
checks: refuse when the worktree contains an initialized submodule (git's own
test is `validate_no_submodules` — a `.gitmodules` entry whose working path holds
a `.git`; `git submodule status` or reading the index for gitlinks with a present
working dir both express it), and pass `--ignore-submodules=none` to the `git
status` call so it does not inherit `diff.ignoreSubmodules`. Add a regression
with a submodule holding an untracked sentinel, asserting the sentinel survives.

### F2 — MEDIUM / correctness. C2: the conceded `fstatat`→`unlinkat` window is not the only one; the clean check itself is not identity-fenced

`crates/orgasmic-cli/src/manager.rs:4063-4118`

`reclaim_managed_worktree` asserts `path → identity` at :4063, then makes **four
independent pathname resolutions in subprocesses** before re-asserting at :4104:

| line | what resolves `worktree.path` | consequence if the name is rebound in the gap |
|---|---|---|
| 4067 | `worktree_has_uncommitted_changes` | dirtiness read off another tree |
| 4069 | `worktree_head_oid` | wrong parent for the salvage |
| 4071 | `salvage_worktree_onto` | **writes another tree's content into the project repo** as `refs/orgasmic/salvage/<sha>`, and mutates that tree's index/HEAD |
| 4092 | `git_would_remove_worktree` | **the clean verdict is about a different inode than the one deleted** |

Rebind the name to a clean decoy across that stretch and back before :4104, and
every assert passes while the classified inode — dirty, unsalvaged — is removed
at :4116. The identity *classified, reserved and deleted* is provably the same
(acceptance item 2 holds). The identity **checked for cleanliness** is not, and
that check is described in the code as "the last gate between this verb and a
worker's unrecoverable output" (:4088).

The report's statement that the only window is between the final `fstatat` and
the final `unlinkat` is therefore not accurate, and the design note's "every such
use is fenced by re-proving that the path resolves to the recorded identity right
now" (:2812-2814) is fenced *before and after*, not *during*.

Precondition is an actor able to rename inside the managed root — the same threat
model findings 4 and 5 were written against, so it is in scope rather than out of
it. Not blocking on its own; it is the honest statement of residual risk that the
report should carry, and it is a second argument for F1's fix (a refusal computed
from the anchored handle rather than from a subprocess is not exposed to this).

### F3 — MEDIUM / test, acceptance. "No test-only hook is reachable in a release build" is met for the prune hook only, and its proof never executes

   dispatch cleanup lock *and* the daemon close-guard reservation — the exact

2. `assert_eq!(worktree_prune_pause_hook_is_compiled(), cfg!(debug_assertions))`

3. That second half runs **only under `--release`**, and `scripts/run-tests.sh`

**Fix direction.** Gate `dispatch_close_pause_after_guard` the same way; make the

### F4 — MEDIUM / docs. Two operator-facing texts still describe the removed mechanism, one of them printed by the verb itself

`crates/orgasmic-cli/src/manager.rs:369-374`,
`shipped/prompt-studio/conventions/manager-dispatch.org:484-486`,
`crates/orgasmic-cli/src/main.rs:941-943`

The manager's C6 fix corrected the subcommand summary but not the `after_help`,
which is what `orgasmic manager worktree-prune --help` actually prints:

> "Salvages a dirty tree to refs/orgasmic/salvage/<sha> first and then removes
> WITHOUT --force, **so git's clean check still gates the removal**."

git does not perform the removal any more, and per F1 git's clean check is not
what gates it. The convention doc says the same ("removes WITHOUT `--force`,
exactly as `dispatch-close` does") and is now doubly wrong, since `dispatch-close`
still uses git and therefore refuses cases prune deletes.

**Does the doc drift block?** The `.org` on its own: no, follow-up. The
`after_help`: yes, it should ship with F1's fix — it is the sentence an operator
reads at the moment of running a destructive verb, and it is the sentence F1
disproves.

Smaller, same family: the new subcommand summary "Salvages a dirty tree first"
(`main.rs:941-943`) is false for the `RepoGone` disposition, which is precisely
the one path that deletes with **no** salvage. The `after_help` says so; the
one-line summary shown by `orgasmic manager --help` does not.

The manager's replacement clause "never touches one an open dispatch or a live
run occupies" **is** earned for every reachable case I could find — three
independent owners checked by identity (`manager.rs:3518-3560`), re-checked under
the cleanup lock (`:4327`), plus the daemon reservation. Its one residual is F5
plus a live run whose `RunRecord.worktree` is `None`, which no dispatch produces.

### F5 — MEDIUM / correctness. C7 confirmed reachable, and the fix is asymmetric: identity is stored at admission but re-derived from a stale path for recorded runs

`crates/orgasmic-daemon/src/supervisor.rs:6068-6080`, `:6129-6132`,
`crates/orgasmic-cli/src/manager.rs:3518-3526`

`AdmittedRun` stores `worktree_identity` **at admission** (`supervisor.rs:515-527`),
which is what makes the pending window rename-proof — the new test
`a_renamed_worktree_still_blocks_the_close_of_the_run_admitted_into_it` proves it.
`RunRecord` stores no identity, so `same_worktree(recorded, worktree_key)`
computes the identity of the *recorded path* at query time. After a rename that
path no longer resolves, `std::fs::metadata(a)` fails, and the function returns
`false`. The CLI's own `claims` closure has the identical shape and falls back to
string comparison of a stale path.

Net: rename a live worker's worktree after its `RunRecord` lands, and prune
classifies the new name `Unclaimed`, the daemon grants the reservation, salvage
runs, and the tree is removed under the running worker. The worker's post-salvage
writes are lost.

Reachability is low (nothing in orgasmic renames a live worktree; it takes
operator action), which is why this is not a block — but it *is* the same class
the whole task is about, the worker stated it as residual risk 2, and the fix is
symmetric and small: store `worktree_identity` on `RunRecord` at insert and
compare stored-vs-current instead of current-vs-current. **Yes, it deserves a
task.**

### F6 — LOW / correctness. Two identity/path asymmetries that survived the sweep

- `supervisor.rs:4134-4136`: the "already reserved" check still uses
  `held.worktree_key == worktree_key` string equality, while `admit_live_run`
  was upgraded to `same_worktree` (`:641-645`). Two cleanups can hold reservations on
  the same inode reached through different recorded paths after a rename.
  Mitigated in practice by the shared `acquire_dispatch_cleanup_lock` within a
  project, so it is a consistency wart rather than a hazard.
- `pending_admission_in_worktree` (`supervisor.rs:573-597`) cannot match a lease
  whose admission carried `worktree: None`. No dispatch path produces that today;
  noting it so the next reader does not have to re-derive it.

### F7 — LOW / correctness. `KEPT` is printed over a tree salvage has already mutated

`crates/orgasmic-cli/src/manager.rs:4067-4086`, `:2465-2536`

`salvage_worktree_onto` mutates in order: `git add -A` → `commit-tree` →
`checkout --detach <sha>` → `anchor_salvage_ref`. A failure at the third or
fourth step returns `Err`, and `reclaim_managed_worktree` prints
`KEPT ... salvage failed, worktree kept` with **no** `SALVAGED` line — while the
index is staged, `HEAD` may be detached at a salvage commit, and (if `checkout`
was the step that failed) the commit is unreferenced. No content is destroyed, so
this is not data loss; but "KEPT means untouched" is literally false on that
branch, and the acceptance's escape clause ("or the report says precisely what it
touched") is not taken either. `touched` is otherwise set correctly on every
destroying path I traced — `remove_contents` (`:3162-3164`), the final
`AT_REMOVEDIR` (`:3230-3236`), and preserved across the `?` in the recursion.

## Open Questions

1. **Acceptance item 1, read literally, is not met — is that acceptable?** "No
   pathname is resolved for any ancestor of the managed root." `<home>` *is* an
   ancestor of the managed root, and `open_trust_root` (`manager.rs:2923-2929`)
   opens it with plain `open(2)` — no `O_NOFOLLOW` on any component, including
   the final one. Symlinking `~/.orgasmic/worktrees` is now refused; symlinking
   `~/.orgasmic` itself is followed. The asymmetry is documented and reasoned at
   `:2816-2821` (macOS `/var`, `/tmp`, temp-rooted fixtures). **My ruling:
   acceptable** — an actor who can replace the operator's configured runtime home
   also controls the daemon socket and the binary path — but it is a boundary the
   manager should record as ruled-on rather than met.
2. Should orgasmic refuse to manage projects with submodules outright, rather
   than growing per-verb handling? F1's fix closes prune; `dispatch-close` is
   already blocked by git in those projects, which means dispatch in a submodule
   project is half-broken today and nothing says so.
3. Was deleting the two TASK-M47E5.3 gate tests right? **Yes** — they assert the
   gate refuses, the gate is gone, and the nine behaviour tests they stood in for
   are all back. Item 2 of the inherited gate review (an empty-tempdir/no-daemon
   fixture for the gate's structural guarantee) is moot for the same reason,
   unless F1 puts the gate back, in which case it becomes live again.
