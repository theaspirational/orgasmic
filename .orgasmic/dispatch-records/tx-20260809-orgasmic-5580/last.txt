# Verdict

REJECT / BLOCK SHIP. TASK-D6N77 does not satisfy the non-negotiable app-created custom-terminal flow, does not enforce the manager singleton, and does not provide fail-closed pane injection. The new `dispatch-wait` also has a false-death race across the existing release-before-terminal-tx boundary. All findings are regressions introduced by `8fc6f542a642fbf77c1c971bc047669cbf311f1d..e98ed372cd496a5367a9fce0f1e0ddc9d87f5386`.

# Findings

1. **HIGH / bug — normal `/orgasmic` startup never claims the terminal.** `shipped/entry/router.org:21-26` still invokes plain `orgasmic manager register`. In `crates/orgasmic-cli/src/manager.rs:1530-1561`, an existing `ORGASMIC_RUN_ID` only enters the claim branch when optional `--provider` is present; plain registration prints `already supervised ... nothing to do`. The shipped convention at `shipped/prompt-studio/conventions/manager-dispatch.org:293-301` documents a separate manual command, so the required user flow depends on a hidden step and has no wake target. Minimal fix: make the normal startup route establish the claim while keeping provider identity explicit internally, e.g. have the app terminal carry trusted provider selection into plain register or add a required startup handshake that the router invokes automatically. Recorded as `tx-20260809-orgasmic-5582`.

2. **HIGH / correctness — a claim does not participate in the singleton lease.** `crates/orgasmic-daemon/src/manager_registration.rs:202-246` checks a supervisor snapshot and then writes a separate in-memory `claims` map. It neither acquires `manager.launch:<project>` nor changes the terminal run's role/task lease. `post_manager_launch` independently acquires the stable manager lease at `crates/orgasmic-daemon/src/api.rs:2855-2895`; external register does the same at `manager_registration.rs:346-395`. Therefore an app manager or external manager can be launched after a terminal is claimed, and claim-vs-launch/register is non-atomic. `GET /manager/state` returns only the supervisor snapshot (`api.rs:3232-3235`), so the UI continues classifying the claimed run as a terminal and exposes no claimed-manager ownership. Minimal fix: represent a claim as an atomic supervisor lease/role transition on the shared manager key, or reserve that lease under the terminal run identity; launch, external register, claim, release, and reattach must all use the same admission boundary. Recorded as `tx-20260809-orgasmic-5583`.

3. **HIGH / security — claim authorization is not bound to the caller run.** The register API accepts a caller-supplied `terminal_run_id` and only checks the target run's project/role/driver (`api.rs:2965-2999`, `manager_registration.rs:202-215`). There is no caller runtime identity in the request. Wake then passes the target run's own identity back into `send_manager_wake` (`api.rs:3082-3098`), making the ownership check at `supervisor.rs:2953-2973` tautological. Any bearer-authenticated local caller can name and claim another custom terminal. Minimal fix: require the calling `RuntimeIdentity` and verify it matches the named terminal before claiming or waking; do not synthesize caller authority from the target snapshot. Recorded as `tx-20260809-orgasmic-5584`.

4. **HIGH / security — the pane proof can still paste into a shell or busy provider.** Rmux uses `foreground_state()` at `crates/orgasmic-drivers/src/modes/rmux.rs:3368-3390`; the installed rmux-sdk 0.9.0 documents that result as best-effort and potentially about one second stale (`rmux-sdk-0.9.0/src/handles/pane.rs:396-404`). The code ignores field source labels and the second call can return the same stale observation. Both muxes then accept any viewport line beginning with `❯`/`›` (`tmux.rs:2682-2695`, `tmux.rs:3096-3100`), not a bounded current composer, so output prose or an old prompt retained during a busy turn can authorize delivery. Finally, tmux performs separate `load-buffer`, `paste-buffer`, and `send-keys Enter` subprocesses after the final check (`tmux.rs:598-632`, `tmux.rs:2114-2181`); rmux likewise calls paste after its final snapshot (`rmux.rs:3514-3528`). Provider exit in that gap can redirect bytes to zsh. Minimal fix: treat a transport as `unsupported` until it offers a fresh, source-qualified, conditional send tied atomically to the same foreground/composer revision; replace the glyph scan with a provider-specific bounded composer-state proof. Recorded as `tx-20260809-orgasmic-5585`.

5. **HIGH / correctness — `dispatch-wait` can falsely report a successful finalize as death.** The loop scans the local tx ledger first and then fetches live runs (`crates/orgasmic-cli/src/manager.rs:2908-2939`). Worker finalize intentionally releases the supervisor run before appending its terminal tx (`crates/orgasmic-daemon/src/api.rs:8477-8565`). A poll in that gap sees `reported=false` and `run_live=false`, exits 2, and wakes the manager on a fabricated worker death. Also, because `known` is built only from `scan_open_dispatches`, a generation closed by another authority while a multi-generation wait continues becomes `no open dispatch generation` exit 1 rather than a stable terminal result (`manager.rs:2908-2916`). Minimal fix: make one daemon-side generation-state/long-poll endpoint authoritative, or at least rescan terminal tx/session state after run disappearance and retain closed-generation outcomes by `started_tx`; never decide death from two unsynchronized sources. Recorded as `tx-20260809-orgasmic-5588`.

6. **HIGH / test — the required proof and P1 safety matrix are absent.** The range adds only `dispatch_wait_timeout_parser_is_explicit_and_nonzero` (`manager.rs:9719`) and a narrow provider-glyph unit test (`tmux.rs:4028`). There are no tests for claim authorization, claim/launch/register races, release/restart recovery, status/exit mapping, fresh foreground evidence, shell-after-exit, output glyphs, busy turns, or the release-to-terminal-tx wait race. The implementer report explicitly says no real dispatch was created. Acceptance item 2 requires a real-dispatch proof that returns promptly on report and does not return early on `[pid-gone]`; that remains unmet. Minimal fix: add isolated-daemon concurrency/lifecycle tests plus a non-billed Claude/Codex x tmux/rmux terminal matrix, and record the real dispatch report transition. Recorded as `tx-20260809-orgasmic-5589`, corrected line evidence in `tx-20260809-orgasmic-5590`.

7. **MEDIUM / correctness — wake outcomes collapse at both boundaries.** The API maps every non-accepted driver ack, including provider mismatch and stale/unknown foreground, to `busy` (`crates/orgasmic-daemon/src/api.rs:3100-3109`). It has no provider-mismatch/unknown status. The CLI prints the response and then returns the same generic failure exit for every non-accepted status (`crates/orgasmic-cli/src/manager.rs:1651-1661`), so automation cannot distinguish busy, unavailable/dead, unsupported, or mismatch. Minimal fix: define a closed typed status enum and stable distinct CLI exit codes for every required outcome; preserve the driver reason rather than folding it into busy. Recorded as `tx-20260809-orgasmic-5586`.

8. **MEDIUM / correctness — claim lifecycle is not recoverable or internally consistent.** Claims are daemon-memory-only (`manager_registration.rs:166-184`), so restart forgets a claim even if a system-wide rmux terminal reattaches. `manager release` only releases external registrations first and otherwise releases the entire `manager.launch:*` run (`api.rs:3143-3197`); it has no explicit unclaim operation, so release from the claimed pane kills the custom terminal while release elsewhere cannot clear the claim. Generic terminal release leaves the claim stale until a later wake lazily removes it (`manager_registration.rs:249-268`). Minimal fix: define claim/unclaim lifecycle in supervisor state, persist or deterministically restore it on reattach, clear it on every terminal release path, and make manager release demote/unclaim a custom terminal without unexpectedly destroying it unless termination was requested. Recorded as `tx-20260809-orgasmic-5587`.

# Open Questions

- Does rmux expose a conditional input operation keyed to a foreground/state revision? If not, rmux automated wake must remain unsupported rather than relying on a documented stale snapshot.
- Can tmux make a server-side conditional send against a trustworthy pane process identity? If no atomic condition exists, the non-negotiable never-paste-into-shell property cannot honestly be claimed for tmux.
- The repo exposes daemon event streaming to the UI but no CLI long-poll/SSE generation endpoint was found. A daemon-owned generation wait would remove the `dispatch-wait` cross-source race and answer the task's polling-design question directly.

# Fix Directions

1. Make the plain startup path claim atomically under the supervisor's manager lease and bind it to the calling runtime identity.
2. Fail closed on transport delivery: a fresh, revision-bound composer/foreground proof and atomic conditional send, or `unsupported`.
3. Move generation waiting behind one daemon authority and preserve terminal outcomes after close.
4. Add typed outcome/exit contracts and the isolated real-terminal/concurrency matrix before re-review.
