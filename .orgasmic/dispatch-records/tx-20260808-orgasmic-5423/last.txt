## Findings

### F1 (HIGH — docs / unmet acceptance 5a) — the shipped help is still false about the repo-gone branch
`crates/orgasmic-cli/src/manager.rs:381-385`, rendered from the built binary.

Two clauses, both false, in the sentence that exists to describe that branch:

> "Once the repository is gone **no such record survives to be read** and git has
> no verdict left to reproduce, so that branch is checked a DIFFERENT and WEAKER
> way: the anchored walk of the tree's own contents refuses any NESTED `.git`
> entry, of any type, **and nothing else there is checked**."

Both are false. `.gitmodules` lives in the **worktree**, not in the admin
directory, so it survives `RepoGone` intact — and `worktree_submodule_refusal`
still reads it there. The `NoRepository` arm at `:4085-4100` returns early only
when `nested_git` is `Some`; otherwise control **falls through** to
`gitmodules_paths` (`:4110`) and `nonempty_dir_under` (`:4123`), either of which
can refuse.

**Measured, not inferred** (probe A, source copy under `/tmp`, shipped
predicates called directly):

```
premise: worktree_index_gitlinks => NoRepository
premise: walk.nested_git         => None
worktree_submodule_refusal(...)  => Some(
  "<tmp>/wt contains an initialized submodule at vendor/sub, and
   `git worktree remove` refuses such a worktree outright — …")
```

Probe B: a symlinked `.gitmodules` on the same branch also refuses
("`.gitmodules` is a symlink, so what it names cannot be read through this
worktree's handle"). So on `RepoGone` at least **three** things are checked, not
one.

Direction: safe. The operator is told they have less protection than they do.
That is why this does not block the ship — but acceptance 5a is not met, and the
help should not be read as pinned truth.

### F2 (MEDIUM — bug / unmet acceptance 3) — a `NoRepository` refusal reached via `.gitmodules` still offers the impossible remedy
`manager.rs:4064-4069` (`submodule_advice`), used at `:4123-4129`.

Acceptance 3: "A `NoRepository` refusal carries its OWN advice text with a remedy
that exists." The refusal in probe A **is** a `NoRepository` refusal, and it
carries `submodule_advice`, ending:

> "… or — **while the repository is still there** — remove the worktree with
> `git worktree remove --force`"

The repository is not still there; that is what put the worktree on this branch.
The hedge keeps the sentence from being flatly untrue, but the operator gets a
conditional escape whose condition they cannot satisfy and **no statement that
`--force` is unavailable** — unlike the arm three lines above it, which says
"`git worktree remove --force` CANNOT run here". F-D is closed on the
`nested_git` arm only.

This is the same class round four filed F-D on. It survived because of F3.

### F3 (MEDIUM — test) — C5 is realized: `RepoGone` + `.gitmodules` now has zero coverage
`crates/orgasmic-cli/tests/dispatch.rs:8960-9081`
(`worktree_prune_refuses_a_repo_gone_worktree_containing_a_submodule`).

The brief asked me to check that this test "still passes for the same reason".
It does not, and I measured why rather than assuming:

```
$ git --version                     → git version 2.52.0
$ git submodule update --init       (inside a LINKED worktree)
$ file vendor/sub/.git              → ASCII text
  gitdir: ../../../super/.git/worktrees/wt/modules/vendor/sub
```

The fixture's submodule therefore leaves a nested `.git` **file**, the walk finds
it, and the new arm returns before `gitmodules_paths` is ever called. The test's
two assertions (`contains("submodule")`, `contains("vendor/sub")`) both match the
new message verbatim, so it stays green for a different reason — exactly the
shape the brief flagged as hiding a regression.

Consequence: nothing in the suite now exercises the `.gitmodules` arm on
`RepoGone`. That is how F2 shipped, and it is why F1's "nothing else there is
checked" went unchallenged.

(Incidentally this same measurement independently confirms the implementer's
"correction 1" — a `.git` **directory** predicate would have missed the single
likeliest shape. That call was right.)

### F4 (LOW — docs) — "WEAKER" mischaracterises the repo-gone check, and the over-refusal is undocumented
`manager.rs:382-385`.

The repo-gone check is not weaker; it is **different**, in both directions:
broader than git (it refuses a vendored `.git` git would have let you delete —
ruling 1's deliberate cost asymmetry) and narrower (blind past `MAX_DEPTH = 64`
and under directories that fail to open). An operator told only "WEAKER" is not
warned that this branch can KEEP a worktree git itself would have removed, which
is the one operator-visible consequence of ruling 1.

### F5 (LOW — test) — the strengthened `cli_parity` pin is still defeatable in the dangerous direction
`crates/orgasmic-cli/tests/cli_parity.rs:154-196`.

This is the direct answer to C2: **yes, I can make the help false in a way this
pin still passes**, and the dangerous direction is reachable two ways.

1. **A false universal sentence that names no branch.** The pin only inspects
   sentences containing `repo-gone` / `repository is gone` / `repo is gone`. Add
   *"The submodule refusal reads the worktree's own INDEX for gitlinks on every
   branch."* — no marker, so `about_repo_gone` never sees it; the existing
   repo-gone sentence still satisfies the `nested `.git`` + `any type` clause;
   `"index"` is already a required global substring. Pin green, help dangerously
   false, and none of the three `dispatch.rs` regressions contradicts it.
2. **An over-claim inside the repo-gone sentence itself.** *"…refuses any NESTED
   `.git` entry, of any type, at any depth and through unreadable directories."*
   Contains both required phrases, contains no `"index"`, passes — and is false
   (`MAX_DEPTH` 64; `open_child_dir` errors are skipped). Again uncontradicted by
   the regressions, which pin one true instance, not a universal.

So the implementer's stated division — "the pin constrains shape, the regressions
constrain truth" — is **not sound**: the regressions constrain truth only for the
shapes they instantiate. Its live proof is F1: the pin is currently passing on a
false sentence. Acceptance 5b is met in shape ("strengthened past substring
matching") but not in guarantee ("so it cannot pass on a false sentence").

The implementer disclosed this plainly, so it is a recorded limitation, not a
concealed one. I am filing it so 5b is not later read as achieved.

## Answers to the numbered claims

**C1 — `rewinddir`, and the blast-radius question. Classification "latent, not
shipped" HOLDS; keep it in this round.**

I enumerated every `entry_names` caller rather than taking the implementer's
word: `remove_contents` (`:3180`), `AnchoredManagedRoot::child_names` (`:3364`),
`walk_worktree` (`:3833`), `nonempty_dir_under` (`:4608`). Each enumerates a
handle it opened itself (`open_child_dir`), or enumerates a long-lived handle
exactly once per instance. In `worktree_prune`, `scan_managed_worktrees` walks
`child.dir` once and `reclaim_managed_worktree` re-opens a **fresh** child handle,
so the two enumerations never share a file description.

The nearest real hazard is the one the implementer did not name:
`nonempty_dir_under` starts from `worktree.try_clone()` — a `dup`, so a **shared**
description — and for a `rel` that resolves to zero components (a `.gitmodules`
with `path = .`) it enumerates the worktree handle itself. But that call returns
a refusal immediately on a non-empty listing, so a second zero-descent call
cannot be reached in the fail-open direction inside one invocation. No shipped
path double-enumerates.

On blast radius: **keep it here.** It is one POSIX line that makes a shared
primitive match its own documented contract, it is a no-op for every
single-enumeration caller, and reverting it leaves a live landmine in the
enumeration primitive of a destructive verb with no test guarding it. Splitting
it out to buy a cleaner five-fix round would trade a real hazard for a tidier
changelog.

**C2 — is the pin/regression division sound? No.** See F5, and F1 as its live
proof.

**C3 — is the keep-direction over-breadth acceptable? Yes, keep ruling 1.** The
state only arises once the repository has already disappeared; the cost of a
wrong KEEP is an operator running `rm -rf` with full knowledge, and the cost of a
wrong DELETE is a worker's unrecoverable output on the one branch that never
salvages. In this repo specifically I could not construct a realistic false
positive — `target/`, `node_modules/`, and venvs do not leave a nested `.git`.
My only ask is F4: say so in the help, because right now the operator is told
this check is weaker and is never told it can over-refuse.

**C4 — do the disclosed fail-opens hold everywhere the signal is consulted?
Yes, and on a stronger argument than "it only ever adds."** Both disclosed
fail-opens are covered by a **symmetric limit in the removal path**:

- `MAX_DEPTH`: `walk_worktree` returns silently at `depth > anchored_dir::MAX_DEPTH`
  (`:3829`); `remove_contents` **bails** at the same constant, from the same
  starting depth 1, with the same `depth + 1` descent (`:3176-3178`). A `.git`
  too deep for the walk sits inside a directory too deep for the removal.
- Unreadable entries: `walk_worktree` skips on `open_child_dir` `Err` (`:3843`);
  `remove_contents` propagates that same `Err` with `?` (`:3181`). A `.git` under
  a directory the walk could not open is under a directory the removal cannot
  open either.

In both cases the outcome is a `RemovalFailure` — reported, and by TASK-RMA18's
"kept means untouched" contract never printed as KEPT — not a silent deletion of
the nested repository. Caveat: `remove_contents` is readdir-ordered, so siblings
may already be gone when it stops; the guarantee is about the nested repository,
and the report is a partial-removal failure, not a clean KEEP.

The genuinely uncovered residual is staleness — a nested repository created
between the scan and the reclaim — which the reservation bounds and which the
call site discloses at `:4824-4832`. I agree with the disclosure.

**C5 — verified, and the answer is no.** See F3: it passes for a different
reason, the assertions do still hold, and the cost is a coverage hole that F2
fell through.

**C6 — the four verify artifacts. Re-authoring did not weaken anything; checked,

## Fix directions

1. **F1 + F4, one sentence.** Replace "no such record survives to be read … and
   nothing else there is checked" with what is true, e.g.: *"Once the repository
   is gone there is no index and no `modules/` directory left to read, and git
   has no verdict to reproduce. `.gitmodules` still survives inside the tree and
   is still read there; on top of it, the anchored walk of the tree's own
   contents refuses any NESTED `.git` entry, of any type — which can refuse a
   vendored repository git itself would have let you delete."* That is true, it
   keeps every phrase the pin requires, and it closes F4 in the same breath.
2. **F2, one advice string.** Give the `nonempty_dir_under` refusal a
   `NoRepository`-aware remedy — simplest is to pass the branch down and select
   between `submodule_advice` and a repo-gone variant, reusing the "`--force`
   CANNOT run here" wording that already exists three lines above.
3. **F3, one fixture.** Add a regression for `RepoGone` + `.gitmodules` with **no**
   nested `.git` (delete the submodule's `.git` after `update --init`, or use a
   `.gitmodules` naming an ordinary populated directory). Assert the `KEPT` line
   does **not** offer `git worktree remove --force`. That one test closes F2's
   coverage hole and pins F1's corrected sentence at the same time.
4. **F5, optional.** If the pin is to earn "cannot pass on a false sentence", it
   needs the complement: assert that **no** sentence anywhere attributes
   index-reading universally (e.g. no sentence containing "index" may contain
   "every branch" / "all branches"), and drop the unqualified "at any depth"
   escape hatch. Cheap, and it closes shape (1) above. Shape (2) is not reachable
   by a clap-text pin at all and should stay a disclosed limitation.

Items 1–3 are small enough to land as a fix-forward on this branch alongside the
reinstall rather than as a sixth review round. That is my recommendation.
