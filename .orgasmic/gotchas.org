#+title: orgasmic gotchas
#+orgasmic_version: 1

* Gotchas

Durable code-level traps for any agent touching the Rust/TS workspace, including
codex implementers in their worktrees (which auto-read repo `AGENTS.md`). Each
entry names the symptom/evidence, the cause, and the fix; transient entries also
carry an exit condition and the task expected to make them obsolete.

** Org TODO-keyword recognition is an allowlist, not "uppercase token"
The app-owned Org parser must only recognise the per-kind state-machine states
declared in `shipped/schema/state-machine.org` as TODO keywords. Otherwise
untyped headings like `* PROJECT orgasmic`, `* TX …`, `* PROMPT …`,
`* SCHEMA …`, `* SLOTS`, `* AGENT-TEMPLATE …` get misclassified. When you add a
state to the state machine, mirror it in
`crates/orgasmic-core/src/org.rs::TODO_KEYWORDS`. Durable invariant.

** Slot field names allow kebab-case
`{{skills.my-skill}}` and `{{skill_path.my-skill}}` are legal: the field
component after the first `.` accepts `[A-Za-z0-9_-]+`. The namespace component
is stricter (no dashes). Durable invariant.

** macOS append-mode files are not readable
`OpenOptions::new().append(true)` returns `EBADF` on read, so a tx-style appender
cannot seek/read its own descriptor to decide on a leading blank line. Read the
path with `std::fs::read` *before* opening the append handle, then carry the
"needs blank line" decision in a bool. Encoded in arch_BVH7M.2. Durable invariant.

** {{conventions.<name>}} slots are runtime-recognized
Recognized by `crates/orgasmic-core/src/slots.rs::is_dynamic_skill_slot` (along
with `skills.*` and `skill_path.*`). New convention bundles authored under
`shipped/conventions/*.org` are immediately usable from any prompt without
runtime allowlist changes. (An earlier note deferred this to TASK-D6Y0Y; that note
is stale as of TASK-EZ0ST [2026-05-28].) Durable invariant.

** macOS notify reports /private/var while temp_dir returns /var
macOS `notify` reports `/private/var/...` while `std::env::temp_dir()` returns
`/var/...`. Any `starts_with` comparison between a watcher event path and a
configured project path must `std::fs::canonicalize` both sides first. The
daemon's watcher does this in `crates/orgasmic-daemon/src/watcher.rs::flush`
(encoded in arch_C87Z9.3); new watcher consumers should follow the same pattern.
Durable invariant.

** claude-acp quarantine LIFTED [2026-06-10] (was: DEFERRED since 2026-05-28)
TASK-TGGAJ closed the silent simulated-mode fallback (merge =6262dc9=, reviewer
verdict no-blocks-ship): real-wire is now the default whenever an executable
`claude` is detectable on PATH; simulation is opt-in only via
`ORGASMIC_DRIVER_SIMULATE=1` (or genuinely absent binary), and the fallback
logs WHICH check failed. The exit condition of the old quarantine entry is
met — claude-acp may be used again. Residual caution: the driver has had far
less live mileage than codex-acp/tmux/rmux; watch the first few dispatches'
capabilities events for `simulated:true` regressions. `cursor-acp` (TASK-GYMSP)
remains a separate implementation either way.

** Workspace MSRV is 1.87; avoid std APIs newer than that
Workspace MSRV is 1.87 (per `Cargo.toml` `workspace.package`). The old 1.78
floor stopped being truthful once current transitive dependencies adopted
edition 2024 / higher `rust-version` metadata (TASK-BTESP verified the 1.78
gate fails on `idna_adapter` and then `clap_builder`; the lockfile metadata now
contains 1.87 dependencies).

New std methods can still compile fine on the default toolchain while breaking
MSRV CI/dev checks. Known offender:
- `std::fs::File::unlock` / `try_lock_exclusive` (stable 1.89) — these also
  shadow the `fs2::FileExt` trait when both are in scope. Call the trait methods
  explicitly: `fs2::FileExt::unlock(&file)` / `fs2::FileExt::try_lock_exclusive(&file)`.

For new code, prefer APIs available on Rust 1.87 unless this gotcha and
`Cargo.toml` are intentionally raised together.

** Never pipe cargo test output — redirect to a file and read it
A test or driver that spawns a subprocess with inherited stdio can leave a
descendant holding the pipe's write end open, so `cargo test … 2>&1 | tail`
hangs forever *after* all tests pass (silence is indistinguishable from "still
compiling"; this SIGKILLed one agent for 25 min on [2026-06-05]). Run
`cargo test … > /tmp/x.log 2>&1` then read the file. When writing tests that
spawn placeholder processes: null stdio + a Drop-guard that kills the whole
process group (reference patterns: `ProcessGroupGuard` in
`crates/orgasmic-drivers/tests/`, `SessionGuard` in `tmux.rs` tests, the
supervisor-test `process_group(0)` reap). The production-side group reap is
`reap_process_group` (TASK-AJZCK.3); don't reintroduce direct-child-only kills.
Durable invariant.

** Warm one shared executable fixture instead of creating scripts per test on macOS
Measured 2026-07-26 on macOS: the first exec of each newly created script took
0.15-0.18 s while its second exec took 0.00 s. Gatekeeper/syspolicy evaluates
that first exec through a serialized system daemon. A full parallel daemon
suite that created many distinct executable fixtures therefore queued the
checks: a trivial two-line script took 3 s, 6 s, and once 63 s before executing,
even though it started instantly in isolation.

Spawn-based tests must reuse the pre-warmed executable in
=crates/orgasmic-daemon/src/test_fixtures.rs=. Put per-test behavior and paths
in argv; when a production-shaped path cannot accept fixture-only argv, hard
link the shared file and keep the variation in adjacent data files. Do not
raise a test deadline or serialize the tests: both retain the per-file cost and
only change where it queues. This is primarily a developer-Mac failure mode;
Linux CI has no Gatekeeper and will likely stay green even when a fresh-script
regression makes the macOS suite fail in parallel. Durable invariant as of
TASK-STWVB.

Two corrections measured 2026-07-26 after that entry was written. First, the
cheapest sidestep is not warming at all: run the script through a signed
interpreter. On one fresh file, =./script= took 270 ms, =/bin/sh script= 5 ms,
and =/bin/bash script= 3 ms. Prefer that for new fixtures — it needs no shared
state, no OnceLock, and no argv multiplexing. Second, the cache key is the
inode, not the path: a hard link to a warmed file execs in 4 ms while a
byte-identical copy pays the full 162 ms.

** A worker's green test count means nothing until you know which tests ran
Seven rmux-dependent tests in =crates/orgasmic-daemon/src/api.rs= used to call
=return= — and therefore PASS — when =probe_rmux_binary().found= was false. The
skip only printed to stderr, which =cargo test= swallowed without =--nocapture=.

Measured 2026-07-26 on one commit, one machine, one variable: with =rmux= on
PATH the daemon suite is =502 passed / 2 failed= in 106 s; with =rmux= hidden
it is =504 passed / 0 failed= in 22 s. Read that second row as what it is: a
reproduced failure *simulation*, produced by hiding =rmux= from PATH by hand. It
is not a measurement taken inside a dispatched worker.

The mechanism this entry originally claimed — "a dispatched worker inherits a
launchd PATH that does not carry =~/.local/bin=" — was measured false on this
machine on 2026-07-28 (TASK-R2HDN): the LaunchAgent plist embeds the PATH
captured at =daemon start=, =ps eww= on the live daemon shows =~/.local/bin= with
an executable =rmux= in it, and =command -v rmux= succeeds inside a dispatched
worker. Do not repeat that diagnosis. Why worker and manager test counts have
historically diverged is still an open question; settle it by capturing the
=required_test_tooling_is_present= result and per-test execution evidence from
inside a real dispatched worker, not by inferring a PATH difference.

The audit footprint was fourteen files across =orgasmic-daemon=,
=orgasmic-drivers=, and =orgasmic-cli=, not just =api.rs=. Twelve contained
tooling- or capability-gated tests; the =watcher.rs= and =manager.rs= grep hits
were production diagnostics rather than test skips. TASK-RRT4T routes the real
guards through one helper and adds one sentinel named
=required_test_tooling_is_present= per affected default-running test binary.
The sentinel fails once, naming each missing tool and how many tests it gates.
Explicit live smokes use =#[ignore]= so default output counts them instead of
letting an opt-in guard pass silently.

The environment-only escape hatch is comma-separated and per tool:
=ORGASMIC_ALLOW_MISSING_TOOLS=claude,cursor-agent=. It is deliberately not a
boolean and has no config/dotenv equivalent. A green run using the opt-out
writes an uncaptured warning to default =cargo test= output naming the missing
tool and gated-test count, so it cannot be mistaken for a fully exercised run.

Manager rule: every test claim for these crates must include either the
=required_test_tooling_is_present= result or the visible
=ORGASMIC_ALLOW_MISSING_TOOLS= warning and counts. Do not substitute
=orgasmic-rmux-run-*= session counts for that: since TASK-Z3093 made release
unconditional, zero net growth no longer distinguishes "the test skipped" from
"the test ran and released its session". Durable invariant as of TASK-RRT4T,
amended by TASK-R2HDN and TASK-69CW6.

There is exactly one fail-closed lane, and it is the sentinel.
=ORGASMIC_REQUIRE_LIVE_RMUX= was **deleted** by TASK-69CW6 rather than wired up:
it was set nowhere in the tree, so an "opt-in gate lane" that never ran looked
like coverage while providing none. Do not reintroduce a third environment
variable to express "this test must really run" — declare the tests in the
binary's sentinel instead (=RMUX_GATED_TESTS= and its siblings), where the count
is visible in default output and adding a gated test is a one-number change.

The two remaining variables mean different things and neither is a substitute
for the other: =ORGASMIC_ALLOW_MISSING_TOOLS= waives a *missing binary*, and it
is the only waiver. A *degraded* acquisition — a compatible binary present but
the SDK or daemon failing to start, which =run_live_session= converts into an
inert =Ready= — is never waivable and fails unconditionally via
=assert_not_degraded= (TASK-R2HDN). A degraded daemon is a defect, not a missing
tool; waiving it is how the false green came back the first time.

=ORGASMIC_ALLOW_BILLED_TESTS= (TASK-MFJZ7) is a third variable and is *not* the
forbidden shape. The rule above bans a fail-closed "this test must really run"
lane, because one that is set nowhere looks like coverage and provides none.
This one runs in the opposite direction: it *arms* tests that are off by default
because executing them spends money, and nothing fails when it is unset — that
unset state is the safe default, not a silent gap. It is also not a waiver:
=ORGASMIC_ALLOW_MISSING_TOOLS= excuses a binary that is absent,
=ORGASMIC_ALLOW_BILLED_TESTS= permits a charge on a host where every binary is
present. Its accounting is the sentinel's, same as everything else: billed tests
are declared in the binary's =BILLED_TESTS= list and =report_billed_tests= names
them in default output, deliberately outside the =ToolRequirement= counts, since
those count tests skipped for missing tooling and these are withheld by policy.

** Test daemon port isolation from checkout-resident production daemon
Tests that spawn isolated test daemons must ensure the daemons don't default to
port 4848 when running in parallel from a checkout where a production daemon is
also running. The test infrastructure (DaemonClient, daemon_lifecycle) falls back
to reading the home's config.yaml if ORGASMIC_DAEMON_URL is not set. When tests
run in parallel from the main checkout (where the real daemon listens on 4848),
any test daemon whose home config has the default port 4848 will collide: if the
subprocess somehow loses the ORGASMIC_DAEMON_URL env var due to environment
leakage in parallel mode, the CLI will silently talk to the main daemon instead
of failing obviously. Fixed in TASK-CJXKM: test boot() now writes the home config
with bind_port: 65533 (an unlikely port) so failed env-var inheritance fails
fast rather than routing to the wrong daemon. Exit condition: either test
daemons use unique ports that don't match the prod daemon (4848), or
ORGASMIC_DAEMON_URL is guaranteed to be inherited in subprocess environments
across all test modes. Durable invariant (parallel isolation).

** cargo test/build does NOT run npm — release build does
Debug and test builds skip `npm --prefix ui run build` and embed a placeholder
UI. Only `cargo build --release` (or `ORGASMIC_EMBED_UI=1`) triggers the npm
build and embeds the real dist. If npm fails in a release build, the error names
npm/node as the cause and the one-line fix. Durable invariant; see build.rs.

** Format
Use one heading per repeated operational pattern. Each gotcha should include
evidence, the likely cause, an exit condition, and the backlog task expected to
make the gotcha obsolete. Entries marked "Durable invariant" are permanent
engineering constraints rather than transient patterns awaiting a fix.

** Overwriting an in-use codesigned macOS binary in place gets it silently SIGKILLed
Replacing the bytes of a codesigned binary AT THE SAME PATH/INODE while any
process still has it open (e.g. swapping `~/.orgasmic/runtimes/<v>/bin/orgasmic`
in place to test a fix against the live LaunchAgent-managed daemon) causes ALL
subsequent execs of that exact path to be silently killed by the kernel
(exit 137, zero stdout/stderr) even though `codesign --verify` reports the file
"valid on disk" and the bytes match a known-good copy exactly. Symptom looks
like a sandbox/tool problem, not a codesign one. Fix: never overwrite in place;
`rm` the file first and then write the replacement (fresh inode), e.g.
`rm -f "$BIN" && cp "$SRC" "$BIN" && chmod +x "$BIN"`. Copying the identical
bytes to a different path also works fine, which is the tell that it is a
path/inode-identity issue, not a signature or content problem. Observed
2026-07-06 verifying TASK-VXXQC's launchd stop-agent fix. Durable invariant.

** rmux workers intentionally do not auto-spawn babysitters
rmux worker templates are interactive PTY smoke/proof surfaces, not the default
production dispatch lane. Auto-spawning =babysitter_worker= there would require a
second rmux-backed Claude pane, doubling scarce interactive PTY/runtime capacity
and adding an observer whose prompt is tuned for implementer sessions rather than
all rmux roles. Operators should not expect companion babysitters for
=*-rmux.org= workers unless a future task designs a dedicated rmux babysitter
policy and template. Durable policy as of TASK-GD0W1.

** Session JSONL is transcript-shaped, and lifecycle lives at both ends
On a real 198-file board, 2.239 GiB of session JSONL was almost entirely
=text_chunk= driver events; only a few hundred lines across all files carried
lifecycle meaning. Two traps follow.

=SessionWriter::append= does =flush= + =sync_all= on every line, so building a
multi-megabyte fixture through it takes tens of seconds. Write the JSONL
directly with =serde_json::to_string(&SessionEnvelope { .. })= instead.

Lifecycle truth clusters at both ends of a file: =acquire=, =run_meta=,
=native_runtime= and the first =ready= sit within the first tens of KiB
(observed worst case 56 KiB), and =release=, the terminal driver event, and
appended =recovery_origin= links sit within the last few KiB (observed worst
case 13 KiB). Everything between is =reattach= markers and transcript, which no
classifier consumes. That is why =scan_session_lifecycle= can answer recovery
questions from a bounded prefix/tail window — and why any *new* mid-file
lifecycle event would be invisible to run enumeration unless
=SessionScanBudget= or the retention rule in =line_is_lifecycle_relevant=
changes with it. Durable invariant as of TASK-KWSTJ.

** Re-signing the installed runtime destroys its macOS permissions
The installed binary carries an identity-based designated requirement:
=identifier "com.theaspirational.orgasmic" and certificate root = H"a705..."=.
A rebuilt binary re-signed with the *same* =orgasmic dev codesign= identity
satisfies it, so replacing the file at a fixed path is safe. Signing ad-hoc
(=codesign --force --sign -=) replaces the certificate root, the requirement
stops matching, and every TCC grant for that binary dies.

Restoring the original bytes does NOT bring the permission back — verified
2026-07-25 with a byte-identical restore (same SHA-256) that still could not
read =~/Documents=. Recovery took two separate System Settings approvals, and
in the end only Full Disk Access worked where the Files and Folders grant did
not; that asymmetry is unexplained and worth confirming before relying on it.

The daemon does not fail loudly when this happens. It hangs pre-bind at 0% CPU
with no project files open, launchd respawns replacements that refuse on the
instance lock, and =orgasmic status= just hangs. Symptom looks like a daemon
bug, not a permissions one.

Never test a source build by swapping the installed runtime. Run it against a
throwaway =ORGASMIC_HOME= on a non-default port instead; an APFS =cp -c= clone
of a real project's =.orgasmic/tmp/sessions= gives production-shaped data with
copy-on-write isolation, so writes cannot reach the originals. Durable
invariant as of TASK-9P810.

** The executed path is what macOS grants permission to, not the path you typed
=env::current_exe()= on macOS returns the *invocation* path, so a LaunchAgent
written by =daemon start= names whatever the operator ran. That is not what TCC
records. The kernel resolves symlinks at =exec=, so a plist naming
=~/.orgasmic/bin/orgasmic= while that entry was a link produced grants against
=~/.orgasmic/runtimes/<version>/bin/orgasmic=. =codesign -d= shows the same
resolution: pass it the link and its =Executable== header prints the versioned
path. Every release was therefore a new TCC client — 16 granted paths and 37
rows on one machine between 2026-06-18 and 2026-07-25 — and retention then
pruned the very directories those grants pointed at.

Path and identity are two independent halves. Holding the path still is useless
if the signature changes, and holding the identity still is useless if the path
moves. TASK-9P810 pins both: =bin/orgasmic= is a real file replaced by fresh
inode, and an install whose designated requirement differs from the incumbent's
is refused rather than published.

=codesign -d -r-= prints the requirement to *stdout* and the =Executable==
header to stderr — reading the merged stream misleads. Worse, an ad-hoc
signature has no explicit requirement, so the implied one is printed *commented
out*:

: designated => identifier "com.theaspirational.orgasmic" and certificate root = H"a705..."
: # designated => cdhash H"b35e..." or cdhash H"45d6..."

A parser that misses the =#= form reads an ad-hoc binary as "identity unknown"
and waves it through — precisely the case the guard exists to catch. Resolve
=codesign= as =/usr/bin/codesign=, never through PATH: this decides whether a
binary keeps the operator's grants, and anything earlier on PATH could answer
for it. Durable invariant as of TASK-9P810.

** Tests that set PATH break every other test in the binary
=ScopedEnv= in =path_env= mutates the *process* environment, which all test
threads share. Setting PATH to a bare tempdir made any concurrently running test
that spawns a PATH-resolved tool fail with a bare =NotFound= and no hint of the
cause: =manager::tests::local_dispatch_rollback_keeps_branch_when_worktree_validation_fails=
(spawns =git=) failed roughly three runs in four, and passed alone every time.
Keep the system dirs on any test PATH — =format!("{local_bin}:/usr/bin:/bin")= —
and prefer absolute paths for system tools in production code. Fixed 2026-07-25
under TASK-9P810.

** A successful reindex does not prove the daemon has permission
Measured 2026-07-25 during the TASK-9P810 migration. Immediately after the
executed path moved to =~/.orgasmic/bin/orgasmic=, every project scan timed out
at boot and =status= reported =projects: 0=. Running =orgasmic reindex= then
succeeded in 1.3 s and loaded all five projects with zero parse errors — which
reads as proof that permissions are fine. It is not.

Restarting with the grant actually in place produced zero scan timeouts and
=projects: 5= directly from boot. The boot warning naming Files-and-Folders
access was right; the reindex was the red herring. Do not treat a later
successful scan as evidence against a permission problem: compare a *boot* with
and without the grant, because the boot scan is the bounded one that gives up.

Corollary for TASK-9P810 migrations: the first install that moves the executed
path to the stable location does cost exactly one grant, as the installer says.
The difference from the 2026-07-25 outage is that the daemon now stays bound and
answerable while it is missing (TASK-KKGKM), so the operator can see the reason
instead of finding a wedged runtime. Durable invariant as of 0.0.15-dev.1.

** Harness status commands disagree about stream and exit code
Measured 2026-07-25 while writing the TASK-TJKFC readiness probes, against the
three harnesses installed here. Nothing about their answers is uniform:

- =claude auth status= writes JSON to stdout and exits *1* when logged out,
  0 when logged in.
- =codex login status= writes its answer to *stderr*, leaves stdout empty, and
  exits 0 in both states.
- =cursor-agent status= writes prose to stdout and exits 0 in both states.

Both defaults a reader reaches for are wrong. Reading only stdout classified a
logged-in codex as "no answer"; gating on a zero exit classified a logged-out
claude the same way - the single case the probe exists to catch. Read both
streams, and let the *recognisability of the answer* decide whether a verdict
was reached, never the exit status.

Caught by =installed_harnesses_answer_their_own_readiness_probe=, which asserts
against the real binaries precisely because a unit test supplies the answer it
then classifies and so can never find this. To capture a logged-out answer
without logging the operator out, point =HOME= (and =CODEX_HOME=) at an empty
directory.

** Asking a harness to prove it can work costs real money
Measured 2026-07-25 on claude 2.1.220. The only way to make the harness itself
rule on a credential is to submit a turn, and a one-character prompt cost
$0.0994 and 24.5k tokens - the request writes the system prompt, tools and
skills to cache before any answer comes back. Cancelling early does not refund
it: the failure verdict and the outbound request are simultaneous (0.326 s vs
0.390 s), so no deadline is short enough to catch the former and miss the
latter.

A check that silently bills a tenth of a dollar on every dispatch is not a check
worth having. Interrogate the resolved credential locally instead ($0, 0.28 s)
and return an inconclusive verdict where only a billed turn could reach a real
one. The corollary is worth stating where operators read it: a preflight that
answers "ready" claims less than it sounds like - it proves a credential exists,
not that the provider accepts it.

The test that does submit a turn is now gated in code, so *stop passing =--skip=*.
=legacy_drivers_and_explicit_pairs_emit_equivalent_start_events=
spends real money, and until TASK-MFJZ7 the only thing preventing that was every
brief remembering
=-- --skip legacy_drivers_and_explicit_pairs_emit_equivalent_start_events=. It
did not survive: on 2026-07-28 the TASK-QRB8S worker, whose brief carried the
constraint in bold, ran the bare suite twice anyway. It happened not to cost
anything because the real binary rejected the session id before the turn - luck,
not a control.

The current instruction is: *run =cargo test -p orgasmic-drivers= with no extra
flags.* The test carries two locks. =#[ignore]= keeps it out of a bare run, which then prints
=ignored, billed: submits a real provider turn= - so the skip is visible instead
of tribal. =ORGASMIC_ALLOW_BILLED_TESTS=1= is the second, and it exists because
=--include-ignored= is the flag people reach for to run "the slow ones" and must
not silently also mean "and charge me". Opt in deliberately with both:

: ORGASMIC_ALLOW_BILLED_TESTS=1 cargo test -p orgasmic-drivers --test driver_modes \
:   legacy_drivers_and_explicit_pairs_emit_equivalent_start_events -- --ignored

Audited at the same time, for the whole repo, "does any other test spawn a real
harness and submit a turn?" - the answer is no other *ungated* one.
=real_claude_stream_json_bridge_reports_auth_error= runs by default and does
spawn real =claude=, but it names =api_key_env= with a deliberately invalid key,
and a configured =api_key_env= selects =--bare= deterministically
(=resolve_credentials= rule 2, pinned by =a configured api_key_env selects the
bare path=), where the key is the only credential read. Every request is
rejected at authentication before token accounting. =real_claude_input_ready_smoke=
spawns the real Claude TUI but sends no prompt, and is =#[ignore]=d. The
=live_rmux_*= family runs =sh=/=sleep= under rmux and reaches no provider at all.
The billing-capable daemon tests
(=dispatch_endpoint_routes_cursor_agent_through_supervisor_and_emits_run_created=,
=dispatch_endpoint_routes_acp_stdio_codex_through_supervisor=,
=dispatch_grace_path_writes_artifacts_without_terminal_session_marker=,
=real_cursor_agent_stream_json_bridge_emits_events_and_releases=) are all
=#[ignore]=d, so they are default-safe; their ignore reasons say "requires X
installed" rather than "this bills", which is a wording gap, not a control gap.

** `orgasmic node` cannot write gotchas.org
There is no gotchas node layer: =NodeLayer= covers decision, architecture,
glossary, project, task, goal and handoff only, and =NodeLayer::for_id= falls
back to *glossary* for any unrecognised id. So
=orgasmic node body append gotchas ...= fails with "glossary file not found" -
an error that names the wrong file and reads like a missing artifact rather than
an unsupported target. This file is maintained as a source file in dispatch
WRITE_SCOPE instead, which is why it is edited directly.

** A project can be registered, listed, and still absent from the index
Observed 2026-07-25 (TASK-MRJRK). Ten minutes after a daemon restart, every
=orgasmic node= route answered =404 {"error":"project orgasmic"}= for two of the
five registered projects (orgasmic and ddd), while =orgasmic project list= kept
showing all five. =orgasmic reindex= fixed it immediately.

The trap is the error message. =select_project= looks up =snap.projects[id]= and
reports a miss as ="project <id>"=, which reads as "no such project" - so the
obvious next move is to check registration, which is fine, and the actual
problem (the id is not in the index snapshot) is never suggested. Worse, the
=404= comes from the CLI's *base_version GET*, before any edit, so it looks like
a read failure on a node rather than a stale index.

When a node route 404s on a project you can see in =project list=, reindex
before believing anything is misconfigured.

What is NOT established, so do not repeat it as fact: =status= does not read
board registration - =projects= is =snap.projects.len()=, the same map the
lookup missed. So =status= should have reported the smaller count during the
window; it was simply never checked at that moment. Whether the two projects
were dropped after boot, never loaded, or keyed differently is open.

** Manager commands run from a dispatch worktree report stale state as fact
A shell's cwd persists across commands, and a dispatch worktree carries its own
frozen =.orgasmic/= snapshot from the commit it was created at. Run
=orgasmic manager ...=, =task update=, or =tx record= from inside one and they
resolve *that* snapshot, failing plausibly rather than loudly. Measured
2026-07-28: =manager dispatch-status= returned **empty** with three healthy
workers running and was briefly read as "all three died";
=dispatch-close --started-tx tx-...-3305= failed with "no manager.dispatch_started
tx in the tx log" because the snapshot predated that tx; and
=task update --property BLOCKED_BY=...= returned a tx id and silently did not
apply. Meanwhile =git worktree list= (which works from anywhere in a repo) and
=rmux ls= both showed everything healthy.

Writes routed through the daemon with =--project orgasmic= - =task create=,
=node body set= - are safe and did land correctly. Anything that reads local
