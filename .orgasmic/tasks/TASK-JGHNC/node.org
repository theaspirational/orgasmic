From TASK-K4G1D (2026-07-29), measured, not inferred: inside an orgasmic
worker, `tmux` on PATH is the rmux shim, and a `-L`-pinned call through the
shim creates an RMUX server (the socket lands in /private/tmp/rmux-501/, and
the real tmux cannot connect to it). The 0RCRY owned-server mechanism does not
protect against this — the isolation holds, but the multiplexer is the wrong
one.

Consequence: seven tmux-gated daemon tests gate on `tmux_on_path()`, which
accepts the shim, so IN EVERY WORKER-RUN SUITE they have been measuring rmux
while reporting tmux:

  boot_rehydration_reattaches_tmux_session,
  explicit_reattach_tmux_session_endpoint,
  pending_plan_reattach_existing_session,
  boot_reattach_respawns_when_session_gone,
  failed_terminal_with_live_tmux_session_is_not_resurrected,
  production_resume_native_fork_uses_pinned_claude_not_path_shim,
  two_recovery_chain_second_resume_uses_first_fork_session_id

(names as listed in K4G1D's report §6.2; verify against HEAD before acting).

K4G1D added the strict availability rule (`tmux_mode_availability_for` — a
shimmed tmux counts as ABSENT, loudly) but deliberately did NOT widen
`tmux_on_path()`: regating seven tests is a decision, not a fix — it would
newly fail the tmux sentinel in every worker environment, and it partly
reframes the worker-vs-manager failure comparisons recorded on TASK-STWVB.

=== Ask

1. Decide: should these seven tests demand REAL tmux (strict rule), or is
   testing-through-the-shim acceptable for some of them (in which case they
   should SAY they ran rmux)? Record the decision and its reason.
2. Apply it: either regate on the strict rule (accepting that worker-run
   suites will report tmux NOT RUN via the honesty manifest — that is the
   truth), or split tests into genuinely-mode-agnostic (rename/parameterize per
   K4G1D's pattern) vs really-tmux-specific (strict gate).
3. Re-examine any STWVB comparison that relied on "the worker ran these under
   tmux" — it ran them under rmux.
