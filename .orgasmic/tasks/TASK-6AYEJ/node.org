* DONE TASK-6AYEJ manager dispatch-close is unreachable after a worker finalize, so success-path cleanup never runs :dispatch:lifecycle:defect:

The worker's own success signal closes the dispatch record, so the manager's
`dispatch-close` can never run on a successful dispatch. Found while trying to
close TASK-D0GA3 after merging it.

REPRODUCED, not inferred:
- TASK-D0GA3 merged at 0daa77c. `orgasmic manager dispatch-close --task
  TASK-D0GA3 --status done --merge-sha 0daa77c ... --worktree-remove
  --branch-delete` fails with "no open manager.dispatch_started tx for
  TASK-D0GA3".
- `orgasmic manager dispatch-status` prints nothing — zero open dispatches —
  while `git worktree list` shows 17 live dispatch worktrees and their branches.

MECHANISM, read from code: scan_open_dispatches (crates/orgasmic-cli/src/manager.rs:3316)
pairs each manager.dispatch_started with the first terminal tx it sees, and
manager.rs:3338-3341 counts `implementer.done` / `reviewer.done` /
`architector.done` / `manager.dispatch_aborted` as terminal. Per dec_3M7M0 the
worker's `orgasmic dispatch finalize --commit` is the SOLE success signal and it
emits `implementer.done` itself. So the dispatch is closed by the worker before
the manager has even read the report.

The tx history shows the switchover cleanly. Every terminal tx up to 2026-07-23
carries ACTOR theaspirational@users.noreply.github.com (the manager, via
dispatch-close). Every one from 2026-07-26 carries ACTOR agent.implementer or
agent.reviewer (the worker, via finalize). Not one manager-recorded close since.

WHAT IS LOST, per successful dispatch:
1. Worktree and branch cleanup never runs. cleanup_dispatch — and with it the
   whole salvage path just hardened by TASK-2BPWM and TASK-D0GA3 — is dead on
   the success path. 17 stale worktrees is the accumulated evidence.
2. MERGE_SHA in the close tx is the WORKER's commit, not the manager's merge.
   TASK-D0GA3's implementer.done (tx-20260726-orgasmic-2967) records
   SHA = MERGE_SHA = e7837f1; the actual merge is 0daa77c. Any later audit that
   trusts MERGE_SHA is looking at a commit that was never on main as such.
3. REVIEWED_DIFF, worker-session, tokens and wall are never recorded, because
   only dispatch-close accepts them.
4. The manager's verdict is not the closing record. The worker's self-report is.
   That inverts the "treat worker summaries as claims" rule at the tx layer.

NOT AFFECTED, so scope this correctly: the salvage machinery still runs on the
failure paths, which is where it matters most — cleanup_created_resources
(dispatch rollback), the daemon POST cleanup endpoint, and dispatch-close on an
orphan dispatch that never finalized. TASK-2BPWM and TASK-D0GA3 are not wasted
work.

DIRECTION, to be argued rather than assumed:
- The likely fix is that `finalize` should record worker completion WITHOUT
  closing the dispatch — a distinct tx type (implementer.reported?) that
  scan_open_dispatches does not treat as terminal — leaving implementer.done to
  the manager. That preserves dec_3M7M0's "finalize is the sole success signal"
  for the WATCHER while restoring the manager's close.
- Whatever shape is chosen, closing must stay idempotent and must not strand a
  dispatch open forever when the manager dies mid-integration.
- Backfill is out of scope, but the fix must not choke on the ~10 dispatches
  already closed this way.

Acceptance:
- after a worker runs `dispatch finalize --commit`, `manager dispatch-status`
  still lists the dispatch as open
- `manager dispatch-close --status done --merge-sha <real merge>` succeeds and
  records the manager's merge sha, and removes the worktree and branch
- a dispatch that is never finalized still closes via dispatch-close, unchanged
- double-close is a clean no-op, not an error

MANAGER FINDINGS:

   cheaper than the brief predicted, which is true, but the reason matters more
   than the count: the daemon keys completion off the finalize TOMBSTONE
   (requires_worker_finalize / finalized_by_worker), never the tx type. That is

   architecture notes rather than leaving in a dispatch report.

   run on main has no manager.dispatch_started, so a report-only tx leaves

   habitual sequence and will surprise the first manager who hits it.
