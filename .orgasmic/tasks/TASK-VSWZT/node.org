could clear it.

THE DEAD END

- `POST /api/runs/:id/release` returned 404 `{"error":"active run <id>"}` — even
  though the same run was present in `GET /runs` .live. Both the snapshot lookup
  (api.rs:6173) and `SupervisorError::RunNotFound` (api.rs:6197) return that same
  string, and `.live` is fed from `supervisor.snapshot()` (api.rs:7651), so the
  run was in the snapshot while `release_with_finalization` could not find it.
  Those two views of the supervisor disagreed.
- `orgasmic manager lease-release` refuses while a live run holds the lease.
- `orgasmic run recover` offers only reattach_tmux / resume_native_fork /
  start_recovery_run. The rescue-policy convention lists *abandon* as one of four
  manager judgments, but no verb implements it.
- `orgasmic manager dispatch-close` had already run; the dispatch record was
  closed and the run stayed live regardless.

WHY IT IS NOT COSMETIC

`refuse_if_live_runs` (crates/orgasmic-cli/src/update.rs:436-462) reads exactly
`GET /runs` .live and refuses the runtime update for any entry. One phantom run
therefore blocks `orgasmic update` and any publish behind that fence, with no
documented way out. The only route that worked was a full daemon restart.

WHY THE SESSION NEVER CLOSED

The session JSONL ends at seq 1657 `run_complete` ("worker finalize for
TASK-STWVB") and seq 1658 fatal `driver_error` ("claude exited with status exit
status: 143"), with no `Lifecycle::Release`. The supervisor kept its entry; the
tombstone was never written. On the next boot the classifier read the same file
and correctly returned terminal_noop ("session ended with terminal driver
event") via `session_driver_terminal_event` (api.rs:9104), so the durable
evidence was sufficient all along — only the live supervisor disagreed.

Note this is the second wrong answer recorded about this same run. The prior
handoff asserted it had been released and that `run list` reported 0 live; it had
not been, and did not.

WORK

1. Reconcile the two supervisor views, or make `POST /runs/:id/release` able to
   clear anything that `GET /runs` .live reports. A run the fence refuses to
   ignore must be releasable by the surface documented to release it.
2. Implement abandon as a first-class manager verb so the fourth branch of
   rescue-policy is executable, not just describable.
3. Write the release tombstone when a driver reports a fatal terminal event.
   `run_complete` followed by a fatal `driver_error` should end the run rather
   than leave it working; the boot classifier already treats that pair as
   terminal, so the two paths disagree about the same evidence.
4. Consider having `refuse_if_live_runs` name the escape hatch in its error text.
   It currently says "Close them or use the existing force path deliberately"
   without saying how, which is what sent this session looking for a verb that
   does not exist.

Acceptance:
- a run reported in `GET /runs` .live can always be cleared without restarting
  the daemon
- a worker whose harness dies after run_complete leaves a release tombstone
- `orgasmic run list` .live and the release path never disagree about whether a
  run exists
