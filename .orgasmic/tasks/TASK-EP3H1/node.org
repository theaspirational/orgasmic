* DONE TASK-EP3H1 dispatch-close tears under load: tx appended, lifecycle stranded, and a timed-out request can succeed invisibly :cli:daemon:hardening:
:PROPERTIES:
:ID: TASK-EP3H1
:PRIORITY: P1
:END:

Measured 2026-07-29 at load average ~190 (a worker deliberately inducing load).
`orgasmic manager dispatch-close --task TASK-G7E4R --status done` produced:

  warning: close tx appended but lifecycle update failed: daemon request
  failed ... is the daemon reachable?
  closed: TASK-G7E4R implementer.done tx=tx-20260728-orgasmic-3500

State afterwards: close tx recorded, dispatch record closed, task stranded at
`in_review`. The warning is loud (good — this is not a silent tear), but the
operator is left to repair the lifecycle by hand.

The repair then hit the second half of the defect: a follow-up
`task update --state done` returned `"changed": {}` with an EMPTY tx_id —
because the "failed" lifecycle request had actually landed server-side after
the client gave up. Client timeout is not server failure. Two consequences:

1. `dispatch-close` is not atomic across its two writes (tx append +
   lifecycle update) and does not retry or reconcile the second on failure.
2. A timed-out request can succeed invisibly, so naive retry logic can
   double-apply or mis-read state. The `{"changed":{}, "tx_id":""}` no-op
   response was correct here, but nothing documents that contract.

=== Ask

1. Make dispatch-close's task-state transition part of the same daemon
   operation as the close tx (single request, single commit), or make the CLI
   reconcile on startup of the next manager command ("close tx tx-N exists but
   task is in_review -> finish the transition").
2. Idempotency: closes and state updates should carry the started-tx (they
   already do) and the daemon should treat a re-submitted close/transition for
   an already-closed dispatch as a clean no-op with a response that SAYS it was
   already applied, distinguishable from "nothing to do".
3. While in the file: the CLI's timeout error text "is the daemon reachable?"
   misdiagnoses scheduler starvation as daemon death (three occurrences on
   2026-07-29, all with the daemon healthy and answering raw HTTP in 0.4s).
   Say "request timed out after Ns; the daemon may be healthy but the system
   is under load" and name the load if cheaply readable.

=== Acceptance

- A close whose lifecycle leg is injected to fail leaves a state the NEXT
  manager command repairs automatically, proven by test.
- A re-submitted close is a labelled no-op, proven by test.
- Injection per the TCTTD standard; verify artifact `git apply`-clean.
