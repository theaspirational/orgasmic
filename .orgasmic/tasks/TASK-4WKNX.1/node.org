** Description

Fix round for the one BLOCK SHIP on TASK-4WKNX's review, confirmed by the manager
against the code. The full mechanism is on the parent under "Review round 1 —
REJECT (confirmed)"; read it there rather than re-deriving it.

In one line: ~close_done_request~ pushes caller ~--property~ entries before it
pushes its own typed keys, and ~parse_close_property~ accepts any uppercase key,
so a bypass-audit key can be forged or contradicted by the caller it is meant to
audit.

** The class, not the instance

The reviewer found it on ~FIX_ROUND_FINAL~. The manager found the same hole on
~NO_REVIEW_REQUIRED~ (manager.rs:4720), which is PRE-EXISTING — 4WKNX did not
introduce it, it introduced a second instance of it. ~VERDICT~ is the only key of
this class currently fenced (TASK-YN5FJ.1 RULING 3), and it is fenced by a
hand-written one-off ~if let (Some, Some)~ pair.

Three keys, two unfenced, one bespoke fence: the fix is a rule about
manager-owned tx keys, not a third copy of the same ~if~.

  ~--property~. Covers at minimum ~FIX_ROUND_FINAL~, ~NO_REVIEW_REQUIRED~ and

=== The finding, confirmed

=MANAGER_OWNED_CLOSE_PROPERTIES= is a three-key denylist, not the class rule the
task asked for. =close_done_request= pushes caller properties (=:4751=) and THEN
appends manager-derived structural keys — =CLOSED_TX= (=:4763=),
=push_lifecycle_extra=, =push_cleanup_extra=, =GOAL_ID= — none of which are in
the table. With =extra()= first-wins, the caller's forged value is the one every
reader sees.

=== Why this is worse than the report says: these keys are CONSUMED

The report frames the risk as forged audit data. Manager checked the consumers
and it is not only audit:

- =close_matching_dispatch= (=:7033=) selects WHICH open dispatch record a close
  terminates by matching =CLOSED_TX=. A forged value marks the WRONG generation
  closed and leaves the real one open.
- =close_tx_ran_cleanup= (=:7059=) sets =record.cleanup_already_run= from
  =CLEANUP_STATUS=. A forged =ok= makes a close that never ran cleanup look like
  it did — and cleanup is the path that SALVAGES uncommitted worker output before
  removing a worktree. This project has already destroyed a worker's work once
  (TASK-2BPWM, TASK-D0GA3).
- =cleanup_status_reports_failure= (=:7158=) scans the ledger for cleanup
  failures; a forged =ok= hides a real one from that report.

So the vector is state corruption and suppressed salvage, not a false record.
BLOCK SHIP stands and the severity is right.

=== This is MY scoping failure, not the implementer's

The round-2 brief said "a rule about manager-owned close-tx keys, not a third
copy of the same =if=" — and then named exactly three keys, in a table, in the
brief's own markdown. The implementer built precisely what was described. The
table it produced is good work: the =const fn reserved(...)= default and the
verbatim =VERDICT= text are both right and both survive into round 3. What was
missing was in the specification.

=== The structural answer, found while verifying

*Every tx-extra reader in the workspace is first-wins.* Verified:
=manager.rs:7101=, =crates/orgasmic-daemon/src/index.rs:2008=, and the assertion
helpers — all =.iter().find(...)=. No last-wins reader exists.

So pushing the manager's own extras BEFORE the caller's =--property= loop makes
every forged duplicate INERT for consumption, for every manager-owned key
including ones nobody has written yet, with no list to maintain and no drift to
detect. That is the property the acceptance actually wants and it costs a
reorder.

It is not sufficient alone, and saying why matters: an inert duplicate still sits
in the ledger where a human reads it, and for the three deliberate bypass keys a
silent no-op is the wrong answer — forging =FIX_ROUND_FINAL= should be a loud
refusal, not a shrug. Hence two layers in round 3.
