** Description

Second review round on the compact run catalog. Reviewer verdict NEEDS FIXES —
five HIGH findings block ship, two MEDIUM remain actionable
(=reviewer.done= tx =tx-20260802-orgasmic-4111=; findings
=tx-4096=..=tx-4102=).

The unifying defect, and the thing to fix rather than patch around: DELETION
AUTHORITY IS DERIVED RATHER THAN REPROVEN. The catalog documents itself as
disposable derived state, and compaction then treats its cached semantics as
permission to destroy session evidence.

*1. HIGH, BLOCKS SHIP* — =run_catalog.rs:1523-1547=, =run_history.rs:587-602=.
=classify_history_line= takes the FIRST byte occurrence of =type= anywhere in
the first 64 KiB instead of proving =event.type=. A valid pane semantic event
whose nested payload contains =type=text_chunk= BEFORE its outer type is
classified =rendered_tui=, and =build_compacted= then drops the whole record.
The regression at =run_catalog.rs:2636-2689= only covers minimal events whose
first =type= happens to be the outer discriminator. Impact: explicit
maintenance destroys tool and result evidence.
FIX: identify the envelope and outer discriminator with a bounded STRUCTURAL
streaming parser; if it cannot be proven, classify unparsed and FAIL CLOSED.
Add nested-type collision regressions and assert byte-for-byte preservation.

*2. HIGH, BLOCKS SHIP* — =run_history.rs:379-436,513-531,683-755=.
=apply_compaction= mutates a session file, appends the result in memory, and
IGNORES every per-file =write_manifest= failure. A crash or ENOSPC after the
live rename but before a durable manifest update leaves the archived original
and the rewritten live file absent from =manifest.results=, and rollback
iterates only =results= — so it cannot restore them. Manifest and live-directory
renames are not followed by mandatory directory fsyncs.
FIX: a durable per-file state machine, propagated journal failures, parent
directory fsyncs, and a rollback reconstructable from PLANNED archive identities
even when the final result record is missing. Fault-inject after archive, stage,
rename, and result-journal boundaries.

*3. HIGH, BLOCKS SHIP* — =run_history.rs:465-531,574-620,683-755=,
=writer.rs:748,790-845,938-943=. Forward compaction does ONE pre-read
fingerprint check, compares only reclaimable record and byte COUNTS, never
compares the planned =reclaimable_sha256=, builds from one read and archives
from a SECOND read. There is no maintenance lock and no session-writer fence.
An append landing after the check is omitted from the replacement, and the
rename leaves the cached append handle writing to an ORPHANED INODE. Rollback
then overwrites the current path without proving it still holds the compacted
generation.
FIX: serialize maintenance per project, fence or close the writer handle,
compact and archive ONE proven byte generation, compare the planned digest,
revalidate immediately before commit, and refuse rollback unless the destination
matches the recorded post-compaction fingerprint and digest.

*4. HIGH, BLOCKS SHIP* — =run_catalog.rs:608-666,787-820,1039-1060=,
=run_history.rs:208-245=. Snapshot admission checks JSON shape, version, session
path and file fingerprint — then accepts =lifecycle=, =terminal=, =driver= and
=transport= VERBATIM. A steady-state refresh treats the unchanged fingerprint as
a cache hit and never rederives those semantics, and =plan_compaction= trusts
=entry.is_terminal= and =entry.transport= as deletion authority. So a valid-JSON
but semantically corrupt snapshot can present a LIVE or ACP file as terminal
rmux data and authorize its deletion. Note =semantically_corrupt_snapshot_entries_are_refused=
(=run_catalog.rs:2115-2202=) tests PATH and FINGERPRINT corruption, not semantic
field corruption — the name overclaims what it proves.
FIX: never use the derived catalog as sole deletion authority. Rederive terminal
state and transport from the CURRENT session generation during planning and
apply, or cryptographically bind every semantic field to verified source bytes,
and fail closed.

*5. HIGH, unmet acceptance, BLOCKS SHIP* — =session.rs:175-200,574-595,1595-1660=.
=SessionWriter= has no transport context and ACCEPTS =DriverEvent::TextChunk=
from a pane transport, retaining a bounded head plus digest. The lock test
injects a 4 MiB repaint but asserts only that the file grows by LESS THAN 8 KiB.
So one repaint is bounded — not forbidden — and repeated redraw events still
grow the JSONL linearly, contrary to the zero-persisted-redraw acceptance
criterion and to the test comments themselves.
FIX: reject pane =text_chunk= at a transport-aware writer/supervisor boundary,
and make the regression assert ZERO =text_chunk= envelopes and no
repaint-derived growth. A real tmux/rmux production-path test is still needed.

*6. MEDIUM* — =run_catalog.rs:787-833,883-915=. Rebuild and authority updates
capture and compare a per-path invalidation counter, but STALE paths capture no
generation and commit with an unconditional remove — and the commit deletes the
counter too. A refresh that observed a path absent can commit after another
refresh or the writer recreated it, evict the newer entry and RESET the
generation: a lost-update/ABA window. The stress test at
=run_catalog.rs:2415-2474= hides it behind a final quiet refresh.
FIX: plan stale eviction with a monotonic generation and remove only if it is
unchanged and no newer entry exists. Do not delete the path generation.

*7. MEDIUM* — =run_catalog.rs:1097-1141=. A tombstone revives when the current
directory has the recorded device and inode. Inode numbers ARE reusable, so an
unrelated checkout can eventually satisfy it; conversely a legitimate returned
volume with renumbered inodes never revives, and a tombstone that never had an
identity can never recover. The recreated-path test assumes a fresh directory
gets a different inode, which is an assumption about the filesystem rather than
a guarantee.
FIX: either make tombstones truly terminal, or model temporary unavailability as
its own state and verify continuity with immutable worktree/dispatch authority
rather than dev+inode alone.

** Open questions the reviewer raised, which need a DECISION before coding

- Is =run-catalog.json= trusted authority or disposable derived state? The
  module docs say derived and rebuildable; compaction treats cached semantics as
  deletion authority. These cannot both be true.
- Should a pruned worktree ever revive? If yes, the design needs a stronger
  persistent identity and a distinct unavailable state. If no, the same-inode
  revival path should be removed outright.
- What component owns maintenance exclusion against the writer and against
  concurrent compact/rollback requests? No such owner exists on the reviewed
  route.

Answer these in the task or in =decisions.org= before writing code — findings 3,
4 and 7 all resolve differently depending on the answers.
