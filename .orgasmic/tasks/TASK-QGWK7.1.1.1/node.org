** F-1 — MEDIUM — a failed record persist is UNRECOVERABLE, and re-running the close refuses
=crates/orgasmic-core/src/paths.rs:317= (tmp unlink) ->
=crates/orgasmic-cli/src/manager.rs:5636=. MANAGER-VERIFIED IN SOURCE.

=promote_validated_dispatch_attempt= unlinks the tmp artifacts as soon as the
COPIES succeed — before =commit_promoted_dispatch_record= is ever called. So a
failed commit leaves: record on disk untracked, tmp gone, =CLEANUP_ERROR= set,
status =partial=. There is then no way back into git:
=promote_dispatch_artifacts_in_place= bails on =last_path missing= (tmp is gone);
re-running =dispatch-close= hits =CloseTarget::AlreadyClosed= and returns a no-op
by design (=manager.rs:960-983=, verified); and there is no =--repersist= verb.

*The one path where the guarantee fails is the one path with no repair*, and its
only signal is a =warning:= line. That is the regression back to "manager habit"
that F-1 of the parent existed to remove, narrowed to the error path.

Worse, the rollback is unguarded: =manager.rs:5689= runs =git restore --staged=
behind =let _ =, so if the index lock is held at THAT moment the restore fails
silently and the record is left STAGED — which is M-0's symptom back verbatim.

*Fix:* make persistence idempotent and re-entrant. =commit_promoted_dispatch_record=
already works from =dest_dir= alone; only its CALLER is gated on tmp. Route the
already-closed no-op into it when the recorded =CLEANUP_STATUS= was non-ok.
Minimum viable: stop discarding the =git restore= result.

** F-2 — MEDIUM — the =update-ref= CAS can pass on the WRONG BRANCH
=crates/orgasmic-cli/src/manager.rs:5800-5812=.

The CAS compares OIDs, not ref identity. Reviewer measured: with a sibling
branch at the same OID, =git branch other && git checkout other= between the
=rev-parse= and the =update-ref= makes the check PASS and the record commit land
on =other=. Millisecond window, requires a concurrent checkout.

*Fix:* resolve =git symbolic-ref -q HEAD= alongside the OID and CAS that specific
ref instead of =HEAD=, falling back to =HEAD= when detached — which also gives
F-5 a place to refuse.

** F-3 — MEDIUM (PRE-EXISTING, not a regression) — a close inside a conflicted rebase is discarded by =rebase --abort=
Measured in four scratch repos. Conflicted merge -> close -> resolve -> commit is
SAFE (=MERGE_HEAD= survives, both parents intact). =rebase --continue= is SAFE.
=cherry-pick --abort= is SAFE and the record survives on disk. Only
=rebase --abort= destroys the record — and *the staged-only baseline loses it
identically*, which is why this is classified pre-existing from TASK-QGWK7.1 and
was NOT the BLOCK SHIP the brief pre-authorised.

*Fix:* refuse persistence (or skip it and say so through =CLEANUP_ERROR=) when
=.git/rebase-merge=, =.git/rebase-apply=, =.git/MERGE_HEAD=,
=.git/CHERRY_PICK_HEAD= or =.git/BISECT_LOG= exists. Four =exists()= calls close
the whole class.

** F-4 — LOW — =commit-tree= ignores =commit.gpgsign=, and one stated residual is FALSE
Measured: with =commit.gpgsign=true= and a garbage =user.signingkey=,
=git commit-tree= exits 0 and produces an UNSIGNED commit — so a repo enforcing
signatures gets unpushable history silently. Correctly named by the implementer.

But the implementer's residual "if =user.name=/=user.email= are unset the commit
fails" is WRONG: =commit-tree= succeeds using git's derived =user@host= ident.
Harmless in effect; remove it rather than carry a false failure mode.

** F-5 — LOW — detached HEAD persists the record to no branch
Measured: on a detached HEAD, =update-ref HEAD= moves only the detached HEAD;
=refs/heads/*= is untouched, so the record commit is on NO branch and the
manager's next =git checkout= orphans it. The close still reports =ok=.

Unborn HEAD is SAFE by contrast — =rev-parse --verify HEAD^{commit}= fails before
the real =git add=, so nothing is staged. The two unusual shapes are not
symmetric; only one is guarded.

** F-6 — LOW — M-5's refusal was inserted AHEAD of the torn-close recovery
=crates/orgasmic-cli/src/manager.rs:951= vs =:957=. MANAGER-VERIFIED IN SOURCE.

=normalize_report_path_property= now runs above =reconcile_torn_closes_best_effort=,
whose own comment says it must run "before anything else, including the
already-closed no-op below". So re-running a torn close with a command line
carrying an absolute =REPORT_PATH= bails BEFORE the stranded transition is
reconciled. Refusing is still right; the ORDERING silently demoted a path that
was explicitly ordered first. *Fix:* move the call below the reconcile.

** F-7 — LOW (docs) — the sidecar now has two meanings and the convention documents one
=crates/orgasmic-core/src/paths.rs:394-460=, convention at
=manager-dispatch.org:334-340=. A =stdout.log.bytes= with NO =stdout.log= means
either "the harness printed nothing" (value =0=) or "the promote failed partway"
(value non-zero) — distinguishable only by reading the value, and the prose
documents only the first. Also: the promoted excerpt is =64 KiB + ~180= bytes
(the banners ride on top of the cap) while the convention still says "64 KB".

Fold in the two other doc gaps: record commits are UNSIGNED (F-4), and
*promote-only =--no-worktree-remove= closes advance the branch too* — the
convention says "a close moves the branch you are on by one commit" without
saying it applies to those as well.
