What follows is what the round claimed and did not establish.

** 1. HIGH — `ExitTimeOut 60` is not larger than the worst-case shutdown, because
   half of that shutdown has no budget at all

`crates/orgasmic-cli/src/daemon_service.rs:707-727`,
`crates/orgasmic-daemon/src/lib.rs:665-688`,
`crates/orgasmic-daemon/src/writer.rs:513-522`.

After SIGTERM, `RunningDaemon` waits up to 20s for release finalizations and then
calls `WriterHandle::shutdown().await`. That call queues behind prior writer
commands and awaits its reply **with no timeout**. `RESTART_WRITER_DRAIN_TIMEOUT`
bounds only the pre-stop marker, not `WriterHandle::shutdown`.

Concrete failure: a terminal-tx append is still blocked in writer I/O or fsync
when the 20s release drain expires; shutdown then waits behind that append, and
launchd sends SIGKILL at 60s while the append is still non-durable. That
recreates the released-but-unreported loss the whole WGXKD family exists to
prevent.

The comment at daemon_service.rs:707 reasons "drain (20s) + writer shutdown < 60",
but the second term is unbounded, so the inequality is unprovable rather than
generous. The budget test added in this round checks 40 > 20 + 5 and 35 > 20 — it
never proves the plist timeout covers writer shutdown.

**This is live on the operator's machine right now.** The plist was rewritten with
`ExitTimeOut 60` on 2026-07-28 (tx-20260728-orgasmic-3118); the window is wider
than it was, and still not closed.

Required: give writer shutdown an explicit finite budget and a durable timeout
outcome, then **derive** the service-manager timeout from release drain + writer
shutdown + margin rather than hard-coding 60. If the derived number differs from
60, the plist must carry the derived one, and a test must assert the plist value
is the derived value — not a literal.

** 2. LOW — the production lifecycle composition still has no end-to-end regression

`crates/orgasmic-cli/src/daemon_lifecycle.rs:1498-1563`,
`crates/orgasmic-cli/tests/daemon_lifecycle.rs:99-181`.

The >5s test uses a stand-in HTTP server and stops after parsing its response; the
SIGTERM test has no in-flight release. Both pass even if the real `daemon restart`
sequence parses the drain response and then has launchd cut off the old daemon
during writer shutdown — which is exactly finding 1.

Required: drive the actual lifecycle restart path with a release lasting beyond
five seconds, including service stop and replacement bind. Testing the HTTP wait
and the SIGTERM routing in isolation is what let finding 1 through.

** Acceptance

- `WriterHandle::shutdown` has a finite budget and a defined outcome on timeout;
  the outcome is durable or recoverable, not silent.
- The macOS `ExitTimeOut` is derived from the drain and writer budgets, and a test
  asserts the rendered plist carries the derived value.
- A SIGTERM test holds a terminal-tx append in flight through the release timeout
  and proves either durability before exit, or a durable run-specific recovery
  record written before the watchdog can kill the daemon.
- An end-to-end restart regression covers service stop and replacement bind with a
  release that outlasts five seconds.
