Found 2026-07-26 running the TASK-8W30B merge gates on main (433fef1 + merge).

SYMPTOM

`cargo test -p orgasmic-drivers --test driver_modes` fails:

    ---- legacy_drivers_and_explicit_pairs_emit_equivalent_start_events ----
    assertion `left == right` failed: legacy=claude-acp mode=acp-stdio harness=claude
      left:  Ready { protocol_version: "claude-code-stream-json/1", ... }
      right: TextChunk { stream: Stderr,
             chunk: "Error: Session ID 6fc90d23-2093-4957-9fa9-ccb9488e0bb1 is already in use." }

CAUSE

The test deliberately shares one identity across the two spawns it compares
(driver_modes.rs:1665-1684, comment: "Share one identity so harness-aware native
metadata (e.g. the tmux claude --session-id pinned to runtime_id) is identical
across the legacy and explicit drivers being compared"). That was harmless while
`--session-id` was computed and then dropped. TASK-SGRTX (f5c6913) and 0f65de5
made the flag actually reach the claude process, so the second spawn of each pair
now asks claude for a session id the first spawn just claimed.

This is fallout from making the claude driver real, not from TASK-8W30B. The
8W30B implementer saw this suite green (28/28) in its worktree and the manager
saw 27/1 on the merged tree an hour later, so it presents as intermittent — the
collision depends on whether the first spawn has registered the session by the
time the second starts. Treat it as a race that is always latent, not as a test
that sometimes breaks.

TWO SEPARATE PROBLEMS, BOTH WORTH FIXING

1. The equivalence assertion needs identical *metadata* across the pair, not an
   identical live session. Give each spawn its own session id and normalize the
   id out of the compared Ready event, the way `normalize_volatile_ready_event`
   already removes `session_id` at line 1724 — or make the case inert.

2. This test spawns a REAL `claude` process, twice per case. Per the gotcha
   "Asking a harness to prove it can work costs real money", a claude turn cost
   $0.0994 and 24.5k tokens when measured 2026-07-25. A default-suite test that
   bills the operator on every run is a problem independent of the collision, and
   it got worse the moment the driver stopped being inert. Decide whether this
   case belongs behind an opt-in gate.

Acceptance:
- `cargo test -p orgasmic-drivers --test driver_modes` is green on repeated
  consecutive runs, not once
- the claude case either does not spawn a billable real turn by default, or its
  cost is a deliberate, documented choice
- the equivalence property being asserted is still actually asserted
2026-07-27, TASK-RWCRN dispatch: this test is now actively costing money on ordinary gate runs, not just on deliberate invocation. The brief explicitly told the worker not to run it; the worker ran it once anyway and was right to flag why — `cargo test -p orgasmic-drivers` is a declared verification gate and this test is not #[ignore]d, so the gate as written cannot avoid it. It failed on a real claude spawn with "Error: Session ID 377794d3-... is already in use", the documented TASK-099T6 collision, made more likely because the suite ran inside a live claude dispatch. Until this is #[ignore]d, every brief must carry a --skip instruction and every gate run must use `-- --skip legacy_drivers_and_explicit_pairs_emit_equivalent_start_events`, which is exactly the kind of tribal knowledge that does not survive. The manager's own gate run used the skip and was green: 239/4/28/1.
