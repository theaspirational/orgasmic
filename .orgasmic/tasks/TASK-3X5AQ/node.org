CONCURRENCY IS HANDLED BY CARGO, PROVEN NOT ASSUMED. Two =cargo build= runs
against one target dir were started 2s apart; the second printed:

: Blocking waiting for file lock on artifact directory
: Finished `dev` profile ... in 0.13s

So workers need no coordination protocol and cannot corrupt each other — the
second simply waits. That answers the "how does a worker know" question: it does
not have to.

THREE THINGS THE LOCK DOES NOT COVER, and they are the real design work:

1. *The lock covers BUILDING, not TESTING.* Once artifacts exist, =cargo test=
   just runs binaries, and two workers can run suites concurrently against the
   same target dir with no lock at all. That is exactly the load condition
   measured FIVE times this session to redden the live-mux and process-probe
   tests spuriously. A shared target dir does not cause that, but it removes the
   incidental staggering that per-worktree builds provided.

2. *Flag divergence causes rebuild thrashing.* =cargo clippy --all-targets=,
   =cargo test -p orgasmic-daemon --lib= and =cargo build --release= select
   different artifact sets; workers alternating between them invalidate each
   other and each waits for a rebuild of what the other just discarded. With a
   25 GB target and multi-minute daemon builds this is the dominant cost, and it
   is worse than the lock wait. MITIGATION: briefs should name ONE gate command
   set and workers should not improvise flags — largely already true, and now
   load-bearing rather than stylistic.

3. *Shared blast radius.* One worker running =cargo clean=, or a disk-pressure
   cleanup, destroys every concurrent workers artifacts mid-run. Worth an
   explicit "never cargo clean in a dispatch" line alongside the other
   prohibitions.

ONE CLEAR WIN, measured: each worktree currently carries its own target —
=task-8ed6v= alone is 3.0 GB against the shared 25 GB. Sharing removes that
duplication per concurrent worker, which also reduces the =syspolicyd= scan
surface, since the gotcha attributes the bursts to executing freshly written
binaries.

** Disproof of the shared target dir (2026-08-03)
STOP — THE 2026-08-03 DECISION IS DISPROVED. Do NOT implement the shared
=CARGO_TARGET_DIR=. It is not merely contended, it is UNSOUND: a dispatch
worker's =cargo build= becomes a silent no-op and its integration suite greens
against a DIFFERENT checkout's binary.

*Reproduced 2026-08-03 in the exact production shape* — a git worktree of a
cargo workspace, both pointed at the repo-root target dir (cargo 1.94.1):

: repo root:        main.rs prints MAIN_BRANCH   -> cargo build -> target/debug/probe-cli = MAIN_BRANCH
: git worktree A:   main.rs prints TASK_A_BRANCH -> cargo build -> "Fresh probe-cli", NO compile
:                   target/debug/probe-cli still = MAIN_BRANCH
:                   cargo test in worktree A: 1 passed, BIN_SAYS=MAIN_BRANCH

The worker edited a source file, built, and tested. Nothing errored. The suite
was green. It ran the MANAGER's binary.

*Mechanism, and why the earlier lock measurement missed it.* The file lock is
real and does serialize concurrent builds — that measurement was correct and is
not what fails. What fails is freshness. Cargo's =-C metadata= hash for a path
package does not include the checkout path, so BOTH checkouts share ONE
fingerprint directory (=target/debug/.fingerprint/probe-cli-<hash>=, verified: a
single dir, not one per worktree). Freshness is then decided by comparing the
mtimes of the files recorded in the OTHER checkout's dep-info. The worker's own
edited file is not in that list, so nothing looks stale and cargo reports
=Fresh=. The stale uplifted binary at =target/<profile>/<name>= is what
=CARGO_BIN_EXE_*= resolves to, so every integration test inherits it.

It is also NOT ordering-dependent: after making worktree B's file genuinely
dirty and rebuilding, rebuilding worktree A reported =Fresh= and left B's binary
in place. Either checkout can silently receive the other's program.

*Why this outweighs the problem it was chosen to solve.* The TCC prompt costs
the operator a click and leaves a dead db row; no run has ever failed on it.
This trades that for a class of false green — and this session already lost real
work to two of those (a re-cut =orgasmic verify= artifact that never reached its
assertions, and a shipped artifact that became a false green when a fix made its
defect unreproducible). The whole point of the gate is that green means
something. Sharing a target dir across checkouts makes green mean nothing, in a
way no test on this repo would detect.

*Option 5, which satisfies BOTH constraints — the recommendation.* The tension
is: TCC needs the EXECUTED BINARY PATH to be stable across dispatches, while
cargo needs ONE checkout path per target dir. A fixed pool of stable worktree
slots gives both:

: .orgasmic/tmp/dispatch/slot-1/worktree  (own target/)
: .orgasmic/tmp/dispatch/slot-2/worktree  (own target/)   ... N slots

A slot's binary path never changes, so the operator grants it ONCE and the grant
survives — the prompt stops for good and the TCC db stops filling with dead
rows. Each slot keeps its own target dir with exactly one checkout path in it,
so cargo's freshness logic is the ordinary, sound, single-checkout case. Two
concurrent workers never share a slot, so there is no lock contention and no
flag thrashing either. Disk is bounded at N targets instead of unbounded, which
is strictly better than today.

Cost: the dispatch directory is named by slot rather than by task, so the
task->worktree mapping has to be read from the dispatch record instead of the
path. Several gotchas and briefs name task-shaped worktree paths and would need
updating, and slot release has to be part of worktree teardown.

*Reopened for a decision.* The operator picked option 2 on 2026-08-03 with the
lock measurement in hand and without this one; that choice should not be
executed as recorded. Options 1 and 3 stand as previously described. Option 5 is
the recommendation.
** The cdhash measurement: option 5 withdrawn, and the general-vs-specific split
OPTION 5 (STABLE WORKTREE SLOTS) IS WITHDRAWN AS THE TCC FIX. The manager
recommended it on 2026-08-03 on the assumption that a STABLE BINARY PATH keeps a
TCC grant. Measured 2026-08-05: it does not. The premise was wrong.

*The measurement.* Decoding the =csreq= blob stored on each grant in the user
TCC db:

: worktree-built binary   -> cdhash H"b081c98ab06c6ab3611c357bdb900420b3e66d54"
: installed runtime binary -> identifier "com.theaspirational.orgasmic" and
:                            certificate root = H"a70531007cd128ff081597cb27bee0816613d86d"

A grant for a linker/ad-hoc-signed binary is pinned to that binary's exact
CONTENT HASH, not to its path. Rebuild the same file at the same path and the
cdhash changes, so the grant no longer matches and macOS prompts again.

*Consequence, and it inverts the recommendation.* Slots would make the prompt
fire ONCE PER BUILD instead of once per dispatch — strictly WORSE than today,
since a worker builds many times per dispatch. Any scheme whose mechanism is "a
stable path earns a durable grant" fails for the same reason.

*What actually makes a grant durable* is the second row: a stable SIGNING
IDENTITY. =identifier ... and certificate root= survives rebuilds, which is
exactly why the 2026-08-03 runtime reinstall kept its Documents access while
the gotcha warns that a linker-signed binary is "a stranger to TCC". That is a
real fix but not one orgasmic can apply generally — it cannot codesign arbitrary
projects' build outputs, and requiring a signing identity to run a dispatch is a
much heavier ask than the problem justifies.

=== The remaining general fix is option 3, and the framework owns it
Get dispatch worktrees OUT of TCC-guarded directories, rather than trying to
make grants survive. macOS guards =~/Documents=, =~/Desktop=, =~/Downloads= and
iCloud Drive; nothing outside them needs a grant at all, so there is no cdhash
to invalidate and no prompt to answer.

This is the right layer because ORGASMIC CREATES THE PROBLEM: it chooses to put
worktrees at =<project>/.orgasmic/tmp/dispatch/<task>/worktree=, which inherits
whatever guarded ancestor the project root has. A project rooted in
=~/Documents= gets it for free and cannot opt out.

*To verify before building* (do not assume, this task has already burned one
assumption): a worktree outside Documents still has a =.git= file pointing at
=<project>/.git/worktrees/<name>= INSIDE Documents. Confirm whether git
operations from the worker trip a prompt, and if so whether a separate git dir
or a shared clone avoids it.

=== Is this orgasmic-specific or general? — general, with a specific accent
GENERAL: any orgasmic project that (a) runs on macOS, (b) COMPILES BINARIES it
then executes, and (c) is rooted under a guarded folder. Interpreted projects
mostly escape it because the executed binary is the interpreter
(=/usr/bin/python3=, =node=), which is already known to TCC; it is freshly
COMPILED output that is a stranger. So Rust, Go, C/C++, CGo, Tauri and Electron
projects hit it; plain Python/Node/Ruby ones typically do not.

SPECIFIC to this repo: only the vocabulary of the disproved fix
(=CARGO_TARGET_DIR=) and the fact that this project happens to live in
=~/Documents=. Neither belongs in the framework.

=== So: bundle the behaviour, do not write a convention
- The FIX belongs in the daemon's worktree placement — one code path, applies to
  every dispatch in every project, nothing to remember.
- A repo-wide convention is the wrong instrument for the reason already recorded
  here ("a prose instruction is skippable and this needs to hold for every
  dispatch") and for a reason this session demonstrated three times: prohibitions
  in prose get missed. The ORGASMIC_HOME outages happened WITH a written
  prohibition in force.
- Do NOT bundle toolchain knowledge. Orgasmic should not know what cargo is. If
  a per-project environment is ever needed, it should be a generic
  project-declared env map, not a =CARGO_TARGET_DIR= special case.

=== What slots are still worth
Bounded disk (N targets instead of one per concurrent worktree, measured at
3.0 GB for a single worktree) and, if anyone ever revisits sharing a target dir,
they are the only shape that keeps cargo sound. Keep them on the table as a
disk/scale change; just not as the TCC answer.

dispatch's chain (daemon -> tmux -> harness -> cargo -> test binary) is
different. The argument for the fix does NOT rest on that result. It rests on
the fact that a worker whose worktree is outside Documents HAS NO REASON to read
Documents at all: its cwd, sources, target dir and =.orgasmic= snapshot are all

separately granted, path-stable binary — follows.

=== Recommended placement
: ~/.orgasmic/worktrees/<project-id>/<task-id>/

Keyed on PROJECT ID, not display name: the id is what the CLI and daemon already
use everywhere (=--project <id>=), and names can collide or change.

Why a TOP-LEVEL =worktrees/= rather than the proposed
=~/.orgasmic/user/projects/<name>/worktrees=:
- =user/= currently means user-level CONFIG — it holds =auth/= and =board.org=,
  both small. Worktrees are multi-GB regenerable scratch; mixing them buries the
  largest thing on disk inside a config namespace.
- =user/= also carries a bad association: =user/workers/= was the retired
  residue that TASK-8ED6V was filed about. A new =user/projects/= invites the
  same "is this live or dead?" question that incident was about.
- Top-level makes the cost visible: =du -sh ~/.orgasmic/*= shows it at a glance.

Why NOT =~/Library/Caches/orgasmic/...=, the otherwise idiomatic macOS choice:
it is unguarded (confirmed: zero TCC rows for Cache services), but macOS may
PURGE it under disk pressure, which would destroy a worktree mid-dispatch.
Rejected on that alone.

=== What moves and what stays
Move only the SCRATCH. The dispatch RECORD — brief, report =last.txt=, stdout
log under =.orgasmic/tmp/dispatch/<task>/= — stays in the project, because it is
part of the durable record, it is small, and it is written by the daemon, which
is identity-signed and already granted. Splitting on "record stays, scratch
leaves" keeps every existing brief-path reference valid.

=== Already has an escape hatch
=orgasmic manager dispatch --worktree <PATH>= already exists ("omitted -> a
managed path under =.orgasmic/tmp/dispatch/="). So this change is to the MANAGED
DEFAULT only, and the override is precedent, not new surface.

=== Make it universal, not macOS-gated
Linux has no TCC, but the move is still correct there: the repo stops
accumulating multi-GB build trees, =git status= in the repo stays clean, and
disk is attributable per project. One code path beats a platform branch.
