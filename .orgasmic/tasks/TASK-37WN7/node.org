** Description
=sigterm_exits_through_graceful_shutdown_rather_than_default_disposition=
(=crates/orgasmic-cli/tests/daemon_lifecycle.rs:319=) failed once under
parallel load during TASK-YN5FJ.1 and passed everywhere else.

WHAT MAKES IT WORTH A TASK RATHER THAN A SHRUG: the test ALREADY carries a
mitigation for exactly this race. =wait_until_serve_awaits_signals= was added by
TASK-Q07Y5 precisely because =serve= registers its SIGTERM handler AFTER
=Daemon::run= returns, so a SIGTERM sent on the strength of a successful connect
can land on the default disposition. Its own comment says the window is
"invisible on an idle machine" but not "under a loaded test binary".

So this is not an unmitigated race — it is a mitigation that does not hold. Either
=wait_until_serve_awaits_signals= does not actually prove the handler is
installed, or there is a second window it does not cover. That distinction is the
task.

** Evidence
Already fixed on main: install_sigterm_handler() runs before the readiness banner since ab5cb079 (2026-08-10). Verified 2026-09-02 (manager sprint): sigterm_exits_through_graceful_shutdown_rather_than_default_disposition 10/10 isolated and 40/40 under 8-way parallel on unmodified main; injection (banner moved before the install) -> 0/10, proving the test detects the defect. The remaining SIGINT lazy-arm window (daemon stop sends SIGINT) is closed by commit 52b3424d on sprint-20260902 (TASK-GGWW2/4PPPE), which also removes this task's flake-registry entry. No further work.

** Why it is NOT in verify/flake-registry.toml yet
Deliberate, and this is the part to not undo casually. No panic signature was
captured — the failure was observed through the wrapper verdict, not a saved log.
A registry entry with no =signature= makes EVERY future failure of that test name
read as this known flake, which is precisely the "trains everyone to discount
failures" failure the registry exists to prevent. Registering it blind would buy
a quieter suite at the cost of the signal.

So: capture the panic first (which assertion — the =status.signal()= one, or the
30s =try_wait= deadline), THEN either fix the mitigation or register the entry
with that signature and this task as owner.

** Acceptance
- The failing assertion is identified from a captured red, not inferred.
- Either =wait_until_serve_awaits_signals= is strengthened so the window is
  genuinely closed under load, or a signature-bearing =[[flake]]= entry is added
  with this task as owner and a rationale for why the race is not worth closing.
- =scripts/run-tests.sh --check= stays green (owner must be an open task).
** Mechanism found — the mitigation watches the wrong side of the boundary
**The mechanism is now known, and it retires the "either/or" this task was filed
with.** Manager traced it 2026-08-05 against =f60af0a=. Do not re-derive it.

=serve= (=crates/orgasmic-cli/src/main.rs=) does this, in this order:

: :2299   let _ = writeln!(io::stdout(), "  press Ctrl+C to stop");
: :2300   wait_for_shutdown_signal().await;
: :2320       match signal(SignalKind::terminate()) {   // <- handler installed HERE

And =wait_until_serve_awaits_signals= (=daemon_lifecycle.rs:29=) waits for
exactly that =press Ctrl+C to stop= line on stdout.

So the helper proves the process reached a point *strictly before* registration.
It observes the WRONG SIDE OF THE BOUNDARY. This is not a mitigation that fails
under load — it is a mitigation that is STRUCTURALLY INCAPABLE of closing the
window it was built for, and no amount of strengthening the helper can fix it,
because the thing it would need to observe has not happened yet when the only
observable signal is emitted.

That also explains the measurement better than the load hypothesis did: the race
reproduces at roughly 7% with NO load at all (1 failure in the first 14 isolated
runs, then 12/12 green). Load was never the variable. The window is simply always
there, and 7% is how often a SIGTERM sent immediately after the print lands
inside it.

=== This changes the acceptance

The task as filed offered a legitimate terminal outcome: "register the flake with
a rationale for why the race is not worth closing". *That branch is now
withdrawn.* Its premise was that closing the race might be expensive or subtle.
It is neither — the fix is to install the SIGTERM handler BEFORE announcing
readiness, so that the announcement means what every caller already assumes it
means.

=== Is it a real defect or only a test artifact? Real, but narrow.

In ordinary operation a SIGTERM arrives long after startup and cannot land in a
microsecond window. The exposure is the restart path: =launchctl kickstart -k=
sends SIGTERM, and a KeepAlive-thrashing daemon can be signalled promptly after
boot (see the =orgasmic-local-update-launchd= history). When it does land there,
the consequence is the one TASK-WGXKD.1 built the graceful shutdown to prevent:
no release-finalization drain, no writer shutdown.

So: worth fixing, not worth panicking about. P3 is the right priority.

=== Corrected acceptance

- =serve= installs its SIGTERM handler BEFORE it prints =press Ctrl+C to stop=,
  so the readiness announcement is a true precondition for signal delivery.
- SIGINT gets the same treatment or an explicit note saying why not —
  =tokio::signal::ctrl_c()= has its own registration point with the same shape,
  and leaving one of the two half-fixed is how this returns.
- The existing test passes without =wait_until_serve_awaits_signals= needing to
  become cleverer; if the helper survives, it is because it is still a useful
  readiness gate, not because it is load-bearing for this race.
- The =verify/flake-registry.toml= entry owned by this task is REMOVED in the
  same change — the excuse expires with the defect. =scripts/run-tests.sh --check=
  stays green.
- An injection proof is appropriate and the defect is pinnable: pre-fix, the
  reordering is absent and the pinned red is the =serve died on SIGTERM's default
  disposition= assertion. Note the difficulty honestly — at ~7% a naive replay is
  not deterministic, so the proof needs to force the window (a test hook that
  delays registration) rather than hope for it.
