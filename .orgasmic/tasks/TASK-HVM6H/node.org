From TASK-K4G1D (2026-07-29): the artifact-regenerate hot path cannot be
measured under tmux today, for two independent structural reasons, both
measured:

1. `("tmux", "custom")` is not in `orgasmic_drivers::SUPPORTED` — and it is the
   repo's canonical UNSUPPORTED pair, used by two api.rs tests precisely
   because it must fail. Registering it needs tmux's `build_spawn_plan` to grow
   a custom arm mirroring rmux's (harness_args[0] as command) AND an equivalent
   of rmux's `custom_dispatch_misconfig` guard (which stops a dispatch prompt
   being pasted into a bare shell). Product decision, not test plumbing.
2. `TmuxTuiControl` implements only transition_state/babysitter_action/release;
   `send_input` falls to the trait default → `Unsupported("send_input")`,
   measured against live tmux 3.6a on an owned server. The hot path IS
   send_input (api.rs:15793), so `post_artifact_regenerate_hot_path_reuses_
   live_run_id` cannot hold under tmux by construction.

K4G1D's caveat binds any implementation: a differential whose tmux arm is
brand-new code cannot answer "is rmux at fault" — red under new tmux code
indicts the new code. So this task is only worth doing if the tmux driver's
send_input is wanted AS A FEATURE (interactive follow-up under tmux), with the
differential as a byproduct once the code has matured.
