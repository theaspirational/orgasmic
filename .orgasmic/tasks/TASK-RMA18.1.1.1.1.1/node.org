*** R1 (MEDIUM, docs) — the help still makes ONE unbounded universal about the walk
=crates/orgasmic-cli/src/manager.rs:386-388=

: "…the anchored walk of the tree's own contents refuses any NESTED `.git` entry, of any type…"

The walk is bounded THREE ways: =:3833= returns at =depth > anchored_dir::MAX_DEPTH=
(64), =:3836= returns on an =entry_names= error, =:3855= skips an
=open_child_dir= =Err=. So "refuses ANY nested =.git= entry" is, read literally,
an over-claim — *the dangerous direction* — and it is the same class
=cli_parity.rs:156-161= now bans in the wording ="at any depth"=, while the
shipped sentence makes the identical claim more compactly and passes.

*WHY IT IS MEDIUM AND NOT HIGH — the reviewer re-derived round five's symmetry
claim from source and it HOLDS EXACTLY:*

| fail-open in =walk_worktree=                     | matching limit in the removal |
|--------------------------------------------------+-------------------------------|
| =:3833= =depth > MAX_DEPTH=, entered =walk(root,1,…)= =:3860= | =:3180= =bail!= at the same constant, entered =remove_contents(&child,1,…)= =:3243= |
| =:3836= =let Ok(names) = entry_names(dir) else { return }=    | =:3183= =for name in entry_names(dir)?= — propagates |
| =:3855= =Err(_) => continue= on =open_child_dir=              | =:3184= =open_child_dir(dir,&name)?= — propagates |

=open_child_dir= (=:2977-2984=) maps only =ENOTDIR=/=ELOOP=/=EMLINK=/=ENOENT= to
a non-error; everything else including =EACCES= is =Err=. So a =.git= too deep or
too unreadable for the walk sits inside a directory too deep or too unreadable
for =remove_contents= → a =RemovalFailure=, *never a silent clean deletion.*

*BUT THE SYMMETRY DOES NOT DELIVER WHAT THE HELP IMPLIES.* =RemovalFailure=
carries =touched= (=:3174-3177=) and =remove_contents= is READDIR-ORDERED, so
siblings enumerated before the blocked directory are ALREADY GONE — and on the
repo-gone branch there is no salvage. The operator's inference from this sentence
— "a nested =.git= anywhere means the worktree is KEPT untouched" — is wrong in
the fail-open shapes: they get a *reported partial removal.* The nested
repository itself survives (it is inside the thing that blocked the walk), which
is why this is docs and not data-loss.
