** Question
Per-type regenerate prompts and the universal consume-on-regenerate rule. What does regenerate even mean for a task or a decision (vs a glossary term or artifact)?
** Resolution
Grilled with owner 2026-08-22; four decisions. Facts: artifact regenerate today = a follow-up into the live artifactor run (prior content + open comments + extra prompt → new version → open comments CONSUMED); the prompt text is hardcoded Rust (assemble_regen_context); prompt-studio spec artifact-generator.org exists for the initial generate; descriptors (.2) reserve :REGENERATE_PROMPT: as a spec name.
1. Meaning per type: regenerate = recompile this node's current content + open comments (+ extra prompt) through the descriptor's :REGENERATE_PROMPT: spec; the agent returns new node content; version bumps; open comments are consumed. Task → rewrite the task (title/body/acceptance) from comments — NOT re-dispatch the work (dispatch stays its own verb). Decision → redraft the decision text. Glossary → redefine the term. Artifact → unchanged.
2. Prompt source: the hardcoded assemble_regen_context becomes a prompt-studio spec per type (artifact's is the first); the kernel composes node content + open comments + extra prompt into it. No per-type Rust.
3. Universal consume rule, unchanged from artifacts: on close-out every open comment is marked consumed, the regenerated journal entry lists CONSUMED_CIDS, content is replaced (git keeps the old). A type with no :REGENERATE_PROMPT: has no regenerate (no button).
4. Runner: the existing artifactor-style supervisor path, run task id node.regenerate:<id> (today artifact.generate:<id>), one live regenerate per node.
