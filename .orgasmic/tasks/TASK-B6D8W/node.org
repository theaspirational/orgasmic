Filed by TASK-H0TYV (VB9DQ fix round) from the recorded cross-harness matrix. Sibling of TASK-F9VEZ (codex); same shape, different protocol.

`CursorAcpAdapter` never overrides `HarnessEventAdapter::native_runtime`, so it takes the trait default `None` (`crates/orgasmic-drivers/src/trait.rs:248`).

The session id is server-minted and post-launch: `sessionId` is read out of the `session/new` result in `on_ws_thread_started` (`crates/orgasmic-drivers/src/adapters/cursor_acp.rs:288-292`) and surfaced only inside `Ready.capabilities` (`:320`). Unlike codex this is not an implementation choice orgasmic could lobby to change: ACP defines `session/new` as the agent minting the session id, so a pre-launch pin in the claude `--session-id` sense has no protocol slot at all.

Consequences: no `resume_native_fork` for cursor-agent runs, and dec_Y5MPK item 6 attribution is not computable — 909 JSONL files under `~/.cursor` on the operator machine (measured 2026-07-28), none attributable to an orgasmic dispatch.

The transcript finder already handles the fallback: recorded path confined to `~/.cursor/projects`, else Ready `session_id` + worktree at **high** confidence, else cwd+launch-time at **medium** (`crates/orgasmic-drivers/src/transcript_finder.rs`). So locating a transcript mostly works; what is missing is the recorded NativeRuntime that makes it deterministic and makes attribution possible.

Work: emit `NativeRuntimeMeta` from the `session/new` result — provider `cursor-agent`, session id, resolved session path, and whatever ACP `session/load` (or the cursor equivalent) needs as resume argv. Verify against the binary rather than the spec; `session/new` already returns an undocumented structured models block (`:295`), so the shipped surface is wider than the published one.

Blocked on the same contract decision as TASK-F9VEZ, recorded against TASK-SGRTX: post-launch handshake capture versus mandatory pre-launch pinning. Cursor is the strongest evidence that pre-launch pinning cannot be made universal.
