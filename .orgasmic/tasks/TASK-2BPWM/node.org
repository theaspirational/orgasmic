Verified 2026-07-26 by reading the cleanup paths after the operator asked
whether a stuck dispatch can end with its work unrecoverable. It can, and the
destructive behaviour is the default.

THE PATH

`orgasmic manager dispatch-close` declares `--worktree-remove` with
`default_value_t = true` (crates/orgasmic-cli/src/manager.rs:124) and
`--branch-delete` with `default_value_t = false`. Removal is
`git worktree remove --force` (manager.rs:2007; the daemon does the same at
crates/orgasmic-daemon/src/api.rs:4438). `--force` is exactly the flag that makes
git delete a DIRTY worktree instead of refusing.

No dirty check guards it. `worktree_has_uncommitted_changes` exists at
manager.rs:1331 but is only consumed by `commit_worktree` on the worker-driven
`dispatch finalize --commit` path. Nothing consults it before removal.

The two guards that do run before removal —
`validate_dispatch_cleanup_targets` and `verify_dispatch_worktree_identity` —
protect against deleting the WRONG worktree. Neither protects against deleting
UNSAVED WORK.

THE SCENARIO, WHICH IS NOT HYPOTHETICAL

1. A worker does real work and never reaches `dispatch finalize --commit`,
   because its harness dies. Observed today: the TASK-STWVB run emitted
   `run_complete` at 09:54:47 and `claude exited with status exit status: 143`
   at 09:54:48.
2. The run can then sit live for a long time (80 minutes, observed).
3. The manager reaches for the documented cleanup verb,
   `dispatch-close --status aborted`.
4. Default flags delete the worktree with `--force`. Uncommitted work is gone,
   with no prompt, and no tx entry recording that anything was discarded.
5. The branch survives, because branch-delete defaults false. If the worker never
   committed, that branch sits at the base commit and holds nothing — so the
   surviving branch creates a false impression of recoverability.

WHAT IS NOT WRONG, so nobody widens this

There is no automatic or background pruning of dispatch worktrees. No retention
sweep touches them. The loss always requires an explicit manager action. The
problem is not a daemon deleting things unasked; it is that the verb the manager
is instructed to use is destructive by default, at exactly the moment a worker
has failed and its output is most likely to be uncommitted.

In practice the opposite failure dominates: 17 worktrees are on disk right now,
including several from 2026-07-23. Cleanup usually is not run at all. That makes
the risk distribution the worst possible shape — litter for the careless, silent
data loss for the conscientious.

FIX

`commit_worktree` already exists, so the cheap fix loses nothing and needs no
judgment call:
1. Before removing a worktree, test it with `worktree_has_uncommitted_changes`.
   If dirty, make a salvage commit on the dispatch branch (which already survives
   by default) with a message naming the task and that it was manager-salvaged,
   then remove.
2. Record the salvage in the close tx — sha and file count — so the recovery
   story is discoverable from state rather than from memory.
3. Consider making `--worktree-remove` default false for `--status aborted`
   specifically. A done close follows a worker that committed; an aborted close
   is by definition the case where it did not.
4. Say what happened in the CLI output. "worktree removed" should distinguish
   clean removal from salvaged-then-removed.

Related: TASK-TJKFC already states the right principle for the other half of this
("once startup has been accepted and meaningful work has occurred, later failures
retain normal failed-run history and inspection artifacts"), and that half is
unimplemented.

Acceptance:
- closing a dispatch whose worktree is dirty never loses the diff
- the salvage is recoverable from tx alone, without knowing the branch name
- a clean close behaves exactly as it does today

WHAT LANDED
- `salvage_worktree_if_dirty` runs before every `git worktree remove --force`, on
  both the CLI path (remove_worktree_required) and the daemon's
  (remove_dispatch_worktree). Commit subject is
  "<TASK>: manager-salvaged uncommitted worker output".
- The dispatch branch is RETAINED whenever salvage occurred, even if
  --branch-delete was requested — `if branch_delete && salvage.is_none()`.
  Deleting it would have destroyed the salvage commit, so this is load-bearing.
- Close tx carries SALVAGE_SHA and SALVAGE_FILE_COUNT, so recovery is
  discoverable from tx alone without knowing the branch name.
- CLI output distinguishes "worktree salvaged sha=... files=...; worktree
  removed" from "...; worktree retained after removal failure".
- A failing salvage stops before removal — asserted by
  dispatch_close_does_not_remove_worktree_when_salvage_commit_fails and its
  daemon twin.
- commit_worktree now re-checks porcelain after committing and bails if anything
  remains, so a partial commit cannot be mistaken for a complete salvage.

dominant failure (17 worktrees on disk). Accepted.
