Treat the crash-loop report as a regression audit of the now-present lock-first boot protocol, not as proof that all suggested redesigns are still needed. Current source already acquires the home lock before project scanning, publishes boot-state heartbeats, makes explicit start return `StillBooting` after 20 seconds, lets autostart follow live heartbeats up to a finite backstop, retries bind for 8 seconds, and the current 3,118-tx daemon reached listening in about 8.45 seconds. Preserve those semantics.

Work:
1. Add a deterministic service-level test with an artificially slow project scan longer than the old readiness timeout and concurrent `daemon start`/autostart attempts. Assert exactly one lock owner and one eventual listener, callers observe the same pid/boot phase, no competitor reaches bind, and no healthy boot is killed/restarted.
2. Add an explicit `ThrottleInterval` to the generated macOS LaunchAgent and verify install/update rewrites existing plists. Keep restart policy intentional and test repeated abnormal exits use launchd backoff.
3. Correlate `daemon.lock`, boot-state owner, pid liveness, and authenticated status in diagnostics. A lock-held pre-bind owner with fresh heartbeat is `starting`, not unhealthy; a dead owner is stale and may be replaced only after the OS lock is actually released. Never break a live file lock based only on HTTP failure.
4. Capture phase durations and tx/project counts for config, project scan, session migration/catalog load, watcher attach, reattach, and bind. Optimize or make replay incremental only if measurement still exceeds the accepted startup budget after the run-catalog work; do not expose normal API reads from a partially rebuilt index merely to make health green. A tiny early health responder is allowed only if it cannot serve normal routes and tests prove the handoff to the full router.
5. Make the no-progress/absolute readiness budgets configurable only if production measurement shows current heartbeat behavior insufficient; preserve a finite backstop.

Acceptance: the slow-start matrix produces no alternating Address-in-use/instance-lock errors, launchd does not hot-loop, one daemon becomes ready, and normal routes see a fully rebuilt index. Include a real generated-plist assertion and a macOS smoke or launchctl transcript where available.
