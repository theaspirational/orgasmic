Findings, as filed: tx-20260726-orgasmic-2942 through -2946.

HIGH 1 — the salvage commit is not anchored to the recorded dispatch branch.
manager.rs:1432-1445 and api.rs:4496-4551 commit whatever HEAD the worktree
currently has; neither helper is told which branch was recorded. The later
retention guards keep the RECORDED branch merely because salvage.is_some().

MANAGER-CONFIRMED EMPIRICALLY, not taken on the reviewer's word. In a scratch
repo: worktree on task-probe-impl, dirty file, `git checkout --detach`, then
add+commit exactly as commit_worktree does. Result — the salvage sha is NOT an
ancestor of the recorded branch, and `git for-each-ref --points-at` returns
nothing. The commit is unreferenced and prunable by `git gc`. So the close tx
advertises a recovery path that git is free to delete.

HIGH 2 — a late writer between the dirty check and `--force`. The CLI's last
clean check is manager.rs:1414-1440 and removal is manager.rs:2080-2084; the
daemon has the same gap at api.rs:4534-4551 vs 4569-4573. Anything writing in
that window produces a dirty worktree that `--force` then deletes silently. No
lock, and removal is not fail-closed.

MEDIUM 3 — a concurrent CLI close can delete another close's salvage branch.
manager.rs:2268-2273 checks only whether THIS invocation salvaged, then runs
unfenced `git branch -D`. Two concurrent `--branch-delete` closes: one salvages
and removes, the other sees salvage=None and deletes the branch now pointing at
the first salvage. The daemon path is already fenced with an expected OID; the
CLI is not.

LOW 4 — the CLI dirty + --branch-delete path is untested. Confirmed: the three
new CLI tests all pass branch_delete=false. This was the manager's own finding
and the reviewer ranked it correctly BELOW the three above.

LOW 5 — SALVAGE_FILE_COUNT under-reports. manager.rs:1381-1385 and
api.rs:4504-4507 count porcelain records, and default `git status --porcelain`
collapses an untracked directory into a single `?? dir/` entry. The tx promises a
file count and records a status-entry count.

FIX DIRECTION, from the reviewer and endorsed:
1. Pass the expected dispatch branch and OID into both salvage helpers. Require
   symbolic HEAD to match, or atomically move the intended ref from its
   pre-salvage OID to SALVAGE_SHA. Fail BEFORE removal on mismatch. Consider the
   reviewer's open question: a dedicated durable ref under refs/orgasmic/salvage/
   would make the tx sha independently reachable and simplify --branch-delete.
2. Stop using unconditional `--force` after salvage. Fail-closed removal plus a
   cleanup lock spanning final validation through removal, and a deterministic
   late-writer test.
3. In CLI close, never delete a branch after worktree missing/failure, and
   replace `git branch -D` with expected-OID `update-ref -d` fencing.
4. Tests: dirty + --branch-delete, detached HEAD / switched branch, removal
   failure after salvage, duplicate close, nested untracked directory. Mirror
   branch-identity and late-writer coverage on the daemon side.
