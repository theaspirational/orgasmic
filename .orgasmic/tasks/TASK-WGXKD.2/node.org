** Finding 1 - HIGH: release admission is not atomic with tracker closure
api.rs:217-240, 6672-6702, 9857-9861. post_run_release reads is_closed() and THEN awaits supervisor.snapshot() before calling spawn(). close() only flips an independent atomic flag, while spawn() increments active unconditionally and never rechecks the closed state. On the multi-thread runtime a release can read false, restart can then close the tracker and observe active == 0, and the release can register and run AFTER the release drain and potentially after the writer barrier. That recreates the exact graceful-shutdown loss this task exists to eliminate: the lease is released while its terminal tx lands after the barrier or dies with the service.

The added late-release assertion does not cover this straddling request - it sends the release only after the restart response, when is_closed() is already true. The endpoint test at dispatch_endpoint.rs:3734-3774 sleeps 500ms until it is inside the injected delay and only then requests restart, so it proves waiting for an ALREADY-REGISTERED task, not atomic close-versus-registration.

FIX DIRECTION: replace the separate is_closed() + spawn() sequence with one atomic admission operation (try_acquire / try_spawn) that checks closed and increments active under the same synchronization boundary, acquired BEFORE any await that restart can overtake. If closure won, drop the count and return 503. Add a barrier-controlled race test with a deterministic hook between handler admission and tracker registration, raced against controlled restart, proving the release is either tracked to completion or rejected.

** Finding 2 - HIGH: the real restart command abandons the drain after 5s, discards warnings, and stops the service anyway
daemon_lifecycle.rs:242, 847-868; api.rs:145-148, 9856-9877; main.rs:1795-1833. request_restart_drain() gives the HTTP request a 5-SECOND timeout, DROPS the send() result, returns Ok, and stop_inner() immediately invokes the OS service stop. The new API may legitimately wait 15 seconds. Driver teardown alone is budgeted 5s plus producer join 5s (supervisor.rs:4021-4051), and rmux can spend 2s on the SDK kill plus 2s on the CLI fallback (rmux.rs:83-87, 1514-1525). So a realistic teardown exceeds the lifecycle client's 5s fuse before the terminal tx append.

The endpoint warning is not actionable because the CLI never parses it. And the non-restart mirror in lib.rs is NOT a backstop for service shutdown: cmd_serve converts only Ctrl+C into RunningDaemon.shutdown, whereas LaunchAgent/systemd stop terminates the service.

Include run ids / dispatch generations and copyable rescue commands in timeout output. Route SIGTERM and service-stop through RunningDaemon.shutdown so the library drain actually runs. Add an end-to-end lifecycle test with a delay beyond 5s and the real stop sequence.

** Finding 3 - MEDIUM: a panicked or aborted finalization decrements the count but its lost tx is invisible
api.rs:178-195, 230-239, 6702-6705. The drop guard correctly lets wait_idle() finish, but the tracker retains only a COUNT, not the JoinHandle or the completion outcome. The sole join-error log lives in the HTTP request future - and dropping that future is the NORMAL worker-finalize case this whole change documents. If the detached task panics after release and before append, the guard moves the count to zero, restart reports a clean drain, and no durable warning or rescue record identifies the lost tx. There is no panic/abort regression test. This is a live-daemon task failure, NOT the accepted whole-daemon crash gap.

FIX DIRECTION: give the tracker ownership of task OUTCOMES, not just a count. Catch and retain panic/abort results keyed by run id and intended terminal tx, surface them through restart warnings and dispatch recovery/status, and add panic/abort tests proving both count release and visible loss recovery.
