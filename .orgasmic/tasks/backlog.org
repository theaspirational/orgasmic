* BACKLOG TASK-CM5KV Evaluate real ACP as an orgasmic transport    :drivers:research:
:PROPERTIES:
:ID: TASK-CM5KV
:PRIORITY: P2
:DEPENDS_ON: TASK-XCJYC
:END:

Evaluate adding the Agent Client Protocol as a real orgasmic transport, once TASK-XCJYC frees the name.

ACP is an open standard from Zed Industries (August 2025, Apache-licensed): JSON-RPC 2.0 over stdio for local agents, HTTP/WebSocket for remote (work in progress). It standardises the editor-to-agent boundary; MCP standardises tool access beneath it. Adopted by JetBrains, Google and GitHub, with 25+ agents.

The draw is consolidation. Zed's ACP Registry already lists Claude Agent, Codex, Gemini CLI, OpenCode, Copilot, Cursor and Pi Coding Agent. Orgasmic currently maintains a bespoke adapter per harness — `adapters/claude.rs` (stream-json), `adapters/codex.rs` (app-server), `adapters/cursor_acp.rs`, `adapters/hermes.rs` — each with its own event mapping, session identity story and transcript-finder strategy. One ACP transport could in principle serve several of them through a single event mapping.

Open questions to answer before committing to it:
1. Does ACP expose what orgasmic's supervisor actually needs — terminal declaration, tool-call visibility, stall signals, and a resumable native session identity? A protocol built for editor UX may not carry the lifecycle facts recovery depends on.
2. Does an ACP-launched agent still write its vendor-native transcript, or does the adapter layer hide it? The retro contract depends on vendor JSONL existing and being resumable (see dec on transcript ownership).
3. Is the ACP adapter an extra process between orgasmic and the harness, and what does that mean for the startup preflight (TASK-TJKFC) and for credential handling (TASK-Z8WEJ)?
4. Would it replace the bespoke adapters or sit alongside them? A fifth transport that duplicates four existing ones is a cost, not a saving.

This is deliberately a research-and-decide task, not an implementation commitment. If the answer is that ACP does not carry orgasmic's lifecycle needs, recording that is a complete and useful result.

Depends on TASK-XCJYC only for the name; the evaluation can start earlier.

* BACKLOG TASK-5M45A Hermes ignores the provider and model a dispatch asks for    :P1:
:PROPERTIES:
:ID: TASK-5M45A
:END:

Measured 2026-07-25 on hermes 0.16.0, driving `hermes acp` directly with the
same JSON-RPC handshake `acp_stdio` performs.

On the hermes stdio path orgasmic transmits the dispatch's provider and model
only inside `thread_start._meta.orgasmic` (`spawn_payload`, hermes.rs), and the
argv is a bare `hermes acp`. Hermes does not read them. Two `session/new`
calls, identical but for the provider:

  provider = "anthropic"             -> currentModelId ollama-cloud:glm-5.2
  provider = "nonexistent-provider"  -> currentModelId ollama-cloud:glm-5.2

Neither errored. Both landed on hermes's own configured default. An unknown
provider id is not even rejected, so there is no signal that the request was
dropped.

Consequences, in order of how much they cost:
1. A dispatch that specifies a provider silently runs on a different one. The
   operator is billed to the wrong account and gets a different model's output,
   with nothing in the session to say so.
2. It is worse than invisible, it is actively misreported: the `Ready` event's
   capabilities echo `cfg.provider` and `cfg.model` back
   (`on_ws_thread_started`), so the session JSONL records the provider that was
   ASKED FOR as though it were the one in use. Reading the session is the normal
   way to find out what a run did, and here it lies.
3. It blocks a hermes readiness probe. Checking a credential requires knowing
   which credential the launch consumes; while the provider is ignored, orgasmic
   cannot know. See the comment on `HermesAdapter` (TASK-TJKFC decided against a
   probe on exactly this ground).

Not yet established: whether hermes exposes any supported way to select a
provider per ACP session (a `session/set_config_option` equivalent, an argv
flag, or an env var). The adapter already builds a `/model ... --provider ...`
slash command in `transition_state`, so mid-run switching works; whether that
same path can be driven at startup was not tested. The fix might be as small as
issuing that command once after `session/new`.

Minimum acceptable outcome if selection turns out to be impossible: stop echoing
a provider and model the run is not using, so the session records what actually
happened rather than what was requested.

* BACKLOG TASK-A55J7 Persist model and effort on the run record and the dispatch tx    :dispatch:runtime:observability:

Filed 2026-07-26 alongside a manager prompt change requiring every dispatch to
state driver, harness, model and effort. That rule is currently unenforceable
after the fact, because two of the four are never written down.

WHAT IS RECORDED TODAY

`manager.dispatch_started` carries `:WORKER:`, `:DRIVER:`, `:HARNESS:` and no
model or effort (verified on tx-20260726-orgasmic-2861 and -2869).
`orgasmic run list` reports `driver`, `harness`, `worker_id`, `kind`, `role`,
`sub_state` — and no model or effort field on the live run object.

`orgasmic manager dispatch` accepts `--model` and `--effort` and passes them
through to the adapter, so the values exist at dispatch time. They are simply
dropped before anything durable is written. A manager who sets them cannot prove
it afterwards, and a manager who omits them cannot discover what the harness
chose instead.

WHY IT MATTERS

Two failures on 2026-07-26 came from exactly this blind spot. A reviewer was
dispatched over a P1 concurrency fix and the manager could not afterwards say
what model was reviewing it. Separately, a TASK-STWVB implementer ran on
claude-opus-5 when nothing had selected it, discovered only by reading argv on a
live process (TASK-SGRTX).

The cost is not tidiness. Worker output is treated as a claim to be weighed, and
weighing a claim requires knowing its author. An evidence section that says "the
implementer measured +5 sessions per run" means something different depending on
what produced it, and today that is unrecoverable the moment the process exits.

WORK

1. Thread the resolved model and effort — the values actually sent to the
   adapter, not the ones requested — onto RunMeta, so they survive boot reattach
   the way last_path/stdout_path/worktree do.
2. Emit them on `manager.dispatch_started` as `:MODEL:` / `:EFFORT:`, and on
   `run.created`.
3. Surface them in `orgasmic run list` and `orgasmic manager dispatch-status`.
4. Record what the harness actually resolved when the manager passed nothing.
   The default is the case most worth capturing — it is the one nobody chose.
   Where the harness does not report its own resolved model, record the request
   as absent rather than inventing a value, and say so in the field.
5. Show them wherever a run is displayed in the UI Runs surface.

Note the task node already carries `model` and `reasoning_effort` properties
(both null on most headings). Decide whether those are the requested values and
the new run fields are the resolved ones, or whether the task properties should
be retired in favour of run-level truth. Two half-populated surfaces for the same
fact is how this became invisible in the first place.

Acceptance:
- a completed dispatch can be asked what model and effort ran it, from state
  alone, after the process is gone
- a dispatch where the manager passed neither still records what was resolved,
  or records explicitly that nothing was requested and the harness default
  applied
- `orgasmic run list` and `dispatch-status` both show all four of driver,
  harness, model, effort

** Description
Found by the TASK-JQARS worker while classifying its own gate failures, and
correctly excluded from that task's scope. It is a **test defect, not a
production defect** — the production path was probed directly and is sound.

=== Measured

`crates/orgasmic-cli/tests/daemon_lifecycle.rs`,
`sigterm_exits_through_graceful_shutdown...`.

- On the JQARS branch: **3 pass / 6 runs**.
- On the pristine baseline (`git stash -u`, same command): **2 pass / 3 runs**.

It fails on both, so it is pre-existing and unrelated to that change.

=== Mechanism

The test sends SIGTERM the instant `serve` prints "press Ctrl+C to stop".
`main.rs` prints that line **before** `wait_for_shutdown_signal()` registers the
handler, so a SIGTERM that arrives inside that window hits the default
disposition and kills the process instead of running the graceful path. The
test's own comment describes the window.

Direct probe of the built binary using the test's exact home, config and
process-group setup: `rc=0` in **3/3 with SIGTERM at 0 ms delay**, and **3/3
with a 300 ms delay**. The production sequence is fine; the test races its own
readiness signal.

=== Why it matters beyond the flake

The readiness line is a **lie about readiness** for one specific consumer: a
supervisor that treats "press Ctrl+C to stop" as "safe to signal" has the same
race. Nothing in the product does that today, but the plist and any future
service adapter are exactly the kind of consumer that would. Decide whether the
line should move after handler registration, or whether a separate, explicit
readiness signal is owed — and record which, because "the test is racy" and
"the readiness announcement precedes readiness" are different bugs with the same
symptom.

=== Ask

1. Make the readiness announcement follow handler registration, or introduce a
   readiness signal that does, and say which you chose and why.
2. Remove the race from the test rather than papering it with a sleep — a sleep
   restores green without restoring the guarantee.
3. Check the same ordering question for Ctrl+C and for the service-stop path
   ATAXN's marker protocol now depends on.

- The test passes 10/10 consecutive runs, and a run with SIGTERM at 0 ms delay
  still exits through graceful shutdown.
- Prove it by injection: restore the announcement to its current position, watch
  the test fail, move it back, watch it pass — with output.
- State whether any shipped consumer (plist, installer, docs) tells an operator

** Disproof of the shared target dir (2026-08-03)
STOP — THE 2026-08-03 DECISION IS DISPROVED. Do NOT implement the shared
=CARGO_TARGET_DIR=. It is not merely contended, it is UNSOUND: a dispatch
worker's =cargo build= becomes a silent no-op and its integration suite greens

*Reproduced 2026-08-03 in the exact production shape* — a git worktree of a
cargo workspace, both pointed at the repo-root target dir (cargo 1.94.1):

: repo root:        main.rs prints MAIN_BRANCH   -> cargo build -> target/debug/probe-cli = MAIN_BRANCH
: git worktree A:   main.rs prints TASK_A_BRANCH -> cargo build -> "Fresh probe-cli", NO compile
:                   target/debug/probe-cli still = MAIN_BRANCH
:                   cargo test in worktree A: 1 passed, BIN_SAYS=MAIN_BRANCH

The worker edited a source file, built, and tested. Nothing errored. The suite
was green. It ran the MANAGER's binary.

*Mechanism, and why the earlier lock measurement missed it.* The file lock is
real and does serialize concurrent builds — that measurement was correct and is
not what fails. What fails is freshness. Cargo's =-C metadata= hash for a path
package does not include the checkout path, so BOTH checkouts share ONE
fingerprint directory (=target/debug/.fingerprint/probe-cli-<hash>=, verified: a
single dir, not one per worktree). Freshness is then decided by comparing the
mtimes of the files recorded in the OTHER checkout's dep-info. The worker's own
edited file is not in that list, so nothing looks stale and cargo reports
=Fresh=. The stale uplifted binary at =target/<profile>/<name>= is what
=CARGO_BIN_EXE_*= resolves to, so every integration test inherits it.

It is also NOT ordering-dependent: after making worktree B's file genuinely
dirty and rebuilding, rebuilding worktree A reported =Fresh= and left B's binary
in place. Either checkout can silently receive the other's program.

*Why this outweighs the problem it was chosen to solve.* The TCC prompt costs
the operator a click and leaves a dead db row; no run has ever failed on it.
This trades that for a class of false green — and this session already lost real
work to two of those (a re-cut =orgasmic verify= artifact that never reached its
assertions, and a shipped artifact that became a false green when a fix made its
defect unreproducible). The whole point of the gate is that green means
something. Sharing a target dir across checkouts makes green mean nothing, in a
way no test on this repo would detect.

*Option 5, which satisfies BOTH constraints — the recommendation.* The tension
is: TCC needs the EXECUTED BINARY PATH to be stable across dispatches, while
cargo needs ONE checkout path per target dir. A fixed pool of stable worktree
slots gives both:

: .orgasmic/tmp/dispatch/slot-1/worktree  (own target/)
: .orgasmic/tmp/dispatch/slot-2/worktree  (own target/)   ... N slots

A slot's binary path never changes, so the operator grants it ONCE and the grant
survives — the prompt stops for good and the TCC db stops filling with dead
rows. Each slot keeps its own target dir with exactly one checkout path in it,
so cargo's freshness logic is the ordinary, sound, single-checkout case. Two
concurrent workers never share a slot, so there is no lock contention and no
flag thrashing either. Disk is bounded at N targets instead of unbounded, which
is strictly better than today.

Cost: the dispatch directory is named by slot rather than by task, so the
task->worktree mapping has to be read from the dispatch record instead of the
path. Several gotchas and briefs name task-shaped worktree paths and would need
updating, and slot release has to be part of worktree teardown.
