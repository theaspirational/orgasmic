* BACKLOG TASK-CM5KV Evaluate real ACP as an orgasmic transport    :drivers:research:

:PRIORITY: P2

Evaluate adding the Agent Client Protocol as a real orgasmic transport, once TASK-XCJYC frees the name.

ACP is an open standard from Zed Industries (August 2025, Apache-licensed): JSON-RPC 2.0 over stdio for local agents, HTTP/WebSocket for remote (work in progress). It standardises the editor-to-agent boundary; MCP standardises tool access beneath it. Adopted by JetBrains, Google and GitHub, with 25+ agents.

The draw is consolidation. Zed's ACP Registry already lists Claude Agent, Codex, Gemini CLI, OpenCode, Copilot, Cursor and Pi Coding Agent. Orgasmic currently maintains a bespoke adapter per harness — `adapters/claude.rs` (stream-json), `adapters/codex.rs` (app-server), `adapters/cursor_acp.rs`, `adapters/hermes.rs` — each with its own event mapping, session identity story and transcript-finder strategy. One ACP transport could in principle serve several of them through a single event mapping.

Open questions to answer before committing to it:
1. Does ACP expose what orgasmic's supervisor actually needs — terminal declaration, tool-call visibility, stall signals, and a resumable native session identity? A protocol built for editor UX may not carry the lifecycle facts recovery depends on.
2. Does an ACP-launched agent still write its vendor-native transcript, or does the adapter layer hide it? The retro contract depends on vendor JSONL existing and being resumable (see dec on transcript ownership).
3. Is the ACP adapter an extra process between orgasmic and the harness, and what does that mean for the startup preflight (TASK-TJKFC) and for credential handling (TASK-Z8WEJ)?
4. Would it replace the bespoke adapters or sit alongside them? A fifth transport that duplicates four existing ones is a cost, not a saving.

This is deliberately a research-and-decide task, not an implementation commitment. If the answer is that ACP does not carry orgasmic's lifecycle needs, recording that is a complete and useful result.

Depends on TASK-XCJYC only for the name; the evaluation can start earlier.

* BACKLOG TASK-7QM8M Bound the bytes boot auto-reattach reads per session file    :daemon:boot:performance:
:PROPERTIES:
:ID: TASK-7QM8M
:PRIORITY: P1
:END:

Boot auto-reattach reads every session file whole. It calls
=read_session_file= -> =std::fs::read_to_string=, so a project with large TUI
transcripts pays their full size at every daemon start. This is the same
unbounded read TASK-KWSTJ removed from =GET /api/runs=, still present on the
boot path; measured there, a 2.4 GB board cost 24.7 s and the bounded scanner
reduced it to 28 MB inspected.

TASK-KKGKM moved this scan after bind and onto a blocking thread, so it can no
longer stop the daemon serving, and it is no longer on the critical path. What
remains is cost and latency: reattachment of the operator's live manager
terminal is delayed by however long the read takes.

=boot_reattach_candidate= consumes only lifecycle-class events — acquire,
run_meta, release, the terminal driver event, and the external-registration
marker — which is exactly what =scan_session_lifecycle= retains, so the
substitution should be direct.

One correctness subtlety must be handled explicitly rather than assumed. The
function calls =latest_run_segment=, which picks the newest contiguous run
segment by run_id. On a truncated scan the prefix may hold one segment's
acquire while the tail holds a later segment's end, so the two windows can
describe different runs. =classify_session_files= already guards this with
=scan.final_envelope_retained= before trusting =release_outcome=; reattach needs
an equivalent rule. Getting it wrong means a live run is silently not
reattached, which looks like the run vanished.

Acceptance:
- boot reattach inspects bounded bytes per session file, not file size
- a truncated scan cannot combine two run segments into one candidate
- a still-live run in a multi-segment session file is still reattached
- measured against a production-shaped board, as TASK-KWSTJ was

:PRIORITY: P1
:END:

Problem: =GET /api/runs= answers three unrelated questions with one full pass
over every session file on disk.

1. "Is anything live?" — the CLI's fence before restart, update, and
   dispatch-close (=daemon_lifecycle.rs::live_manager_runs=). It reads the
   response, keeps =live=, and filters to =task_id= starting =manager.launch:=.
2. "What should the UI badge show?" — =ui/src/hooks/useTaskRuns.ts=.
3. "What needs recovery?" — the actual crash-recovery inventory, which is the
   only one of the three that genuinely requires reading durable history.

Question 1 needs no disk at all. Live runs are supervisor-local: the daemon
already holds them in memory, with their identities. Answering it through the
recovery inventory means a restart fence pays for classifying every historical
run on the board.

The codebase already contains this reasoning, applied to the singular endpoint
and never to the plural one. =get_run= (api.rs, "Exact active-run lookups are
supervisor-local") checks =state.supervisor.snapshot()= first and only falls
back to =recovery_status= when the id is not live, with the comment: "Worker
finalize and manager close must not scan unrelated durable recovery history
before they can act on a live run whose id they already know." That is exactly
the argument for splitting the list endpoint too.

Why this is worth doing even though the scan is now cheap: the coupling, not the
duration, is the defect. Measured on the operator's board 2026-07-25 after
TASK-KWSTJ: 224 session files, 2.42 GB on disk, 31.4 MB inspected, 0.24 s to
first byte — down from 41.9 s. Before that fix the same fence failed outright:
=manager dispatch-close --status aborted= died after 10.03 s against the CLI's
10 s deadline, so a dispatch that failed at startup could not be closed by the
documented verb. Two defects multiplied — startup left the mess, enumeration
prevented cleaning it. A control-path check that cannot fail for reasons
belonging to unrelated historical runs removes that whole class.

Work:
1. Give the liveness question its own answer sourced from the supervisor
   snapshot, with no session-file reads. The CLI fence and any other
   "is something running right now" caller move onto it.
2. Keep =GET /api/runs= as the recovery inventory it actually is. Decide
   explicitly whether the UI badge path belongs on the live source, the
   inventory, or a third shape — it wants live state per task, not history.
3. Do not duplicate classification logic. If the live bucket is derived in two
   places it will drift; the supervisor snapshot should be the single source for
   "live" and the inventory should consume it rather than recompute it.
4. Naming should stop implying that =/api/runs= is a general run list. It is a
   recovery inventory and reads as one only after reading the handler.

Acceptance:
- the restart/update/dispatch-close fence performs no session-file reads
- that fence still refuses correctly while a manager terminal is live, and
  still permits when only historical runs exist
- =GET /api/runs= keeps its current classifications and bounded-scan metrics
- a regression proves the fence answers on a board whose session files are
  unreadable or absent, since its correctness no longer depends on them

* BACKLOG TASK-MRJRK A registered project can be missing from the index, and the 404 blames the wrong thing    :P1:
:PROPERTIES:
:ID: TASK-MRJRK
:PRIORITY: P1
:END:

Problem: a project can be registered on the board, listed by `orgasmic project
list`, and still be absent from the index snapshot, at which point every route
that addresses it by id fails with a 404 that names the project as though it
were unregistered. The operator's only signal is an error that points at the
wrong thing, and the only known remedy is `orgasmic reindex` - which nobody
tries, because nothing suggests the index is the problem.

Two things need fixing, and they are separable.

1. The diagnosis. `select_project` (api.rs) reports a missed lookup as
   `not_found("project {id}")`. That message is indistinguishable from a genuinely
   unknown project, so it sends the reader to check registration - the one thing
   that is definitely fine, since `project list` just showed it. The message
   should distinguish "no such project on this board" from "registered but not
   in the current index snapshot", and the latter should name the remedy
   (`orgasmic reindex`). This is cheap and is most of the operator-visible value.

2. The underlying gap. A project that is registered but missing from the
   snapshot is a state the daemon can sit in indefinitely: nothing retries, and
   nothing reports it. Whatever the cause, the daemon should either converge on
   its own or say plainly that it has not. A `status` field naming registered-
   but-unindexed projects would make the condition self-reporting rather than
   something an operator stumbles into through an unrelated 404.

Do not start by assuming a cause. What is actually established is thin, and one
plausible-sounding explanation has already been checked and ruled out.

THE ARITHMETIC
- Heartbeats arrive every 30 s (observed: 118 of them, seq 0..115, exactly 30 s
  apart).
- `DEFAULT_STALL_TIMEOUT` is 600 s (supervisor.rs:65).
- Stall is computed from `last_activity_at = rec.last_input_at.max(rec.last_driver_event_at)`

  drained event, variant-agnostically. The crate's own test says so:
  `heartbeat_is_non_terminal_so_drain_never_releases_on_it` — "The event drain
  resets last_driver_event_at for every drained event (variant-agnostic)".

So a harness that is alive and emitting heartbeats can never trip the 600 s stall
timeout, no matter how long it does no work. The only backstop is
`DEFAULT_MAX_RUN_DURATION` at 14_400 s — four hours of a billed session producing
nothing before the daemon acts.

daemon could not tell the difference. A run with zero tool calls and 118
heartbeats is, to the supervisor, exactly as healthy as one with 243 tool calls.

worker exited. Same family, and this is the mechanism.

append-only ledger unparseable. Every subsequent CLI read fails, so no verb —
including the ones you would use to repair it — can run. The only way out is a
hand-edit of the file the manager is forbidden to hand-edit.

REPRODUCED [2026-07-26], not inferred. `orgasmic tx record --type manager.action
--project orgasmic --task TASK-D0GA3 --reason "$(cat multi-line-file)"` returned

    {"tx_id": "tx-20260726-orgasmic-2973", "tx_path": ".orgasmic/tx/2026-07.org"}

and the next command failed with

    Error: parse .orgasmic/tx/2026-07.org
    Caused by: ...:29850: malformed property drawer entry: blank line inside
    property drawer

The remaining `--extra KEY=VALUE` properties were appended AFTER the injected
prose, so they landed outside the drawer too. A second, subtler failure mode:
once the blank lines were removed the parser then rejected the entry with "tx
entry has trailing content after property drawer" — tx entries are drawer-only
and carry no body at all, which is not stated anywhere in `tx record --help`.

BLAST RADIUS. The write is accepted, so a manager has no signal until the next
read. Both ledgers were hit in one session: the project ledger and, because
`tx record` is not project-scoped by default (TASK-HXSW0 instance 6),
`$ORGASMIC_HOME/state/tx/2026-07.org` as well. A daemon that cannot parse its
tx file cannot dispatch, cannot close, cannot update a task.

THREE SEPARATE DEFECTS, all in this one path:
1. No validation. A value containing a newline must be rejected at the API
   boundary with a clear error, before anything is written.
2. No atomicity or verification. The writer should re-parse what it produced
   before reporting success — a ledger that only accepts what it can read back
   cannot be bricked by its own writer.
3. No documented body support. If long prose belongs in a tx (and
   `tx-scannable-bodies` implies it does), the entry format needs a body region
   the parser accepts, or `--reason` needs to be documented as single-line and
   the convention corrected.

Acceptance:
- `tx record --reason` with an embedded newline fails with a clear message and
  writes nothing
- a tx write that would not round-trip through the parser is rejected rather
  than committed
- `tx record --help` states the single-line constraint, or a body region exists
  and is tested with multi-paragraph prose
- a regression test asserts the ledger still parses after each supported write
