Problem: dec_WDR5K item 10 retired worker templates with a hard cutover, and the daemon "warns-and-ignores a leftover `user/workers/` directory" (`crates/orgasmic-daemon/src/lib.rs`). The warning goes to the daemon log. No agent reads the daemon log.

Observed 2026-07-25: `~/.orgasmic/user/workers/` still held `implementer-codex-acp.org` and `reviewer-codex-acp.org`, both written 2026-07-16, one day before dec_WDR5K. The general defect: retired content stays on disk looking exactly like live configuration, and the only signal that it is dead is written where the reader never looks. A stale file with plausible content is worse than a missing one, because it produces confident wrong reasoning rather than a lookup failure.

Work:
1. `orgasmic doctor` reports retired-content residue by name — leftover `user/workers/`, and any other path a hard cutover left behind — with the deciding node id (here dec_WDR5K) so the reader can check the rationale rather than guess.

Acceptance:

- the check names the deciding node, not just the path

* TODO TASK-XCJYC Rename non-ACP transports and reserve acp-* for the real protocol :drivers:cli:naming:
:PROPERTIES:
:ID: TASK-XCJYC
:PRIORITY: P1
:END:

Problem: orgasmic uses "acp" for transports that are not the Agent Client Protocol. ACP is a specific open standard from Zed Industries (released August 2025, JSON-RPC 2.0 over stdio for local agents, HTTP/WebSocket for remote): it standardises the editor-to-agent boundary while MCP standardises tool access. It is adopted by JetBrains, Google, GitHub and 25+ agents, and Zed ships an ACP Registry containing Claude Agent, Codex, Gemini CLI, OpenCode and others.

What orgasmic labels `acp` is not that:
- `acp-stdio` + claude runs `claude -p --input-format stream-json --output-format stream-json` — Claude Code's own stream-json wire
- `acp-stdio` / `acp-ws` + codex runs `codex app-server` — Codex's own JSON-RPC app-server
- `cursor-acp` is a cursor-agent adapter

The source half-knows: `adapters/claude.rs` documents itself as "ACP-like stdio stream-json", and the `protocol_version` values are already honest (`claude-code-stream-json/1`, `codex-appserver/1`). Only the wrapper names lie. One genuine error remains at `adapters/claude.rs:364`, which reports `protocol_version: "acp/1"`.

Cost, in increasing order of severity:
1. It misleads readers into treating two unrelated native protocols as one protocol's two implementations. This happened twice in one manager session on 2026-07-25.
2. It hides that ACP-vs-MCP is a live architectural distinction, precisely the layering an operator asking for a worker "without MCP" is reasoning about.
3. It squats on the name. If orgasmic adds real ACP, the correct name is taken by something that is not it.

Decision (operator, 2026-07-25): modes name the wire only, since the harness field already determines the protocol.
- `("acp-stdio", H)` becomes `("stdio", H)`
- `("acp-ws", H)` becomes `("ws", H)`
- driver id `claude-acp` becomes `claude-stream-json`; `cursor-acp` becomes `cursor-agent`
- `acp-stdio` and `acp-ws` are reserved for real ACP and must not be reused for anything else

Scope: roughly 371 occurrences of `acp` across 12+ files, concentrated in `orgasmic-daemon/src/api.rs`, the CLI and daemon dispatch tests, `orgasmic-daemon/src/supervisor.rs`, `orgasmic-daemon/src/config.rs`, and the drivers crate.

This is a cutover, not a find-and-replace. `--mode acp-stdio` is user-facing, the pair list is the `SUPPORTED` matrix authority per dec_WDR5K item 1, and the old names are persisted: 70 historical runs carry `transport: "acp-stdio"` and 1 carries `acp-ws`, plus worker ids such as `reviewer-codex-acp-stdio` throughout tx history.

Work:
1. Rename the mode pairs, driver ids, transport constants, and the `acp/1` protocol_version error.
2. Follow dec_WDR5K item 10's precedent for historical data: no alias table, old records render their historical strings as plain text. Confirm the recovery classifier and transcript finder still resolve pre-rename records, since `persisted_run_address_from_session` reads `transport` from old RunMeta.
3. Record the reservation so a future contributor cannot re-take `acp-*` for a non-ACP transport.
4. Add a glossary term distinguishing ACP, MCP, and orgasmic's transport modes.

Acceptance:
- no identifier, mode value, doc comment or protocol_version calls a non-ACP transport "acp"
- pre-rename session records still classify and still resolve to their native transcripts
- `acp-stdio` and `acp-ws` are unused and documented as reserved

* TODO TASK-3CM0Q Require a recorded tier declaration before manager-direct source edits :workflow:runtime:process:
:PROPERTIES:
:ID: TASK-3CM0Q
:PRIORITY: P1
:DEPENDS_ON: TASK-YGB1R
:END:

Problem, observed 2026-07-25 on TASK-KWSTJ: a manager session read the resolved `default` workflow printed by `orgasmic entry`, registered that manager-implementer is a sanctioned mode, and went straight to editing source. It never classified the work as trivial / ordinary / risky at all. The result was ~900 lines of P0 daemon-recovery code across four crates landing with no independent reviewer pass and no user decision about tier.

The failure mode is structural, not textual. The workflow states the rule clearly, but it only imposes a *reading* obligation. An agent under execution momentum skims a reading obligation; it cannot skim an *output* obligation. Nothing in the current flow requires the agent to emit anything before its first source edit, so skipping the decision is silent and leaves no trace to audit afterwards.

Also note the existing escape hatch does not fire: "if the tier is unclear, ask the user" only triggers when the agent notices ambiguity, and an agent that never asked the question never notices any.

Work:
1. Add a manager-side tier declaration recorded through the daemon, e.g. `orgasmic manager tier --task <id> --tier trivial|ordinary|risky --reason <text>`, appended to tx like any other manager state write so it is auditable after the run.
2. Invert the default in `shipped/entry/router.org` and `shipped/workflows/default.org`: no tier stated for the current task means the manager may not edit source directly. Manager-direct becomes a thing you claim, not a thing you fall into.
3. Make the declaration cheap for genuinely trivial work — one command, no prompt round-trip when the tier is `trivial` and the task carries no escalating trigger (see the sibling triggers task).
4. Decide and document what happens on a mid-task tier change (scope grew from trivial to ordinary): re-declare, or escalate to the user.

Out of scope: enforcing this in the daemon against arbitrary file writes. This is a manager-discipline surface, not a sandbox.

Acceptance:
- a manager session that edits source with no declared tier is visibly out of policy, and the omission is detectable from tx after the fact
- declaring `trivial` costs one command
- router and workflow text agree with the CLI surface, with no leftover prose implying manager-direct is the default

written today would reproduce it.

Note what is NOT in conflict: the matrixs reviewer row already specifies a
different vendor on the review side, which AGREES with TASK-0JY7M item 3. The
conflict is items 1 and 2 — the ask, and the no-storage rule — not reviewer

- Re-check the =--mode= guidance against reality rather than copying it: tmux is
  only safe once the runtime carries TASK-4CSMY, and the convention should say
