* TODO TASK-YGB1R Replace workflow tier adjectives with derivable escalating triggers :workflow:runtime:process:
:PROPERTIES:
:ID: TASK-YGB1R
:PRIORITY: P1
:END:

Problem: `shipped/workflows/default.org` classifies work with bare adjectives — "trivial", "ordinary", "risky". Those are subjective enough that an agent already in execution momentum resolves them in whichever direction keeps it moving. On TASK-KWSTJ a P0 daemon-recovery change touching ~900 lines across orgasmic-core, orgasmic-daemon, orgasmic-cli and the UI read as manager-direct without the classification ever being contested.

Replace the adjectives with triggers a reader cannot argue with, while keeping the three-tier shape.

Work:
1. Define concrete escalating triggers, at minimum: task priority (P0/P1 is never trivial); blast-radius paths (daemon recovery, supervisor, boot, auth, dispatch lease, writer durability); breadth (crate count / file count / net line count over a stated threshold); and presence of a `depends_on` chain or an umbrella parent.
2. Any trigger firing means the work is at least `ordinary`; two or more, or a safety/auth path, means `risky`.
3. Keep the tiers as guidance for *how much process*, not a hard gate — the point is to remove the judgement call about which tier applies, not to remove judgement about how to work.
4. Where a trigger is derivable from the task heading itself (priority, tags, depends_on), surface it: an agent reading `orgasmic task get` should see the floor tier without recomputing it.
5. Reconcile with the manager-implementer clause in `shipped/entry/router.org` so router and workflow do not drift.

Non-goal: an exhaustive rubric. Four or five unambiguous triggers beat twenty debatable ones, and long prose dilutes the instruction it is meant to strengthen.

Acceptance:
- two agents reading the same task heading reach the same floor tier
- the P0/multi-crate/recovery-path shape that produced this task classifies as at least `ordinary` with no interpretation
- the fast path for genuinely small work stays fast

* TODO TASK-TW3N3 Document and guard the committed-history precondition for worker dispatch :workflow:dispatch:docs:
:PROPERTIES:
:ID: TASK-TW3N3
:PRIORITY: P1
:END:

Problem: the workflow tells a manager to delegate ordinary work and to run an independent reviewer pass on risky work, but never says that delegation only works on committed history. `orgasmic manager dispatch` builds the worker a git worktree from a ref, so a dispatched implementer or reviewer sees exactly nothing of the manager's uncommitted edits. A reviewer dispatched against an uncommitted patch reports a clean review of code it never read.

This compounds a known sibling trap already recorded for `.orgasmic/` state: a worker in its own worktree also cannot see the live daemon's uncommitted writes to the manager's `.orgasmic/tx`, tasks, and decisions, so reviewers give false negatives on graph changes too.

The two together mean delegation is quietly useless at exactly the moment a manager-implementer reaches for it — after doing the work, wanting a second opinion before landing.

Work:
1. State the precondition explicitly in `shipped/entry/router.org` and `shipped/workflows/default.org`: commit to a branch before dispatching any worker that must see your changes, and pass that ref as `--from`.
2. Document the `.orgasmic/` blindspot in the same place, with the verification workaround (check graph state through the daemon CLI rather than through the worktree's files).
3. Consider a guard rather than only prose: when `manager dispatch` is invoked with a dirty worktree in the project root, warn (or refuse without an explicit override) naming the uncommitted paths the worker will not see.
4. Add the reviewer-specific case to whatever grill/review dispatch guidance exists — a review dispatch with nothing committed is the highest-cost version of this mistake, because it returns a confident wrong answer.

Acceptance:
- an agent following the router can dispatch a reviewer that actually reads the intended diff, without discovering the constraint by being surprised
- a dispatch that would silently review the wrong tree is either blocked or loudly flagged
- the `.orgasmic/` blindspot and the uncommitted-source blindspot are documented as one coherent constraint, not two folk facts

* TODO TASK-4YX1K Default to proceeding; confirm only for irreversible or outward-facing actions :workflow:runtime:process:
:PROPERTIES:
:ID: TASK-4YX1K
:DEPENDS_ON: TASK-YGB1R
:PRIORITY:   P1
:END:

Problem: the runtime tells a manager what work to do and how much process to apply, but says nothing about when to stop and ask a human. Agents fill that vacuum with timidity. Observed 2026-07-25: a manager finished TASK-KWSTJ, correctly identified that a reviewer cannot see uncommitted source, and then asked the user for permission to commit to a local branch — a reversible, machine-local step that was already the precondition for a review the user had asked for. The question contained no decision. It cost a round-trip and stalled the work.

This is the mirror image of TASK-3CM0Q. That task stops an agent from silently proceeding through a decision that is genuinely the user's. This one stops an agent from interrupting on something that is not a decision at all. An agent without an explicit line between them oscillates: the same session skipped a real tier decision, was corrected, then over-corrected into asking about a mechanical step. Both failures are the human checkpoint landing in the wrong place, and neither is fixed by telling the agent to "use judgement".

Work:
1. State the default in `shipped/entry/router.org` and `shipped/workflows/default.org`: proceed. Asking is the exception and needs a reason that names which property of the action triggers it.
2. Define confirmation triggers by property, not by feeling. Confirm when an action is hard to reverse, leaves the machine, or spends someone else's resources — pushing to a remote, publishing a release or artifact, force-pushing or rewriting history, deleting or rewriting operator session/run history, touching the LaunchAgent or a live production daemon, or anything that mutates a shared or external service.
3. Name the proceed class just as explicitly, because a bare "proceed by default" will not survive contact with a cautious agent: committing to a local branch, creating and removing worktrees, running gates and test suites, reading anything, and `.orgasmic/` state writes through the CLI.
4. Cover the standing-authorization case: once a user has approved a plan, the mechanical steps that plan obviously entails do not each need their own approval. Re-asking inside an approved plan is itself the defect.
5. Say what to do instead of asking when an agent is unsure but the action is in the proceed class: act, then report what was done plainly enough to be reversed.

Non-goal: expanding autonomy on the confirm class. This narrows *where* the human is asked, it does not reduce *whether* they are asked about the things that matter.

Acceptance:
- committing to a branch, creating a worktree, or running gates never produces a permission question
- pushing, publishing, force-pushing, or touching the live daemon still does
- the router text distinguishes the two classes by a stated property, so an agent reaching an unlisted action can classify it rather than guess
- reads coherently against TASK-3CM0Q: one task puts a checkpoint where a decision exists, this one removes checkpoints where none does

Problem: dec_WDR5K item 9 states that "per-kind model preference is manager judgment per dispatch, not configuration", and removes every model and effort identifier from orgasmic code and config. That is a deliberate and correct constraint — it is what makes vendor model bumps require no orgasmic change. But it leaves the manager with no way to learn what the operator actually wants, and nothing in the runtime prompts it to find out.

Observed 2026-07-25 on TASK-KWSTJ: a manager dispatching a reviewer for its own P0 daemon-recovery change chose `acp-stdio` + `claude` by taking the first entry of the `SUPPORTED` array, passed no model and no effort, and never asked the operator anything. Three separate defects in one dispatch:
- the transport pair was decided by source ordering, not judgment
- effort was left at harness default for a review the workflow itself says warrants a premium tier
- the reviewer ran on the same model family as the author of the code under review

The third is the structural one. A reviewer sharing the implementer's model family shares its priors and its blind spots, which is most of what an independent pass is for. That is a runtime policy question, not manager taste, and it should not be re-derived per dispatch by whoever happens to be holding the session.

Because configuration was removed by design, a session-level ask is the only durable channel left. This is an elicitation that *removes* downstream friction, so it does not conflict with TASK-4YX1K's default-to-proceeding rule: ask once, cheaply, then stop asking.

Work:
1. The manager asks the operator once per session for agent-selection preference — harness family, and effort posture for review and risky stages — at the first dispatch, not at session start, so a session that never dispatches never asks.
2. Carry the answer for the session so subsequent dispatches do not re-ask. Decide whether it persists beyond the session, respecting item 9: an operator's *harness family* preference is not model knowledge, but a pinned model identifier would be, and must stay per-dispatch.
3. Encode reviewer independence as runtime policy: a reviewer dispatch defaults to a different harness family than the run under review, and the manager states its reason when it does not. Where the implementer harness is unknown, ask rather than defaulting to the manager's own family.
4. Fold in the premium-tier rule already in `shipped/workflows/default.org` — review and risky stages should carry an explicit effort, so leaving it unset is a visible choice rather than an oversight.
5. Reconcile with TASK-4YX1K so the two read as one policy: this is the sanctioned once-per-session elicitation; everything downstream of it proceeds without asking.

Non-goal: reintroducing worker templates or any stored model catalog. dec_WDR5K stands. This is about the manager acquiring a preference at runtime, not about orgasmic storing model knowledge.

Acceptance:
- a manager cannot complete its first dispatch of a session without either an operator preference or an explicit recorded reason for the default it chose
- a reviewer defaults to a different harness family than the code's author
- review and risky-stage dispatches carry an explicit effort
- no model identifier enters orgasmic config or code

* TODO TASK-XCJYC Rename non-ACP transports and reserve acp-* for the real protocol :drivers:cli:naming:
:PROPERTIES:
:ID: TASK-XCJYC
:PRIORITY: P1
:END:

Problem: orgasmic uses "acp" for transports that are not the Agent Client Protocol. ACP is a specific open standard from Zed Industries (released August 2025, JSON-RPC 2.0 over stdio for local agents, HTTP/WebSocket for remote): it standardises the editor-to-agent boundary while MCP standardises tool access. It is adopted by JetBrains, Google, GitHub and 25+ agents, and Zed ships an ACP Registry containing Claude Agent, Codex, Gemini CLI, OpenCode and others.

What orgasmic labels `acp` is not that:
- `acp-stdio` + claude runs `claude -p --input-format stream-json --output-format stream-json` — Claude Code's own stream-json wire
- `acp-stdio` / `acp-ws` + codex runs `codex app-server` — Codex's own JSON-RPC app-server
- `cursor-acp` is a cursor-agent adapter

The source half-knows: `adapters/claude.rs` documents itself as "ACP-like stdio stream-json", and the `protocol_version` values are already honest (`claude-code-stream-json/1`, `codex-appserver/1`). Only the wrapper names lie. One genuine error remains at `adapters/claude.rs:364`, which reports `protocol_version: "acp/1"`.

Cost, in increasing order of severity:
1. It misleads readers into treating two unrelated native protocols as one protocol's two implementations. This happened twice in one manager session on 2026-07-25.
2. It hides that ACP-vs-MCP is a live architectural distinction, precisely the layering an operator asking for a worker "without MCP" is reasoning about.
3. It squats on the name. If orgasmic adds real ACP, the correct name is taken by something that is not it.

Decision (operator, 2026-07-25): modes name the wire only, since the harness field already determines the protocol.
- `("acp-stdio", H)` becomes `("stdio", H)`
- `("acp-ws", H)` becomes `("ws", H)`
- driver id `claude-acp` becomes `claude-stream-json`; `cursor-acp` becomes `cursor-agent`
- `acp-stdio` and `acp-ws` are reserved for real ACP and must not be reused for anything else

Scope: roughly 371 occurrences of `acp` across 12+ files, concentrated in `orgasmic-daemon/src/api.rs`, the CLI and daemon dispatch tests, `orgasmic-daemon/src/supervisor.rs`, `orgasmic-daemon/src/config.rs`, and the drivers crate.

This is a cutover, not a find-and-replace. `--mode acp-stdio` is user-facing, the pair list is the `SUPPORTED` matrix authority per dec_WDR5K item 1, and the old names are persisted: 70 historical runs carry `transport: "acp-stdio"` and 1 carries `acp-ws`, plus worker ids such as `reviewer-codex-acp-stdio` throughout tx history.

Work:
1. Rename the mode pairs, driver ids, transport constants, and the `acp/1` protocol_version error.
2. Follow dec_WDR5K item 10's precedent for historical data: no alias table, old records render their historical strings as plain text. Confirm the recovery classifier and transcript finder still resolve pre-rename records, since `persisted_run_address_from_session` reads `transport` from old RunMeta.
3. Record the reservation so a future contributor cannot re-take `acp-*` for a non-ACP transport.
4. Add a glossary term distinguishing ACP, MCP, and orgasmic's transport modes.

Acceptance:
- no identifier, mode value, doc comment or protocol_version calls a non-ACP transport "acp"
- pre-rename session records still classify and still resolve to their native transcripts
- `acp-stdio` and `acp-ws` are unused and documented as reserved

- the process IS alive the whole time — it is not killed, not starved of a slot
- it has ZERO children, so it never reached even its first `&`
- state is S (blocked), never R (runnable), so it is not losing a CPU race
- CPU time stays at 0:00.00 across 28+ seconds of sampling — it never executed
  a single instruction

A process that is alive, blocked, and has consumed no CPU is wedged BEFORE
execution, not running slowly.

THE DISCRIMINATOR

An unrelated trivial bash script (`#!/bin/bash` + one `touch`), spawned from
outside the test binary while the suite ran, timed at:

    6205 ms, 2993 ms, 63771 ms, 64 ms, 354 ms

Sixty-three seconds to spawn a two-line shell script, then 64 ms a few seconds
later. Process creation on this machine intermittently stalls for seconds to a
minute while this suite runs. Nothing about the test is special; it is just the
one test that asserts a 30 s deadline on a freshly spawned external process.

Caveat on that measurement, stated so nobody over-reads it: the timestamps were
taken by spawning python3, so each figure includes one additional process
spawn. That does not change the conclusion — spawning anything is what is slow —
but the per-call attribution is not exact.

Peak process count during a run was only ~720 against a 5333 maxprocperuid, and
fd limit is 1048576, so this is not simple resource exhaustion. The likely
mechanism is serialization in macOS exec (code-signing / syspolicy validation)
under many concurrent spawns, which is worth confirming before designing around
it.

CONSEQUENCE FOR THE FIX

Do not fix this by raising the 30 s deadline. Sixty seconds was observed, so any
constant is a guess. Either remove the dependence on a freshly spawned external
process reaching a checkpoint, or serialize the process-spawning tests against
each other so the suite stops competing with itself for exec.

The same mechanism is a plausible cause for post_artifact_regenerate_hot_path:
its two run_ids are 10 s apart, consistent with round one exceeding a deadline
and its run being released before round two. Not yet confirmed — do not record
it as established.
MECHANISM CONFIRMED [2026-07-26]. It is macOS first-exec evaluation, and it is
measurable in three lines on a completely idle machine:

    fresh script #1 first exec: 0.18 s    second exec: 0.00 s
    fresh script #2 first exec: 0.15 s    second exec: 0.00 s
    fresh script #3 first exec: 0.16 s    second exec: 0.00 s

macOS charges roughly 150-180 ms of syspolicy/Gatekeeper evaluation the first
time a newly created executable is exec-ed, and nothing thereafter. Idle spawns
of an already-evaluated script are 0.00 s, which is why every one of these tests
passes alone.

That per-file cost is paid through a single system daemon, so concurrent first
execs queue. This suite writes many fresh executable fixtures into tempdirs and
execs them in parallel, which is how a 150 ms cost becomes the 3 s / 6 s / 63 s
spawns measured earlier. The failing test is not special; it is the one that
asserts a 30 s deadline against that queue.

So the chain is: fresh fixture -> per-file Gatekeeper evaluation -> serialized
daemon -> queue under suite parallelism -> a spawned helper that never reaches
its first instruction inside the deadline.

FIX DIRECTION

Stop paying the per-file cost per test. The fixture script should be created and
exec-ed ONCE per test binary and then reused, with the per-test variation moved
out of the file contents and into argv, so the second and subsequent uses hit
the warm path. Pre-warming a shared fixture is preferable to serializing the
tests, because it removes the cost rather than queueing it, and it also speeds up
every other spawn-based test in the crate.

Raising the deadline is not a fix. 63 s was observed; any constant is a guess.

NOTE FOR CI (TASK-S2KM0): this mechanism is macOS-specific. A Linux runner has
no Gatekeeper and will very likely not reproduce it, so this test could pass in
CI while failing on every developer Mac. That is an argument for fixing the
fixture rather than tolerating the failure locally, and for not concluding "green
in CI" means "green".
