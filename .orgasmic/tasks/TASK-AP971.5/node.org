** Question
Which event types stay in the project-level monthly tx/ ledger vs move to per-node journals? What happens to recovery-claim machinery and the activity feed that lean on tx today?
** Resolution
Grilled with owner 2026-08-22; five decisions. Facts behind them: all 6,243 tx entries ever carry :PROJECT: (no home-ledger traffic); most node-scoped types (task.created/edited/property_updated, every graph.*) are write-only audit with no reader; readers exist only for the .11 dispatch set, task.state_transitioned (CLI torn-close repair + legacy close replay), comment/run.* (activity feed) and question.raised/answered (notification bell). Recovery claims live as daemon-MAC'd files under ~/.orgasmic, not in tx/ — the split does not touch them. The dispatch-close commit is the one cross-ledger atomic op (close tx + task.state_transitioned per task + N task-file rewrites via transaction_multi); the writer already does N rewrites with backup/rollback and refuses N ledgers.
1. Routing rule: an event goes to a node's journal iff it is about exactly one node that has a directory; everything else stays in project tx/. Journal: comment, worker.comment, task.state_transitioned (non-dispatch flips), task.property_updated, task.edited, graph.{decision,glossary,architecture,gotcha,convention}.edited, graph.decision.reparent, reviewer.finding, review.verdict, artifact.* (already per-dir). tx/: the .11 dispatch set + implementer.commit_pending (a manager signal), all manager.*, goal set/clear/supersede, graph.handoff.edited, project.*, release.published, daemon.*, benchmark.*, question.raised/answered, legacy untyped (note/review/verification/correction), node deletions.
2. Singletons (tasks/handoff.org, tasks/goal.org, project.org) stay files; their events stay in tx/ — project-level by nature.
3. Node birth/death: creation = the node dir appears and its journal's first entry is created; nothing in tx/ (the project feed derives it). Deletion = a tombstone record in tx/ and the dir is removed (git keeps it); a journal cannot hold its own deletion.
4. Dispatch-cycle flips and the atomic close: the close stays ONE tx append (FROM/TO per task as today) + N node.org rewrites, atomic with the writer as it is. No journal entry is written for dispatch-cycle flips; the journal view derives them from the close tx (same rule as dispatch.linked in .11). This deletes inventory risk #1 (multi-ledger atomic append) and makes torn-close repair legacy-only. Non-dispatch flips (task update --state) are 1 journal append + 1 node.org rewrite — already within the writer.
5. Journal entry ids: one project sequence shared by tx/ and journals; the cold-start max scan (scan_project_tx_max_seq) extends to cover journals, once per boot; .7's index may feed it later. No sidecar, no second namespace.
Consequences: the activity feed becomes a projection over tx/ + journals with unchanged types (AP971.1 item 12); pre-cutover tx/ stays in place read-only and every fold keeps reading it (no backfill); recovery-claim machinery untouched.
