** READ THIS FIRST — STATUS
Filed [2026-08-08] immediately after the manager rebooted this machine by running
=scripts/run-tests.sh -p orgasmic-daemon= with no watchdog. Third occurrence of
the chain: =WindowServer-2026-08-08-105749.ips=, after =2026-07-29-112228= and
=2026-08-02-200136=.

** What happened
=.orgasmic/gotchas.org= carries the remedy already, and has since 2026-08-03:

: IF YOU MUST RUN THE SUITE WHILE UNATTENDED, GUARD IT. syspolicyd is pid-stable
: per boot; sample ps -o pcpu= -p <pid> every 10s and kill the cargo run if it
: holds above ~400% for a minute.

The manager READ that entry in full during bootstrap, then ran the suite without
the guard, because the sentence is conditioned on =WHILE UNATTENDED= and the
manager classified itself as attending. That classification is wrong, and the
wrongness is the point: a manager fires a command and waits for a completion
notification, so nobody is sampling the load curve — which is the only thing the
guard does. The preceding paragraph of the same entry establishes that the burst
comes from test EXECUTION, which does not care who is watching.

*So the condition does not discriminate, and a reader who applies it faithfully
still reboots the machine.* This is the project index case of a claim measured on
some situations and written down as a universal.

** Why this is not a docs fix
TASK-M47E5.3 ruled, on a different destructive path, that *a protection that
lives in a document is not a protection*. The same ruling applies here and has
now been paid for three times. Rewording the gotcha produces a fourth reader who
reasons their way around it.

The watchdog is ~10 lines of shell, and =run-tests.sh= is already the single
chokepoint every suite invocation goes through — CI (=ci.yml:191=), every
dispatched worker, and every manager. Putting it inside the script makes the
protection structural: unskippable, and applied identically by all three.

MEASURED THE SAME DAY, and it is why the guard is cheap: the full daemon lib
suite re-executed against the already-built binary on a calm host ran
*738 passed / 0 failed in 49.37s* with syspolicyd flat at 0%. The run that
rebooted the machine was the same suite through cargo under load. The guard costs
nothing on the fast path.

** Direction
1. Sample =syspolicyd= CPU from inside =run-tests.sh= for the life of the cargo
   run, on the interval and threshold the gotcha already names (~400% sustained
   for ~60s), and kill the run when it trips.
2. A trip is NOT a code verdict. It is the same class as the existing
   =INCONCLUSIVE= exit 4 — the host, not the diff — and must classify that way
   rather than as a failure. Do not let it read as green either.
3. Say what it did, loudly, in the summary: the sampled rate, the threshold, and
   that the run was truncated by the guard.
4. Only then trim the gotcha entry to point at the mechanism instead of asking
   the reader to implement it.

** Acceptance
- A =run-tests.sh= invocation that drives syspolicyd above the threshold for the
  sustained window is killed BY THE SCRIPT, with no watchdog written by the
  caller.
- The guard trip classifies as host-state (exit 4 family), never as REAL and
  never as green, and the summary names the measured rate.
- The guard is active on every path into the script, including per-crate =-p=
  runs; =--classify= runs execute nothing and are trivially inert.
- A selftest case covers the trip, in the same style as the existing ladder cases.
- =.orgasmic/gotchas.org= no longer asks the reader to build the sampler.
** Evidence
MEASURED BY A WORKER'S OWN WATCHDOG [2026-08-08], TASK-2QK4P.1's daemon gate.
This is the strongest argument yet for putting the guard inside =run-tests.sh=,
and it is not the argument the task was filed on.

The worker ran =scripts/run-tests.sh -p orgasmic-daemon= under the mandated
10s-sampling watchdog. The gate's own VERDICT said:

: host : calm (threshold syspolicyd_rate>=1.50; load=8.21 elevated (>=8.0), corroborating only)
: delta load=8.21 syspolicyd_cpu=117.8 wall_s=168
: rate  0.7012

*While the watchdog simultaneously recorded a genuine ~20-second syspolicyd burst
PEAKING AT 796.3%*, decaying to 167% and then to single digits. The hot streak
reached 2 of the 6 consecutive samples required to kill. *Only its DURATION kept
it under the guard — its amplitude was twice the 400% line.*

*THE MECHANISM: =rate= IS TOTAL CPU OVER WALL TIME, SO IT CANNOT DISTINGUISH A
SHORT VIOLENT SPIKE FROM A LONG GENTLE SIMMER — AND IT IS THE SPIKE THAT WEDGES
tccd.* Nearly all of the run's syspolicyd CPU was concentrated in ~20 seconds,
and dividing by a 168-second wall spread it into a number that reads calm. Two
instruments looked at the same 20 seconds: the instantaneous sampler saw 796.3%,
the averaged gate saw 0.7012 against a 1.50 threshold.

This is NOT an argument that TASK-STWVB's rate design was wrong. The rate answers
"was this host degraded across the run", and the round-6 review upheld the
reasoning that a verdict must not be routed through a measurement of something
else. *It is an argument that the rate cannot serve as the REBOOT guard*, because
the reboot chain (syspolicyd -> tccd -> WindowServer) is driven by sustained
INSTANTANEOUS contention, which is exactly what an average destroys.

So the guard =run-tests.sh= needs is not a stricter threshold on the number it
already computes. It is a *second, instantaneous sampler running for the duration
of the suite* — the thing every worker is currently told to hand-roll in prose,
which is what this task exists to fix. A worker hand-rolling it is why this
measurement exists at all; a worker forgetting to is why the machine rebooted on
2026-08-08.

*ONE WORD, TWO BLIND SPOTS.* TASK-K9WWM records the same =host: calm= verdict
printed while the 1m load average at the moment of failure was 13.64-15.03. The
host word is derived from syspolicyd rate and is structurally blind BOTH to a 10s
HTTP budget expiring under scheduler pressure AND to an instantaneous CPU spike.
Whatever this task ships should say plainly what the word does and does not
cover, because operators and workers alike read it as "was the host to blame".
