** Description
`sigterm_exits_through_graceful_shutdown_rather_than_default_disposition`
(`crates/orgasmic-cli/tests/daemon_lifecycle.rs:319`) fails intermittently with
"serve died on SIGTERM's default disposition".

Root cause is documented in the test's own comment and is TASK-Q07Y5's shape:
`serve` registers its SIGTERM handler AFTER `Daemon::run` returns, so a signal
delivered in that window hits the default disposition and kills the process.

MEASURED [2026-08-02] by the TASK-4CSMY implementer, as the base-commit control
the flake convention requires — isolated runs, one worktree held constant:

| tree | isolated runs | failures |
|------|---------------|----------|
| base 9017514 | 8 | 3 |
| with TASK-4CSMY | 5 | 1 |

So it is pre-existing and load/timing sensitive, not a regression. It was NOT
added to `verify/flake-registry.toml` at the time, correctly: that file requires
an OPEN owning task, and an entry with no owner is a permanent exemption.

** Work
1. Register the panic in `verify/flake-registry.toml` against this task id, so
   the suite classifies it rather than reporting an unexplained REAL red.
2. Fix the race: install the SIGTERM handler before `Daemon::run` can return,
   so there is no window in which the default disposition applies.
3. Remove the registry entry in the same change that fixes it — a registered
   flake outliving its fix is the next person's false signal.

** Acceptance
- The handler is installed before the window opens; no ordering-dependent gap
  remains between `Daemon::run` returning and the handler being live.
- The test passes 20 consecutive isolated runs in one worktree.
- `verify/flake-registry.toml` carries no entry for this test once fixed.
