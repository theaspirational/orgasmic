=== HIGH — preflight does not pin the credential decision it admitted

`crates/orgasmic-drivers/src/trait.rs:455-467`,
`crates/orgasmic-drivers/src/adapters/claude.rs:365-385,421-426,885-898`,
`crates/orgasmic-drivers/src/modes/acp_stdio.rs:419-429,518-524`,
`crates/orgasmic-drivers/src/modes/subprocess_stream_json.rs:60-66`,
`crates/orgasmic-daemon/src/supervisor.rs:970-987`.

`preflight_via_adapter` clones the adapter, observes `claude auth status`,
resolves the mode — and discards it. After the supervisor has reserved the
lease, `AcpStdioDriver::acquire` clones again and `compose_request` observes
again; for claude's subprocess arm ACP-stdio then delegates to
`SubprocessStreamJsonDriver`, which clones and composes a second time. A normal
acp-stdio claude dispatch asks `auth status` **three independent times**: once
before ownership and twice after it.

Rule 4 makes this correctness-critical. With a valid native login and a stale
ambient `ANTHROPIC_API_KEY`, a `Present` answer at preflight yields
`NativeLogin` and `Ready`; a timeout or malformed answer at either later
composition yields `Unknown`, which `resolve_credentials` treats as `Absent`
and flips to `BareApiKey`. **The run then launches with the stale key that
preflight never judged, after the lease is held.** The reverse transition is
equally possible. `RunMeta` records the last selection; recording is not pinning.

Reviewer's invariant probe:

```
369:        let probe = ClaudeAuthProbe::observe(&command).await;
425:            resolve_credentials(&cfg, &ClaudeAuthProbe::observe_blocking(&spawn.command))?;
FAIL: credential mode is independently observed at 2 production sites
```

Neither existing test can catch it: `the_probe_and_the_launch_resolve_the_same_credential`
uses a configured `api_key_env`, whose precedence is deliberately independent of
status, and `the_resolved_claude_credential_mode_survives_the_mode_layer` uses a
stub that always returns the same answer.

=== HIGH — acquire blocks the async runtime, and its advertised bound is incomplete

`crates/orgasmic-drivers/src/adapters/claude.rs:577-584,637-642,732-777`, plus
the two compose paths above.

`claude_available` runs a synchronous `Command::status()` for `claude --version`
with **no timeout**, called from `simulation_reason` during synchronous
`compose_request`, directly inside async `WorkerDriver::acquire`, with no
`spawn_blocking`. The blocking status probe then polls with
`std::thread::sleep`. Because ACP-stdio composes twice, acquisition pays two
unbounded `--version` calls and two blocking `auth status` calls *after* the
async preflight already completed.

Measured by the reviewer on installed claude 2.1.220, no turn submitted: three
sequential `auth status` calls `real 0.88s`, two `--version` calls `real 0.15s`
— about **1.03s of probing** on the production call graph, two thirds of it
after preflight. If `--version` hangs, acquisition has no bound at all and holds
a Tokio worker thread. The 5s `STATUS_TIMEOUT` on `blocking_native_login_evidence`
does not bound the preceding availability probe.

This is the TASK-Z3093 lesson recurring: blocking work on a runtime worker
thread.

=== Ask

1. Resolve a single immutable credential plan **before ownership** and carry
   that exact plan into acquire and composition. Do not re-probe in
   `compose_request`. The plan carries mode plus the non-secret launch facts
   (whether to neutralise the ambient key, whether to inline helper settings);
   secret values stay non-durable.
2. Remove the duplicate ACP-stdio composition for subprocess-stream-json, or
   make the first composition the request actually delegated and spawned.
3. Keep every harness probe async and wall-clock bounded. No `Command::status`,
   no `std::thread::sleep`, no pipe-draining wait on a Tokio worker.
4. Decide the `Unknown` policy explicitly and record it. Treating `Unknown` as
   `Absent` preserves key-only installs, but it lets a transient timeout change
   the credential tier between otherwise identical dispatches. Explicit
   `api_key_env` and `--credential-mode bare_api_key` already give a
   deterministic key choice; say whether an *unchosen* ambient key should also
   win on inconclusive detection, and why.

=== Acceptance

- A regression whose status stub returns `Present` at preflight and
  `timeout/Unknown` at composition, asserting the admitted mode, the spawned
  argv/env and the RunMeta entry are all identical. Prove it by injection:
  restore the re-probe, watch it fail, remove it, watch it pass — with output.
- A regression where `claude --version` hangs, proving acquisition stays bounded
  and the daemon stays responsive.
- Count the production `auth status` observations per dispatch and assert the
  number. One is the target; the test should name the number, not describe it.
