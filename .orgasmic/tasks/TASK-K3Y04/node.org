** Description
Follow-up to TASK-EBVHJ. The =ConnectGate= "Advanced →" button calls =goView('settings')=, but =pathForView= (=AppShell.tsx= ~136) falls back to =/board= whenever =projectId= is null, and Settings is only project-scoped (=/projects/$projectId/settings=). So for the exact target user — a fresh tunnel visitor with no project selected — "Advanced →" lands on =/board= instead of Settings, where they can't adjust baseUrl/profiles before connecting.

Pick the smallest coherent fix:
1. Add a global, project-independent Settings route (e.g. =/settings=) the gate can always reach (the connection/profile section needs no project); OR
2. If a global route is too invasive pre-MVP, hide/disable "Advanced →" in =ConnectGate= when there is no active project (so the button never dead-ends), and surface profile/baseUrl editing inline in the gate instead.

** Acceptance Criteria
- [ ] From a projectless origin, the visitor can reach connection/profile settings (baseUrl + token) without first selecting a project — OR the dead-end affordance is removed and equivalent control lives in the gate.
- [X] No regression to TASK-EBVHJ's blocking token flow; =npm --prefix ui run build= + =tsc --noEmit= green.

** Evidence
Chose option 1 (global route — cleaner than hiding the affordance, and =SettingsView= already handles =projectId: null= by disabling the project-config section). Implemented directly by the manager (trivial ~16-line scope), landed on main in =cbe7c6e=: new root-level =globalSettingsRoute= (path =settings=) → =<SettingsView projectId={null}/>= in =ui/src/app/router.tsx= (added to =routeTree=); =pathForView= in =AppShell.tsx= now returns =/settings= for =goView('settings')= when =projectId= is null (else the existing =/projects/$projectId/settings=). So "Advanced →" and the header settings button both reach Settings projectless. Gates: =tsc --noEmit= + =npm run build= green.
