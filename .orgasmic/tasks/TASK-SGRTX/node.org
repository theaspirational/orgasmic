THE DEFECT

`modes/acp_stdio.rs::compose_stdio_request` takes the adapter's fully composed
`HarnessRequest::Subprocess` and destructures it as:

    HarnessRequest::Subprocess { stdin_payload, close_stdin, env: request_env, .. }

The `..` silently swallows `args`. It then calls `subprocess_from_stdio_spawn`,
which rebuilds the request with `args: spawn.args.clone()` — the bare
`stdio_spawn()` list. Only `env` and `stdin_payload` survive the round trip.

So on acp-stdio, everything `adapters/claude.rs::compose_request` computes is
recorded and then thrown away before the process is spawned:

- `--session-id <runtime_id>`  (TASK-VB9DQ item 2)
- `--bare` / `--strict-mcp-config`  (TASK-Z8WEJ credential mode)
- `--model <model>`

           --include-partial-messages --verbose

inert. Its acceptance criterion "an acp-stdio claude run leaves a native

WHY THE TESTS DID NOT CATCH IT

`every_mode_persists_a_locatable_native_session` asserts on what
`compose_request` returns — the adapter's output — not on what the mode spawns.
The discard happens one layer above, in the mode. Every test in that file can
pass forever while the production path ignores all of it. Any regression for
this must assert on the argv of the request the MODE returns, or better, on a
live process.

of rebuilding from `spawn`. `spawn.args` should be the base that
`compose_request` extends, which it already is — the mode just needs to stop
discarding the extension. Check whether `binary` should also be honoured.

Then re-verify LIVE, not by test: dispatch an acp-stdio claude run and confirm
the spawned argv carries `--session-id`, and that the transcript filename equals
the run's runtime_id.

THE ACTUAL MECHANISM

`adapters/claude.rs::simulation_reason` returns `Some(EndpointEmpty)` whenever
`cfg.endpoint` is empty — which is every ordinary dispatch, since nothing sets
an endpoint. `compose_request` therefore returns `HarnessRequest::Simulated` at
its top and NEVER REACHES the argv composition below it. Every flag TASK-VB9DQ
and TASK-Z8WEJ added lives after that early return.

`compose_stdio_request` then takes its Simulated arm, sees
`upgrades_simulated_to_subprocess()` and an installed `claude`, and calls
`subprocess_from_stdio_spawn(spawn, ..)` — the bare base. Separately,
`AcpStdioDriver::acquire` delegates `Subprocess` with no jsonrpc_init to
`SubprocessStreamJsonDriver`, so there are two routes to the same bare spawn.

WHAT 61b9b7f ACTUALLY DID

Before it, `stdio_spawn` itself carried `--bare` and `--no-session-persistence`
(confirmed: `git show 61b9b7f~1`, lines 136 and 144). Those reached the process
because the bare-args path is the one that spawns. The commit REMOVED both from
`stdio_spawn` and ADDED their replacements to `compose_request`.

So its net production effect is subtraction only:
- `--no-session-persistence` gone → persistence genuinely works. This is real,
  and is why the transcript count moved 501 to 502.
- `--bare` gone → claude falls back to OAuth. TASK-Z8WEJ's symptom disappeared
  by removal, not by the credential-mode logic, which never runs.
- `--session-id`, `--model`, `--strict-mcp-config` → added to dead code.

TASK-VB9DQ's implementation is therefore unreachable in production in its
entirety apart from the deletion. Its regression test passes because it calls
`compose_request` with a config that has an endpoint, which no dispatch does.

THE FIX IS A DESIGN DECISION, NOT A PATCH

Two candidate shapes, and the choice should be recorded:

A. Compose the argv before the simulation check, and have the Simulated-upgrade
   path spawn the composed argv rather than `spawn.args`. Smallest change,
   keeps `EndpointEmpty` meaning "no ACP endpoint".

B. Stop treating an empty endpoint as a simulation reason for claude. The
   `-p` stream-json path is a real transport, not a simulation of one; calling
   it Simulated and then immediately upgrading it is what hid this. Larger
   blast radius — `upgrades_simulated_to_subprocess` exists for other adapters
   too.

B is the honest model and A is the safe one. Recommend A now with a decision
recorded, and B filed separately.

Do not close this task on a green test again. The acceptance is the observed
argv of a live spawned process, and the vendor transcript filename equalling the
run's runtime_id.
SCOPE EXPANDED [2026-07-26] by operator ruling, recorded as dec_S18RH: the
defect is not claude-specific and must not be patched as if it were.

Every acp-stdio adapter returns Simulated on its normal path and depends on
`upgrades_simulated_to_subprocess` to make it real. cursor_acp does it
unconditionally and says so in a comment. Claude is merely the only adapter that
composes argv beyond `stdio_spawn`, so it is the only one visibly losing
something today — the design flaw is shared, and the next adapter to compose
anything inherits the same silent discard.

Required shape (dec_S18RH):
- Simulated means ONLY explicit override or a genuinely missing binary
- no configured endpoint means spawn the local binary, and the composed request
  is what gets spawned, argv included
- `upgrades_simulated_to_subprocess` is removed, not left as a second meaning

Known obstacles, measured:
- codex, hermes and cursor_acp have NO module-level availability probe; only
  `claude` and `cursor` do. The mode currently supplies that via
  `command_available(&spawn.command)`. Keeping the availability check in the
  mode therefore needs a new adapter hook to produce genuine-simulation events
  on the binary-missing fallback, since `simulated_start_events` is per-adapter.
- `AcpStdioDriver::acquire` has a second discard: `Subprocess` with no
  jsonrpc_init delegates to `SubprocessStreamJsonDriver`, and that path
  hardcodes `native_runtime: None` (subprocess_stream_json.rs:171). So even a
  correctly composed NativeRuntimeMeta is dropped there. Both discards must go.
- 229 drivers tests exist and many assert the current Simulated shape.

Already landed toward this, insufficient alone: b43fc70 stops
`compose_stdio_request` rebuilding argv from spawn on the Subprocess arm. That
arm is correct and needed for endpoint-configured runs, but production does not
reach it. Keep it; it is step one, not a fix.

Acceptance is unchanged and is live-only: the argv of a live spawned process
carries the composed flags, and the vendor transcript filename equals the run's
runtime_id. A green test is not evidence for this task.

=== RESOLVED — verified by the manager 2026-07-28, closed without a dispatch

Every element of this task is discharged in the tree; nothing here needed a new
round. Checked directly rather than inferred from the chain:

1. **The argv discard is gone.** `modes/acp_stdio.rs::compose_stdio_request`
   now destructures and forwards `args`, with a comment naming this task: 'The
   `..` that swallowed `args` is why that...'. The rebuild from
   `spawn.args` is gone.
2. **The actual mechanism — `simulation_reason` returning `EndpointEmpty` for
   an empty endpoint — is gone.** The function is now
   `fn simulation_reason(_cfg: &ClaudeAcpConfig)`: it does not read the config
   at all, only the explicit override and binary availability. That is the shape
   dec_S18RH requires.
3. **Live evidence, recorded on TASK-VB9DQ** (run-20260727T131952, runtime
   4d1369a): the spawned process carried
   `claude --strict-mcp-config -p ... --session-id df92384b-... --model
   claude-opus-5 --effort high`, the driver reported
   `capabilities.simulated=false` with `endpoint=""`, and the vendor
   transcript landed at a filename equal to the runtime_id. That is this task's
   own live acceptance criterion, met.
4. **The test gap this task identified is closed too.** It observed that
   `every_mode_persists_a_locatable_native_session` asserts on the adapter's
   output, one layer below the discard. TASK-H0TYV added
   `the_spawned_session_id_is_the_runs_runtime_id` and TASK-S0QRM/TASK-KKBTP
   added `the_resolved_claude_credential_mode_survives_the_mode_layer` and
   `acp_stdio_spawns_the_request_it_composed` — all of which assert on the
   request the *mode* returns, which is exactly what this task asked for.

The model-override finding ('the model override is silently ignored on this
transport too') is covered by item 3: `--model claude-opus-5` reached the
process.
