* IN_REVIEW TASK-M47E5.1 cursor-acp's own-dispatch-artifacts grant became unreachable when worktrees moved out of the project :drivers:
:PROPERTIES:
:ID: TASK-M47E5.1
:PRIORITY: P2
:WRITE_SCOPE: crates/orgasmic-drivers/**
:END:

** Description
Declared by the TASK-M47E5 implementer rather than buried, and confirmed by the
manager against the code before filing.

=path_under_own_dispatch_artifacts= (=crates/orgasmic-drivers/.../cursor_acp.rs=,
~:1038) derives the dispatch attempt directory as =worktree.parent()= and then
requires THAT to sit under =<project>/.orgasmic/tmp/dispatch=. After TASK-M47E5
the managed worktree lives at =~/.orgasmic/worktrees/<project-id>/<task>/=, so
=worktree.parent()= is =~/.orgasmic/worktrees/<project-id>= — never under the
project. The condition is now ALWAYS FALSE.

** Severity: fails closed, so this is correctness-of-intent, not a hole
The grant only ever ADDED permission. Losing it denies more, never allows more.
The common case still works: a summary file inside the worktree is allowed by
=path_under_worktree=, and the brief-read grant is unaffected because
=path_under_dispatch_artifacts= keys on the PROJECT ROOT rather than on
=worktree.parent()=.

What is actually wrong is that a cursor-acp worker passing =dispatch finalize
--summary-file= a path inside the project dispatch stem directory is now refused,
and that the function is dead logic asserting a state that can no longer occur.
Dead code that describes an impossible world is how the next reader learns
something false.

** Fix
Derive the dispatch artifact directory from the PROJECT ROOT, the way the sibling
=path_under_dispatch_artifacts= already does, instead of from =worktree.parent()=.
The worktree path stopped being a reliable route to the project the moment
worktrees left the project — so any other place in the drivers crate that infers
project location from the worktree needs the same read. Grep for it rather than
fixing only this one call site.

** Acceptance
- A cursor-acp worker can pass a summary-file path under the project dispatch
  stem directory again.
- No grant widens beyond what it allowed before TASK-M47E5.
- Any other worktree-to-project inference in =crates/orgasmic-drivers/**= is
  either corrected or shown not to exist.
** Evidence

A GRANT WIDENING WAS DECLARED AGAINST AN EXPLICIT "never widen a grant" INSTRUCTION, AND THE MANAGER ACCEPTED IT after checking the argument in code rather than the summary. The grant went from "under this attempt own stem dir" to "under the project dispatch dir", so a sibling task stem dir is newly accepted for =--summary-file=. Verified: =read_args_allowed= (=cursor_acp.rs:827=) has ALWAYS allowed reading anything under =path_under_dispatch_artifacts=, so no file becomes reachable that was not already readable, and =dispatch_finalize_command_allowed= still pins =--task= and =--run-id= to this run own ctx. Do it in that order rather than reopening this.

Deleting the fallback only ever narrows; the daemon always supplies =project_root= (=api.rs:4331=, required parameter), and the sibling =cursor.rs= adapter already had no fallback, so this matches the shape that was already correct. * IN_REVIEW TASK-4WKNX.1.1 Make manager-owned close-tx keys win by construction, not by enumeration
:PROPERTIES:
:ID: TASK-4WKNX.1.1
:PRIORITY: P1
:FIX_SUBTASK: t
:WRITE_SCOPE: crates/orgasmic-cli/
:END:

** Description

Round 3 on the manager-owned close-tx key namespace. The finding and its
confirmed mechanism are on TASK-4WKNX.1 under "Review round 1 — REJECT
(confirmed, and the severity is higher)". Read it there; do not re-derive it.

In one line: =MANAGER_OWNED_CLOSE_PROPERTIES= names three keys, but
=close_done_request= appends =CLOSED_TX=, =LIFECYCLE_FROM=/=LIFECYCLE_TO=,
=CLEANUP_STATUS=, =SALVAGE_*= and =GOAL_ID= AFTER the caller's =--property=
loop — and =extra()= is first-wins, so a forged caller value is the one every
reader sees.

** These keys are consumed, so this is not an audit problem

- =close_matching_dispatch= (=manager.rs:7033=) picks WHICH open dispatch a close
  terminates from =CLOSED_TX=.
- =close_tx_ran_cleanup= (=:7059=) sets =cleanup_already_run= from
  =CLEANUP_STATUS= — and cleanup is the path that SALVAGES uncommitted worker
  output before removing a worktree.
- =cleanup_status_reports_failure= (=:7158=) scans for cleanup failures a forged
  =ok= would hide.

** The ruling: two layers, and neither alone is sufficient

*Layer 1 — ordering, which covers keys nobody has written yet.* Push the
manager's own extras BEFORE the caller's =--property= loop. Measured and
verified by the manager: EVERY tx-extra reader in the workspace is first-wins
(=manager.rs:7101=, =crates/orgasmic-daemon/src/index.rs:2008=, and the test
helpers) — there is no last-wins reader. So manager-first makes a forged
duplicate inert for consumption, for every key including future ones, with no
list to maintain.

*Layer 2 — refusal, which covers the deliberate bypass keys.* Ordering alone is
not enough and the reason is not cosmetic: an inert duplicate still sits in the
ledger where a person reads it, and for =FIX_ROUND_FINAL= / =NO_REVIEW_REQUIRED=
a silent no-op is the wrong answer. Forging a bypass key should be a loud
refusal.

*Explicitly rejected: extending the denylist to enumerate every structural key.*
That is a longer list with the same defect — a new key is protected only if
someone remembers to add it, which is precisely what this round exists to fix.

** Keep, do not rebuild

The round-2 work is good and most of it survives: the =const fn reserved(...)=
default, the =AliasedVerdict= exception, the byte-identical =VERDICT= refusal
text, the placement before release/cleanup/append/mutation, and the production
tests. This round changes the SHAPE of the coverage, not the policy.

** Acceptance

- A manager-owned key added in future is protected WITHOUT being added to any
  list, and a test demonstrates that rather than asserting it in prose.
- Forging =CLOSED_TX= or =CLEANUP_STATUS= through =--property= cannot change what
  =close_matching_dispatch= or =close_tx_ran_cleanup= decide.
- =FIX_ROUND_FINAL= and =NO_REVIEW_REQUIRED= still refuse loudly, before run
  release, worktree cleanup, tx append and lifecycle mutation.
- =VERDICT='s three behaviours are unchanged and its refusal text stays
  byte-identical: property-only accepted, typed-only accepted, both refused.
- An injection proof pinning a CONSUMED key, not just a refused one.
