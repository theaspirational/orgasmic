*** FINDING 1 (P0) — a symlinked managed root redirects =remove_dir_all= outside it
=scan_managed_worktrees= calls =std::fs::read_dir= on the project managed root
without first proving that root is a real directory. =read_dir= FOLLOWS a symlink.
Each CHILD is then checked with =symlink_metadata=, which is correct but too late:
the children enumerated are real directories inside whatever the root points at.

The direct-child fence in =remove_orphaned_worktree_dir= does not catch it, and
this is the part worth understanding rather than patching blind: =path= is built
as =<managed_root>/<child>= from =entry.path()=, so =path.parent()= is literally
=managed_root=. The comparison passes trivially — and =normalize_path=
canonicalizes BOTH sides through the same symlink, so it passes under either
reading. The final =symlink_metadata= sees a real directory, because it IS one; it
just belongs to the victim.

Net: if =~/.orgasmic/worktrees/<project-id>= is replaced by a symlink, a bare
=worktree-prune= recursively deletes real directories somewhere else. The root is
user-writable and this codebase runs AI workers with filesystem access, so
same-user replacement is not a hypothetical threat model.

*** FINDING 2 (P0) — prune bypasses the reservation this project already built
=RunSummary= deserializes =run_id= AND NOTHING ELSE, so the CLI cannot match a
live run to a worktree at all; =scan_managed_worktrees= makes the tx ledger the
sole ownership decision and uses live-run data only to decorate an
already-held record. Under the cleanup lock, prune re-reads only that ledger, then
removes.

So a live run whose open dispatch record is absent or torn classifies as
UNCLAIMED, and a recovery acquired in the classification-to-removal gap is not
fenced either. The local file lock is shared with CLI =dispatch-close=, but the
daemon acquire/recovery path does not take it.

THIS EXACT RACE IS ALREADY SOLVED, one path over. =Supervisor::reserve_dispatch_close=
(=crates/orgasmic-daemon/src/supervisor.rs= ~:3984) installs a cleanup reservation
and decides liveness UNDER THE SAME LOCK, and =admit_live_run= (~:543) reads that
fence last so no run can be admitted into a reserved worktree. Its own doc comment
says why a CLI-side audit cannot substitute: "a concurrent POST /runs/:origin/recover
acquires in *another process*, so no audit of await points in the CLI can close
that window — the authority has to sit where the supervisor lock already is."

Prune reproduces precisely the defect TASK-1T3FZ was filed to close. Do not
re-solve it in the CLI; route through the existing authority.

*** FINDING 3 (P1) — "repo gone" fails OPEN on I/O error, into the only unsalvaged delete
=worktree_repo_gone= treats ANY =read_to_string(.git)= error as evidence the
repository is gone: the =else= branch falls through to =(!dot_git.is_dir())=,
which is false for an unreadable regular file, yielding "no .git link". A
permission, ACL or transient I/O failure therefore selects =RepoGone= — the one
disposition that deliberately SKIPS SALVAGE and calls =remove_dir_all=.
=resolved.exists()= collapses errors the same way.

Classification also happens before the multi-GB size walk and before the cleanup
lock, and the under-lock re-check looks only at open dispatches, never at whether
the gitdir became reachable again. So an unreadable-then-restored repository can
lose dirty work with no salvage attempted.

** Fix
1. Anchor the managed root with no-follow semantics BEFORE scanning or deleting —
   refuse a symlinked root (and unsafe symlinked ancestors), or traverse and remove
   relative to a directory handle so a later rename cannot redirect the target. Add
   a tempdir regression in which the managed root points at a victim directory and
   every sentinel file survives.
2. Route each reclaim through the daemon existing cleanup reservation before
   salvage or removal, hold it across the whole mutation, release after. Match live
   runs by CANONICAL WORKTREE and project, which means =RunSummary= must carry
   =worktree= and =project_id=. Add tests for a live run with no open tx, and for a
   recovery acquired in the classification-to-removal gap.
3. Make repository classification FALLIBLE. Only a =NotFound= on the =.git= link or
   the admin directory may yield =RepoGone=; permission and other I/O errors become
   an explicit kept/skipped reason with that reason printed. Re-check repository
   state immediately under the guard, right before the unsalvageable direct delete.

THE FIX IS THE RIGHT SHAPE, NOT THE CHEAP ONE. =remove_orphaned_worktree_dir= was DELETED rather than repaired: all three of its guards were statements about a PATH, and a path ancestors are re-resolved by every syscall. =AnchoredManagedRoot::open= opens the root once with =O_NOFOLLOW | O_DIRECTORY | O_CLOEXEC= — which refuses a symlinked root outright — and the resulting DIRECTORY HANDLE, not the path, is what enumeration (=fdopendir=/=readdir=) and removal (=openat=/=unlinkat=) resolve against thereafter. A rename of the root path afterwards cannot redirect a removal because no removal consults the path again, and a test proves exactly that by renaming the real root aside mid-prune and moving a victim into its place.

FINDING 2 WAS ROUTED THROUGH THE EXISTING AUTHORITY, AND THE API DID NOT NEED EXTENDING — the implementer said so plainly instead of dressing it up as work. Reclaim goes through =POST /projects/:id/tasks/:task/dispatch/close-guard= onto =Supervisor::reserve_dispatch_close=, which is already keyed on the canonical worktree. Prune request differs from a close in two fields and both say prune is entitled to nothing: =releasing_run_id: None= and =owned_run_ids: []=, so EVERY live occupant blocks it. CLI =RunSummary= now deserializes =worktree=/=project_id=/=task_id= (the daemon side always carried them; only this mirror was blind, which is why the CLI could not match a live run to a worktree at all), each =#[serde(default)]= so an older daemon degrades to "unknown" and unknown refuses to reclaim. An unreachable daemon now FAILS CLOSED, where it previously fell back to "nothing is live".
