* IN_REVIEW TASK-Z3093 LiveSessionGuard serializes but never reaps, so every failing live-session test leaks an rmux session :testing:rmux:leak:production:
:PROPERTIES:
:ID: TASK-Z3093
:PRIORITY: P1
:test_cmd: cargo test -p orgasmic-daemon
:END:

`LiveSessionGuard` serializes live-session tests and reaps nothing. Every one of
its 9 copies is the same flock-only type whose `Drop` calls `fs2::FileExt::unlock`
and returns. Cleanup of the rmux session the test created is a *trailing
statement* in the test body, so a panic anywhere above it skips the reap and the
session, its pty and its harness process survive the test binary.

This is the open source of the TASK-8W30B leak that a production-path fix cannot
close. TASK-6FNAY hardened `RmuxControl::release` (merged 83ea420) and the leak
still reproduced afterwards: two orphan sessions found 2026-07-28 at 13:20,
ages 3h18m and 2h46m, both running
`orgasmic_daemon-e5f5d4f31537ab72.fixture.sh artifact-ready`, both 404 to the
daemon and absent from every ledger, i.e. from test fixtures rather than from a
dispatch (tx-20260728-orgasmic-3117). Earlier the same day three more were found
at 09:57 (tx-20260728-orgasmic-3103, refiled onto 8W30B by
tx-20260728-orgasmic-3110).

** Measured inventory

- 9 definitions of `struct LiveSessionGuard(std::fs::File)`, byte-identical in
  behaviour, across 3 crates:
  - `crates/orgasmic-daemon/src/api.rs:15772`
  - `crates/orgasmic-daemon/src/supervisor.rs:5478`
  - `crates/orgasmic-drivers/src/modes/rmux.rs:2329`
  - `crates/orgasmic-drivers/src/modes/tmux.rs:2481`
  - `crates/orgasmic-drivers/tests/rmux_release_reaps_session.rs:23`
  - `crates/orgasmic-cli/src/test_support.rs:37`
  - `crates/orgasmic-cli/tests/dispatch.rs:38`
  - `crates/orgasmic-cli/tests/list_output.rs:33`
  - `crates/orgasmic-cli/tests/bootstrap_smoke.rs:46`
- 85 `live_session_guard()` call sites. Heaviest: `cli/tests/dispatch.rs` 30,
  `daemon/src/api.rs` 19, `drivers/src/modes/rmux.rs` 12,
  `drivers/src/modes/tmux.rs` 12.
- All 12 artifactor tests in `api.rs` that call `seed_test_artifactor_harness` /
  `seed_busy_artifactor_harness` spawn a real rmux session. 11 end with a
  trailing `supervisor.release(..)` or `release_with_finalization(..)`; one,
  `launch_artifact_generation_persistence_failure_releases_run`
  (api.rs:27530), has no release in the test body at all and relies on the
  production path releasing for it — confirm that it actually does.
- The fixture never exits on its own. `artifact-ready` loops
  `echo '> ready'; read -r line || exit 0`, and inside an rmux pane stdin never
  closes, so an unreaped session runs until something kills it
  (`crates/orgasmic-daemon/src/test_fixtures.rs:20`).

** Why this compounds

TASK-STWVB records four daemon tests that fail on every full-suite run and pass
alone, and the TASK-C0XMR merge note (`0860861`) says that family gained two more
members under load. A load-induced failure is a panic, and a panic is exactly the
path that skips the trailing release — so **the flake and the leak are the same
event**. Every dispatched worker runs the full suites, so leak rate scales with
dispatch volume, which is what the two-per-day observation shows.

A leaked session also outlives its worktree: pid 42520 still named
`.orgasmic/tmp/dispatch/task-C0XMR/worktree`, a directory `dispatch-close` had
already removed.

** Fix

One shared guard that owns cleanup, not nine that own a file lock.

- Give the guard a registration surface (`guard.owns(run_id)` /
  `guard.owns_session(name, endpoint)`) and reap on `Drop`, unconditionally,
  before releasing the flock. Drop runs on the panic path, which is the whole
  point.
- The reap must not itself depend on a live SDK transport — reuse the CLI
  fallback shape TASK-6FNAY established (`rmux_session_reap_args(endpoint,
  name)`, rmux.rs:1505), addressed at the endpoint the handle owned. A `Drop`
  cannot await, so the reap has to be a blocking call or a spawned-and-joined
  helper; pick one and say why.
- De-duplicate: one definition in a shared test-support location that all three
  crates use. Nine copies is how a fix to one of them silently misses the other
  eight.
- Keep the flock behaviour exactly as it is. Serialization is load-bearing and
  independent of the leak.

** Acceptance

- A live-session test that panics mid-body leaves no session behind — proven by
  a test that deliberately panics inside the guard's scope and then asserts the
  session is gone.
- `rmux ls` is empty after a full `cargo test -p orgasmic-daemon` and after
  `cargo test -p orgasmic-cli` on a machine that started with no sessions.
- One `LiveSessionGuard` definition remains in the tree.
- `launch_artifact_generation_persistence_failure_releases_run` either releases
  through the production path (demonstrated) or gains a guard registration.

** Non-goals

- Do not change `RmuxControl::release`; TASK-6FNAY owns the production path and
  is in review.
- Do not fix the TASK-STWVB flakes themselves. This task makes their cost
  bounded, not zero.
- Do not run `legacy_drivers_and_explicit_pairs_emit_equivalent_start_events`
  (TASK-099T6) — it bills real money. Skip it explicitly on the drivers suite.

The defect is the one the brief named as worse than the original bug, and it is

** HIGH — a genuine terminal failure followed by a worker finalize is turned green

`crates/orgasmic-daemon/src/api.rs:6098,6141-6149`.

`DriverEvent::RunFail` is a real failure: the production drain maps it to
`ReleaseOutcome::Failed` and stores it on the run
(`supervisor.rs:3429-3463`). Explicit release deliberately waits for that drain
and persists the stored terminal outcome, so a finalize racing a queued `RunFail`
produces the authoritative shape
`Release { outcome: Failed, finalized_by_worker: true }`
(`supervisor.rs:2181-2228`).

The new scan sets `pending_failure` and then clears it **unconditionally** on
`finalized_by_worker`, inspecting neither the failure kind nor the release
outcome, and returns `StageOutcome::Completed`. The stage watcher then writes
`<stage>.completed` for a run the supervisor classified as failed.

The added negative test does not cover the claimed case:
`stage_outcome_fails_when_a_fatal_driver_error_has_no_worker_finalize_after_it`
uses `finalized_by_worker: false`, while the adversarial case is failure **plus**
finalize.

Required (reviewer's direction 1): make semantic failure sticky across worker
finalize. At minimum `RunFail` must survive a later finalize. For fatal driver
errors, persist enough release-boundary or classification data to suppress only
the errors *caused by* the finalize teardown, rather than clearing every earlier
failure. Add a regression for
`RunFail -> Release { outcome: Failed, finalized_by_worker: true }`, plus a
production-path race test.

** Open question the reviewer raised, and it is the crux

What durable session event should identify the finalize-admission boundary? The
trailing release cannot distinguish a queued genuine `RunFail` from a fatal error
caused by teardown, because **both are drained before that release**. Answer this
explicitly before writing the fix; a suppression rule that cannot name its
boundary will get one of the two cases wrong. Record the answer in the task or a
decision, not only in a code comment.
The reviewer is right that the trailing release cannot carry the boundary, and
the evidence is stronger than "cannot distinguish": the two cases produce a
byte-identical release. `terminal_outcome_for_event` maps `RunFail` and fatal
`DriverError` to the same `ReleaseOutcome::Failed`
(`supervisor.rs:3429-3436`), both are drained before `release_one` freezes
`rec.terminal_outcome.unwrap_or(outcome)`, so a genuine queued `RunFail` and a
teardown-induced fatal error both write
`Release { outcome: Failed, finalized_by_worker: true }`. The release is not a
weak discriminator; it is not a discriminator at all. Asserted directly by the
production-path test pair
`worker_finalize_does_not_clear_a_run_fail_drained_during_teardown` and
`worker_finalize_still_suppresses_the_error_its_own_teardown_caused`, which
assert the identical release shape and opposite stage outcomes.

The boundary is two rules, not one, because no single durable event answers
both halves.

1. KIND, for semantic failure. `RunFail` is only ever emitted from a harness
   protocol result — Claude `is_error`, a failed codex turn, a cursor stop
   reason. Teardown reaps the process group, and every transport classifies
   that as a fatal `DriverError` (`classify_pane_exit`,
   `orgasmic-drivers/src/modes/rmux.rs:1901-1959`); nothing synthesizes a
   `RunFail`. So `RunFail` is sticky across a later worker finalize,
   unconditionally and regardless of position. Position must not matter: a
   `RunFail` still queued when the finalize is admitted is drained AFTER the
   admission marker, so a marker-only rule would clear exactly the case this
   task exists to fix.

2. A durable ADMISSION MARKER, for driver errors. The supervisor appends a
   `SessionEventKind::Note` carrying `{"note": "worker_finalize_admitted"}` at
   the instant it grants finalize admission — after
   `explicit_release_in_progress = true`, before
   `stop_and_join_driver_producer`, awaited so it is on disk first
   (`supervisor.rs`, `release_one`). Teardown cannot produce anything before
   it. A fatal driver error after the marker is one this finalize caused and
   stays suppressed; one before it was already there and is sticky.

Why a new event rather than an existing one: the release is the only other
durable session event on this path, and it is appended after the drain, so
every candidate discriminator is already behind it. This is a session-schema
addition, but not a `Lifecycle` variant change — `Note` is the existing
free-form supervisor channel, so `orgasmic-core` is untouched and every reader
that filters by kind ignores it.

Backward compatibility: sessions with no marker (written before this change, or
where the append failed and logged) keep the TASK-C0XMR reading for driver
errors — dominance by the following finalize. Rule 1 still applies to them, so
the reported HIGH is fixed for old sessions too.

If a third case appears later, the question to ask is which of the two rules it
belongs to: is the failure semantically declared by the harness (rule 1, sticky
by kind), or is it a transport/process artifact whose blame depends on whether
this finalize caused it (rule 2, sticky unless after the marker)? A signal that
fits neither means a new durable event is needed, not a new heuristic on the
existing ones.

** Acceptance

- A run with a queued `RunFail` that is then finalized by its worker is recorded
  as failed, not completed.
- A teardown-induced error after a clean finalize is still suppressed — the
  original C0XMR symptom must not regress.
- Both cases have regressions, and the failure case exercises
  `finalized_by_worker: true`.
- The finalize-admission boundary is named and durable, not inferred from
  ordering alone.

** Non-goals

- Do not revert `0533735`.
- Reviewer finding 2 (a live stage loses its completion watcher across daemon
  restart) is **out of scope** and filed separately. It is pre-existing and
  outside this diff.

Filed 2026-07-28 from three measured false readings in one session, all caused

- The worker-authority `dispatch` verb group still functions from inside its

* IN_REVIEW TASK-TCTTD Injection proofs are re-authored at merge time against the fixed tree; ship them as artifacts replayed by one verb :cli:verification:mechanism:
:PROPERTIES:
:ID: TASK-TCTTD
:PRIORITY: P1
:END:

Filed 2026-07-28 after a session in which the manager's own re-injection probes
were malformed four times, every time failing toward FALSE GREEN: an org-verbatim
span tested against a backtick extractor, a std-Mutex API probe against a tokio
Mutex, a "removed" lock that was still one shared static, and a genuine removal
run after the ambient load that reproduced the race had gone. A broken probe
that passes looks identical to a working fix. Each was caught only by manual
suspicion, which does not scale and fails silently.

Root cause: the injection proof is a RITUAL, re-authored from scratch at merge
time against the ALREADY-FIXED tree — which is precisely where false green
lives. The worker demonstrated red once, pre-fix, when red was cheap; that
demonstration is then thrown away and the manager improvises a new probe.

=== The mechanism

Make the injection a shipped ARTIFACT, authored once at the moment the defect
demonstrably exists, then replayed — never re-authored.

1. The implementer, while the defect still reproduces (pre-fix), captures:
   - a patch that reintroduces the defect onto the fixed tree (reverse of the
     fix, or a minimal hand-written defect patch),
   - the exact test command (single line, with the mandatory
     `--skip legacy_drivers_and_explicit_pairs_emit_equivalent_start_events`
     baked in where the drivers suite is involved),
   - the expected RED signature: a substring/regex of the failure output plus
     the nonzero exit class.
2. These live in the repo with the fix (suggested: `verify/TASK-<id>/` with
   `injection.patch`, `cmd`, `expect-red`), so they survive worktree removal
   and travel with the merge. The task drawer records the path.
3. A new verb `orgasmic verify TASK-<id>` replays it: assert clean tree, apply
   patch, run cmd, ASSERT RED MATCHING SIGNATURE (a green or wrong-red run
   fails verification loudly), revert patch byte-clean, run cmd, assert green.
   Machine-readable result; nonzero exit on any deviation.

The property this buys: probe authorship happens exactly once, against a
known-broken state, with its red output pinned. Replay cannot silently degrade
into false green — a probe that no longer bites fails the replay itself.
It also makes merge verification delegable (reviewer or manager runs one verb)
instead of a manager-serial bespoke step.

=== Design points the worker must decide and record

- Patch application on a moved tree: if `injection.patch` no longer applies,
  verify must FAIL (stale artifact), not skip.
- Where the verb lives (`orgasmic verify` vs `orgasmic task verify`) and how it
  finds the artifact (drawer property vs path convention). Prefer drawer
  property `verify_artifact` set by the implementer, validated at close.
- Safety: refuse to run on a dirty tree; always restore (RAII/temp-worktree ok,
  but note dispatch worktrees already exist — do not invent a second worktree
  mechanism if `git stash`-discipline suffices).

=== Acceptance

- One real, already-merged fix (suggested: TASK-R74E8's drain-budget defect) is
  re-expressed as a verify artifact, and `orgasmic verify` shows the full
  red-then-green replay with output.
- A deliberately malformed artifact (patch that does not change behavior, or
  wrong expected signature) makes verify FAIL loudly — demonstrated, with
  output. This is the false-green detector and the core of the task.
- Replay leaves the tree byte-identical (`git status` clean, `git diff` empty).
- `verify --help` documents the artifact layout.

=== Non-goals

- Do not retrofit artifacts onto historical merges beyond the one exemplar.
- Do not gate `manager dispatch-close` on verify yet — that is a follow-up
  decision once the verb has been used in anger.
- Do not touch the billed harness test in any way; its name appears here only
  inside the mandatory skip flag.

Related: TASK-S2KM0 (a CI lane could run `orgasmic verify` per merged task),
TASK-MFJZ7 (mechanism-over-prose for the billed test, same philosophy).

** Description

The only thing standing between a contributor and a charge is remembering to
pass `-- --skip legacy_drivers_and_explicit_pairs_emit_equivalent_start_events`

=== It already fired

2026-07-28, the TASK-QRB8S worker. Its brief carried the constraint in bold and

`Error: Session ID … is already in use`, which is a pre-turn rejection. **That is

that lives in a document rather than in the code. A worker who is told the rule

1. Gate the test so the **default is safe**. `#[ignore]` plus an explicit

   already availability-gated but availability is not the same as billing.
4. Make the sentinel account for it. The `required_test_tooling_is_present`

   silently change that count in a way that hides it.

- `cargo test -p orgasmic-drivers` with no extra flags does not run the billed
  test, and prints something that names why it was skipped.
- Prove it by injection: remove the gate, show the test being collected and
  attempted, restore it, show it skipped — with output. Do **not** let the

=== Non-goals

* IN_REVIEW TASK-DJ1WV Red classification is manual folklore; a runner wrapper must retry failures in isolation against a signed flake registry :testing:mechanism:
:PROPERTIES:
:ID: TASK-DJ1WV
:PRIORITY: P2
:END:

Filed 2026-07-28. Five tests fail on full-suite runs under load and pass in
isolation. Today every full run therefore ends with a MANUAL classification
step: a human (or manager agent) rereads the failure list, recalls which names
are "known", reruns them alone, and decides whether red means anything. That
step was performed from memory at least four times today; once a failure was
misattributed to the wrong owning task (the 5HBST/STWVB mislabel — one test
name, two distinct failure modes) and was caught only by reading the panic

discount red, which is exactly how the next TASK-Q07Y5 walks through a green
gate.

=== Mechanism

1. A machine-readable flake registry in the repo (suggested:
   `verify/flake-registry.toml` or similar): per entry the exact test name, the
   owning open TASK id, the failure SIGNATURE (substring/regex of the panic —
   this is what makes the 5HBST/STWVB confusion impossible: one test may carry
   two entries with different signatures and different owners), the evidence
   ("fails under load, green in isolation, N/M runs on <date>"), and the date
   filed. An entry whose owning task is done must fail a check — a registry
   that only grows is a graveyard.
2. A test-runner wrapper (script or cargo alias the whole project adopts —
   workers, manager, and the future TASK-S2KM0 CI lane) that: runs the suite,
   reruns each failure IN ISOLATION, and emits a final verdict block that
   separates `REAL:` failures from `FLAKE (green in isolation, owner
   TASK-STWVB, signature matched):` ones. Exit code nonzero iff REAL is
   nonempty OR a failure matched no registry entry.
3. A failure that matches a registered NAME but not its SIGNATURE is REAL —
   that is the mislabel detector.
4. The wrapper must bake in the mandatory
   `--skip legacy_drivers_and_explicit_pairs_emit_equivalent_start_events`
   default for the drivers suite so the safe invocation is the short one
   (until TASK-MFJZ7 lands the in-test gate; then keep both).

=== Acceptance

- A full-suite run under induced load ends with the verdict block; the five
  seeds classify as FLAKE with owners named; an injected genuine failure (any
  deliberately broken test) classifies as REAL and the wrapper exits nonzero.
- A failure matching a registered name with a different panic signature is
  reported REAL — demonstrated.
- Registry entries pointing at a done/cancelled task fail a check.
- The wrapper never runs the billed test by default — demonstrated by output.

=== Non-goals

- Not fixing the flakes themselves (TASK-STWVB, TASK-QCG6J, TASK-Y9BY6 own
  those). This task makes red mean something while they are being fixed.
- Not the CI lane itself (TASK-S2KM0 consumes this — its work item 2, "decide
  what to do about known-red tests before the lane goes required", is answered
  by this registry).
