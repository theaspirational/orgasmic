** THE TRAP — two marker syntaxes, one word

*=// arch:= and =// orgasmic:arch_= are DIFFERENT SYNTAXES WITH DIFFERENT
READERS, and they sit on ADJACENT LINES OF THE SAME FILES.* Line 1 is
=// arch: arch_A53QX.2=; line 2 is =// orgasmic:arch_A53QX, dec_ASB1A=.

- =// arch:= is read ONLY by =architecture_drift.rs= (=strip_prefix("// arch:")=
  at =:265=). It dies with the comparator.
- =// orgasmic:<ids>= is the GENERIC marker syntax read by
  =orgasmic-core/src/marker.rs= and served by =/graph/markers/:node_id=. It also
  carries =dec_=, =TASK-= and =term_= ids. *There are 60 =orgasmic:arch_=
  markers and every one of them MUST SURVIVE this stage.* The coupling map is
  explicit that the generic scanner stays.

A grep-and-delete keyed on the word "arch" destroys the second set. Key on the
exact prefixes.

=== The trap was avoided, and proven avoided

The one way to get this stage wrong was to delete =// orgasmic:arch_= markers
alongside =// arch:= ones — different syntaxes, different readers, ADJACENT LINES
of the same files. A grep-and-delete on "arch" destroys the wrong set and the
diff still looks plausible.

The implementer proved the survivors are intact with a normalized sha256 of the
whole marker inventory, before and after. That is a better instrument than a
count: a count cannot tell a preserved marker from a mangled one.

: git grep -h "orgasmic:arch_" f59ce41 -- crates/ ui/ scripts/ | sort | shasum -a 256
: git grep -h "orgasmic:arch_" bb06bc4 -- crates/ ui/ scripts/ | sort | shasum -a 256
