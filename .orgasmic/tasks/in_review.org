Live capture of the fake cursor-agent during a full run (three separate runs,
same result). The test writes a bash script that backgrounds two sleeps, touches
`children-ready`, then sleeps; it waits up to 30 s for that file:

- the process IS alive the whole time — it is not killed, not starved of a slot
- it has ZERO children, so it never reached even its first `&`
- state is S (blocked), never R (runnable), so it is not losing a CPU race
- CPU time stays at 0:00.00 across 28+ seconds of sampling — it never executed

A process that is alive, blocked, and has consumed no CPU is wedged BEFORE
execution, not running slowly.

THE DISCRIMINATOR

An unrelated trivial bash script (`#!/bin/bash` + one `touch`), spawned from
outside the test binary while the suite ran, timed at:

    6205 ms, 2993 ms, 63771 ms, 64 ms, 354 ms

Sixty-three seconds to spawn a two-line shell script, then 64 ms a few seconds
later. Process creation on this machine intermittently stalls for seconds to a
minute while this suite runs. Nothing about the test is special; it is just the
one test that asserts a 30 s deadline on a freshly spawned external process.

Caveat on that measurement, stated so nobody over-reads it: the timestamps were
taken by spawning python3, so each figure includes one additional process
spawn. That does not change the conclusion — spawning anything is what is slow —
but the per-call attribution is not exact.

Peak process count during a run was only ~720 against a 5333 maxprocperuid, and
fd limit is 1048576, so this is not simple resource exhaustion. The likely
mechanism is serialization in macOS exec (code-signing / syspolicy validation)
under many concurrent spawns, which is worth confirming before designing around
it.

CONSEQUENCE FOR THE FIX

Do not fix this by raising the 30 s deadline. Sixty seconds was observed, so any
constant is a guess. Either remove the dependence on a freshly spawned external
process reaching a checkpoint, or serialize the process-spawning tests against
each other so the suite stops competing with itself for exec.

The same mechanism is a plausible cause for post_artifact_regenerate_hot_path:
its two run_ids are 10 s apart, consistent with round one exceeding a deadline
and its run being released before round two. Not yet confirmed — do not record
it as established.
MECHANISM CONFIRMED [2026-07-26]. It is macOS first-exec evaluation, and it is
measurable in three lines on a completely idle machine:

    fresh script #1 first exec: 0.18 s    second exec: 0.00 s
    fresh script #2 first exec: 0.15 s    second exec: 0.00 s
    fresh script #3 first exec: 0.16 s    second exec: 0.00 s

macOS charges roughly 150-180 ms of syspolicy/Gatekeeper evaluation the first
time a newly created executable is exec-ed, and nothing thereafter. Idle spawns
of an already-evaluated script are 0.00 s, which is why every one of these tests
passes alone.

That per-file cost is paid through a single system daemon, so concurrent first
execs queue. This suite writes many fresh executable fixtures into tempdirs and
execs them in parallel, which is how a 150 ms cost becomes the 3 s / 6 s / 63 s
spawns measured earlier. The failing test is not special; it is the one that
asserts a 30 s deadline against that queue.

So the chain is: fresh fixture -> per-file Gatekeeper evaluation -> serialized
daemon -> queue under suite parallelism -> a spawned helper that never reaches
its first instruction inside the deadline.

FIX DIRECTION

Stop paying the per-file cost per test. The fixture script should be created and
exec-ed ONCE per test binary and then reused, with the per-test variation moved
out of the file contents and into argv, so the second and subsequent uses hit
the warm path. Pre-warming a shared fixture is preferable to serializing the
tests, because it removes the cost rather than queueing it, and it also speeds up
every other spawn-based test in the crate.

Raising the deadline is not a fix. 63 s was observed; any constant is a guess.

NOTE FOR CI (TASK-S2KM0): this mechanism is macOS-specific. A Linux runner has
no Gatekeeper and will very likely not reproduce it, so this test could pass in
CI while failing on every developer Mac. That is an argument for fixing the
fixture rather than tolerating the failure locally, and for not concluding "green
in CI" means "green".

** How to fix it — design [2026-08-05]
The classification machinery ALREADY EXISTS and is good. =scripts/run-tests.sh=
(654 lines) runs the suite, reruns every failure IN ISOLATION, and matches panic
text against =verify/flake-registry.toml= (6 entries, each requiring an OPEN
owning task and a literal panic SIGNATURE, so one name carrying two failure
modes cannot be confused). Do not rebuild any of that.

*THE GAP, precisely.* The classifier has exactly three outcomes:
1. not in the registry -> REAL
2. registered NAME but unregistered SIGNATURE -> REAL (the mislabel detector)
3. registered + signature match + green alone -> FLAKE (exit 0 eligible)

and NO HOST-STATE AWARENESS whatsoever — the only occurrence of "load" in the
script is a comment. So the 2026-08-02 run (14 failures, 4 registered, all 14
green alone in 8s, =syspolicyd= at 586% and load average 11.41) put 10 tests in
branch 1 and returned RED. The verdict vocabulary has no way to say "the host
was degraded, so this run has no verdict".

*THE FIX IS NOT TO REGISTER THE TEN.* The registry's own header says an entry is
"an excuse with an expiry" that must name an open owning task, and warns that
"a registry that only grows is a graveyard". Ten environment-induced failures
have no owner because there is no code defect to own. Registering them would
corrupt the instrument that currently works.

=== A. Attack the trigger — the only durable fix
Test EXECUTION is the trigger, not compilation (measured 2026-08-02: a full
rebuild at jobs=4 kept syspolicyd at 0-64%, while the test RUN pinned it at
586%). The mux and process-probe suites write and exec MANY short-lived shim
scripts per test, and first-exec of a newly written file is what gets scanned.

- Create the shims ONCE PER SUITE RUN behind a shared fixture rather than once
  per test, so repeated execs of an identical path+content hit a cached scan
  verdict instead of a fresh one.
- Prefer a long-lived helper process or an in-process fake over spawning a fresh
  script per assertion.
- Where a fresh script is unavoidable, reuse content-identical files from one
  directory instead of minting a new temp path each time.

This lowers scan load at the source. Everything else below is instrumentation
around a load problem; this is the part that removes it.

=== B. Make host state a first-class input to the verdict
Sample load average and =syspolicyd= CPU before, during and after the run, and
stamp it on the verdict. If the host was degraded past a threshold, the run
returns *INCONCLUSIVE — re-run when calm*, which is a THIRD outcome the exit
codes do not currently have (today: 0 clean/all-flake, 1 REAL, 2 registry).

Two things this buys, and the second is the sharper one:
- a red on a thrashing host stops being read as a code fact;
- a GREEN on a thrashing host stops being trusted, which today it silently is.
  Right now a degraded run that happens to pass reports clean, and nothing in
  the output hints that the run was not worth believing.

=== C. Separate two different facts that currently look identical
"Passes alone because of a genuine race" is a code defect: it has an owner, an
expiry, and belongs in the registry. "Passes alone because the host was
thrashing" is an environmental fact with no owner at all. Branch 1 collapses
both into REAL, and the obvious workaround collapses both into the registry.

Add a classification for load-sensitivity that is valid ONLY when the run's
MEASURED host state (from B) justifies it. That interlock is what keeps the
"excuse with an expiry" discipline intact: the excuse is bounded by a
measurement taken during that run, not by a name sitting on a list forever.

=== Sequencing
B before C — C is unsound without a measurement to gate it. A is independent and
is the one that actually shrinks the problem, so it can run in parallel and
should not wait on the gate work.

=== What NOT to do
- Do not serialize the whole suite. The original acceptance already rejected
  this, and it hides the interference rather than naming it.
- Do not raise timeouts to fit a degraded host; that makes every future run
  slower and still returns a meaningless verdict.
- Do not add registry entries for the ten unregistered 2026-08-02 failures.
