Two independent review rounds produced SIX BLOCK SHIP findings, every one on the

** The six findings, which are the design input
ROUND 1 (tx =tx-20260805-orgasmic-4474=):
1. =read_dir= on the managed root followed a symlinked root; the direct-child
   fence could not fail because =path.parent()= IS =managed_root= by construction.
2. Ownership came from the tx ledger alone; =RunSummary= deserialized only
   =run_id=, so the CLI could not match a live run to a worktree at all.
3. =worktree_repo_gone= treated ANY =read_to_string= error as proof the repo was
   gone — the one disposition that skips salvage and deletes.

ROUND 2 (tx =tx-20260805-orgasmic-4495=), against the fixes for those:
4. =O_NOFOLLOW= GUARDS ONLY THE FINAL COMPONENT. =open_dir_nofollow= opens
   =<home>/worktrees/<project-id>= in one syscall, so replacing the ANCESTOR
   =<home>/worktrees= with a symlink is followed and the fd anchors a victim
   directory. The round-1 regression replaced only the final component, so it
   could not catch it. Confirmed by the manager against POSIX semantics and the
   code.
5. THE HANDLE WAS NOT THE REFERENCE POINT FOR THE WHOLE DECISION. Enumeration used
   the fd, but classification reconstructed =root.path().join(name)= and freshly
   resolved metadata, canonicalization, repo state, sizing AND the daemon
   reservation through that pathname. So the reservation can describe tree B while
   =unlinkat= deletes anchored tree A. The salvageable branch has the same gap:
   =git worktree remove= is itself the destructive remover and receives only a
   re-resolved pathname, with no child inode ever captured or passed.
6. The reservation task-id fallback to the directory name misses the window where
   an acquire is admitted but its =RunRecord= is not yet inserted —
   =blocking_run_for_close= detects that window ONLY by lease lookup on
   =params.task_id=, and =--worktree= may name any directory.

** Design directions from the reviewers, not yet ruled on
- Walk from a trusted anchored home fd and open =worktrees= and =<project-id>=
  with =openat(..., O_NOFOLLOW|O_DIRECTORY)= each, so no ancestor is ever resolved
  by pathname.
- Carry a child directory HANDLE plus a stable identity from enumeration through
  classification to removal; use fd-relative metadata and repo inspection. Either
  stop letting git own the recursive deletion through a rebindable pathname, or
  prove the exact child inode at the destructive syscall.
- Key the daemon fence on a stable worktree identity that survives rename, not a
  canonical pathname.
- Make pending admissions worktree-addressable in the supervisor: store the
  canonical/stable worktree identity when =admit_live_run= installs the lease, and
  have =reserve_dispatch_close= reject a matching pending admission regardless of
  task-name guessing. THIS IS A DAEMON CHANGE, which is why it did not fit a CLI
  fix round.
- Retain the deterministic pause-file race test under a =debug_assertions= or
  test-hooks compile gate; today =ORGASMIC_WORKTREE_PRUNE_PAUSE_FILE= is live in
  the release binary and can hang forever holding the global cleanup lock and the
  daemon reservation.

** Two things measured along the way, worth keeping
- FD accounting peaks near the anchored root plus 65 child fds against a macOS
  soft =RLIMIT_NOFILE= of 256; depth 65 and =EMFILE= propagate an error, but
  earlier siblings can already have been removed.
- A mid-stream =readdir= error is treated as EOF, so recursive removal can delete
  entries already returned, fail =rmdir= with =ENOTEMPTY=, and print KEPT. "Kept"
  currently does not mean "untouched", and it should.

** F1 — BLOCK SHIP. git refuses to remove a worktree containing a submodule; our reproduction does not
=crates/orgasmic-cli/src/manager.rs:3915-3979=

TASK-RMA18 stopped calling =git worktree remove= and now removes through the
anchored handle, gating on =git_would_remove_worktree= — a reproduction of git's
non-forced refusals. It reproduces TWO (locked, unclean) and omits a THIRD, which
git checks BEFORE cleanliness and which is categorical: *any worktree containing
an initialized submodule*.

MEASURED BY THE REVIEWER, then REPRODUCED INDEPENDENTLY BY THE MANAGER on git
2.52.0 — a clean worktree containing one initialized submodule:

: git status --porcelain          -> []          (our check says "clean")
: git worktree list --porcelain   -> no `locked` line
: git worktree remove ../wt       -> fatal: working trees containing submodules
:                                    cannot be moved or removed        EXIT=128
: git worktree remove --force ../wt                                    EXIT=0

So =git_would_remove_worktree= returns =Ok(())= and =remove_child= recursively
deletes a tree git refuses to touch without =--force=.

THE DATA-LOSS VARIANT IS ONE COMMITTED CONFIG LINE AWAY. With
=submodule.<name>.ignore = all= in =.gitmodules= — committed, so every clone
inherits it — a submodule holding uncommitted work reports CLEAN to the parent,
so prune proceeds with no salvage. Salvage could not rescue it anyway: the
parent's =git add -A= records a submodule as a gitlink, so files inside it are
never captured. Git passes =--ignore-submodules=none= in its own check
(=builtin/worktree.c= =remove_cmd=) and our =git status= call does not — a
second, independent divergence in the same call.

REACHABLE, not theoretical: =git worktree add= does not init submodules, but a
worker that must BUILD runs =git submodule update --init=. And =dispatch-close=
still shells out to =git worktree remove=, so in exactly those projects the close
FAILS and worktrees accumulate — which is the state that makes an operator reach
for =worktree-prune=. This change therefore makes prune strictly MORE destructive
than the close whose semantics it claims to match. =grep -rn submodule crates/
shipped/ .orgasmic/*.org= returns ZERO hits: before this change git enforced the
boundary for free.

The parity claim is stated in three places and is now false in all three:
=manager.rs:3431=, =manager.rs:3912=, and the operator-facing =after_help= at
=manager.rs:369-374=.

*Fix:* after the registered/locked checks, refuse when the worktree contains an
initialized submodule (git's own test is =validate_no_submodules=: a =.gitmodules=
entry whose working path holds a =.git=), and pass =--ignore-submodules=none= to
the =git status= call. Regression: a managed worktree with an initialized
submodule holding an untracked sentinel; assert the sentinel SURVIVES and the
report says why. Update =after_help= in the same change — it currently promises
the property this fix restores. Prefer computing the refusal from the anchored
handle rather than a subprocess, which also shrinks F2.
