*Why this matters beyond one test.* That test encodes the CLOSE-THEN-MERGE flow
the review gate itself prescribes: its refusal message tells the manager to
dispatch a reviewer and close it with =--verdict=, and only then does the
default-branch merge unlock. A manager following that instruction literally
closes first and merges second — and now the merge fails. This session's manager
did not hit it only because it merged BEFORE closing, which the gate permits but
does not prescribe.

*It also sharpens the review's claim 1.* The reviewer asked what could UNSTAGE
the record between =git add= and the commit. The answer that matters turned out
to be the opposite direction: staging does not get undone, it BLOCKS a merge that
wants to touch the same path.

*Fix direction — decide, do not patch reflexively.* The options are not equal and
the choice is part of this task:
1. Stage only when the index is otherwise clean for that path, and report through
   =CLEANUP_ERROR= when it is not. Preserves the guarantee in the common case.
2. Commit the record instead of staging — rejected once already, because WHEN to
   commit needs manager judgement; do not re-open without a reason.
3. Keep staging and make the manager's documented flow merge-before-close.
   Cheapest, but it moves the guarantee back into habit, which is exactly what
   F-1 existed to remove.
4. Stage with a mechanism that does not participate in merge conflict detection.
   Investigate whether one exists before assuming it does.

Whichever lands, *the failing test must go green with the durability property
intact* — do not fix it by dropping the assertion or by un-staging in the test.
