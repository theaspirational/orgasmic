* IN_REVIEW TASK-M47E5.1 cursor-acp's own-dispatch-artifacts grant became unreachable when worktrees moved out of the project :drivers:
:PROPERTIES:
:ID: TASK-M47E5.1
:PRIORITY: P2
:WRITE_SCOPE: crates/orgasmic-drivers/**
:END:

** Description
Declared by the TASK-M47E5 implementer rather than buried, and confirmed by the
manager against the code before filing.

=path_under_own_dispatch_artifacts= (=crates/orgasmic-drivers/.../cursor_acp.rs=,
~:1038) derives the dispatch attempt directory as =worktree.parent()= and then
requires THAT to sit under =<project>/.orgasmic/tmp/dispatch=. After TASK-M47E5
the managed worktree lives at =~/.orgasmic/worktrees/<project-id>/<task>/=, so
=worktree.parent()= is =~/.orgasmic/worktrees/<project-id>= — never under the
project. The condition is now ALWAYS FALSE.

** Severity: fails closed, so this is correctness-of-intent, not a hole
The grant only ever ADDED permission. Losing it denies more, never allows more.
The common case still works: a summary file inside the worktree is allowed by
=path_under_worktree=, and the brief-read grant is unaffected because
=path_under_dispatch_artifacts= keys on the PROJECT ROOT rather than on
=worktree.parent()=.

What is actually wrong is that a cursor-acp worker passing =dispatch finalize
--summary-file= a path inside the project dispatch stem directory is now refused,
and that the function is dead logic asserting a state that can no longer occur.
Dead code that describes an impossible world is how the next reader learns
something false.

** Fix
Derive the dispatch artifact directory from the PROJECT ROOT, the way the sibling
=path_under_dispatch_artifacts= already does, instead of from =worktree.parent()=.
The worktree path stopped being a reliable route to the project the moment
worktrees left the project — so any other place in the drivers crate that infers
project location from the worktree needs the same read. Grep for it rather than
fixing only this one call site.

** Acceptance
- A cursor-acp worker can pass a summary-file path under the project dispatch
  stem directory again.
- No grant widens beyond what it allowed before TASK-M47E5.
- Any other worktree-to-project inference in =crates/orgasmic-drivers/**= is
  either corrected or shown not to exist.
** Evidence
Landed =ff5aee2= (merge) on main. Implementer: =implementer-claude-tmux= (tmux / claude / claude-opus-5 / high), run =run-20260805T175326-b63f2fd760a94ef3a4f4c34c1d9754e2=, started_tx =tx-20260805-orgasmic-4491=.

The attempt stem is not identifiable from anything the driver holds — it comes from the operator-chosen brief FILENAME (=dispatch_artifact_stem=), while =DriverContext= carries run id, task id, worker id, project id and worktree but never the stem or attempt token. Nothing could narrow the predicate honestly, and a distinctly-named function with a body identical to its sibling was ruled out, so the one caller routes to =path_under_dispatch_artifacts=.

A GRANT WIDENING WAS DECLARED AGAINST AN EXPLICIT "never widen a grant" INSTRUCTION, AND THE MANAGER ACCEPTED IT after checking the argument in code rather than the summary. The grant went from "under this attempt own stem dir" to "under the project dispatch dir", so a sibling task stem dir is newly accepted for =--summary-file=. Verified: =read_args_allowed= (=cursor_acp.rs:827=) has ALWAYS allowed reading anything under =path_under_dispatch_artifacts=, so no file becomes reachable that was not already readable, and =dispatch_finalize_command_allowed= still pins =--task= and =--run-id= to this run own ctx. Bounded, and it adds no reachability. The alternative — drop the grant and require summary files inside the worktree — fails acceptance criterion 1 as written.

THE STRICTLY-NARROW GRANT BECOMES IMPLEMENTABLE AGAIN IF TASK-A1KJW LANDS. That task makes the dispatch record stem TASK-DERIVED rather than brief-filename-derived, and a driver already holds =task_id=, so the "own attempt dir" predicate becomes expressible. Do it in that order rather than reopening this.

A SECOND WORKTREE-DERIVED INFERENCE WAS FOUND THAT THE BRIEF DID NOT NAME — which is why the brief asked for a grep rather than a point fix. =cursor_acp::project_root()= fell back to =worktree.parent()=; post-move that names =~/.orgasmic/worktrees/<project-id>=, so the dispatch-artifact READ grant would have keyed on a =.orgasmic/tmp/dispatch= path inside the managed worktree root, a surface no project owns. Deleting the fallback only ever narrows; the daemon always supplies =project_root= (=api.rs:4331=, required parameter), and the sibling =cursor.rs= adapter already had no fallback, so this matches the shape that was already correct. A third hit was a test-only opt-in transcript probe encoding the in-project layout, also corrected.

* IN_REVIEW TASK-4WKNX FIX_SUBTASK closes straight to done, so a fix round that the goal requires to be reviewed cannot be dispatched a reviewer without a manual stage flip :cli:manager:
:PROPERTIES:
:ID: TASK-4WKNX
:PRIORITY: P2
:WRITE_SCOPE: crates/orgasmic-cli/**,crates/orgasmic-daemon/**
:END:

** Description
Found by running into it, 2026-08-05, closing TASK-YN5FJ.1.1.

=close_lifecycle_transitions= sends an implementer close to =Done= when the task
carries =:FIX_SUBTASK: t=, and to =InReview= otherwise. That encodes one-round
fix semantics, which the manager-dispatch convention states deliberately.

The ACTIVE GOAL says something else, and it is not reconcilable by reading
harder: "Fix subtasks minted from reviewer findings count as tasks: a BLOCK SHIP
is not closed until its fix round lands and passes a fresh review."

So for a fix round minted from a BLOCK SHIP, the two rules point opposite ways.
What happens in practice: =dispatch-close= flips the task to =done=, and the
reviewer dispatch then refuses with

: task TASK-YN5FJ.1.1 is in lifecycle stage done; reviewer dispatch is allowed only from IN_REVIEW

The refusal is CORRECT — a done task should not accept a reviewer. The defect is
upstream: the close had no way to say "this fix round still owes a review", so the
manager has to flip =done= -> =in_review= by hand afterwards to get the review the
goal demands. A state the board cannot express is a state managers will fake.

** Why this matters beyond one flip
The manual flip records a =task.state_transitioned= that reads like a correction,
not like policy. Anyone auditing later sees a task moved backwards out of done
with no way to tell whether that was process or panic. And a manager who does NOT
know the goal clause will simply not review the fix round at all — the tooling
actively steers them away from it.

** Fix directions, not yet decided
1. Let the close say it: a flag on =dispatch-close= (or a property on the task)
   that means "fix round, still owes review", so the close lands =in_review=
   without the manual flip.
2. Or derive it: a fix subtask minted from a reviewer finding labelled BLOCK SHIP
   goes to =in_review=; one minted from a non-blocking finding goes to =done=.
   That matches the goal clause exactly and needs no new operator input, but it
   requires the finding severity to be recorded somewhere the close can read —
   today it is prose in the reviewer report.
3. Or change the convention and the goal to agree on one rule. Cheapest, and it
   is a real option: decide that one-round fix semantics win and the goal clause
   is wrong.

Pick deliberately; do not implement all three.

** Acceptance
- A fix round minted from a BLOCK SHIP reaches its reviewer without a manual
  backwards stage transition.
- Whatever rule is chosen is stated in ONE place that both the convention and the
  close read from, so the next manager cannot find two answers.
- Existing one-round fix behaviour for non-blocking fix subtasks is preserved or
  its removal is explicit.
** Evidence
Landed =2d9d8b8= (merge) on main. Implementer: =implementer-claude-tmux= (tmux / claude / claude-opus-5 / high), run =run-20260805T184048-efc1a81d6ebb47439ce722ca7b4edbc2=, started_tx =tx-20260805-orgasmic-4519=.

THE MANAGER RULED THE POLICY, THE IMPLEMENTER CHOSE THE MECHANISM, and the split held. A =FIX_SUBTASK= implementer close now lands =in_review= like any other; the opt-out is =--fix-round-final=, which requires =--reason= and stamps =FIX_ROUND_FINAL=true= on the close tx.

THE RULING WAS MADE ON THIS SESSION OWN EVIDENCE, not taste. Five fix rounds ran 2026-08-05. One of them — TASK-M47E5.2, the fix round for three data-loss findings — was itself REJECTED with three MORE BLOCK SHIP findings, two P0. Under the old default it would have closed straight to =done= and six confirmed defects would be sitting on main unreviewed. The only thing that caught it was the manager flipping =done= -> =in_review= by hand, three separate times in one day, which nobody who had not read the goal would know to do. The asymmetry decides it: the old default fails as "a fix for a data-loss finding lands unreviewed"; the new one fails as "a trivial fix waits for a cheap review".

THREE IMPLEMENTER DECISIONS, all defensible and all stated:
- A FLAG, NOT A TASK PROPERTY. A property would describe the task forever, when what is recorded is a judgement about ONE round outcome, made at close time by the manager who read the diff.
- NAMED =--fix-round-final=, NOT another =--no-*=. The brief warned the two bypasses must not read as one concept; a near-homonym of =--no-review-required= would have invited exactly that. The flag names the state of the round rather than negating the word "review".
- REASON REQUIRED. Stronger here than for =--no-review-required=: this bypass is INVISIBLE IN THE OUTCOME — a task at =done= looks identical whether it was reviewed or declared not to need it — so the ledger has to carry the difference.

THE RULE NOW LIVES IN ONE PLACE: =implementer_done_stage(fix_subtask, fix_round_final)=, a four-row table with a unit test enumerating all four rows. =close_lifecycle_transitions= encodes nothing itself. Both shipped docs describe it by NAMING the flag, and =cli_parity= resolves shipped invocations against the real binary, so prose that lags the code is a gate failure.

A SECOND SHIPPED FILE WAS EDITED OUTSIDE THE DECLARED WRITE SCOPE, DECLARED RATHER THAN BURIED, and the manager accepts it: =shipped/schema/state-machine.org= still restated the old mapping ("transitions IN_PROGRESS -> DONE"). Leaving it would have preserved exactly the two-answers state this task acceptance forbids, so fixing it was the task, not scope creep.
