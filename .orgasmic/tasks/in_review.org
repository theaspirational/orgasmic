* IN_REVIEW TASK-Z8WEJ Select the claude credential mode instead of hardcoding --bare :drivers:dispatch:bug:
:PROPERTIES:
:ID: TASK-Z8WEJ
:PRIORITY: P0
:END:

Problem: `crates/orgasmic-drivers/src/adapters/claude.rs:136` hardcodes `--bare` in the claude stdio argv. Per the CLI's own help, `--bare` means "Anthropic auth is strictly ANTHROPIC_API_KEY or apiKeyHelper via --settings (OAuth and keychain are never read)". An operator authenticated through a claude.ai subscription therefore cannot dispatch a claude worker at all: the credential exists, `claude auth status` reports `loggedIn: true, authMethod: claude.ai, subscriptionType: max`, and the dispatch still dies 1.2 s after acquire with "Not logged in - Please run /login" (observed TASK-KWSTJ reviewer dispatch, run-20260725T073841).

`--bare` is wanted and should stay available: it skips hooks, LSP, plugin sync, auto-memory, background prefetches and CLAUDE.md auto-discovery, which is the right shape for a worker. The defect is that it is unconditional, and it silently carries a credential policy that a subscription operator cannot satisfy.

Measured channel matrix, same binary and prompt, obviously-fake credential values (2026-07-25, claude 2.1.220):

Under `--bare`:
- no credential -> "Not logged in - Please run /login"
- `ANTHROPIC_API_KEY=<fake>` -> "Invalid API key - Fix external API key" (channel LIVE)
- `CLAUDE_CODE_OAUTH_TOKEN=<fake>` -> "Not logged in" (channel DEAD; the token is ignored)
- `apiKeyHelper` via `--settings` -> "Invalid API key" (channel LIVE)

Without `--bare`:
- keychain OAuth -> authenticates and completes
- `--strict-mcp-config` + empty `--mcp-config` + minimal `--settings` -> authenticates, `mcp_servers: []`, 30 tools, 2.0 s round trip

Critical negative result: `CLAUDE_CODE_SIMPLE=1` on its own, with no `--bare` flag, also fails with "Not logged in". The lightweight behaviour and the credential policy are the same switch, so there is no way to keep bare-mode lightness while reading the keychain. Any design that assumes they can be separated is wrong.

Both live `--bare` channels want an API key, not an OAuth credential, and a subscription's keychain credential is not an API key. So "`--bare` plus the user's keychain auth" is not achievable, by the flag's contract rather than by oversight.

Work:
1. Make the claude adapter select a credential mode instead of hardcoding one. At minimum: bare+API key (preferred, lightest) when an API key or apiKeyHelper is configured; non-bare with narrow isolation when auth is OAuth/subscription.
2. Build the fallback tier explicitly rather than by dropping flags: `--strict-mcp-config` with an empty `--mcp-config`, a minimal `--settings`, and the existing `--no-session-persistence`. Verify it suppresses MCP, hooks, and CLAUDE.md discovery — do not assume the narrow flags cover everything `--bare` did, and record what is not covered.
3. Detect, do not guess. `claude auth status` is non-interactive and returns structured JSON with `authMethod`; use it to choose the tier. Note it is necessary but not sufficient — see 5.
4. Let the manager override the tier per dispatch, and record which tier was used in the run's RunMeta so a failure is diagnosable from the session JSONL alone.
5. Feeds TASK-TJKFC: a generic auth probe is not enough. `claude auth status` reports `loggedIn: true` while the `--bare` invocation fails. The preflight must exercise the argv the worker will actually run.
6. Consider whether the same credential-mode question exists for codex, cursor-agent, and hermes, or whether this is claude-specific. Do not generalise without checking.

Acceptance:
- a subscription-authenticated operator can dispatch a claude worker with no API key
- an API-key operator still gets the light `--bare` path
- the selected credential mode is visible in RunMeta
- a mode that cannot authenticate is rejected before a worktree, lease, or dispatch record is created

It passes an orgasmic-minted session id up front, so correlation is deterministic rather than discovered. acp-stdio should follow that pattern.

Three consequences, all currently live:

1. TASK-VBSG2 is impossible for this transport. Its slice A resolves "verified NativeRuntime provider/session/path metadata" and parses "Claude native JSONL". Neither exists for acp-stdio runs, so retro over an arbitrary past claude run cannot work no matter how good the materializer is.

2. dec_WDR5K item 7 is violated in effect. TUI screen capture was removed on the premise that "session transcripts come from harness-native JSONL located by per-harness transcript finder adapters". For acp-stdio claude the finder adapter has nothing to find, so those runs have no transcript at all — not a lossy one, none. The decision's own sequencing constraint (finders must land before capture removal, or runs lose their session inputs) is satisfied in letter and broken in substance here.

3. Recovery is degraded. `resolve_recovery_actions` offers `resume_native_fork` only when `session_native_runtime` yields a validated claude session id. acp-stdio records none, so that action can never be offered for this transport; recovery falls through to a fresh run even when resuming was possible.

Work:
1. Drop `--no-session-persistence` from the acp-stdio claude argv, or make it a deliberate per-dispatch option rather than a hardcoded default.
2. Mint and pass an explicit `--session-id`, matching the TUI path, so correlation never depends on discovery heuristics.
3. Emit a `NativeRuntime` lifecycle event from the acp-stdio path with provider, session id, launch argv, and resume argv, so recovery and retro read one shape regardless of transport.
4. Weigh and record the retention tradeoff rather than assuming it away. Persisting worker sessions grows `~/.claude/projects` without bound (446 transcripts already present on this machine), and the retro contract holds vendor JSONL to be vendor-owned and immutable — so orgasmic may not prune it. Decide explicitly whether that is acceptable, whether worker sessions should be distinguishable from operator sessions, and record the answer.
5. Check the same three properties for codex, cursor-agent, and hermes under acp-stdio. Do not assume this is claude-specific.

Coordinates with TASK-Z8WEJ: both change `stdio_spawn` in the same adapter and should land together.

Acceptance:
- an acp-stdio claude run leaves a native transcript that the existing transcript finder resolves
- its session id is recorded in a NativeRuntime lifecycle event, not discovered after the fact
- `resume_native_fork` is offered for a recoverable acp-stdio claude run

* IN_REVIEW TASK-8W30B RmuxControl::release aborts its tasks before kill, leaking a session, pty and harness process per run :drivers:rmux:bug:production:
:PROPERTIES:
:ID: TASK-8W30B
:PRIORITY: P1
:test_cmd: cargo test -p orgasmic-drivers

Production defect, root-caused by the TASK-STWVB implementer while diagnosing a
test flake. It is not a test problem.

THE DEFECT

`RmuxControl::release` (crates/orgasmic-drivers/src/modes/rmux.rs:1760) aborts
its lifecycle task and its startup task BEFORE calling `Session::kill()`. The
kill is then issued over a torn-down SDK transport and fails. Instrumented probe:

    PROBE rmux Session::kill -> Err(Transport { operation: "complete
      `kill-session` request/response exchange with rmux daemon",
      source: BrokenPipe: "rmux SDK request was cancelled while its ordered
      response was pending" })

The session survives. The only report is a `tracing::warn!`, invisible under
`cargo test` and easy to miss in a daemon log.

WHY IT MATTERS BEYOND TESTS

Every released rmux run leaks a session, a pty and a harness process into the
per-user rmux daemon — a singleton on `$TMPDIR/rmux-$uid`, shared across every
run and every test binary, started by launchd and therefore inheriting a 256-fd
soft limit (`launchctl limit maxfiles` → `maxfiles 256 unlimited`, confirmed
independently on this machine 2026-07-26).

Once saturated the daemon cannot create sessions, and the rmux driver degrades
to INERT — silently. A developer's machine reaches that state on its own, and
from then on every rmux dispatch quietly does nothing useful.

MEASURED

- 8 leaked sessions per `--lib artifact` run (109 → 189 across 12 runs; 7 still
  present 15 s after the process exited)
- 236 stale `orgasmic-rmux-run-*` sessions and 69 orphaned
  `artifactor-test-harness.sh` processes found accumulated, oldest predating the
  dispatch that found them
- at 236 sessions the daemon held 253 open fds against the 256 limit
- dose-response over 10 consecutive full-suite runs: green at 204/210/217/221/226
  leaked sessions, failing at 233/236/236/236/236. The count stopped growing
  exactly when failures began — the daemon could no longer create sessions.
- the resulting symptom is `409 capability_unsupported: send_input` on all 40
  retries, not a deadline that wanted lengthening

SUGGESTED FIX

`RmuxControl` already carries `rmux_bin` and `session_target`. Either kill the
session before aborting the tasks, or add a CLI `kill-session` fallback for when
the SDK transport is already gone. Prefer both: the CLI path also cleans up
sessions leaked by earlier builds.

Also make the failure visible. A kill that fails is currently a warn on a path
nobody watches; it should be an error the release path surfaces.

NOTE ON CURRENT MACHINE STATE: the accumulation was cleared incidentally during
this session (rmux servers were killed during unrelated cleanup), so a check
right now reports 0 sessions and no running daemon. That is not the defect being
fixed — it will re-accumulate from the next rmux run.

Downstream: this is the production root cause of
`api::post_artifact_regenerate_hot_path_reuses_live_run_id` flaking, which is why
TASK-STWVB deliberately did not patch that test.
