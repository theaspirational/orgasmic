* IN_REVIEW TASK-Z8WEJ Select the claude credential mode instead of hardcoding --bare :drivers:dispatch:bug:
:PROPERTIES:
:ID: TASK-Z8WEJ
:PRIORITY: P0
:END:

Problem: `crates/orgasmic-drivers/src/adapters/claude.rs:136` hardcodes `--bare` in the claude stdio argv. Per the CLI's own help, `--bare` means "Anthropic auth is strictly ANTHROPIC_API_KEY or apiKeyHelper via --settings (OAuth and keychain are never read)". An operator authenticated through a claude.ai subscription therefore cannot dispatch a claude worker at all: the credential exists, `claude auth status` reports `loggedIn: true, authMethod: claude.ai, subscriptionType: max`, and the dispatch still dies 1.2 s after acquire with "Not logged in - Please run /login" (observed TASK-KWSTJ reviewer dispatch, run-20260725T073841).

`--bare` is wanted and should stay available: it skips hooks, LSP, plugin sync, auto-memory, background prefetches and CLAUDE.md auto-discovery, which is the right shape for a worker. The defect is that it is unconditional, and it silently carries a credential policy that a subscription operator cannot satisfy.

Measured channel matrix, same binary and prompt, obviously-fake credential values (2026-07-25, claude 2.1.220):

Under `--bare`:
- no credential -> "Not logged in - Please run /login"
- `ANTHROPIC_API_KEY=<fake>` -> "Invalid API key - Fix external API key" (channel LIVE)
- `CLAUDE_CODE_OAUTH_TOKEN=<fake>` -> "Not logged in" (channel DEAD; the token is ignored)
- `apiKeyHelper` via `--settings` -> "Invalid API key" (channel LIVE)

Without `--bare`:
- keychain OAuth -> authenticates and completes
- `--strict-mcp-config` + empty `--mcp-config` + minimal `--settings` -> authenticates, `mcp_servers: []`, 30 tools, 2.0 s round trip

Critical negative result: `CLAUDE_CODE_SIMPLE=1` on its own, with no `--bare` flag, also fails with "Not logged in". The lightweight behaviour and the credential policy are the same switch, so there is no way to keep bare-mode lightness while reading the keychain. Any design that assumes they can be separated is wrong.

Both live `--bare` channels want an API key, not an OAuth credential, and a subscription's keychain credential is not an API key. So "`--bare` plus the user's keychain auth" is not achievable, by the flag's contract rather than by oversight.

Work:
1. Make the claude adapter select a credential mode instead of hardcoding one. At minimum: bare+API key (preferred, lightest) when an API key or apiKeyHelper is configured; non-bare with narrow isolation when auth is OAuth/subscription.
2. Build the fallback tier explicitly rather than by dropping flags: `--strict-mcp-config` with an empty `--mcp-config`, a minimal `--settings`, and the existing `--no-session-persistence`. Verify it suppresses MCP, hooks, and CLAUDE.md discovery — do not assume the narrow flags cover everything `--bare` did, and record what is not covered.
3. Detect, do not guess. `claude auth status` is non-interactive and returns structured JSON with `authMethod`; use it to choose the tier. Note it is necessary but not sufficient — see 5.
4. Let the manager override the tier per dispatch, and record which tier was used in the run's RunMeta so a failure is diagnosable from the session JSONL alone.
5. Feeds TASK-TJKFC: a generic auth probe is not enough. `claude auth status` reports `loggedIn: true` while the `--bare` invocation fails. The preflight must exercise the argv the worker will actually run.
6. Consider whether the same credential-mode question exists for codex, cursor-agent, and hermes, or whether this is claude-specific. Do not generalise without checking.

Acceptance:
- a subscription-authenticated operator can dispatch a claude worker with no API key
- an API-key operator still gets the light `--bare` path
- the selected credential mode is visible in RunMeta
- a mode that cannot authenticate is rejected before a worktree, lease, or dispatch record is created

* IN_REVIEW TASK-VB9DQ Persist native session evidence for acp-stdio claude runs :drivers:recovery:evidence:
:PROPERTIES:
:ID: TASK-VB9DQ
:PRIORITY: P1
:END:

Problem: `crates/orgasmic-drivers/src/adapters/claude.rs:144` passes `--no-session-persistence` on every acp-stdio claude run, and the adapter never passes `--session-id` or emits a `NativeRuntime` lifecycle event. The consequence is that acp-stdio claude runs leave no harness-native evidence of any kind.

Measured 2026-07-25 (claude 2.1.220, counting files under `~/.claude/projects`):
- run with `--no-session-persistence`: 0 new native transcripts
- identical run without it: 1 new native transcript

Confirmed by inspection:
- `NativeRuntimeMeta` appears only in `modes/rmux.rs` and `modes/tmux.rs`; `adapters/claude.rs` never emits it
- the acp-stdio reviewer run `run-20260725T073841` recorded lifecycle phases `acquire, run_meta, release` only — no `native_runtime`

Contrast the TUI path, which already does this correctly. A real rmux run recorded:
- `launch_argv: [claude, --dangerously-skip-permissions, --model, claude-sonnet-5, --session-id, a9fe25ff-...]`
- `resume_argv: [claude, --resume, a9fe25ff-..., --fork-session, --dangerously-skip-permissions]`
- `session_id: a9fe25ff-...`

It passes an orgasmic-minted session id up front, so correlation is deterministic rather than discovered. acp-stdio should follow that pattern.

Three consequences, all currently live:

1. TASK-VBSG2 is impossible for this transport. Its slice A resolves "verified NativeRuntime provider/session/path metadata" and parses "Claude native JSONL". Neither exists for acp-stdio runs, so retro over an arbitrary past claude run cannot work no matter how good the materializer is.

2. dec_WDR5K item 7 is violated in effect. TUI screen capture was removed on the premise that "session transcripts come from harness-native JSONL located by per-harness transcript finder adapters". For acp-stdio claude the finder adapter has nothing to find, so those runs have no transcript at all — not a lossy one, none. The decision's own sequencing constraint (finders must land before capture removal, or runs lose their session inputs) is satisfied in letter and broken in substance here.

3. Recovery is degraded. `resolve_recovery_actions` offers `resume_native_fork` only when `session_native_runtime` yields a validated claude session id. acp-stdio records none, so that action can never be offered for this transport; recovery falls through to a fresh run even when resuming was possible.

Work:
1. Drop `--no-session-persistence` from the acp-stdio claude argv, or make it a deliberate per-dispatch option rather than a hardcoded default.
2. Mint and pass an explicit `--session-id`, matching the TUI path, so correlation never depends on discovery heuristics.
3. Emit a `NativeRuntime` lifecycle event from the acp-stdio path with provider, session id, launch argv, and resume argv, so recovery and retro read one shape regardless of transport.
4. Weigh and record the retention tradeoff rather than assuming it away. Persisting worker sessions grows `~/.claude/projects` without bound (446 transcripts already present on this machine), and the retro contract holds vendor JSONL to be vendor-owned and immutable — so orgasmic may not prune it. Decide explicitly whether that is acceptable, whether worker sessions should be distinguishable from operator sessions, and record the answer.
5. Check the same three properties for codex, cursor-agent, and hermes under acp-stdio. Do not assume this is claude-specific.

Coordinates with TASK-Z8WEJ: both change `stdio_spawn` in the same adapter and should land together.

Acceptance:
- an acp-stdio claude run leaves a native transcript that the existing transcript finder resolves
- its session id is recorded in a NativeRuntime lifecycle event, not discovered after the fact
- `resume_native_fork` is offered for a recoverable acp-stdio claude run
- the retention tradeoff is a recorded decision, not an implicit one

* IN_REVIEW TASK-TJKFC Preflight harness readiness and atomically abort fatal startup dispatches :P1:
:PROPERTIES:
:DEPENDS_ON: TASK-KWSTJ
:ID: TASK-TJKFC
:PRIORITY: P0
:END:

Problem: dispatch can create a worktree and enter the daemon before provider or harness authentication is known to be usable. A fatal startup DriverError can then leave an open dispatch record and resources that block later work. Add a bounded non-interactive preflight at the provider-local driver boundary after configuration is resolved but before lease, session, or manager.dispatch_started ownership is committed. The default capability must be explicit unsupported, not false success; supported adapters return ready or a typed fatal reason. Claude and ACP implementations must test the same execution context used by the worker and must never prompt. A definitive preflight failure returns a normal rejected dispatch so the existing CLI rollback restores lifecycle state and removes the newly created worktree and branch. Also make dispatch attempt creation atomic with the earliest driver events: a fatal event during the startup gate must record an aborted attempt, close any open dispatch, release the lease, and safely clean only attempt-owned resources. Once startup has been accepted and meaningful work has occurred, later failures retain normal failed-run history and inspection artifacts. Acceptance: fake-provider tests prove auth failure creates no lease, session, or open dispatch and CLI rollback removes attempt resources; a race test emits fatal before dispatch bookkeeping and proves no orphan; supported-preflight success reaches running; unsupported preflight preserves current drivers; a post-start fatal remains a failed historical run and does not erase work. Provider-specific parsing stays inside the driver adapter; manager and supervisor consume only typed readiness/startup outcomes.

PARTIAL IMPLEMENTATION (2026-07-25, manager-implementer). The startup gate
exists and is wired; the concrete probes and the atomic-abort half do not.

LANDED
- =Preflight= on =WorkerDriver=: three-valued Ready / Fatal{reason} /
  Unsupported, defaulting to Unsupported. The default is the point: a driver
  that never implemented a probe must not be able to report readiness it never
  checked. Only Fatal rejects a dispatch, so an inconclusive probe leaves the
  pre-existing behaviour intact.
- Called in =spawn_worker_run= immediately after =driver.validate=, which is the
  last point at which rejecting is free. Verified by reading the ordering rather
  than assuming it: the session path, babysitter, lease and acquire all come
  after, and =record_dispatch_started= runs after =spawn_worker_run= returns.
- A Fatal returns =400 Bad Request=. Verified this routes correctly:
  =dispatch_failure_needs_daemon_cleanup= treats any "daemon returned ..."
  message as an unambiguous rejection, so the CLI runs
  =cleanup_created_resources= (worktree + branch + artifact paths) and
  =restore_task_lifecycle_stages=. Pinned by a test using the actual
  preflight message shape, because routing it as ambiguous would leave behind
  exactly the litter the 2026-07-25 dispatch left.
- The probe receives placement (worktree, task, run kind, project) and an empty
  =RuntimeIdentity=. A probe must not depend on a run id it exists to avoid
  creating.
- Driver-level tests: the default is Unsupported and does not reject; only Fatal
  rejects; a harness answering "Please run /login" is classified Fatal rather
  than surfaced into a worker that would wait on a prompt nobody will answer.

NOT LANDED, and this matters for reading the task's status honestly
1. No adapter implements =preflight= yet, so nothing changes behaviourally
   today. The gate is structural.
2. The claude probe has an unresolved design question worth deciding before
   writing it. Auth failure is observable in ~39 ms because it happens before
   any model call, but a probe that exercises "the same execution context the
   worker will use" and succeeds will have made a real (small) model call on
   every dispatch. Cheaper probes exist and are all weaker: =claude auth status=
   is exactly the check measured to give a false pass (loggedIn: true while the
   dispatch argv answered "Not logged in"). Pick deliberately.
3. The atomic-abort half is untouched: a fatal driver event *after* startup has
   been accepted still leaves an open dispatch record, and the race test the
   task asks for (fatal emitted before dispatch bookkeeping completes) does not
   exist.
4. Consequently the acceptance clause "fake-provider tests prove auth failure
   creates no lease, session, or open dispatch and CLI rollback removes attempt
   resources" is only half covered: the reject-before-commit ordering is proven
   by construction and by the routing test, but there is no end-to-end test
   driving a fake provider through the daemon and asserting the absence of a
   lease and session.

Note on the original incident: its specific cause was fixed separately in
61b9b7f — orgasmic's own =--bare= argv, not an operator credential problem.
This task remains worth finishing for the class, not that instance.

PROBES LANDED (2026-07-25, manager-implementer). All three installed harnesses
now rule on their own credentials before a dispatch commits anything. The
atomic-abort half is still open; see NOT LANDED below.

The design question this task flagged is decided, and the answer is the opposite
of what the original evidence implied. Both halves were measured, not reasoned:

1. What a truthful probe costs. Making the harness itself rule on a credential
   means submitting a turn. Measured on claude 2.1.220, a ONE-CHARACTER prompt
   cost $0.0994 and 24.5k tokens, because the request writes the system prompt,
   tools and skills to cache before any answer returns. Cancelling early does
   not refund it: the failure verdict lands at 0.390 s and the outbound request
   at 0.326 s, so no deadline separates them. A check that silently bills a
   tenth of a dollar per dispatch is not a check worth having. Rejected.

2. Why `claude auth status` was actually wrong. The task recorded it as an
   ambient self-report that lied. It is not. Measured: `auth status` reports
   ONLY the claude.ai/keychain login and is blind to ANTHROPIC_API_KEY, while
   the failing dispatch carried `--bare`, whose contract is that OAuth and the
   keychain are never read. The two were answering about DIFFERENT CREDENTIALS,
   so they could disagree without either being wrong.

So the rule on `WorkerDriver::preflight` is rewritten. It was "exercise the
worker's exact argv"; it is now "resolve the same credential mode the worker
will resolve, then check the credential THAT MODE consumes". Once the mode is
resolved first, `auth status` is exactly the right question for native login
and exactly the wrong one for `--bare`. Cost: $0 and 0.28 s.

The guarantee behind it is structural, not documentary: `resolve_credentials`
was extracted out of `compose_request`, so the probe and the launch cannot
resolve different modes. A probe that reasoned its way to a mode independently
could confidently interrogate a credential the worker was never going to use,
which is precisely the failure above.

WHAT EACH ADAPTER NOW DOES
- claude: native login -> `claude auth status`, reads the `loggedIn` boolean.
  `--bare` -> the key it will present; an empty one is fatal, a present one is
  reported as unchecked (only the API can accept a key, and asking is the
  billed turn above).
- cursor-agent: a configured `api_key_env` is judged on the key; otherwise
  `cursor-agent status`.
- codex: `codex login status`.
- everything else: unchanged default `Unsupported`.

All five mode drivers delegate through one `preflight_via_adapter`, since
readiness is the harness's property and not the transport's.

VERIFIED LIVE, BOTH DIRECTIONS
- Healthy machine: Ready from claude, cursor-agent and codex.
- Credential-less machine (HOME/CODEX_HOME pointed at an empty directory, so no
  operator was logged out): Fatal from all three, each naming its remedy.

TWO BUGS THE LIVE TEST CAUGHT THAT UNIT TESTS COULD NOT
Both are recorded in gotchas.org, because both are the kind of thing a
reasonable person assumes.
1. codex writes its status answer to STDERR and leaves stdout empty. Reading
   stdout classified a logged-in codex as "no probe".
2. `claude auth status` EXITS 1 when logged out. Gating the verdict on a zero

This is why `installed_harnesses_answer_their_own_readiness_probe` asserts

can never find either.

DELIBERATE ASYMMETRIES, so a later reader does not "fix" them

  phrase may reject. Anything unrecognised is `Unsupported`. A harness that

- An empty endpoint does NOT skip the probe. acp-stdio upgrades that config into

- The probe does not call `claude_available()`. That is a blocking

- Fatal reasons are constants, never echoes of harness output. `auth status`

ATOMIC ABORT, PART 1 (2026-07-25, manager-implementer). The seventy-minute
orphan is fixed. The dispatch record is deliberately NOT auto-closed, and the
reason is below - it contradicts this task's own acceptance wording.

The incident's session JSONL was still on disk
(.orgasmic/tmp/sessions/dispatch-TASK-KWSTJ-reviewer-20260725T073841.jsonl) and
it settles what actually happened. Read in order:

  07:38:44.754  lifecycle acquire
  07:38:45.166  driver_error  fatal: true   "claude authentication_failed"
  07:38:45.175  driver_event  run_fail      "claude_result_error"
  ...           nothing at all, for seventy minutes
  08:49:23.536  driver_error  "claude exited with status exit status: 143"
  08:49:23.542  lifecycle release  outcome failed, finalized_by_worker false

The 143 is SIGTERM - the operator killing it. So the run did not end when it
failed; it ended when a human intervened, and everything in between was the
system waiting.

ROOT CAUSE, and it is one line. `terminal_event_releases_transport`
(supervisor.rs) allow-listed `tmux | tmux-tui | rmux`. On every other transport
a terminal event set `rec.terminal_outcome` and released nothing, leaving the
release to stream end. That is a bet that the harness will exit once it has
nothing left to do - sound on the success path, where exiting is part of
completing normally, and unsound on the failure path, because
`claude -p --input-format stream-json` holds stdin open waiting for a turn that
is never coming. The stream never ended, so the lease stayed held and the pid
stayed alive, which `dispatch-status` reported as `[pid-alive]`: a fatal startup
that leaves a live process is indistinguishable from work in progress.

FIX. A terminal event whose outcome is Failed now releases on every transport
(`terminal_failure_releases_any_transport`). Releasing reaps the process group -
`reap_process_group` sends TERM then KILL - so the failure now costs 0.4 s
instead of running until someone notices. Artifact draining is untouched:
`artifactor_lifecycle_in_flight` still defers through `pending_terminal_drain`.

The test is `a_declared_failure_releases_without_waiting_for_the_harness_to_exit`
and its shape is the point. Every pre-existing fatal-path test drops the driver
sender as soon as it has emitted, so stream end rescues it and none of them can
see this defect. The new stub keeps the sender in its *control* and drops it
only on release, which is what a real transport does - the reap is what closes
the channel. Its stream therefore never ends on its own, so the two-second
bound can only be met by the fix. Verified by mutation: with the new clause
disabled the test times out; restored, it passes in 0.14 s.

WHY THE DISPATCH RECORD IS STILL NOT AUTO-CLOSED
This task's acceptance says a fatal startup must "close any open dispatch". That
is the wrong instruction for the daemon to follow, and it took reading the CLI
to see why.

A dispatch is closed by `implementer.done` / `reviewer.done` /
`architector.done` / `manager.dispatch_aborted` (`scan_open_dispatches`);
`manager.dispatch_orphaned`, which the watcher does write, is not in that set.
So the obvious fix is to have the daemon write `dispatch_aborted` instead. But
closing is not a bookkeeping act: `cmd_dispatch_close` also runs
`cleanup_dispatch` - it removes the worktree, deletes the branch, and records
`CLEANUP_STATUS` on the closing tx so `close_tx_ran_cleanup` can tell that the
resources are gone. The daemon cannot do that half. It is a git operation on the
operator's repository.

A daemon-written close would therefore mark the dispatch closed with no
`CLEANUP_STATUS`, and `dispatch-status` would stop listing it - while the 15 MB
worktree and the branch stayed on disk with nothing left pointing at them. That
converts a visible orphan into an invisible one, which is strictly worse than
the state this task set out to fix.

So the open-until-acknowledged record is correct, and the thing that was
genuinely broken about it is already fixed elsewhere: `dispatch-close --status
aborted` used to die at 10.03 s against the pre-TASK-KWSTJ `/api/runs`, so the
documented remedy did not work. It does now.

If auto-close is still wanted, it is a different and larger piece of work -
the daemon would have to own worktree and branch removal - and it should be
argued on its own merits rather than inherited from this task's wording.

RACE TEST. `a_failure_declared_before_the_run_is_recorded_still_ends_the_run`
(supervisor.rs). A driver that declares its fatal synchronously inside
`acquire`, before returning the session, so the queue is guaranteed non-empty
when the supervisor inserts the run record. What protects this is an ordering,
not a lock: the record goes in before the drain task spawns, so no event can be
applied through `runs.get_mut` while the record is missing. Verified by mutation
- deferring the insert past the drain's first events produces no release at all.
Worth noting how it fails: not by timing out, but instantly, because a run
absent from the map reads as already released. That is the bug's own shape, an
orphan indistinguishable from a finished run.

CORRECTION (2026-07-25, after root-cause analysis): the harness WAS authenticated. `claude auth status` reports `loggedIn: true, authMethod: claude.ai, subscriptionType: max`. Orgasmic's own argv caused the failure — the claude adapter hardcodes `--bare`, whose contract is that OAuth and keychain are never read (see TASK-Z8WEJ). Do not read this evidence as an operator credential problem. What the failure left behind:

- an open dispatch record, still listed by `manager dispatch-status` 70 minutes later
- a 15 MB worktree at `.orgasmic/tmp/dispatch/task-kwstj-review/`
- a branch `task-kwstj-review`
- zero-byte `last.txt` and `stdout.log`
- the harness process (pid 52741, `claude --bare -p --input-format stream-json ...`) still alive 70 minutes after emitting a fatal error, reported by dispatch-status as `[pid-alive] [run-gone]` — supervisor had dropped the run while the process persisted

The manager treated `[pid-alive]` as "review in progress" and reported it as running to the operator. A fatal startup error that leaves a live process is worse than a crash: it is indistinguishable from work.

Second finding, and the reason this is not merely cosmetic: cleanup was blocked by the very defect TASK-KWSTJ fixes. `orgasmic manager dispatch-close --status aborted` on the installed 0.0.14 CLI fails after exactly 10.03 s with "daemon request failed ... /api/runs — is the daemon reachable?". The pre-fix CLI takes the legacy liveness fence through `GET /api/runs`, which on this board needs 35.2 s to first byte, against a 10 s client deadline. So a dispatch that failed at startup cannot be closed by the documented verb until the bounded-inventory fix ships. The two defects compound: startup leaves the mess, and enumeration prevents cleaning it.

Preflight design note this supports, sharpened by the root cause: the check must exercise the exact argv the worker will run, not merely the harness's ambient credential state. Measured here: `claude auth status` returns `loggedIn: true` while the very same binary invoked with the dispatch's own flags returns "Not logged in" in 39 ms. A preflight that asked the harness whether it was logged in would have passed and still produced this failure. The 39 ms cost of the real probe is also the argument for doing it: it is cheaper than the worktree it prevents.

Also relevant to the preflight's non-interactive requirement: the harness's own answer here was "Please run /login", i.e. an instruction to start an interactive flow. A preflight must classify that as a definitive fatal reason and reject the dispatch, never surface it into a worker that then waits on a prompt nobody will answer.

- Two of the four are tmux/mux-dependent, so a real external session leaking

- `cargo test -p orgasmic-daemon --lib` is green, repeatedly, at full
