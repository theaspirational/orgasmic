** Description
Filed from the TASK-G64ZH review (F-C, MEDIUM, non-blocking). TASK-G64ZH bounded
the REOPEN retry; the ROTATION path was left per-line, and the reviewer measured
it as an order of magnitude worse than the cost F1 was originally filed for.

The mechanism, confirmed by both the reviewer and the manager against the merged
code at =logging.rs:516-584= and =:369=. When =rename= fails PERSISTENTLY but
=try_open_durable()= SUCCEEDS:

1. =:571= the final =rename(daemon.out.log -> .1)= fails -> =record_drop()= plus
   one stderr line;
2. =:580= the reopen succeeds, and =:369= sets =bytes_written= to the length of
   the STILL-UNROTATED file — which is still above =max_bytes=;
3. the next tracing line re-enters =maybe_rotate= at =:516= and pays all of it
   again.

And the intermediate loop at =:552-567= emits =record_drop()= AND a stderr line
PER FAILING RENAME PER LINE. With =keep= = 32 and a full rotation history that is
31 =exists()= calls plus up to 31 failing renames plus the final one — roughly
*32 stderr lines per tracing line*, against the ~3-4x that TASK-G64ZH's F1 was
filed to remove. All of it into =daemon.err.log=, which nothing rotates and
nothing prunes: the same unbounded-unrotated-growth shape the TASK-ZBYH3 chain
exists to remove, on the one branch the chain has never touched.

*Concrete reproducer, no injection hook needed:* logs dir at mode =555= with
=daemon.out.log.1=…=.31= present. Appending to an existing writable file needs no
directory write permission, so opens keep succeeding while every rename fails
=EACCES=.

** Why this is a separate task and not part of the G64ZH fix round
It is PRE-EXISTING, not a regression. The reopen-succeeds sub-case is
byte-identical to =eaa88da^1=; TASK-G64ZH only changed the reopen-FAILS sub-case,
and changed it for the better by removing the =bytes_written = max_bytes + 1=
parking. TASK-G64ZH's F1 acceptance names a persistent OPEN failure and is met on
its own terms. Declaring this a residual was the right call for that round —
leaving it UNDECLARED would not have been.

** Direction
- A =next_rotate_attempt: Instant= gate on =maybe_rotate=, mirroring the
  =next_reopen_attempt= gate TASK-G64ZH added to the reopen path. Same shape, same
  1s->60s backoff, so the two paths are symmetric rather than one bounded and one
  not.
- Collapse the intermediate-rename loop to ONE stderr line per rotation attempt
  instead of one per failing rename, and decide whether a failing rotation should
  count one drop or none — the current code counts a drop for a line that was
  written successfully, which is a different meaning of the counter than
  TASK-G64ZH just established ("one per line that never landed").

** Acceptance
- A persistent rename failure costs a BOUNDED number of syscalls and stderr
  writes per unit time, not per tracing line. Assert the bound, the same way
  TASK-G64ZH asserted the reopen bound.
- =dropped_log_writes= has ONE documented meaning across both paths.
- A test drives the mode-=555= reproducer (or an equivalent that makes renames
  fail while opens succeed) rather than only asserting non-propagation, which is
  all the existing =rotation_failure_does_not_propagate_and_counts_a_drop= and
  =failed_intermediate_rename_counts_a_drop= do today.
