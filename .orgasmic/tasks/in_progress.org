*** F2 (HIGH, BLOCK SHIP) — the bounded scan treats its skipped middle as absence, and the miss is PERMANENT
=crates/orgasmic-core/src/session.rs:1162-1165,1312-1366=;
=recovery_claim.rs:1094-1122,1370-1392=; =supervisor.rs:1383-1395,2309-2341=;

=SessionLifecycleScan= EXPLICITLY DOCUMENTS that a truncated scan's skipped
middle must be treated as *unknown rather than absent*.
=index_recovery_origins_in_session= ignores =scan.truncated= and returns only
retained links. The new enumerator calls that bounded scanner for every file and

Round 2 disclosed this and argued "=RecoveryOrigin= is written near the head".
*The condition is real and is not enforced.* The reviewer named the production
mechanism that violates it: =PromptDraft= is written BEFORE =RecoveryOrigin=;
the committed snapshot embedded in =RecoveryOrigin= REPEATS that draft; and the

pushes the envelope past the 128 KiB prefix, or makes the lifecycle line itself
cross that boundary. Add more than 64 KiB of later driver output and it is
outside the tail too. *No size invariant prevents this.*

The consequence is worse than a miss. On that miss the loaded committed claim is
QUARANTINED (=:1385-1392=), and the catalog uses THE SAME bounded scanner, so a
later reconstruction cannot rediscover the link — *the refusal is PERSISTENT, not
the "retry" the code comment claims.* The handler can then reach the no-plan
branch and mint another replacement. So the safety fix produces the very
duplicate authority it exists to prevent, by a second route.

** THE MANAGER'S C1 RULING — UPHELD, AND CORRECTED TWICE
The manager ruled in round four's brief: *in the =NoRepository= branch only, a
nested populated =.git= found on disk must refuse, naming the path in the =KEPT=
line.* The reviewer agreed with the reasoning — in =RepoGone= git has no oracle,
=RepoGone= reclamation is a feature orgasmic invented, the cost asymmetry is the
one this project has already ruled on, and ruling 4's "vendored repositories"
counterargument lands soft because the heuristic is scoped to a state that only
arises once the repository has already disappeared.

*IT THEN CORRECTED THE RULING IN TWO WAYS THAT WOULD HAVE SHIPPED BROKEN.*

*CORRECTION 1 — "=.git=" MUST MEAN AN ENTRY OF ANY TYPE, NOT A DIRECTORY.*
=git submodule update --init= on git 2.52.0 writes the submodule's =.git= as a
*FILE* holding =gitdir: ../../.git/modules/<name>=. When the superproject's
repository is gone, that admin directory is gone too — so the nested repo
presents as a =.git= FILE pointing at nothing. *A "populated =.git= directory"
predicate returns false on the single most likely shape*, i.e. the manager's
ruling as literally written would have missed the case it exists for.

*CORRECTION 2 — THERE IS NO =--force= ON THIS VERB, AND THE ADVICE IT WOULD
INHERIT IS IMPOSSIBLE.* The shipped options are only =--dry-run= and =--task=. So
there is no forever-refusal, but there is also no in-verb escape: the operator
must delete the nested =.git= by hand. The current shared =advice= string tells
them to run =git worktree remove --force=, *which cannot work when the repository
is gone.* A =NoRepository= refusal therefore needs its own advice text naming the
offending path and saying "remove it yourself" — otherwise this round ships a
refusal whose stated remedy is impossible.

*AND A CHEAPER PREDICATE THE MANAGER DID NOT SEE.* The reclaim path already does
a full anchored size walk of the tree before the reservation
(=manager.rs:3753-3784= — recursive, descends by =openat= from the worktree
handle, already sound against symlinks). Have that walk record "did I see any
child entry named =.git=" and the =NoRepository= branch costs *one boolean*
instead of a second traversal. *Ordering consequence, stated by the reviewer:*
the refusal currently sits ABOVE the size walk, so either the =NoRepository= leg
consumes a result computed later, or the walk moves up.
