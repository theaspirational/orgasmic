* IN_PROGRESS TASK-TJKFC Preflight harness readiness and atomically abort fatal startup dispatches :P1:
:PROPERTIES:
:DEPENDS_ON: TASK-KWSTJ
:ID: TASK-TJKFC
:PRIORITY: P0
:END:

Problem: dispatch can create a worktree and enter the daemon before provider or harness authentication is known to be usable. A fatal startup DriverError can then leave an open dispatch record and resources that block later work. Add a bounded non-interactive preflight at the provider-local driver boundary after configuration is resolved but before lease, session, or manager.dispatch_started ownership is committed. The default capability must be explicit unsupported, not false success; supported adapters return ready or a typed fatal reason. Claude and ACP implementations must test the same execution context used by the worker and must never prompt. A definitive preflight failure returns a normal rejected dispatch so the existing CLI rollback restores lifecycle state and removes the newly created worktree and branch. Also make dispatch attempt creation atomic with the earliest driver events: a fatal event during the startup gate must record an aborted attempt, close any open dispatch, release the lease, and safely clean only attempt-owned resources. Once startup has been accepted and meaningful work has occurred, later failures retain normal failed-run history and inspection artifacts. Acceptance: fake-provider tests prove auth failure creates no lease, session, or open dispatch and CLI rollback removes attempt resources; a race test emits fatal before dispatch bookkeeping and proves no orphan; supported-preflight success reaches running; unsupported preflight preserves current drivers; a post-start fatal remains a failed historical run and does not erase work. Provider-specific parsing stays inside the driver adapter; manager and supervisor consume only typed readiness/startup outcomes.

PARTIAL IMPLEMENTATION (2026-07-25, manager-implementer). The startup gate
exists and is wired; the concrete probes and the atomic-abort half do not.

LANDED
- =Preflight= on =WorkerDriver=: three-valued Ready / Fatal{reason} /
  Unsupported, defaulting to Unsupported. The default is the point: a driver
  that never implemented a probe must not be able to report readiness it never
  checked. Only Fatal rejects a dispatch, so an inconclusive probe leaves the
  pre-existing behaviour intact.
- Called in =spawn_worker_run= immediately after =driver.validate=, which is the
  last point at which rejecting is free. Verified by reading the ordering rather
  than assuming it: the session path, babysitter, lease and acquire all come
  after, and =record_dispatch_started= runs after =spawn_worker_run= returns.
- A Fatal returns =400 Bad Request=. Verified this routes correctly:
  =dispatch_failure_needs_daemon_cleanup= treats any "daemon returned ..."
  message as an unambiguous rejection, so the CLI runs
  =cleanup_created_resources= (worktree + branch + artifact paths) and
  =restore_task_lifecycle_stages=. Pinned by a test using the actual
  preflight message shape, because routing it as ambiguous would leave behind
  exactly the litter the 2026-07-25 dispatch left.
- The probe receives placement (worktree, task, run kind, project) and an empty
  =RuntimeIdentity=. A probe must not depend on a run id it exists to avoid
  creating.
- Driver-level tests: the default is Unsupported and does not reject; only Fatal
  rejects; a harness answering "Please run /login" is classified Fatal rather
  than surfaced into a worker that would wait on a prompt nobody will answer.

NOT LANDED, and this matters for reading the task's status honestly
1. No adapter implements =preflight= yet, so nothing changes behaviourally
   today. The gate is structural.
2. The claude probe has an unresolved design question worth deciding before
   writing it. Auth failure is observable in ~39 ms because it happens before
   any model call, but a probe that exercises "the same execution context the
   worker will use" and succeeds will have made a real (small) model call on
   every dispatch. Cheaper probes exist and are all weaker: =claude auth status=
   is exactly the check measured to give a false pass (loggedIn: true while the
   dispatch argv answered "Not logged in"). Pick deliberately.
3. The atomic-abort half is untouched: a fatal driver event *after* startup has
   been accepted still leaves an open dispatch record, and the race test the
   task asks for (fatal emitted before dispatch bookkeeping completes) does not
   exist.
4. Consequently the acceptance clause "fake-provider tests prove auth failure
   creates no lease, session, or open dispatch and CLI rollback removes attempt
   resources" is only half covered: the reject-before-commit ordering is proven
   by construction and by the routing test, but there is no end-to-end test
   driving a fake provider through the daemon and asserting the absence of a
   lease and session.

PROBES LANDED (2026-07-25, manager-implementer). All three installed harnesses
now rule on their own credentials before a dispatch commits anything. The
atomic-abort half is still open; see NOT LANDED below.

The design question this task flagged is decided, and the answer is the opposite
of what the original evidence implied. Both halves were measured, not reasoned:

1. What a truthful probe costs. Making the harness itself rule on a credential
   means submitting a turn. Measured on claude 2.1.220, a ONE-CHARACTER prompt
   cost $0.0994 and 24.5k tokens, because the request writes the system prompt,
   tools and skills to cache before any answer returns. Cancelling early does
   not refund it: the failure verdict lands at 0.390 s and the outbound request
   at 0.326 s, so no deadline separates them. A check that silently bills a
   tenth of a dollar per dispatch is not a check worth having. Rejected.

2. Why `claude auth status` was actually wrong. The task recorded it as an
   ambient self-report that lied. It is not. Measured: `auth status` reports
   ONLY the claude.ai/keychain login and is blind to ANTHROPIC_API_KEY, while
   the failing dispatch carried `--bare`, whose contract is that OAuth and the
   keychain are never read. The two were answering about DIFFERENT CREDENTIALS,
   so they could disagree without either being wrong.

So the rule on `WorkerDriver::preflight` is rewritten. It was "exercise the
worker's exact argv"; it is now "resolve the same credential mode the worker
will resolve, then check the credential THAT MODE consumes". Once the mode is
resolved first, `auth status` is exactly the right question for native login
and exactly the wrong one for `--bare`. Cost: $0 and 0.28 s.

The guarantee behind it is structural, not documentary: `resolve_credentials`
was extracted out of `compose_request`, so the probe and the launch cannot
resolve different modes. A probe that reasoned its way to a mode independently
could confidently interrogate a credential the worker was never going to use,
which is precisely the failure above.

WHAT EACH ADAPTER NOW DOES
- claude: native login -> `claude auth status`, reads the `loggedIn` boolean.
  `--bare` -> the key it will present; an empty one is fatal, a present one is
  reported as unchecked (only the API can accept a key, and asking is the
  billed turn above).
- cursor-agent: a configured `api_key_env` is judged on the key; otherwise
  `cursor-agent status`.
- codex: `codex login status`.
- everything else: unchanged default `Unsupported`.

All five mode drivers delegate through one `preflight_via_adapter`, since
readiness is the harness's property and not the transport's.

VERIFIED LIVE, BOTH DIRECTIONS
- Healthy machine: Ready from claude, cursor-agent and codex.
- Credential-less machine (HOME/CODEX_HOME pointed at an empty directory, so no
  operator was logged out): Fatal from all three, each naming its remedy.

TWO BUGS THE LIVE TEST CAUGHT THAT UNIT TESTS COULD NOT
Both are recorded in gotchas.org, because both are the kind of thing a
reasonable person assumes.
1. codex writes its status answer to STDERR and leaves stdout empty. Reading
   stdout classified a logged-in codex as "no probe".
2. `claude auth status` EXITS 1 when logged out. Gating the verdict on a zero
   exit turned the one answer this mechanism exists to catch into
   "inconclusive" - the same defect this task is about, reproduced inside its
   own fix. Exit status is now ignored entirely; what decides whether a verdict
   was reached is whether the harness said something recognisable.
This is why `installed_harnesses_answer_their_own_readiness_probe` asserts
against real binaries: a unit test supplies the answer it then classifies, so it
can never find either.

DELIBERATE ASYMMETRIES, so a later reader does not "fix" them
- cursor and codex answer in prose, so only an exactly-observed logged-out
  phrase may reject. Anything unrecognised is `Unsupported`. A harness that
  rewords its message costs us the safeguard, never a working dispatch - the
  only direction worth being wrong in.
- An empty endpoint does NOT skip the probe. acp-stdio upgrades that config into
  a real subprocess whenever the binary is present, so the credential is just as
  real; skipping would have exempted the most common dispatch shape there is.
- The probe does not call `claude_available()`. That is a blocking
  `claude --version` on the async path - the TASK-KKGKM hazard - and is
  unnecessary, because a missing binary makes the status command unspawnable,
  which already reads as inconclusive.
- Fatal reasons are constants, never echoes of harness output. `auth status`
  answers with the operator's email, org and plan, and these reasons reach tx
  records and task evidence.

STILL NOT LANDED
- The atomic-abort half is untouched. A fatal driver event AFTER startup has
  been accepted still leaves an open dispatch record, and the race test this
  task asks for (fatal emitted before dispatch bookkeeping completes) does not
  exist.
- No end-to-end test drives a fake provider through the daemon and asserts the
  absence of a lease and session. The reject-before-commit ordering is proven by
  construction and by the routing test; the absence assertion is not written.
- hermes has no probe. Its auth surface was not measured, and inventing one
  would mean guessing a logged-out string - the one guess that can block a
  dispatch rather than merely fail to save one.

Dispatch `tx-20260725-orgasmic-2741`, run `run-20260725T073841-ef292c73d0e344edb7d475148a3f0c56`, worker `reviewer-claude-acp-stdio`, mode `acp-stdio`, harness `claude`. From the run's own session JSONL:

- 07:38:45.158 driver_event text_chunk, stream system: "claude status: requesting"
- 07:38:45.162 driver_event text_chunk, stream assistant: "Not logged in - Please run /login"

The run was fatally unusable 1.2 seconds after acquire, for a reason knowable before any resource was committed. CORRECTION (2026-07-25, after root-cause analysis): the harness WAS authenticated. `claude auth status` reports `loggedIn: true, authMethod: claude.ai, subscriptionType: max`. Orgasmic's own argv caused the failure — the claude adapter hardcodes `--bare`, whose contract is that OAuth and keychain are never read (see TASK-Z8WEJ). Do not read this evidence as an operator credential problem. What the failure left behind:

- an open dispatch record, still listed by `manager dispatch-status` 70 minutes later
- a 15 MB worktree at `.orgasmic/tmp/dispatch/task-kwstj-review/`
- a branch `task-kwstj-review`
- zero-byte `last.txt` and `stdout.log`
- the harness process (pid 52741, `claude --bare -p --input-format stream-json ...`) still alive 70 minutes after emitting a fatal error, reported by dispatch-status as `[pid-alive] [run-gone]` — supervisor had dropped the run while the process persisted

The manager treated `[pid-alive]` as "review in progress" and reported it as running to the operator. A fatal startup error that leaves a live process is worse than a crash: it is indistinguishable from work.

Second finding, and the reason this is not merely cosmetic: cleanup was blocked by the very defect TASK-KWSTJ fixes. `orgasmic manager dispatch-close --status aborted` on the installed 0.0.14 CLI fails after exactly 10.03 s with "daemon request failed ... /api/runs — is the daemon reachable?". The pre-fix CLI takes the legacy liveness fence through `GET /api/runs`, which on this board needs 35.2 s to first byte, against a 10 s client deadline. So a dispatch that failed at startup cannot be closed by the documented verb until the bounded-inventory fix ships. The two defects compound: startup leaves the mess, and enumeration prevents cleaning it.

Preflight design note this supports, sharpened by the root cause: the check must exercise the exact argv the worker will run, not merely the harness's ambient credential state. Measured here: `claude auth status` returns `loggedIn: true` while the very same binary invoked with the dispatch's own flags returns "Not logged in" in 39 ms. A preflight that asked the harness whether it was logged in would have passed and still produced this failure. The 39 ms cost of the real probe is also the argument for doing it: it is cheaper than the worktree it prevents.

Also relevant to the preflight's non-interactive requirement: the harness's own answer here was "Please run /login", i.e. an instruction to start an interactive flow. A preflight must classify that as a definitive fatal reason and reject the dispatch, never surface it into a worker that then waits on a prompt nobody will answer.
