** The second finding, which may be the more useful one
=run-tests.sh= called the third run =host: calm=. Its host word is derived from
the syspolicyd CPU-seconds-per-wall-second rate (TASK-STWVB.1.1), which was
=0.0000= — correctly, because syspolicyd was idle. *The classifier is blind to
ordinary CPU load*, and ordinary CPU load is exactly what makes these three fail.
Load is deliberately =corroborating display only= per the STWVB chain, and that
was the right call for the syspolicyd question it was solving — but it means a
load-induced red is reported as a calm-host REAL failure, which is the strongest
possible verdict, on the weakest evidence the script has.

Weigh carefully before changing it: the STWVB chain spent a whole round
establishing that an ABSOLUTE load threshold was wrong. The answer is probably
not a load threshold; it may be that a client-timeout failure signature deserves
its own classification arm, since =daemon request timed out after 10s= is a
self-describing host-state error the classifier could read directly.

** Direction — decide, then implement
1. Establish whether the 10s budget is simply too tight for a
   =release=-then-cleanup sequence under parallel test load, or whether something
   on the release path is slower than it should be. Measure it; do not reason
   about it.
2. If the budget is the problem, changing it is a PRODUCTION decision, not a test
   one — the same 10s applies to an operator on a loaded machine. Whatever is
   chosen must apply to both, or be explicitly justified as test-only.
3. Consider the classification arm above, so a client timeout never again reports
   as a calm-host REAL failure.

*A SECOND FINDING, AND THE MORE INTERESTING ONE — THE HOST VERDICT IS BLIND TO
THIS FAILURE MODE.* The same VERDICT block that reported these two failures also
reported:

: host : calm (threshold syspolicyd_rate>=1.50; load corroborating only)
: rate 0.1123

*=run-tests.sh= called the host CALM while the load average at the moment of
failure was 13.64 and 15.03.* That is not a bug in the wrapper — TASK-STWVB
round 3 deliberately derived the host word from the syspolicyd RATE and demoted
load to "corroborating only", and the round-6 review upheld that reasoning
explicitly: =HOST_DEGRADED= is measured from syspolicyd CPU CONTENTION, which is
not evidence of an unrelated failure mode.

But it means *the one word an operator reads to decide whether a red is
attributable is derived from a signal that cannot see a 10s HTTP budget
expiring under scheduler pressure.* The 08-07 handoff said these tests
recurring "on a calm host" would be a real finding rather than a registry
excuse. They recurred, the host word said calm, and the word was measuring
something else entirely. *Whatever fixes the 10s budget should also decide
whether a load-sensitive timeout deserves its own attributability signal, rather
than inheriting a syspolicyd-derived one.*

NOT REGISTERED AS A FLAKE. The registry's own guard says a green-alone failure
is REAL until OWNED, and this task owns it — but registering these two would
make the gate report green-modulo on a real product weakness that is now
three-times measured. The decision to register belongs with the fix, not ahead
of it.
