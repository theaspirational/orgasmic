** Description
From the TASK-YN5FJ manager review, section "Manager review and verdict".
CONFIRMED against production, not reasoned.

The default-branch gate requires a =reviewer.done= carrying a non-empty
=VERDICT=. =VERDICT= has NO FLAG — it is settable only through the generic
=--property VERDICT=...=, and it was previously optional, read by
=reviewer_done_stage= only to choose the task's next stage (=.unwrap_or(false)=).

So the refusal text — "Dispatch and close a reviewer for that reported
generation, or re-run with --no-review-required --reason <why>" — names a first
branch that DOES NOT WORK. Follow it exactly and you are refused again with the
same message.

*Production evidence.* =tx-20260803-orgasmic-4401=, the =reviewer.done= this
manager wrote for TASK-XCJYC, carries =REASON=, =REVIEWED_DIFF=, =CLOSED_TX=,
=MODEL=, =EFFORT= and lifecycle properties and NO =VERDICT=. It is an ordinary,
correctly-formed reviewer close that the new gate rejects. Every historical
reviewer close is the same shape.

** Fix
1. Add a first-class =--verdict= flag to =dispatch-close= for reviewer closes,
   so the value the gate depends on is a documented part of the surface rather
   than an incantation through =--property=. Keep accepting the existing
   =--property VERDICT= spelling so nothing already written breaks.
2. Consider a typed value set (approve / approve-with-follow-ups / reject)
   rather than free text. This also answers the implementer's own declared
   residual risk that any non-empty verdict — including a negative one —
   currently satisfies "a verdict exists". Decide deliberately whether a REJECT
   should unlock a default-branch merge; there is a real argument either way
   (a REJECT the manager then resolved is exactly what happened on TASK-XCJYC),
   so state the reasoning rather than picking silently.
3. Name the verdict requirement IN the refusal text, so the remedy is
   self-contained.

** Ordering
Land this BEFORE any runtime reinstall. The gate is not live until the runtime
is rebuilt, so there is no live breakage today — but the first reinstall after
TASK-YN5FJ without this fix hands the operator a refusal they cannot clear
except by =--no-review-required=, which defeats the feature.

** Acceptance
- A reviewer close can record its verdict through a documented flag.
- Following the refusal's stated remedy actually clears the refusal — pin this
  with a test that walks the full loop: refuse, follow the remedy verbatim,
  succeed.
- Existing =--property VERDICT= closes still work.

** Description
Reviewer REJECT on TASK-YN5FJ.1 (merged =bb2fb24=), from =reviewer-codex-tmux=
(codex / gpt-5.6-sol / high), tx =tx-20260805-orgasmic-4438=. BLOCK SHIP, one
finding, both halves verified by the manager against the code rather than taken
on the reviewer word.

This is the SAME defect class the parent task existed to fix, one level down: a
remedy that cannot be followed as printed.

*Half one — the template is not executable.* =crates/orgasmic-cli/src/manager.rs:955=
prints the remedy as =`manager dispatch-close --task <task> --started-tx
<reviewer-tx> --status done --verdict <...>`=. There is no =orgasmic= in it.
Pasting that into a shell does not invoke this CLI.

*Half two — the test cannot catch that, and says otherwise.* =crates/orgasmic-cli/tests/dispatch.rs:1721=
carries the comment "Follow the printed remedy VERBATIM" and then builds a
separate argv array at =:1758=, with =run_orgasmic= supplying the binary
independently (=:425-432=, =:484-494=). So the loop test passes while the printed
message is uncopyable, and nothing detects future drift between the message and
the hand-built command. A comment claiming verbatim adherence over code that does
not is worse than no claim.

The parent acceptance criterion — "following the refusal stated remedy actually
clears the refusal" — is therefore NOT met, which is why this is a fix round and
not a polish note.

** Fix
1. Print a complete executable template beginning with =orgasmic manager
   dispatch-close=, with the task id(s) already substituted (the refusal knows
   them). =<reviewer-tx>= must stay a placeholder — the reviewer has not been
   dispatched yet at refusal time — so document precisely which tokens are
   placeholders and keep that set as small as the information allows.
2. Rewrite the acceptance test to EXTRACT the backticked command from the actual
   refusal string, substitute only the documented placeholders, tokenize, and
   execute the derived argv. Delete the hand-built close. Keep the existing
   semantic assertions so the extracted remedy must both persist =VERDICT= and
   clear the original refusal.
3. Do not weaken the claim to match the code — the test should earn the word
   verbatim, not drop it.

** Ordering
Same ordering constraint the parent carried: land BEFORE any runtime reinstall.

** Acceptance
- The refusal prints a command a human can paste, executable name included.
- The acceptance test derives the command it runs FROM the refusal text; a
  deliberate edit to the message that breaks the command fails the test.
- Existing coverage stays green, including the =--property VERDICT== compat
  tests and both existing injection proofs, which must still replay.
