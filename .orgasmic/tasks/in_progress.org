** The headline: a demonstrated FALSE GREEN, and it is the worst category yet
Every prior round of this chain produced a false RED or a missing verdict. This
one is a *false GREEN on the live path*, and CI gates on the exit code alone.

=FAIL_COUNT= counts *LISTED* per-test failures. A test binary that aborts or
segfaults contributes ZERO listed failures — libtest dies with the process, so
there is no =---- name ----= block. So a run with BOTH (a) a crashed binary and
(b) any classified failure has =FAIL_COUNT > 0=, the crash arm is skipped, and
the run falls through to =GREEN modulo N registered flake(s)= at *exit 0*.

MANAGER-VERIFIED, and it is worse than the guard alone: =BUILD_BROKE= matches
only =^error: could not compile= and =^error\[E[0-9]+\]= (=:724=), so it does NOT
catch =error: N targets failed=; and =grep -c= for =signal:= /
=didn't exit successfully= / =targets failed= across the whole script returns
*ZERO*. There is no crash detection anywhere.

=FAIL_COUNT -eq 0= is exactly the condition that FAILS on this board whenever a
registered flake fires — and this chain exists because registered flakes fire.
Round 3 traded a live-dead =EXIT_INCONCLUSIVE= for a working one; round 4 traded
a live-dead crash detector back. Round 3's demonstrations missed the flake path;
round 4's missed the crash-plus-flake path.

*CLASSIFICATION: PRE-EXISTING, NOT A REGRESSION.* At =4788e1f= the arm sat BELOW
=FAIL_COUNT > 0= and was equally unreachable. Round 3's reorder plus its dropped
guard accidentally closed it; restoring the guard reopened it. The reviewer filed
it BLOCK SHIP anyway because it is a demonstrated false green on the live path,
and the manager concurs.

** R-1 — HIGH — BLOCK SHIP — a crashed binary is swallowed whenever any failure classifies
=scripts/run-tests.sh:1078=.

REVIEWER REPRODUCTION WITH VERBATIM CARGO OUTPUT. A two-target crate — one
=assert!= failure whose panic matches a registry signature, one
=std::process::abort()= — real =cargo test --no-fail-fast=, log replayed through
the live path:

#+begin_example
  failures : 1
  host     : calm (threshold syspolicyd_rate>=1.50; load corroborating only)
FLAKE (1) — green in isolation, registered signature matched:
verdict: GREEN modulo 1 registered flake(s). No unexplained red.      exit 0
#+end_example

What the SAME log says, verbatim, from cargo:

#+begin_example
error: test failed, to rerun pass `--bin crashdemo`
Caused by:
  process didn't exit successfully: `.../crashdemo-...` (signal: 6, SIGABRT: process abort signal)
error: 2 targets failed:
    `--lib`
    `--bin crashdemo`
#+end_example

WHY THIS REACHES CI: =ci.yml:197= runs the live path and gates on the exit code
alone. *Exit 0 merges.* And the verdict block a human might read does not mention
the crash AT ALL — not in =failures :=, not in any REAL/LOAD/FLAKE section, not
in the verdict line.

*FIX DIRECTION — detect the crash FROM THE LOG*, independent of both
=SUITE_EXIT= and =FAIL_COUNT=:
- =error: test failed, to rerun pass `<target>`= is printed once per failing
  target. Diff that target set against the set of binaries that produced a parsed
  failure block. A target in the first set and not the second is an UNACCOUNTED
  CRASH.
- Corroborate with =process didn't exit successfully:= / =(signal: N, SIG...)=,
  which is crash-specific — an ordinary red does not emit it.
- Report it as its own section (=CRASHED (n)=) and its own RED arm, placed ABOVE
  =FAIL_COUNT > 0= and ABOVE =HOST_DEGRADED=. A crashed binary is a code fact
  whatever else the run found — the same argument F4 made for =REAL_COUNT=.

Pin it with a live-path case whose stub cargo emits *a failure list AND an
unaccounted crashed target* and exits 101 -> RED, exit 1. No such case exists
today, and its absence is why R-1 shipped.

** R-2 — HIGH — BLOCK SHIP — "same verdict for the same log" is unmet
=scripts/run-tests.sh:1078= (reads =SUITE_EXIT=) vs =:604= (=SUITE_EXIT="?"=).

Byte-identical log, both modes:
| mode | verdict | exit |
| live | =RED — cargo exited 101 with no per-test failure list.= | 1 |
| =--classify= | =GREEN — no failures.= | 0 |

The log the human is holding contains =error: test failed, to rerun pass ...=,
and =--classify= prints =GREEN — no failures= over it.

*RULING ON "is =--classify= inherently a weaker mode?" — NO, not on this point.*
The information exists at write time and is simply not written down. That is the
IDENTICAL situation this chain already resolved once: STWVB.1's F3 found
=--classify= sampling host state at reclassify time, and the answer was not
"accept a weaker mode", it was =write_host_stamp=. The suite exit deserves the
same treatment, by the same mechanism.

*Fix:* append =# orgasmic-suite-exit: <n>= alongside the existing
=# orgasmic-host-state:= stamp; under =--classify=, read it and use it instead of
=?=, falling back to =?= only when the stamp is absent (pre-stamp logs). R-1's
log-derived detector covers those legacy logs anyway.

** R-4 — LOW — design note, NO CHANGE REQUESTED — the floor leaves scoped runs unjudged
=scripts/run-tests.sh:111=. The floor itself is RIGHT. But the reviewer measured
the everyday warm scoped invocation at *=wall_s=3=, not the 11 the round-4 report
recorded* (that was a colder run). So the host machinery is inert for scoped runs
ALWAYS, not marginally.

The reviewer traced what =unknown= does to the VERDICT and it is sound:
LOAD-SENSITIVE is correctly suppressed (=classify_one:811= requires
=HOST_DEGRADED -eq 1=, so an unregistered iso-green failure stays REAL at exit 1
— unknown does not mint an excuse); the exit code for an otherwise-green short
run is unchanged at 0. The accepted cost is that INCONCLUSIVE is unreachable
below the floor, which is M-3's own stated fix direction, the reason is named in
the output, and CI's workspace run is never near the floor.

*If host judgment on scoped runs is ever wanted, widen the MEASUREMENT window —
sample syspolicyd over a fixed >=10s window bracketing the run — do NOT lower the
floor.* Lowering it walks straight back into M-3.
