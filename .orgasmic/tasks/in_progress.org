* IN_PROGRESS TASK-9P810 Install the runtime to a stable, identity-checked path so TCC grants survive upgrades :install:runtime:macos:
:PROPERTIES:
:ID: TASK-9P810
:PRIORITY: P0
:END:

Problem: every runtime version costs the operator a macOS permission approval. Measured 2026-07-25 on one machine: 16 distinct runtime paths have been granted, 37 TCC rows in total, since 2026-06-18 — 0.0.1, 0.99.601, 0.0.3, 0.0.6, 0.0.7, three separate 0.0.8 nightlies, and so on through 0.0.13 and 0.0.14. Each one is a System Settings dialog the operator had to find and click, and a daemon that does not work until they do.

Cause: TCC keys a grant to the resolved executable path. The install layout is `~/.orgasmic/runtimes/<version>/bin/orgasmic`, reached through `~/.orgasmic/bin/orgasmic -> ../current/bin/orgasmic -> runtimes/<version>/...`. TCC resolves the symlinks, so it records the versioned path and every release is a new client with no permissions.

The signature is not the problem, and that is the useful part. The designated requirement is identity-based, not byte-based:

  identifier "com.theaspirational.orgasmic" and certificate root = H"a70531007cd128ff081597cb27bee0816613d86d"

A rebuilt binary re-signed with the same `orgasmic dev codesign` certificate satisfies that requirement, so content changes at a fixed path should inherit the grant. The two halves together are the fix: hold the path still and hold the identity still, and one approval covers every future version.

Work:
1. Make the executed binary a real file at a stable path (`~/.orgasmic/bin/orgasmic`) that install/update replaces in place. Keep versioned directories as rollback artifacts, but stop routing execution through a per-version path.
2. Replace with a fresh inode, never overwrite in place — an in-use codesigned binary overwritten in place is silently SIGKILLed on every later exec (existing gotchas entry).
3. Re-sign each installed binary with the pinned identity, so the designated requirement continues to match.
4. Refuse the install when the incoming binary's designated requirement differs from the incumbent's, naming both. This is the guard for item 3: a mis-signed binary should be a rejected install, not a daemon that boots without permissions. Observed 2026-07-25 — an ad-hoc `codesign --force --sign -` replaced the certificate root and cost the operator two separate GUI grants to recover.
5. Decide what `update` does about the LaunchAgent's `ProgramArguments`, which currently names `~/.orgasmic/bin/orgasmic`. If that becomes the real binary the plist may not need rewriting at all, which is its own win.
6. Migration: existing installs already have grants against versioned paths. Decide whether the first stable-path install needs one final approval and say so in the update output, rather than letting the operator discover a dead daemon.

Not in scope: Developer ID signing and notarization. That would anchor the requirement to Apple and a Team ID and is the right answer for distributing to other people, but the operator has deliberately deferred it; this task must work with the existing self-signed identity.

Acceptance:
- upgrading between two runtime versions requires no new permission approval
- a binary signed by a different identity is refused at install time with both requirements named
- the executed binary is replaced by fresh inode, never overwritten in place
- rollback to a prior version still works

IMPLEMENTATION EVIDENCE (2026-07-25, manager-implementer)
Implemented manager-direct. New =crates/orgasmic-cli/src/managed_binary.rs= owns
the single publish path; =update.rs=, =path_env.rs=, =doctor=, =daemon_service=
and =scripts/install.sh= all route through it.

Root cause confirmed, and it differs from the one assumed when this was filed.
The LaunchAgent already named =~/.orgasmic/bin/orgasmic=, so the plist was never
the problem: =env::current_exe()= on macOS returns the *invocation* path (probed
directly), and the kernel resolves the symlink at =exec=. =codesign -d= on the
link confirms it, printing =Executable=.../runtimes/0.0.14-darwin-aarch64/...=.
So item 5 resolves to "no plist rewrite needed" — but =service_spec= now names
the managed binary explicitly, because starting the daemon from a versioned path
would have pinned the service to a directory that retention later prunes.

Item 3 also resolves differently. A release bundle is already signed with the
pinned identity by =package-runtime.sh=, and the signature is embedded in the
Mach-O, so copying preserves it — verified: installing the real 0.0.14 binary
into a scratch home reproduces
=identifier "com.theaspirational.orgasmic" and certificate root = H"a705...d86d"=
byte for byte, and a second install of the same identity reports grants as
preserved. Re-signing at install time is therefore opt-in
(=$ORGASMIC_CODESIGN_IDENTITY=) and exists for contributor source builds, which
carry a linker signature that would otherwise be refused. Operators do not need
the signing key.

A real bug was caught before shipping. The first requirement parser missed
ad-hoc signatures, which =codesign= prints *commented out* (=# designated =>=),
reading them as "identity unknown" and waving them through — i.e. it would have
permitted the exact 2026-07-25 accident this guard exists to stop. Covered now
by a hermetic test that ad-hoc-signs a Mach-O and asserts the refusal end to
end, including that a refused install leaves the incumbent byte-identical.

=codesign= is invoked as =/usr/bin/codesign=, not through PATH: it decides
whether a binary keeps the operator's grants, so a shadowing binary must not be
able to answer for it.

Acceptance:
- no approval between versions — proven at the identity level: same requirement
  in and out, =preserves_grants()= true on re-install
- different identity refused with both requirements named — hermetic test
- fresh inode never in-place — inode compared across an upgrade
- rollback still works — restores from the previous runtime dir and bypasses the
  guard by design, since it restores what the operator already approved

Migration (item 6) is explicit rather than discovered: the first stable-path
install prints that the executed path changed and one final prompt is expected.
=orgasmic doctor= now reports a surviving symlink as a warning naming the cost,
and =doctor --fix= performs the migration instead of only describing it.

Not done here: nothing. Developer ID signing stays out of scope as filed.
