* IN_PROGRESS TASK-TJKFC Preflight harness readiness and atomically abort fatal startup dispatches :P1:
:PROPERTIES:
:DEPENDS_ON: TASK-KWSTJ
:ID: TASK-TJKFC
:PRIORITY: P0

Problem: dispatch can create a worktree and enter the daemon before provider or harness authentication is known to be usable. A fatal startup DriverError can then leave an open dispatch record and resources that block later work. Add a bounded non-interactive preflight at the provider-local driver boundary after configuration is resolved but before lease, session, or manager.dispatch_started ownership is committed. The default capability must be explicit unsupported, not false success; supported adapters return ready or a typed fatal reason. Claude and ACP implementations must test the same execution context used by the worker and must never prompt. A definitive preflight failure returns a normal rejected dispatch so the existing CLI rollback restores lifecycle state and removes the newly created worktree and branch. Also make dispatch attempt creation atomic with the earliest driver events: a fatal event during the startup gate must record an aborted attempt, close any open dispatch, release the lease, and safely clean only attempt-owned resources. Once startup has been accepted and meaningful work has occurred, later failures retain normal failed-run history and inspection artifacts. Acceptance: fake-provider tests prove auth failure creates no lease, session, or open dispatch and CLI rollback removes attempt resources; a race test emits fatal before dispatch bookkeeping and proves no orphan; supported-preflight success reaches running; unsupported preflight preserves current drivers; a post-start fatal remains a failed historical run and does not erase work. Provider-specific parsing stays inside the driver adapter; manager and supervisor consume only typed readiness/startup outcomes.

The design question this task flagged is decided, and the answer is the opposite
of what the original evidence implied. Both halves were measured, not reasoned:

1. What a truthful probe costs. Making the harness itself rule on a credential
   means submitting a turn. Measured on claude 2.1.220, a ONE-CHARACTER prompt
   cost $0.0994 and 24.5k tokens, because the request writes the system prompt,
   tools and skills to cache before any answer returns. Cancelling early does
   not refund it: the failure verdict lands at 0.390 s and the outbound request
   at 0.326 s, so no deadline separates them. A check that silently bills a
   tenth of a dollar per dispatch is not a check worth having. Rejected.

2. Why `claude auth status` was actually wrong. The task recorded it as an
   ambient self-report that lied. It is not. Measured: `auth status` reports
   ONLY the claude.ai/keychain login and is blind to ANTHROPIC_API_KEY, while
   the failing dispatch carried `--bare`, whose contract is that OAuth and the
   keychain are never read. The two were answering about DIFFERENT CREDENTIALS,
   so they could disagree without either being wrong.

So the rule on `WorkerDriver::preflight` is rewritten. It was "exercise the
worker's exact argv"; it is now "resolve the same credential mode the worker
will resolve, then check the credential THAT MODE consumes". Once the mode is
resolved first, `auth status` is exactly the right question for native login
and exactly the wrong one for `--bare`. Cost: $0 and 0.28 s.

The guarantee behind it is structural, not documentary: `resolve_credentials`
was extracted out of `compose_request`, so the probe and the launch cannot
resolve different modes. A probe that reasoned its way to a mode independently
could confidently interrogate a credential the worker was never going to use,
which is precisely the failure above.

WHAT EACH ADAPTER NOW DOES
- claude: native login -> `claude auth status`, reads the `loggedIn` boolean.
  `--bare` -> the key it will present; an empty one is fatal, a present one is
  reported as unchecked (only the API can accept a key, and asking is the
  billed turn above).
- cursor-agent: a configured `api_key_env` is judged on the key; otherwise
  `cursor-agent status`.
- codex: `codex login status`.
- everything else: unchanged default `Unsupported`.

All five mode drivers delegate through one `preflight_via_adapter`, since
readiness is the harness's property and not the transport's.

The incident's session JSONL was still on disk
(.orgasmic/tmp/sessions/dispatch-TASK-KWSTJ-reviewer-20260725T073841.jsonl) and
it settles what actually happened. Read in order:

  07:38:44.754  lifecycle acquire
  07:38:45.166  driver_error  fatal: true   "claude authentication_failed"
  07:38:45.175  driver_event  run_fail      "claude_result_error"
  ...           nothing at all, for seventy minutes
  08:49:23.536  driver_error  "claude exited with status exit status: 143"
  08:49:23.542  lifecycle release  outcome failed, finalized_by_worker false

The 143 is SIGTERM - the operator killing it. So the run did not end when it
failed; it ended when a human intervened, and everything in between was the
system waiting.

ROOT CAUSE, and it is one line. `terminal_event_releases_transport`
(supervisor.rs) allow-listed `tmux | tmux-tui | rmux`. On every other transport
a terminal event set `rec.terminal_outcome` and released nothing, leaving the
release to stream end. That is a bet that the harness will exit once it has
nothing left to do - sound on the success path, where exiting is part of
completing normally, and unsound on the failure path, because
`claude -p --input-format stream-json` holds stdin open waiting for a turn that
is never coming. The stream never ended, so the lease stayed held and the pid
stayed alive, which `dispatch-status` reported as `[pid-alive]`: a fatal startup
that leaves a live process is indistinguishable from work in progress.

FIX. A terminal event whose outcome is Failed now releases on every transport
(`terminal_failure_releases_any_transport`). Releasing reaps the process group -
`reap_process_group` sends TERM then KILL - so the failure now costs 0.4 s
instead of running until someone notices. Artifact draining is untouched:
`artifactor_lifecycle_in_flight` still defers through `pending_terminal_drain`.

The test is `a_declared_failure_releases_without_waiting_for_the_harness_to_exit`
and its shape is the point. Every pre-existing fatal-path test drops the driver
sender as soon as it has emitted, so stream end rescues it and none of them can
see this defect. The new stub keeps the sender in its *control* and drops it
only on release, which is what a real transport does - the reap is what closes
the channel. Its stream therefore never ends on its own, so the two-second
bound can only be met by the fix. Verified by mutation: with the new clause
disabled the test times out; restored, it passes in 0.14 s.

WHY THE DISPATCH RECORD IS STILL NOT AUTO-CLOSED
This task's acceptance says a fatal startup must "close any open dispatch". That
is the wrong instruction for the daemon to follow, and it took reading the CLI
to see why.

A dispatch is closed by `implementer.done` / `reviewer.done` /
`architector.done` / `manager.dispatch_aborted` (`scan_open_dispatches`);
`manager.dispatch_orphaned`, which the watcher does write, is not in that set.
So the obvious fix is to have the daemon write `dispatch_aborted` instead. But
closing is not a bookkeeping act: `cmd_dispatch_close` also runs
`cleanup_dispatch` - it removes the worktree, deletes the branch, and records
`CLEANUP_STATUS` on the closing tx so `close_tx_ran_cleanup` can tell that the
resources are gone. The daemon cannot do that half. It is a git operation on the
operator's repository.

A daemon-written close would therefore mark the dispatch closed with no
`CLEANUP_STATUS`, and `dispatch-status` would stop listing it - while the 15 MB
worktree and the branch stayed on disk with nothing left pointing at them. That
converts a visible orphan into an invisible one, which is strictly worse than
the state this task set out to fix.

So the open-until-acknowledged record is correct, and the thing that was
genuinely broken about it is already fixed elsewhere: `dispatch-close --status
aborted` used to die at 10.03 s against the pre-TASK-KWSTJ `/api/runs`, so the
documented remedy did not work. It does now.

If auto-close is still wanted, it is a different and larger piece of work -
the daemon would have to own worktree and branch removal - and it should be
argued on its own merits rather than inherited from this task's wording.

RACE TEST. `a_failure_declared_before_the_run_is_recorded_still_ends_the_run`
(supervisor.rs). A driver that declares its fatal synchronously inside
`acquire`, before returning the session, so the queue is guaranteed non-empty
when the supervisor inserts the run record. What protects this is an ordering,
not a lock: the record goes in before the drain task spawns, so no event can be
applied through `runs.get_mut` while the record is missing. Verified by mutation
- deferring the insert past the drain's first events produces no release at all.
Worth noting how it fails: not by timing out, but instantly, because a run
absent from the map reads as already released. That is the bug's own shape, an
orphan indistinguishable from a finished run.

END-TO-END ABSENCE. `an_unusable_credential_leaves_no_lease_no_session_and_no_run`
(tests/dispatch_preflight.rs), a real dispatch through the daemon with an empty
`ANTHROPIC_API_KEY`: 400, no session file, no lease, no run.created, and a
second dispatch still refused with 400 rather than 409. Its own test binary
because it mutates process-global env. Non-vacuity checked by running it with a
non-empty key - the dispatch then succeeds and acquires, so the absence really
is the preflight's doing.

MECHANISM CONFIRMED [2026-07-26]. It is macOS first-exec evaluation, and it is
measurable in three lines on a completely idle machine:

    fresh script #1 first exec: 0.18 s    second exec: 0.00 s
    fresh script #2 first exec: 0.15 s    second exec: 0.00 s
    fresh script #3 first exec: 0.16 s    second exec: 0.00 s

macOS charges roughly 150-180 ms of syspolicy/Gatekeeper evaluation the first
time a newly created executable is exec-ed, and nothing thereafter. Idle spawns
of an already-evaluated script are 0.00 s, which is why every one of these tests
passes alone.

That per-file cost is paid through a single system daemon, so concurrent first
execs queue. This suite writes many fresh executable fixtures into tempdirs and
execs them in parallel, which is how a 150 ms cost becomes the 3 s / 6 s / 63 s
spawns measured earlier. The failing test is not special; it is the one that
asserts a 30 s deadline against that queue.

So the chain is: fresh fixture -> per-file Gatekeeper evaluation -> serialized
daemon -> queue under suite parallelism -> a spawned helper that never reaches
its first instruction inside the deadline.

FIX DIRECTION

Stop paying the per-file cost per test. The fixture script should be created and
exec-ed ONCE per test binary and then reused, with the per-test variation moved
out of the file contents and into argv, so the second and subsequent uses hit
the warm path. Pre-warming a shared fixture is preferable to serializing the
tests, because it removes the cost rather than queueing it, and it also speeds up
every other spawn-based test in the crate.

Raising the deadline is not a fix. 63 s was observed; any constant is a guess.
