** Description

*Why the move works, in one line:* a TCC grant for a linker/ad-hoc-signed binary
is pinned to its CDHASH, so no path scheme can make a grant survive a rebuild.
The only durable answer is to stop needing a grant — put the worktree where
macOS does not guard.

=== Part 1 — move the managed worktree root
Change the DEFAULT managed worktree path from
=<project>/.orgasmic/tmp/dispatch/<task>/worktree= to:

: ~/.orgasmic/worktrees/<project-id>/<task-id>/

- Key on PROJECT ID, not display name — the id is what the CLI and daemon
  already use (=--project <id>=) and names can collide or change.
- MOVE ONLY THE SCRATCH. The dispatch RECORD — brief, =last.txt=, stdout log
  under =.orgasmic/tmp/dispatch/<task>/= — STAYS in the project. It is small,
  durable, written by the already-granted daemon, and leaving it keeps every
  existing brief-path reference in gotchas, briefs and memories valid.
- =orgasmic manager dispatch --worktree <PATH>= already exists as the override,
  so this changes the managed default only and adds no new surface.
- UNIVERSAL, not macOS-gated. Linux has no TCC, but the repo still stops
  accumulating multi-GB build trees and =git status= stays clean. One code path
  beats a platform branch.

Verified already (TASK-3X5AQ): a worktree there resolves its =.git= back into
the Documents-hosted repo, =status=/=log=/=remove= all work, the worktree's own
=.orgasmic/project.org= keeps project resolution working, it is on the same
filesystem, and the toolchain builds and runs from it.

Rejected alternative, for the record: =~/Library/Caches/orgasmic/...= is the
idiomatic macOS location and IS unguarded (zero TCC rows for Cache services) —
but macOS may PURGE it under disk pressure and destroy a worktree mid-dispatch.

=== Part 2 — pruning, which is NOT optional here
This is a REQUIREMENT OF THE MOVE, not a follow-up. Today a stray worktree sits
inside the repo where =git status=, =git worktree list= and the operator's own
eyes find it. After the move it is invisible, so the same leak becomes silent
multi-GB accumulation in =~/.orgasmic=. Shipping Part 1 alone trades visible
garbage for invisible garbage.

What exists today, measured 2026-08-05:
- =dispatch-close --worktree-remove= (DEFAULT TRUE) salvages uncommitted work to
  =refs/orgasmic/salvage/<sha>= and then removes WITHOUT =--force=, so git's
  clean check gates it.
- =dispatch-status --orphans-only= REPORTS dispatches whose run is gone.
- =dispatch-status --cleanup-failed= writes the orphan close tx and clears
  LEASES — not worktrees.

What does NOT exist: any call to =git worktree prune=, any age-based GC, any
boot-time or periodic sweep, any disk budget.

So three leaks survive close today, and all three become invisible after Part 1:
1. *A DIRTY worktree is never removed* — removal is deliberately non-forced.
2. *An ABANDONED dispatch* (worker died, manager never closed) keeps its
   worktree forever.
3. *Stale =.git/worktrees/<name>= metadata* accrues if a directory is removed
   out of band, which the move makes MORE likely because the new root is a
   plausible thing for an operator to =rm -rf=.

And Part 1 introduces a genuinely NEW failure mode to handle: a worktree whose
REPO no longer exists. Today worktrees die with the repo; afterwards they are
orphans pointing at a missing gitdir, and =git worktree remove= cannot help
because there is no git to run it from. Detect and handle this explicitly.

*Design constraints for the prune:*
- NEVER remove a worktree with an open dispatch or a live run. Reuse the
  existing health signals rather than inventing new ones.
- Salvage before removing, reusing the existing =refs/orgasmic/salvage/<sha>=
  path — do not add a second salvage mechanism.
- REPORT WHAT IT SKIPPED AND WHY, and how many bytes it reclaimed. Silent
  truncation reads as "cleaned everything" when it did not; this project has
  been bitten by that shape repeatedly.
- Prefer extending the existing orphan surface (=dispatch-status
  --cleanup-failed= and its health checks) over building a parallel reaper.
  Adding machinery where existing machinery can be made consistent is what took
  a sibling chain five fix rounds.
- Decide deliberately whether prune runs automatically (daemon boot and/or at
  close) or only as an explicit verb, and SAY WHY. An automatic reaper that
  deletes a worker's tree is a much sharper tool than a verb.

*** FINDING 1 (P0) — a symlinked managed root redirects =remove_dir_all= outside it
=scan_managed_worktrees= calls =std::fs::read_dir= on the project managed root
without first proving that root is a real directory. =read_dir= FOLLOWS a symlink.
Each CHILD is then checked with =symlink_metadata=, which is correct but too late:
the children enumerated are real directories inside whatever the root points at.

The direct-child fence in =remove_orphaned_worktree_dir= does not catch it, and
this is the part worth understanding rather than patching blind: =path= is built
as =<managed_root>/<child>= from =entry.path()=, so =path.parent()= is literally
=managed_root=. The comparison passes trivially — and =normalize_path=
canonicalizes BOTH sides through the same symlink, so it passes under either
reading. The final =symlink_metadata= sees a real directory, because it IS one; it
just belongs to the victim.

Net: if =~/.orgasmic/worktrees/<project-id>= is replaced by a symlink, a bare
=worktree-prune= recursively deletes real directories somewhere else. The root is
user-writable and this codebase runs AI workers with filesystem access, so
same-user replacement is not a hypothetical threat model.

*** FINDING 2 (P0) — prune bypasses the reservation this project already built
=RunSummary= deserializes =run_id= AND NOTHING ELSE, so the CLI cannot match a
live run to a worktree at all; =scan_managed_worktrees= makes the tx ledger the
sole ownership decision and uses live-run data only to decorate an
already-held record. Under the cleanup lock, prune re-reads only that ledger, then
removes.

So a live run whose open dispatch record is absent or torn classifies as
UNCLAIMED, and a recovery acquired in the classification-to-removal gap is not
fenced either. The local file lock is shared with CLI =dispatch-close=, but the
daemon acquire/recovery path does not take it.

THIS EXACT RACE IS ALREADY SOLVED, one path over. =Supervisor::reserve_dispatch_close=
(=crates/orgasmic-daemon/src/supervisor.rs= ~:3984) installs a cleanup reservation
and decides liveness UNDER THE SAME LOCK, and =admit_live_run= (~:543) reads that
fence last so no run can be admitted into a reserved worktree. Its own doc comment
says why a CLI-side audit cannot substitute: "a concurrent POST /runs/:origin/recover
acquires in *another process*, so no audit of await points in the CLI can close
that window — the authority has to sit where the supervisor lock already is."

Prune reproduces precisely the defect TASK-1T3FZ was filed to close. Do not
re-solve it in the CLI; route through the existing authority.

*** FINDING 3 (P1) — "repo gone" fails OPEN on I/O error, into the only unsalvaged delete
=worktree_repo_gone= treats ANY =read_to_string(.git)= error as evidence the
repository is gone: the =else= branch falls through to =(!dot_git.is_dir())=,
which is false for an unreadable regular file, yielding "no .git link". A
permission, ACL or transient I/O failure therefore selects =RepoGone= — the one
disposition that deliberately SKIPS SALVAGE and calls =remove_dir_all=.
=resolved.exists()= collapses errors the same way.

Classification also happens before the multi-GB size walk and before the cleanup
lock, and the under-lock re-check looks only at open dispatches, never at whether
the gitdir became reachable again. So an unreadable-then-restored repository can
lose dirty work with no salvage attempted.

** Fix
1. Anchor the managed root with no-follow semantics BEFORE scanning or deleting —
   refuse a symlinked root (and unsafe symlinked ancestors), or traverse and remove
   relative to a directory handle so a later rename cannot redirect the target. Add
   a tempdir regression in which the managed root points at a victim directory and
   every sentinel file survives.
2. Route each reclaim through the daemon existing cleanup reservation before
   salvage or removal, hold it across the whole mutation, release after. Match live
   runs by CANONICAL WORKTREE and project, which means =RunSummary= must carry
   =worktree= and =project_id=. Add tests for a live run with no open tx, and for a
   recovery acquired in the classification-to-removal gap.
3. Make repository classification FALLIBLE. Only a =NotFound= on the =.git= link or
   the admin directory may yield =RepoGone=; permission and other I/O errors become
   an explicit kept/skipped reason with that reason printed. Re-check repository
   state immediately under the guard, right before the unsalvageable direct delete.

** Description
Found by running into it, 2026-08-05, closing TASK-YN5FJ.1.1.

=close_lifecycle_transitions= sends an implementer close to =Done= when the task
carries =:FIX_SUBTASK: t=, and to =InReview= otherwise. That encodes one-round
fix semantics, which the manager-dispatch convention states deliberately.

The ACTIVE GOAL says something else, and it is not reconcilable by reading
harder: "Fix subtasks minted from reviewer findings count as tasks: a BLOCK SHIP
is not closed until its fix round lands and passes a fresh review."

So for a fix round minted from a BLOCK SHIP, the two rules point opposite ways.
What happens in practice: =dispatch-close= flips the task to =done=, and the
reviewer dispatch then refuses with

: task TASK-YN5FJ.1.1 is in lifecycle stage done; reviewer dispatch is allowed only from IN_REVIEW

The refusal is CORRECT — a done task should not accept a reviewer. The defect is
upstream: the close had no way to say "this fix round still owes a review", so the
manager has to flip =done= -> =in_review= by hand afterwards to get the review the
goal demands. A state the board cannot express is a state managers will fake.

** Why this matters beyond one flip
The manual flip records a =task.state_transitioned= that reads like a correction,
not like policy. Anyone auditing later sees a task moved backwards out of done
with no way to tell whether that was process or panic. And a manager who does NOT
know the goal clause will simply not review the fix round at all — the tooling
actively steers them away from it.

** Fix directions, not yet decided

**Confirmed — the new audit key is spoofable through the generic `--property` channel.**

`close_done_request` pushes caller properties (manager.rs:4718-4720) BEFORE it pushes the typed key (manager.rs:4726), and `parse_close_property` (:7183) accepts any uppercase key. Two concrete failures, both traced through the code path end to end:
