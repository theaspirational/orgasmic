* IN_PROGRESS TASK-KKGKM A project the daemon cannot read must not prevent it from binding :daemon:boot:resilience:
:PROPERTIES:
:ID: TASK-KKGKM
:PRIORITY: P0
:RELATES_TO: TASK-3R3EZ TASK-5P60H
:END:

Problem: when the daemon lacks filesystem permission for a registered project's path, it does not degrade — it dies. Reproduced 2026-07-25 after a runtime binary swap invalidated the macOS TCC grant for `~/Documents`:

- boot logged `starting pre-bind boot work`, then only `project scan timed out` warnings, then nothing
- the process sat at 0% CPU for minutes, never reaching `listening`
- `lsof` showed no project files open at all, only its own log, lock and binary — consistent with a permission-gated `open()` blocking in the kernel before a descriptor exists
- launchd `KeepAlive` kept spawning replacements, each refusing with `daemon instance lock is held, but the incumbent is not healthy`, so the machine churned without recovering
- the only operator-visible signal was a WARN line in a log file nobody was watching; `orgasmic status` simply hung

The daemon never bound, so every CLI verb, the UI, and the app were dead. A permission problem affecting a subset of projects took down the whole runtime.

The scan timeout works as designed — it logs "omitting project so daemon boot can continue" — but something after it blocks anyway. Find that, and make the whole class non-fatal.

Work:
1. Bind first, or at minimum guarantee that no per-project filesystem work can prevent binding. An operator must always be able to reach `status` and the UI to learn why the runtime is unhealthy.
2. Give a project whose files cannot be read a durable `unavailable` state with the reason, rather than retrying it into a hang. This is the same state TASK-3R3EZ introduces for missing project roots; reuse it rather than inventing a parallel one.
3. Report the condition where an operator will actually see it: `orgasmic status` and `orgasmic doctor` should name the affected projects and the exact remedy, not just emit a WARN into `daemon.out.log`.
4. Identify what blocks after the index scan completes. Boot reattach reads every session JSONL and is the leading suspect, but it was not confirmed — no fd was open at the time of sampling. Confirm before fixing.
5. Bound the launchd churn: repeated replacements refusing on the instance lock is noise that hides the real fault. Relates to TASK-5P60H's backoff work.
6. Regression: a registered project whose path is unreadable must still leave the daemon bound, reporting that project as unavailable.

Acceptance:
- an unreadable project cannot prevent the daemon from binding
- `status` and `doctor` name the affected project and the remedy
- the daemon stays useful for every other project
- a regression covers the unreadable-project case

ITEM 4 CONFIRMED (2026-07-25) — the task said confirm before fixing, so it was
reproduced rather than assumed.

Built an isolated throwaway ORGASMIC_HOME with two registered projects and
planted a FIFO where a session JSONL belongs. A FIFO with no writer blocks
inside open() before a descriptor exists, which is the same shape as the
permission-gated open in the original incident, and it is deterministic without
touching TCC.

Baseline with both projects healthy: bound in 44 ms.
With the blocking session file present:
- never reached listening; curl exit 7 (connection refused) indefinitely
- daemon.boot froze at {"phase": "reattaching runs", "seq": 7}, refreshed_at
  stuck at the boot instant while wall clock advanced 33 s
- 0% CPU, and lsof showed zero descriptors on the blocking file — exactly the
  "no fd was open when the process was sampled" observation from the incident,
  now explained: the process is blocked *inside* open(), before an fd exists
- stack sample:
    tokio::runtime::park::CachedParkThread::block_on
      orgasmic_daemon::api::reattach_live_runs_on_boot
        orgasmic_core::session::read_session_file
          std::fs::read_to_string

So the leading suspect was right, and there is a second finding the task did not
anticipate: the scan runs synchronously on the main thread inside block_on, so
it also starves the boot-progress refresh task. That is why the operator's only
liveness signal froze and `orgasmic status` simply hung — the heartbeat could
not advance even to report the phase it was stuck in.

FIX
1. Boot auto-reattach now runs after the listener is bound, in a spawned task.
   It is best-effort recovery; answering status is what an operator needs in
   order to diagnose anything at all.
2. Its file reads moved to spawn_blocking, so a wedged read costs one blocking
   thread instead of a runtime worker.
3. Session paths that are not regular files are refused by shape with a named
   warning, rather than discovered by hanging.

Verified end to end on the same isolated home: binds in ~50 ms with the
blocking file still present, /api/daemon/status answers in 1.6 ms, and the
warning names the offending path.

REGRESSION
crates/orgasmic-daemon/tests/boot_resilience.rs covers both the blocking-open
case and an unreadable project directory. Both were verified to fail against the
reverted fix, not merely to pass against the current one.

The first version of that test used tokio::time::timeout and hung forever
instead of failing: a synchronous block inside a future stalls the task
mid-poll, so the timer fires but the task can never be woken to observe it. It
now boots on an owned thread and waits on a channel deadline, and a reverted fix
reports itself cleanly at 20.02 s with a message stating the invariant.

NOT DONE HERE, and why:
- Item 2 (durable `unavailable` project state) is the state model TASK-3R3EZ
  introduces. The task says to reuse it rather than invent a parallel one, and
  3R3EZ has not landed, so inventing it here would be something 3R3EZ has to
  unpick.
- Item 3 (status/doctor naming the affected project) depends on that state
  existing to report.
- Item 5 (bounding launchd churn) belongs with TASK-5P60H's backoff work.
- Boot reattach still reads whole session files. That is cost, not a hang, now
  that it is off the critical path; filed as TASK-7QM8M with the correctness
  subtlety that blocks a naive swap to the bounded scanner.
