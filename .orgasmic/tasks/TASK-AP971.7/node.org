** Question
Per-node watcher granularity, apply-own-write projection (no full rescan on comment), and the derived cross-project activity feed. Kills the current full-reparse-per-mutation behaviour (index.rs load_project).
** Resolution
Grilled with owner 2026-08-22; four decisions. Facts: today the watcher (200ms debounce) schedules RefreshTarget::Project = reparse every task file + decisions + glossary + all of tx/; a write's HTTP response awaits a required refresh that includes its own tx id (the felt latency); artifacts already refresh as a separate lazy target; the writer has no link to the index.
1. Granularity: classify a watcher path → (project, collection, node id); reload only that node dir (node.org + journal.org); a tx/ file change re-collects that one file; views/ and tmp/ ignored.
2. Apply-own-write: after a successful structured write the writer parses the one node dir it wrote, applies it to the snapshot directly and publishes; the HTTP response returns then. The watcher's later event for the same file is a no-op on content equality. The required-refresh wait goes away. This is the root fix for comment latency and what makes the daemon's in-memory tx coherent.
3. Dispatch fold (deferred from .11): the daemon's dispatch-wait reads the now-coherent snapshot instead of re-reading disk; the CLI keeps the shared disk fold.
4. Full rescan survives only for boot, project add, orgasmic reindex, and unclassifiable events (dir renames).
The cross-project activity feed is a projection over tx/ + journals maintained by the same per-node / per-file slices (AP971.1 item 12, AP971.5).
