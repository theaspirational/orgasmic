Fix round for the TASK-WGXKD reviewer BLOCK SHIP (run-20260728T054156-cc1dc747e09c42898e9805950fac473f, merge 80dc4ec). Two HIGH findings, verbatim below.

** Finding 1 - HIGH correctness: the version-skew fallback is unreachable on the transport that motivated the task
manager.rs:1326-1412. The new client waits for /runs/:id/release to return and only then POSTs /tx when terminal_tx_id is absent. A pre-80dc4ec daemon ignores the unknown terminal_tx field, performs only release_with_finalization, and returns the old response shape. On acp-stdio that release calls reap_process_group (crates/orgasmic-drivers/src/modes/subprocess_stream_json.rs:231-242) and signals the finalize CLI's own setsid group BEFORE the response or the fallback can execute.

So new CLI + old daemon reproduces the original defect exactly: durable commit, durable report, released lease, no terminal tx. The claimed version-skew safety is false for precisely the transport WGXKD existed to fix. This is a realistic upgrade / source-build window - the two halves ship in one runtime bundle but a user can run a freshly built CLI against a daemon that has not been restarted yet.

FIX DIRECTION (reviewer): add a pre-release capability handshake for atomic release+terminal-tx support. If the daemon lacks it, FAIL BEFORE RELEASING and tell the operator to restart/upgrade the daemon - do not rely on a post-release client fallback, because on subprocess transports there is no 'post-release' for the client. Add a version-skew regression that reproduces pre-80dc4ec daemon behaviour on acp-stdio and asserts either atomic reporting or refusal with the lease still held.

Note the failure mode of the fix itself: refusing to release leaves the lease held, which is the state the ORIGINAL ordering comment was trying to avoid. That is acceptable here because a held lease is visible and rescuable, whereas the lost tx is the invisible fourth state. Say so explicitly in the code comment so the next reader does not 'fix' it back.

** Finding 2 - HIGH correctness: the detached finalization task is not owned by graceful shutdown
api.rs:6561-6565. The detached task's only JoinHandle lives in the request future. When the caller disconnects - which is the normal case this whole fix exists for - that handle is dropped and the task continues untracked.

Controlled restart drains only work already enqueued in the writer (api.rs:9630-9665), while daemon shutdown stops the writer immediately after axum returns (crates/orgasmic-daemon/src/lib.rs:637-650). If a restart lands while the detached task is still in driver teardown or has not yet reached append_tx_request, the drain barrier can pass first, the writer and runtime shut down, and the terminal tx is lost.

This is a normal graceful-restart race, DISTINCT from the already-accepted daemon-crash gap. It is live on the manager's own machine: every launchctl kickstart of orgasmic.daemon during a runtime rebuild is exactly this window.

The existing disconnect test does not cover it - it widens the gap to three seconds via release_terminal_tx_delay but then waits for the tx before shutting down.

FIX DIRECTION (reviewer): register release/finalization tasks in daemon-owned lifecycle state, e.g. a task tracker or JoinSet held outside request futures. Graceful restart/shutdown must stop accepting new releases, await those tasks, THEN place the writer drain barrier and shut the writer down. Add a test that disconnects during release_terminal_tx_delay, initiates controlled restart before the append, and proves the terminal tx is durable before the old daemon exits.
