* BACKLOG TASK-ARNA1 --property is silently dropped on an aborted dispatch-close
:PROPERTIES:
:ID: TASK-ARNA1
:PRIORITY: P3
:END:

** Description

=dispatch-close --status aborted --property FOO=bar= accepts the flag and
silently records nothing. =close_aborted_request= (=manager.rs:4794=) builds its
own extras and never receives =DispatchCloseArgs= or =args.properties= at all.

The =--property= help text (=manager.rs:271=) promises "additional =KEY=VALUE=
properties recorded on the close tx" without limiting that to =--status done=.
So the flag is accepted, documented as recording, and drops operator-supplied
audit metadata on the floor.

Pre-existing — TASK-4WKNX.1.1 did not introduce it. Found by the manager while
checking whether that round's forgery fix needed to cover the sibling function
(it does not: with no caller properties reaching the abort path there is no
forgery vector there), and independently confirmed by that round's reviewer,
which agreed it was right to keep out of a fix round and wrong to leave
undecided.

** Why it is worth a task rather than a shrug

This is the "a flag quietly does nothing" class the TASK-4WKNX author invoked
when they made =--fix-round-final= REFUSE on a non-fix task rather than no-op.
The argument was that a flag which silently does nothing is how an operator comes
to believe it did something. That argument applies here unchanged, and an abort
is exactly when a manager is most likely to be recording why.

** The decision this task owes

Either outcome is defensible; silence is not. Pick one deliberately:

1. *Support them.* Route aborted-close properties through the same manager-first
   finishing boundary =finish_close_tx_extras= gives the done path, so the abort
   tx inherits the construction guarantee rather than a second hand-rolled one.
   The reviewer's stated preference.
2. *Refuse them.* If abort metadata is not wanted, reject =--property= for
   =--status aborted= EARLY — before run release, worktree cleanup, tx append and
   lifecycle mutation — and say so in the help text.

If (1), note that the abort path's extras are currently built without any caller
input, so adding the sink is also adding the first forgery surface it has ever
had. It must go through the manager-first boundary, not around it.

** Acceptance

- =--property= on an aborted close either lands on the tx or is refused by name.
  Not accepted-and-dropped.
- Whichever is chosen, the =--property= help text says so.
- A production-path test proves it: =FOO=bar= is readable off the abort tx, or
  the close is refused with the worktree still present.
- If supported, forging a manager-owned key on an abort close is covered by the
  same construction guarantee as the done path.
