** The defect

`crates/orgasmic-daemon/src/api.rs:6849,7118-7141`.

`terminal_tx` is optional on the release payload. A `finalized_by_worker` release
carrying `terminal_tx: None` releases the run and returns success with
`terminal_tx_id: None`. An old CLI then still owes the separate `POST /tx`.

On acp-stdio the release reaps the old finalize process's own setsid group
**before** that POST is made, leaving a released run with no terminal tx. That is
exactly the loss TASK-WGXKD exists to prevent, arriving through the skew
direction the capability handshake does not cover.

** What is already correct — do not redo it

The other direction is fail-closed and proven: new CLI against an old daemon is
refused by the TASK-WGXKD.1 capability handshake, and its regression passed under
review. Only old CLI → new daemon is open.

** Fix, per the reviewer

Two shapes, choose and record which:

A. Fail closed before releasing when `finalized_by_worker: true` arrives with no
   `terminal_tx`, and tell the operator to upgrade or restart the CLI. Keeps the
   lease held rather than releasing into a known-lossy path.
B. Reconstruct the terminal tx server-side from what the daemon already knows,
   so the old CLI's missing POST stops mattering.

A is the safe one and matches the handshake's existing posture; B removes the
skew concern entirely but has to be correct about what the daemon can reconstruct
without the worker's own report.

** Acceptance

- An old-payload / new-daemon acp-stdio regression that proves either the lease
  stays held, or the terminal tx lands atomically with the release.
- The chosen shape is recorded, not just implemented.
- TASK-WGXKD's version-skew claim is restated to match what is actually true.
