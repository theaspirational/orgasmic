** 1. HIGH — destructive close has a recovery/acquire TOCTOU across a process
   boundary, and can still remove a live worker's worktree (in this diff)

`crates/orgasmic-cli/src/manager.rs:723-791`,
`crates/orgasmic-daemon/src/supervisor.rs:893-905,2763-2885`.

`dispatch-close` releases the recorded run (or takes its 404), optionally
snapshots `/runs` at lines 747-750, and only then runs
`cleanup_dispatch` / `git worktree remove` at line 791 — **in the CLI process**.
Nothing reserves the normalized worktree in daemon state across that gap.

A concurrent `POST /runs/:origin/recover` can acquire a replacement after the
release/snapshot and before local removal. `Supervisor::acquire_impl` blocks only
daemon-owned `cleanup_reservations`, and this close path installs none. The close
then removes the directory beneath a live replacement — precisely the TASK-8W30B
symptom this round was filed to prevent, and precisely the shape observed on
2026-07-28 when a leaked session still named
`.orgasmic/tmp/dispatch/task-C0XMR/worktree` after `dispatch-close` had removed
it (tx-20260728-orgasmic-3117).

Critically: **this is not cured by removing `await` points.** The competing
recovery runs in another request, in another process. An in-process check-then-act
audit will conclude the code is safe and be wrong.

The daemon already demonstrates the required authority boundary:
`prepare_dispatch_cleanup` installs a worktree reservation **under the supervisor
lock, before any await**, and retains it through filesystem mutation. Follow that.

The new integration tests (`crates/orgasmic-cli/tests/dispatch.rs:2887-3098`)
cover a replacement already live before close, and a static unassociated run
before the snapshot. Neither interleaves a recovery **between the liveness
decision and the removal**, which is the only ordering that reproduces this.

Required (reviewer direction 1): move destructive generation-close into a
daemon-owned operation, or extend the existing dispatch cleanup endpoint, that
installs a normalized-worktree cleanup reservation under the supervisor lock
before releasing or declaring absent any run, and holds it until worktree and
branch cleanup completes. Recovery and acquire must observe that reservation. Add
a deterministic hook test that starts recovery **after** the liveness decision and
**before** removal.

** 2. HIGH — a dispatch with no recorded RUN_ID fetches authoritative live state,
   discards it, and cleans up anyway (pre-existing)

`crates/orgasmic-cli/src/manager.rs:770-791`.

Real shape: `manager.dispatch_started` is durable, the daemon acquire succeeded,
and the CLI died before appending `run.created`. The open record then has
`run_id=None` while a worker is live in its worktree. The legacy branch calls
`fetch_live_runs` **only to prove the daemon is reachable**, ignores the returned
runs, and proceeds to `cleanup_dispatch`. The worker stays live while its worktree
is removed.

This violates the rule the brief stated explicitly: undetermined liveness must
refuse, not permit. It predates `edc68b4` so it would not independently block the
round — but finding 1 already does, and the fix is the same reservation path.

Required (reviewer direction 2): route no-`RUN_ID` records through the same
reservation and ownership check. Never treat daemon reachability as proof that an
unidentified live worker is absent.

** 3. LOW — the semantic dangerous-command guard reads only the first `git` token
   per segment (in this diff)

`crates/orgasmic-cli/tests/shipped_conventions.rs:168-200`.

`tokens.iter().position(...)` selects one `git`, classifies only what follows it,
and never continues to a later invocation. Compiled probes of the production
helper returned:

- `git worktree remove $WT --force` => 1 hit
- `run git status, then git worktree remove $WT --force` => 0 hits
- `git \` + continued `worktree remove $WT --force` => 0 hits
- `/usr/bin/git worktree remove $WT --force` => 0 hits

So any ordinary safe `git` mention before a forced removal makes the guard
vacuous. In the current convention the marked forced removal is **not** what keeps
the guard green — the later `git branch -D` after `&&` is what creates the hit.
The guard is passing by accident.

Required (reviewer direction 3): iterate every candidate `git` invocation in each
segment, or use a quote/continuation-aware tokenizer; normalize path-qualified
`git`; ignore structural continuation tokens. Add the three zero-hit probes above
as regressions.
