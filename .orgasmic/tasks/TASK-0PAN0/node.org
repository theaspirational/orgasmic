** Description

Two test gaps found by the TASK-RQ270.3.2.1 review, both NON-BLOCKING and neither
gating the excision. Filed together because they guard the same invariant.

** Gap 1 — the write-time rejection is untested at the API layer

=reject_unresolved_reference_token= is what stops a retired =arch_= id becoming
legal to ADD. There is *no test at any layer* asserting that rejection through a
real handler: =identity_lint.rs:632= tests the helper in isolation only, which is
exactly what the round's brief flagged as insufficient.

The reviewer verified the boundary holds today by code path — all four handlers
(=create_graph_heading=, =mutate_graph_heading=, =post_org_node_edit=,
=post_task_create=) call the guard under =if !req.force= at =api.rs:12971=,
=:13142=, =:13786=, =:14853=. But by code path is not by test.

*Wanted*: one api-layer test asserting a POST with =RELATES_TO=arch_GONE99= and
no =force= returns 400 through a real handler.

** Gap 2 — the invariant that actually holds the boundary is pinned by a comment

The real invariant is not "=unresolved_reference_tokens= is prefix-agnostic". It
is *"=arch_= never enters =graph.nodes=" — and that is true only because
=looks_like_structured_node_id= (=index.rs:1109=) KEEPS =arch_= in its list*, so a
=:PRODUCES: arch_X= target is not materialised as an artifact node.

Failure scenario, and it is a plausible one: after stage D someone drops =arch_=
from that list as cosmetic cleanup of a retired class. A task with
=:PRODUCES: arch_X= then materialises =arch_X= as an artifact node, it enters
=known_reference_ids=, and =reject_unresolved_reference_token= *silently stops
firing on all four write handlers*. Nothing fails. The guard just goes quiet.

*Wanted*: a test pinning =looks_like_structured_node_id("arch_X") == true=, with
the rationale as its docstring so the next reader sees why the entry is
load-bearing rather than vestigial.

*This one is carried into stage D's brief*, because stage D is what makes that
list entry the sole remaining protection.

** Gap 3 — the over-carve guard covers 3 of 5 id classes

=index.rs:2857= asserts unresolved =dec_=, =TASK-= and =term_= markers still
error. Verified real: widening the predicate to =contains('_')= or
=starts_with(\"arch\")= breaks it. It does not cover =ART-=
(=NodeIdClass::Artifact=). Low value; noted for completeness.
