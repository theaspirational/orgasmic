** Description
Every =tmux/cursor-agent= dispatch parks TWICE before it executes anything, each
time at 0% CPU with a full-screen TUI that is indistinguishable from a hung
transport:

1. =⚠ Workspace Trust Required= — "Do you trust the contents of this directory?"
   =[a] Trust this workspace= / =[q] Quit=. Cursor stores trust PER DIRECTORY, and
   since TASK-M47E5 every dispatch gets a fresh worktree path
   (=~/.orgasmic/worktrees/<project-id>/<task-stem>=), so this fires on EVERY
   dispatch and can never warm up.
2. =Not in allowlist: orgasmic= — "Run this command?" on the worker's first
   =orgasmic entry=, with =Run (once)= / =Add Shell(orgasmic) to allowlist= /
   =Run Everything= / =Skip=.

Observed live on 2026-08-06 dispatching TASK-G64ZH: both prompts hit, both were
cleared by hand (=tmux send-keys a=, then =BTab= for "Run Everything"), and the
worker then ran clean. UNATTENDED, EACH ONE IS A DEAD WORKER: the pane emits no
output, so =pane_activity= never fires, and the 600s stall release kills the run —
which then presents as =[run-gone]= and reads like an infrastructure failure. This
is the same misdiagnosis shape that cost three orphans to codex's quota prompt the
same day.

The knowledge already exists on this board and has never been actioned: recorded
as a "Harness note" on TASK-RQ270.4's evidence, and a HIGH review finding on
TASK-AFE5Q ("fresh Cursor TUI worktrees block at workspace trust with no startup
handler; add a startup-only trust transition") that was addressed for the
cursor-acp path and not for =tmux/cursor-agent=. A fact that lives only in a
closed task's evidence is invisible to the next manager.

** Why this is not just a gotcha entry
=cursor-agent= is currently the implementer harness of record on this host, because
codex is out of credits. So today every implementer dispatch needs a human at the
keyboard within ten minutes of launch, which silently removes the "unattended"
property that =orgasmic manager drivers= claims for the =tmux + cursor-agent= pair.

=== MEASURED 2026-08-07 — option 2's flag EXISTS, and this is now the cheapest fix
The direction list above says of option 2: "Pass whatever CLI flag or config
cursor-agent offers to pre-trust the workspace (investigate: a trust file under
the worktree, or a =--force=/=--yolo=-style flag). Cheapest if it exists; verify
it does before choosing it."

*VERIFIED THAT IT EXISTS.* Running =cursor-agent -p "..." --model ...= from an
untrusted directory prints, verbatim:

#+begin_example
⚠ Workspace Trust Required
  Cursor Agent can execute code and access files in this directory.
  Do you trust the contents of this directory?
    /private/tmp
  To proceed, you can either:
    • Run 'agent' interactively to decide
    • Pass --trust, --yolo, or -f if you trust this directory
#+end_example

So the harness DOCUMENTS three non-interactive escapes — =--trust=, =--yolo=,
=-f= — and orgasmic's =tmux/cursor-agent= driver passes none of them. Probed on
=cursor-agent 2026.08.04-aaa8809= (=--version= exit 0, so the binary is healthy).

*Prefer =--trust= over =--yolo= / =-f=* unless measurement shows otherwise:
=--trust= names the property we actually need (this directory is ours; we created
the worktree), while =--yolo= and =-f= are likely to relax more than workspace
trust and would silently widen a worker's authority. VERIFY what each actually
does before choosing — do not assume from the names.

This does NOT by itself close the second prompt (=Not in allowlist: orgasmic=,
the harness's own command allowlist). Check whether the same flag covers it; if
not, the task still needs a startup handler or a config entry for that one.

=== 2026-08-07 — two consecutive worker deaths on tmux/cursor-agent, cause undetermined
Recorded here because this task owns the "a parked prompt must be
DISTINGUISHABLE from a hung transport" acceptance item, and these two deaths are
exactly the ambiguity it names.

Both on TASK-QGWK7.1.1, back to back, same harness and mode:
- attempt 1 (=tx-20260806-orgasmic-5099=): ran ~20 min, produced 712 insertions
  across 8 files plus an authored verify artifact, then the tmux server vanished
  with no report. WIP preserved by the manager as =0273e9f=.
- attempt 2 (=tx-20260806-orgasmic-5106=): fresh worktree and branch, died
  producing NOTHING — empty worktree, 0-byte =last.txt= and =stdout.log=.

RULED OUT both times: machine reboot (=uptime= 4 days), host load (3.91), the
=syspolicyd= -> =tccd= -> WindowServer chain (no DiagnosticReports entry), and
harness health (=cursor-agent --version= exit 0 afterwards). =stdout.log= is
0 bytes, which is normal for tmux and carries no information — so on a tmux
dispatch there is NO artifact that survives to say why a worker died.

*That absence is itself the finding.* The acceptance item asks for a parked
prompt to be distinguishable from a hung transport; today neither is
distinguishable from a CRASH, because the pane is the only witness and it dies
with the session. Whatever lands for this task should leave something behind —
even a last-captured pane snapshot written on stall/exit would have answered this
in seconds.

** Direction — decide, then implement
Options in rough order of preference; the decision is part of the task:
1. A startup-only prompt handler for the =tmux/cursor-agent= driver that answers
   both known prompts by pattern before first execution — the same shape
   TASK-AFE5Q built for cursor-acp. Startup-only, so it cannot be mistaken for a
   general capture-and-respond channel.
2. Pass whatever CLI flag or config cursor-agent offers to pre-trust the workspace
   and pre-allow the harness (investigate: a trust file under the worktree, or a
   =--force=/=--yolo=-style flag). Cheapest if it exists; verify it does before
   choosing it.
3. If neither: make =orgasmic manager drivers= stop calling this pair
   =unattended=, and say in the dispatch output that a human must clear two
   prompts. Honest, but it is the fallback, not the goal.

Whichever lands, the third bullet of Acceptance is not optional: a parked
interactive prompt must be DISTINGUISHABLE from a hung transport in the manager's
own read, because that misdiagnosis has now cost workers twice in one day for two
different harnesses.

** Acceptance
- A =tmux/cursor-agent= implementer dispatch reaches its first tool call with no
  human at the keyboard, from a worktree path never seen before.
- A regression pins it: the trust and allowlist prompt strings are asserted
  somewhere that goes red if cursor-agent changes them, rather than being handled
  by a pattern nobody would notice rotting.
- The manager can tell a parked prompt from a dead transport WITHOUT attaching to
  the pane — a driver event, a dispatch-status line, or a documented one-command
  capture in the dispatch convention.
- =.orgasmic/gotchas.org= carries the two prompts and the manual clearing keys, so
  the fact stops living only in closed-task evidence.
** Evidence
*Third consecutive dispatch, and the manual clearing is racy* [2026-08-06]. Seen
on all three cursor-agent dispatches this session (TASK-G64ZH, TASK-G64ZH.1,
TASK-G64ZH.1.1), each into a fresh =~/.orgasmic/worktrees/<project-id>/<stem>=
path, confirming the per-directory-trust reading: it can never warm up.

The manual workaround is =tmux send-keys -t <session> a= for the trust prompt and
then =BTab= ("Run Everything") for the allowlist prompt — but THE TWO PROMPTS ARE
SEPARATED BY A VARIABLE DELAY, because the second only appears once the worker
tries its first command, which is after it has read its own prompt bundle. A
fixed =sleep= between the two sends is a race: on the third dispatch the
allowlist prompt had not yet appeared when the conditional check ran, the =BTab=
was never sent, and the worker sat parked until a monitor noticed. Poll for the
prompt string instead of sleeping, or drive both from the same watcher that is
already capturing the pane.

*Scoped to cursor-agent, not to tmux.* The two claude reviewer dispatches this
session, on the same transport into the same worktree root, started clean with no
prompt at all.
