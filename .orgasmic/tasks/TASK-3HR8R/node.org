* IN_PROGRESS TASK-3HR8R A task parked in in_review with no reviewer dispatch is invisible
:PROPERTIES:
:ID: TASK-3HR8R
:PRIORITY: P2
:END:

** Description

A task can sit in =in_review= forever with no reviewer dispatch and nothing
surfaces it. Hit live: TASK-M47E5.1 merged at [2026-08-05 Wed 18:09:04], landed
=in_review=, and no reviewer was ever dispatched. It was found hours later by an
ad-hoc board census, not by any tool.

** Why the existing controls all miss it

- =dispatch-status= lists OPEN dispatches. The failure is the ABSENCE of one, so
  the verb is structurally blind to it.
- The handoff's own hygiene rule is "a task in =in_progress= with no dispatch is
  claiming work nobody is doing". =in_review= with no dispatch is the same defect
  wearing a healthier-looking stage, and the rule as written does not cover it.
- Nothing else reads lifecycle stage against dispatch history at all.

The stage is the problem: =in_progress= with no worker LOOKS wrong to a human
skimming a board, and =in_review= looks like patience.

** Two independent sources, which is why this is filed rather than deferred

1. TASK-4WKNX's reviewer suggested exactly this as a follow-up — "a
   =dispatch-status= diagnostic for a =FIX_SUBTASK= parked =in_review= with no
   reviewer dispatch would make the intended trade harder to miss". The manager
   deferred it as usability polish on a workflow that now works.
2. The M47E5.1 miss, found independently the same day, shows it is not polish.
   The =FIX_SUBTASK= case the reviewer named is one instance; the general case
   costs a review that the active goal requires.

The reviewer reasoned forward from a design change and the sweep reasoned
backward from a real miss, and they landed on the same gap. That agreement is
the argument for building it.

** Design notes, not a design

- The signal is cheap and already on disk: the last =implementer.done= for a task
  versus any later =manager.dispatch_started= of kind =reviewer= for it. No new
  state.
- =dispatch-status= is the natural home — it is what a manager already runs — but
  it currently answers "what is open", so adding "what is stalled" widens its
  contract. Decide that deliberately rather than by accretion.
- Beware making it fire on a task that is legitimately parked. A stall needs an
  age threshold or an explicit "awaiting" marker, or it becomes noise a manager
  learns to skim past, which is how the current blindspot got here.
- The =FIX_SUBTASK= case is now the COMMON case, not an edge one: since
  TASK-4WKNX every fix round lands =in_review= by default.

** Acceptance

- A task in =in_review= whose last implementer close has no subsequent reviewer
  dispatch is surfaced by a verb a manager already runs.
- Reconstructing the TASK-M47E5.1 situation surfaces it.
- A task legitimately awaiting a reviewer dispatched moments ago does NOT
  surface.
