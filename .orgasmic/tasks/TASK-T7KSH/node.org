** Description

TASK-JQ8AV.1 funnelled all four supervisor probe subprocesses through
=probe_command_stdout=, which gives each child its own process group, enforces
=PROBE_CHILD_DEADLINE= (2s) against the CHILD, and SIGKILLs the group then reaps.

One probe subprocess escapes that funnel, and it is on the production rmux path.
=orgasmic-drivers/src/modes/rmux.rs::inspect_rmux_binary= runs
=StdCommand::new(&path).arg("-V").output()= with no deadline. The daemon reaches
it through =pane_probe_command= -> =probe_rmux_binary=.

** Evidence

Measured by the JQ8AV.1 implementer while building the hung-mux regression, not
inferred. With a shim that wedged on EVERY invocation rather than only on the
server-contacting verb:

- the supervisor sweep took *5.012s* — the outer =WORK_PROBE_TIMEOUT=, NOT the
  2s child deadline, proving the child was outside the funnel;
- the test binary then took *120s to exit*, i.e. the tokio runtime was waiting on
  a blocking task stuck in a child the funnel never saw.

The shipped test was then deliberately weakened to answer =-V= normally, which
keeps =inspect_rmux_binary= out of its timed section. That is realistic — =rmux -V=
is answered locally and never contacts a server, so a wedged rmux SERVER does not
hang it — but it means *the shipped regression cannot catch this*.

** Why it matters

A wedged or hung rmux BINARY (as opposed to a wedged server) reintroduces exactly
what JQ8AV.1 set out to eliminate: a blocking-pool thread and a live subprocess
leaked per sweep, at one sweep every =RUN_TIMEOUT_CHECK_INTERVAL= (50ms), for as
long as the condition lasts. rmux is currently the transport of choice for
dispatches on this daemon, because it is the only pane transport with a liveness
channel in the installed runtime.

The tmux path has no equivalent exposure: =real_tmux_on_path()= only stats PATH.

** Acceptance

- =inspect_rmux_binary= (and any sibling in orgasmic-drivers that the daemon
  execs on a probe path) runs under an explicit deadline with kill-and-reap,
  owning its child the way =probe_command_stdout= does.
- A deterministic regression proves it, with a shim that wedges on EVERY
  invocation including =-V= — the case the current test deliberately avoids.
  Assert supervisor latency strictly below =WORK_PROBE_TIMEOUT= and that the
  recorded child pid disappears.
- The test binary exits promptly afterwards; a 120s teardown is itself the
  symptom and should be asserted against.
- fmt, clippy -D warnings, and the focused drivers + daemon tests green. Do not
  run the billed harness test (TASK-099T6).
