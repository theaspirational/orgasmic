* DONE TASK-P9T4N Multi-tx writer transaction so dispatch-close is one commit; reconciliation becomes backstop

From TASK-EP3H1 (2026-07-29): `WriterHandle::transaction(rewrites, tx)` takes
exactly ONE tx, which is the only reason `dispatch-close` cannot be a single
commit — a close needs two ledger entries (the terminal `implementer.done` and
the `task.state_transitioned` from `write_task_lifecycle_and_record`), so the
CLI issues N+1 requests and the pair can tear.

EP3H1 shipped the backstop: close txs record LIFECYCLE_FROM/TO and
`reconcile_torn_closes` finishes a torn close on the next manager command, and
labelled idempotency (`already_applied` vs `already_in_state`) makes replays
safe. What remains is making the tear impossible rather than repairable.

=== Ask

Add a multi-tx writer transaction — `transaction_multi(rewrites, Vec<TxAppend>)`
or equivalent — so the close tx and `task.state_transitioned` land under one
flock, then route dispatch-close through it. Reconciliation stays as the
backstop for pre-existing ledgers and for client-side response loss (which no
server-side atomicity can fix — EP3H1's measured loss was a client timeout on a
request that SUCCEEDED server-side).

=== Acceptance

- A close is one commit: an injected crash between the two legs can no longer
  produce a ledger with the close tx but not the transition.
- Reconciler still passes its torn-close tests against old-format ledgers.
- The writer core change is proven with its own tests (concurrent writers, one
  flock, ordering) — this is the risky layer; EP3H1 deliberately did not touch
  it.
- Injection per TCTTD standard.
