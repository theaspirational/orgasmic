ENTRY 1 dead_pid_aborts_joins_hung_producer_then_receiver_releases — FIXED.
Root cause is not the load. Measured ALONE on an idle machine, the test took
10.08s against its own 12s assertion, a 1.19x margin: HungProducerDriver hangs
in BOTH halves of the driver stop (HungReleaseControl::release is pending(),
the producer parks 6s), so stop_and_join_driver_producer spends
DRIVER_RELEASE_TIMEOUT twice. Both hangs are load-bearing — they are the only
way to reach the abort path the test is named for — so the fix injects the
budget instead of removing the hangs: a driver_release_timeout cell on
Supervisor with a #[cfg(test)] setter, mirroring TASK-HAREX's
set_release_drain_budget, compressed to 150ms. Test cost 10.08s -> 0.44s.
Compressing it alone flipped the asserted release to `early-exit subprocess
with no work envelopes`, which exposed a second latent defect: the terminal
event both HungProducerDriver tests are named after ("racing terminal") landed
inside the join window only because that window happened to be [5s, 10s]. It is
now emitted from release(), at the moment the forced stop begins, for any
budget. The sibling timeout_aborts_joins_hung_producer_then_drains_racing_terminal
shares the fixture and got the same compression; it asserts no wall clock and
was never flaky, but it cost the suite 10s per run.

Composition with TASK-HAREX: none of this fights DrainGate. The gate arms on
begin_explicit_release and would fire at RELEASE_DRAIN_BUDGET; the channel now
closes on the real producer abort ~300ms in, so the drain still ends on stream
closure and the gate is never reached. The test's release reason
(`driver stream closed`) proves that — a gate-bounded drain would not produce it.
