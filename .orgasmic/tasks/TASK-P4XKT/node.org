** Description
*NOTHING IN THIS PIPELINE EVER REPEATS A TEST THAT PASSED, SO AN INTERMITTENT
DEFECT MERGES GREEN.* Independently confirmed by the TASK-2QK4P reviewer with
file and line:

- CI invokes =scripts/run-tests.sh= ONCE (=.github/workflows/ci.yml:194-207=).
- The wrapper re-executes ONLY tests that FAILED in that first run
  (=scripts/run-tests.sh:944-959,1007-1015=).

So a green execution receives *no repetition and no pass-rate scoring*. The
existing failure-isolation machinery is structurally incapable of detecting an
intermittent red on an initially green run — it only ever looks at tests that
already went red once.

** Why this is worth a task rather than a note
It is the generating cause of the whole TASK-2QK4P episode, twice over:

1. =recovery_faults_kill_real_daemon_and_preserve_original_pane= failed roughly
   40% of the time and passed every ordinary gate about three rounds in five. It
   shipped, and stayed shipped, for as long as that took.
2. *The manager then ran ONE execution per commit and bisected it to
   TASK-RMA18* — filing a P0 on a false premise and writing that premise into two
   worker briefs as fact. The implementer overturned it (base =3a36858= fails
   3 of 8); the reviewer later confirmed from source history that the causal
   design predates =ebc69c2= entirely.

The flake registry CLASSIFIES known flakes. Nothing DISCOVERS them. Between
those two facts, an intermittent defect is invisible until someone happens to
run it twice.

** Recommended shape
Start narrow and measured, not with a workspace-wide repeat policy:

1. *A focused repeated canary* for the crash-recovery production test — N
   executions, a reported pass count, and a threshold that reds below it. The
   reviewer ran it 6/6 by hand with one test thread and =ORGASMIC_HOME= /
   =ORGASMIC_RUN_ID= removed from the child environment; that recipe is the
   starting point.
2. *Pass-rate as a first-class verdict input* in =run-tests.sh= for an opt-in
   set of tests, so "green" can mean "green N times" for the tests where
   intermittency is the expected failure mode.
3. Consider generalising to a nightly repeat lane rather than the PR lane —
   repetition is expensive and this host reboots under load (TASK-4BBA6), so
   *cost and the syspolicyd budget are design constraints, not afterthoughts.*

** Acceptance
1. At least one crash-recovery test is executed repeatedly with a scored pass
   rate, and the score is visible in =run-tests.sh='s VERDICT block.
2. A demonstrated negative control: an artificially intermittent test is caught
   by the new gate and NOT by the old one.
3. The added cost is measured and stated, against the syspolicyd rate budget the
   TASK-STWVB chain calibrated.
