Fix round for the BLOCK SHIP on TASK-M47E5.1's review. The finding and its
confirmed mechanism are on that task under "Review round 1 — REJECT (confirmed;

In one line: the finalize command grant was widened from *this attempt's stem
directory* to *the whole project dispatch tree*, so a worker on TASK-A can name
another dispatch's report and have it become TASK-A's own terminal record.

** The manager was wrong, and the reason matters for the fix

The widening was DECLARED by the implementer and ACCEPTED by the manager on the
argument that =read_args_allowed= already reaches those paths, so no new surface
appears. That argument does not hold: =dispatch finalize --summary-file X= reads
X, may COMMIT the worktree, writes X's bytes verbatim as this run's =last.txt=,
and emits the terminal tx. A read grant and a finalize grant are different
authorities over the same path.

*The principle to build to: the criterion governs the command/path pair, not the
transitive closure of separately granted actions.*

** Direction: pass the authoritative stem, do not re-derive it

The daemon already knows this run's artifact directory — the CLI's own finalize
resolves =run.last_path= from the live run record (=manager.rs:1934=). So the
adapter should be TOLD its attempt's artifact directory in persisted driver
config and authorize exactly that, rather than inferring anything.

This restores the pre-move semantics precisely: the old predicate allowed
=worktree.parent()=, which WAS =last_path.parent()= before TASK-M47E5 moved
worktrees out of the project.

Rejected alternative: waiting on TASK-A1KJW (task-derived dispatch stem) and
deriving from =ctx.task_id=. A1KJW is a good change and would simplify this
later, but making a security fix wait on an unrelated refactor is the wrong
order. Note in the fix that A1KJW can supersede the plumbing.

*This crosses crates.* Unlike TASK-M47E5.1, the write scope has to include the
daemon and the driver-config type, because the daemon is where the authoritative
value lives.

=== The BLOCK SHIP: the predicate is right, its INPUT is widenable

=path_is_under= accepts EQUALITY — =path == root || path.starts_with(root)=
(=cursor_acp.rs:1530=). So if =dispatch_artifact_dir= is the dispatch ROOT
itself, both halves of =path_under_own_dispatch_artifacts= pass and every sibling
stem is reachable again.

That value is production-reachable, not a forged test config. Manager traced and
confirmed the full chain:

1. =dispatch_artifact_stem= (=manager.rs:6442=) does
   =file_name.strip_suffix("-brief.md")= with no emptiness check. A brief named
   =-brief.md= yields =stem == ""=; =.-brief.md= yields =".".
2. =dispatch_artifact_paths_for_attempt= (=:6631=) does
   =project_dispatch_dir(project_root).join(&stem)=, so =dir= IS the dispatch
   root.
3. =last_path.parent()= is therefore the dispatch root, and =api.rs:4764=
   persists exactly that as =dispatch_artifact_dir=.
4. Equality passes, and the widened grant is back.

*So round 3 fixed the predicate and left its input unvalidated.* The new paired
test hard-codes a well-formed child directory and the daemon test only proves an
already-supplied value is serialized — neither exercises production derivation.

Worth naming: this is the reviewer answering the exact judgement question the
brief asked ("is there a cheaper way to re-widen this without the test
noticing?"). The answer is yes, and it is not by collapsing the predicates —
which is what the test guards — but by feeding the surviving predicate a broader
input.

=== TWO OF THE CORRECTIONS ARE ON THE MANAGER'S BRIEF

*1. The brief was wrong about canonicalization.* It told the reviewer to check
whether =path_is_under= could be fooled by traversal or symlinks, "note this code
does not canonicalize". It DOES: =resolve_policy_path= (=:1513=) canonicalizes,
and recursively canonicalizes the nearest existing parent before normalizing
=.=/=..=. Traversal and symlink escape are genuinely rejected. The real gap was
the one the brief did not think of.

*2. The brief named the wrong baseline.* It asked for a comparison against
=d4922f7= as "pre-M47E5". =d4922f7= is IN the M47E5.2 lineage and already
contains the managed-worktree move, at which point the old own-artifact predicate
was already dead and the normal allowset was worktree-only. The true pre-move
point is =103ed7e=, where the intended shape was worktree plus =worktree.parent()=
when that parent sits under the dispatch root.

The implementer's report claimed "compared with pre-M47E5 commit =d4922f7=, the
grant allows the same path set". That claim was made in good faith against the
baseline the brief supplied, and the baseline was wrong.
