Split out of TASK-RWCRN, whose acceptance included "a released rmux run does not leave a zombie harness process or an orphaned rmux session behind". The session half is met — `rmux ls` is empty after release. The process half is NOT, and the TASK-RWCRN worker measured it with a proper baseline control rather than asserting it.

MEASURED. One live acquire + release leaves exactly one <defunct> child under the rmux-daemon (pid 8920 at time of measurement). Zombie count under that ppid went 3 -> 4 across one release_reaps_live_rmux_session run on the TASK-RWCRN tree, and 4 -> 5 across the same test on the stashed baseline tree (git stash -> run -> git stash pop). Equal deltas on both trees, so the leak is pre-existing and TASK-RWCRN neither caused nor fixed it.

MECHANISM, named at crates/orgasmic-drivers/src/modes/rmux.rs:1094: panes are spawned with keep_alive_on_exit(true) deliberately, because RMUX 0.9 retains a real exit code/signal only for a dead pane it keeps around. The exited child therefore stays unreaped by the rmux daemon, a process orgasmic does not own. So this is not a missing waitpid in orgasmic — any fix has to either negotiate reaping with the rmux daemon, drop keep_alive_on_exit and give up the exit code/signal fidelity that TASK-6FNAY and TASK-8W30B depend on, or accept and bound the leak.

WHY IT MATTERS. One zombie per dispatch is small, but it accumulates across the lifetime of a long-lived rmux daemon, and the standing worker matrix puts every dispatch in an rmux pane. Bounded growth needs to be either proven acceptable or fixed.

ACCEPTANCE:
- name which of the three options is taken, with the tradeoff argued
- if the leak is retained, bound it and prove the bound
- the exit code/signal fidelity relied on by TASK-6FNAY and TASK-8W30B is preserved or its loss is explicitly accepted
