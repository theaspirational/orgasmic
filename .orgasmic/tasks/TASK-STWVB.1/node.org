** The headline, because it changes what this task is about
The gate does not merely mis-measure: it now returns *no verdict at all*, for
the very suite it was built for. The suite trips its own load threshold, and
=INCONCLUSIVE= preempts =REAL= in the verdict ordering. So exit 0 and exit 1 are
both effectively unreachable for =orgasmic-daemon=, and a failure that fails IN
ISOLATION — where load is already excluded as an explanation — comes back
"re-run when calm". The implementer's own gate is the demonstration: *exit 4 on
734 passed / 0 failed*.

That is the mirror image of the risk the brief worried about. Not everything
excused — everything UNADJUDICATED. A gate whose answer is always "no verdict"
gets waved through exactly like a gate that is always red, which is the failure
TASK-STWVB was opened to fix, one level up.

** F1 — HIGH — nothing samples DURING the run
=scripts/run-tests.sh:432=. =HOST_DURING= is taken after =SUITE_EXIT=$?=,
back-to-back with =HOST_AFTER=. The header claim "sampled before / during /
after" is not what the code does, and the worker's own block proves it: =during
load=22.49= and =after load=22.49=, identical. Load average survives this by
1-minute decay, which is why B looks like it works; syspolicyd %CPU does not —
the task's own note says killing the suite dropped it to 75% within seconds.
*So the scan-storm burst is unobservable at that sampling point even once the
regex is fixed.* Manager-verified in the source.

** F2 — HIGH — the syspolicyd signal never fires, and reports a MEASURED ZERO
=scripts/run-tests.sh:320-321=. =ps -axo comm=,pcpu== truncates =comm= to 16
chars, so the line is =/usr/libexec/sys= and the regex can never match. Then
=END { if (NR || s > 0) ... }= makes NR always true, so the miss prints =0.0=
rather than =?= — while the sampler's own contract says a missing signal becomes
=?=. B ships with one of two signals, and the dead one is the mechanism this
whole task documented (586% syspolicyd at load 11.41).

*Load-average-alone is NOT sufficient*, and the reviewer's ruling on this is the
sharpest thing in the review: a scan storm is a SERIALIZATION stall — processes
blocked in exec, not runnable — and this task's own canonical measurement
("alive, blocked, and has consumed ZERO CPU") describes a state that contributes
to load average weakly and inconsistently. The 2026-08-02 reading was load 11.41
on a run 8-15x slowed; load only 2.6x a quiet Mac. Dropping to load-alone deletes
the only signal that discriminates the mechanism.

Also: =ps -o pcpu= is a short-window decaying average, not a lifetime one
(syspolicyd read 9.1 / 0.6 / 13.3 seconds apart against a lifetime 8.26%), so a
point sample is noisy as well as mistimed. *The right instrument is the one this
task already used successfully*: cumulative CPU-time delta (=ps -o time=)
before/after, which produced the clean =+281s with rmux / +32s without= result.
Immune to jitter, immune to F1's timing, needs no background sampler. One piece
of work fixes F1 and F2 together.
