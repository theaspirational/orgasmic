* IN_REVIEW TASK-SJA9W dispatch-status tells the operator to run a close command that cannot be run, and the only runnable variant records a falsehood

** Description
While an implementer dispatch is =[reported]= but its branch is not yet merged —
which is the ENTIRE duration of every review round, by design, because the
default-branch gate correctly wants a reviewer verdict before a merge —
=orgasmic manager dispatch-status= prints:

: HELD_WORKTREE PATH=… WHY=dispatch <tx> is open for <task> but its run is gone
: [run-gone pid-gone] — close it first (`orgasmic manager dispatch-close
: --task <task> --started-tx <tx>` or `orgasmic manager dispatch-status
: --cleanup-failed`), then prune

*Three things are wrong with that advice.*

1. *The command cannot be run as printed.* =--status= is a required argument, so
   the suggested invocation exits with a clap usage error.
2. *The truthful completion is REFUSED.* =--status done= returns
   =Error: --merge-sha is required when closing an implementer dispatch as
   implementer.done=. There is no merge sha yet and there must not be one — the
   review has not happened.
3. *The only runnable variant records a falsehood.* =--status aborted= is
   accepted, but the round did not abort: it reported, its gates are green, and
   it is waiting for a reviewer. Recording =aborted= puts a lie on the ledger and
   leaves the task where it is rather than in review.

So for the whole review round the operator is told to do something impossible,
about a worktree the tool calls HELD, with no correct action available.

Observed 2026-08-08 on runtime =ed0ebbc= with TASK-2QK4P.1.1.1's implementer
dispatch =tx-20260808-orgasmic-5454= reported and deliberately unmerged.

** Why this is the worktree-prune family
The =worktree-prune= chain (TASK-RMA18 → …1.1.1.1.1) ran seven rounds on exactly
this: operator-facing text that is not true. This is the same defect one verb
over. The prune advice is generated on a state the tool itself creates and
considers normal.

** Acceptance
1. Name the state. A reported-but-unreviewed implementer dispatch is a NORMAL
   waypoint, not an orphan and not a failure. =dispatch-status= must say so
   rather than emitting orphan-cleanup advice at it. Distinguish it from
   =[run-gone]=-without-report, which IS the orphan case the advice was written
   for.
2. Any command the tool PRINTS must be runnable as printed — include every
   required flag, or print no command. A pin that renders the advice and shells
   it through the CLI parser would catch the whole class.
3. Decide and state the intended lifecycle: either the implementer dispatch is
   expected to stay open across the review round (then its worktree is not
   "held", it is IN USE, and prune should say that), or there is a close that
   records success without a merge sha (then =--status done= must accept the
   absence of =--merge-sha= for a task entering review, and say what it records).
   Do not add a third waiver flag without reading TASK-4WKNX first — that ruling
   is about keeping distinct gates distinct, and it applies here.
4. A regression that asserts the printed advice for a reported-unmerged dispatch
   parses, and that following it leaves the ledger true.

** Notes
=--cleanup-failed=, the other suggestion in the same message, is documented as
"Record the orphan close tx for dispatches whose worker died" — also wrong for
this state, and it is a WRITE.
