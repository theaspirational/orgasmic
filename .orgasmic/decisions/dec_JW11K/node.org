* dec_JW11K How should subtasks be modeled without nesting headings in the org file?    :task-model:
:PROPERTIES:
:ID:            dec_JW11K
:GLOSSARY_REFS: term_RG690
:DECIDED_AT:    [2026-05-23 Sat 15:08]

:PARENT:        dec_P24WF

** Context
The ClickUp reference shows first-class subtasks, but tasks today are flat with no parent/child schema. Nested headings in the org file conflict with the =** Description= / =** Acceptance Criteria= section convention; flat continuous IDs plus a parent property hide the parent and are harder to scan in logs.
** Decision
Represent a subtask as a normal top-level task heading in sprint/backlog/archive.org with one extra property =:PARENT_TASK: TASK-XC6RJ= and a path-style child ID (=TASK-XC6RJ.1=, =TASK-XC6RJ.2=, next free numeric suffix per parent). The daemon's materialized index rolls up subtasks per parent from the back-edges; there is no nesting in the org file, and IDs do not carry order so reordering is safe.
** Consequences
Subtasks stay compatible with the file structure and easy to scan in logs. The daemon writer validates parent existence on append and the index rejects orphan subtasks.
