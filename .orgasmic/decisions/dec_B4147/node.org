* dec_B4147 How should the release pipeline build and publish the runtime and apps?
:PROPERTIES:
:ID: dec_B4147
:STATUS: accepted
:TAGS: release,install-distribution,ci,build,reliability
:PARENT:     dec_YKFZX
:END:

Context: The systemd unit generated by the daemon's Linux service adapter wrapped single-value path directives (WorkingDirectory=, StandardOutput=/StandardError=append:) in double quotes, which systemd rejects ("path is not absolute"), so on a clean Linux install the daemon never started and `orgasmic status` reported "exited before becoming ready". Fixed in crates/orgasmic-cli/src/daemon_service.rs render_linux_systemd_unit — a sibling class to dec_2D5BC, which hardened the same generated definitions' PATH. Shipping the fix exposed release-pipeline fragility: one vX.Y.Z tag fan-fired three workflows (release-runtime, release-macos, release-android) that all force-moved the rolling `stable` tag and release target, racing so the release label could show a version whose assets were not all present yet. App builds (10x-billed macOS runners, fragile signing-secret deps) ran on every CLI patch though no app is deployed (all app assets show downloadCount 0) and do not gate the runtime release (already parallel) — cost and noise, no speed. CI `runtime-*` build artifacts accumulated under 90-day retention (~300 MB) despite only handing bundles from the build matrix to the publish job. Relates to arch_WZFAX (runtime bundle + install) and dec_XSV21 (home/install layout).

Decision: Split into two independent, fully-manual release lines.
1. Runtime/CLI -> `stable` release, built locally on the maintainer's macOS machine: darwin-aarch64 (native), darwin-x86_64 (rustup cross), linux-x86_64 + linux-aarch64 via cargo-zigbuild with a pinned old glibc floor (hardens against host/target glibc variance). Windows MSVC cannot build from macOS and stays a manual CI dispatch that merges into the same release.
2. Apps (macOS DMG/updater, Android APK) -> separate `apps` release/tag, manual CI dispatch only; the vX.Y.Z push trigger is removed from all workflows. Runtime and apps never write the same release, so the stable-tag race is impossible by construction.

Mechanisms:
- New scripts/publish-runtime.sh: clean-tree guard -> build UI once (build.rs gains skip-when-ui/dist-prebuilt so it is not rebuilt per target) -> build the four targets -> sign the darwin binaries via a throwaway keychain imported from ~/.tauri (stable designated requirement, preserving TCC grants) -> smoke test (native run; x86_64 via Rosetta; linux via docker run) -> MERGE only the built targets into stable's runtime-latest.json and replace only those tarballs.
- runtime-latest.json carries a per-target version; install.sh prefers it so a lagging Windows entry names its runtime dir honestly instead of inheriting a newer top-level version.
- Versioning split: CLI/runtime version = root Cargo.toml [workspace.package]; app version = tauri.conf.json / src-tauri Cargo.toml / android versionCode. A CLI release never edits app files. The interim v0.0.5 commit bumped app files under the old coupled pattern and is to be reverted.
- vX.Y.Z git tags are dropped (existing v0.0.1..v0.0.5 deleted); version provenance lives in Cargo.toml + runtime-manifest.json (commit+version) + release notes.
- CI Actions artifact retention set to 1 day; existing stale artifacts purged.

Consequences: A typical CLI fix releases from the maintainer's machine in minutes with no CI queue and a hardened glibc floor — directly shortening the path the systemd bug exposed. The stable-tag race and the version/asset mismatch are eliminated. App builds become deliberate, occasional, separately-versioned events off the CLI critical path, cutting runner cost. Trade-off: Windows runtime lags until a manual CI dispatch refreshes it (acceptable while Windows downloads are ~0; the per-target version keeps the manifest truthful meanwhile). Local builds rely on maintainer-side toolchain (zig + cargo-zigbuild; Docker for linux smoke) and the ~/.tauri signing material; the clean-tree guard preserves provenance.

Amendment 2 (2026-06-23, versioning): Unify channel versioning on SemVer 2.0
prerelease tags. The CHANNEL is the release tag / updater feed, NEVER encoded in
the version number. Replaces the nightly hack 0.99.<run*100+attempt> — a second,
inflated scheme that made nightly look newer/more mature than stable and broke
the nightly->stable comparison.
- stable: X.Y.Z (runtime from Cargo.toml [workspace.package]; app from tauri.conf.json).
- nightly: <base>-nightly.<YYYYMMDD>.<run>, a prerelease of the NEXT in-development
  version. SemVer orders it correctly: last-stable < <base>-nightly.* < <base>
  (next stable), so a nightly user rolls cleanly onto the next stable instead of
  being stranded above it.
- Convention: the repo holds the next in-dev version, bumped after each release.
  Now runtime=0.0.6, app=0.0.5. publish-runtime.sh/publish-apps.sh publish the
  stripped X.Y.Z; nightly workflows append the prerelease suffix (runtime-bundles.yml
  derives base from Cargo.toml; nightly-macos/android from tauri.conf.json).
- Android keeps a separate monotonic integer versionCode (run-derived) as the
  platform requires; nightly->stable on Android still needs a reinstall (Android
  blocks a versionCode downgrade) — acceptable for the sideload surface.
- Channel switching (single channel-aware app, as decided): the app already queries
  releases/download/<channel>/latest.json with an equality comparator
  (release.version != current) so an explicit switch surfaces even when the target's
  semver is lower. Added: `orgasmic update --channel <stable|nightly>` re-pins +
  installs the runtime channel head (runtime updater is equality-based, recomputes
  the manifest URL on switch); the app's update_runtime now forwards the selected
  channel so app + runtime track one channel together.
Files: runtime-bundles.yml, nightly-macos.yml, nightly-android.yml, update.rs,
main.rs, src-tauri/src/lib.rs, ui/src/lib/appUpdate.ts; versions bumped to next in-dev.
Amendment 3 (2026-06-23, version-less assets): Eliminate release-asset
accumulation by removing the version from asset FILENAMES; the version lives only
in the manifest (runtime-latest.json / latest.json / android-latest.json carry
version + sha/signature + commit). Asset names are version-less per (channel,
target): orgasmic-runtime_<os>_<arch>.tar.gz, orgasmic_darwin_aarch64.dmg,
orgasmic_android_aarch64.apk (orgasmic.app.tar.gz already was). Every publish
`gh release upload --clobber`s its target's one asset in place; targets not built
this run keep theirs (merge-not-clobber preserved, since one file per target).
Result: a FIXED asset set per channel — nothing ever orphans on stable OR nightly,
so ALL delete/prune logic was removed from the runtime + app publishers and the
workflows. This also retires the stable bump-orphan class (e.g. the 0.99.401 /
0.0.5 leftovers that previously needed manual cleanup). Trade-off: only the channel
head is downloadable by URL (no historical-version URLs) — already true since
dec_B4147 dropped per-version tags; provenance stays in the manifest
(version+commit+sha). Bonus: permanent per-channel download URLs. The Android
in-app sideload check now reads android-latest.json for version + apkUrl instead of
scraping the APK filename. Files: package-runtime.sh, publish-runtime.sh,
runtime-bundles.yml, publish-apps.sh, release-macos/android.yml,
nightly-macos/android.yml, ui/src/lib/appUpdate.ts.
Amendment 4 (2026-06-23, runtime retention): orgasmic update now self-prunes old runtime installs — keep the active runtime + N previous for the target (newest by dir mtime; N defaults to 1, override $ORGASMIC_RUNTIME_RETENTION) and remove older ones. Best-effort (a prune failure warns but never fails the update); only runs on an actual install (the up-to-date short-circuit returns first). Version-less assets still unpack to per-version runtimes/{version}-{target} dirs, which previously grew unbounded. Bootstrap gotcha: the prune ships INSIDE the new runtime, so the update that installs it runs under the OLD (no-prune) binary — the first machine to land it needs a one-time manual prune; every later version-advancing update self-cleans. Shipped in runtime 0.0.7 (commit 67f8227); logic in prune_old_runtimes (crates/orgasmic-cli/src/update.rs). Companion fix: publish-runtime.sh now refreshes the stable release title/notes/tag on each publish (the title had stranded at 0.0.5 while serving newer assets).
Amendment 5 (2026-06-23, app tag namespacing): Each product line owns its own release tags. Runtime keeps the bare stable/nightly tags; the app line is namespaced — apps (stable) + apps-nightly (nightly). The shared nightly tag is now RUNTIME-ONLY. One user-facing channel toggle (stable/nightly) maps per-line: runtime is identity (stable->stable, nightly->nightly); app maps via app_release_tag (src-tauri/src/lib.rs) and appReleaseTag (ui/src/lib/appUpdate.ts): stable->apps, nightly->apps-nightly. This fixes a real bug — update_endpoint/fetchAndroidManifest derived the tag straight from the channel name, so app update checks on the STABLE channel hit stable/latest.json (runtime-only) and 404d; only nightly worked because app-nightly happened to share the nightly tag. Also stops app nightlies from force-moving the runtime nightly git tag. nightly-macos.yml/nightly-android.yml retargeted (NIGHTLY_TAG=apps-nightly, title "orgasmic apps nightly"); app-stable still via publish-apps.sh -> apps. Net release tags: stable (runtime), nightly (runtime), apps (app stable), apps-nightly (app nightly).
Amendment 6 (2026-06-23, fully-local nightly builds): publish-runtime.sh and publish-apps.sh both gained --channel <stable|nightly>. Both product lines now build FULLY LOCALLY for BOTH channels on the maintainer Mac (runtime darwin x2 + linux x2; apps mac + android). Windows runtime stays a manual runtime-bundles.yml dispatch for either channel (macOS cannot build MSVC). Nightly derives <base>-nightly.<UTCdate>.<epoch> (epoch seconds = monotonic local stand-in for the CI run number) and STAMPS it into the build source (Cargo.toml [workspace.package] for runtime; tauri.conf.json + ui/package.json for apps) so the binary/app embed it — without stamping the Tauri/runtime updater would re-offer the same nightly forever; the source files are snapshot-restored on exit via the trap (tree left clean). Android nightly versionCode = epoch seconds (monotonic, fits signed int32 until 2038); local codes (~1.7e9) sit far above CI run-derived codes (~1001), so going from a local nightly back to a CI nightly on Android needs a reinstall (Android blocks versionCode downgrade). Nightly release titles stay rolling ("orgasmic nightly" / "orgasmic apps nightly") so repeated publishes do not churn the title. CI nightly workflows (nightly-runtime/macos/android) remain the hands-off fallback. Validated by dry-run: runtime smoke reported orgasmic 0.0.8-nightly.<...> on all four targets and the working tree restored clean. Commit f00e296.
Amendment 7 (2026-06-24, unified Android versionCode): all four APK paths (publish-apps.sh stable+nightly, nightly-android.yml, release-android.yml) previously used different versionCode scales — semver-derived (~6), CI run-derived (~1001), epoch (~1.7e9) — so mixing local and CI nightlies, or switching nightly->stable, could hit Androids monotonic-versionCode downgrade block. Now EVERY APK uses build-time epoch seconds (Math.floor(Date.now()/1000)): one scale, globally monotonic by build time. Local and CI builds are interchangeable, and a nightly user converges onto a later stable as an in-place update (the old "Android needs a reinstall on nightly->stable" caveat is RESOLVED). Fits a signed 32-bit versionCode until 2038; the human-facing version string is unchanged; existing small codes (<=1001) are all below epoch so it is a one-way step up with no regression. Commit 60ff60b. Validated live: cut real local nightlies — runtime 0.0.8-nightly.* (darwin/linux -> nightly) and apps 0.0.6-nightly.* (mac+android -> apps-nightly, versionCode 1782250801). Windows runtime nightly lags until a manual runtime-bundles.yml dispatch (by design).
