* dec_R6G0A How should the UI let an operator work across several projects at once?    :ui-ia:ui-routing:

** Context
The single-project selector in the sidebar caps the UI at one project at a time, and switching projects discards where you were. Managing several projects (the common manager workflow) means constant re-selection and lost context. A browser-tab mental model fits: keep several projects open and jump between them.
** Decision
Replace the sidebar project selector with a Chrome-style tab strip in the top header: one tab per project, each tab remembering its current view (label = colored project chip + project id + view). The URL (=/projects/<id>/<view>=) stays the source of truth for the active project and view; the open-tabs list is separate state persisted to localStorage. Sidebar nav drives the active tab's view in place. Tabs support session restore, drag-to-reorder, quick close (×, middle-click, right-click menu: close / others / to the right), and a "+" menu that opens any not-yet-open project or adds a new one. Closing the last tab lands on =/board= as the empty surface. Tabs whose project no longer exists are pruned against the live project list. Visual treatment: refined pills (active = solid surface + teal ring + soft shadow), reusing existing tokens.
** Consequences
Several projects are workable at once without losing place; the sidebar selector is removed. Introduces a small dependency-free tab store (=ui/src/lib/tabsStore.ts=) + =ProjectTabs=, and =setActiveProject= / the index route now restore each project's last view. Per-project identity moves from the selector into the tab chip (=ui/src/lib/projectColor.ts=).
