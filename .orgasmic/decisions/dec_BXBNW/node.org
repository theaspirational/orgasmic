* dec_BXBNW Which branch should a dispatch worktree be based on and merged into?
:PROPERTIES:
:ID: dec_BXBNW
:TAGS: dispatch,contribution,convention,branch
:END:

Context: The manager-dispatch convention's Integrate step hardcoded "git merge --no-ff <topic> from main", and CONTRIBUTING led with the source install as the primary contributor mode. Both obscured that the dispatch loop is branch-relative: create_worktree (crates/orgasmic-cli/src/manager.rs) bases each worktree on HEAD (or --from), orgasmic runs no merge/fetch/push and never opens a PR (the manager merges by hand; manager dispatch-close --merge-sha only records the merge commit in tx), and :DEFAULT_BRANCH: in config.org is consumed only as the project.default_branch prompt slot and a registered-branch fallback - no git operation reads it. A contributor running the parallel-worktree machinery on a fork feature branch therefore had no documented integration target and risked editing the tracked :DEFAULT_BRANCH: or merging onto the wrong branch.

Decision: The operative integration branch for the dispatch loop is the base branch HEAD was on at dispatch (git branch --show-current) - main in the default upstream flow, the feature branch when developing a feature via parallel worktrees for a PR - not :DEFAULT_BRANCH:. :DEFAULT_BRANCH: stays an informational prompt signal plus registered-branch fallback and is left at main (tracked). manager-dispatch step 4 is generalized to "merge into your base branch" and step 2 notes the worktree is based on HEAD (--from overrides); manager-contribution gains an integration-branch subsection for fork/feature work; CONTRIBUTING is rewritten to lead with the bundle install (source build only for Rust-code changes), branch-agnostic .orgasmic state writes, and operator-owned local git with contributor-opened PRs.

Consequences: Backward compatible - dispatching from main still means merge into main. Contributors can run the parallel-worktree loop on a feature branch and PR feature into theaspirational/orgasmic:main without touching tracked config. These are shipped/ + doc edits: PR candidates that change defaults for all users once released, but they take effect immediately for a daemon whose content root points at this checkout since conventions are read from disk at prompt-compile time (no rebuild needed).
