* dec_CKMW3 How should install put the orgasmic CLI on the user's PATH?
:PROPERTIES:
:ID: dec_CKMW3
:STATUS: accepted
:TAGS: install,path,onboarding,update
:PARENT: dec_YKFZX
:END:

Extends dec_YKFZX. Placing bin/orgasmic on disk is not enough for a bare `orgasmic` command — the bin dir must be on PATH, and the source-mode symlink must point at the real binary.

PATH wiring (rustup-style): install writes a managed POSIX env file at $ORGASMIC_HOME/env that prepends $ORGASMIC_HOME/bin to PATH behind a dedupe guard, and adds one marker-guarded `. "$ORGASMIC_HOME/env"` line to the user's shell startup files (zsh: .zshrc + .zprofile; bash: .bashrc + .profile, never creating .bash_profile because it would shadow .profile on Debian/Ubuntu; plus a .profile fallback). All operations are idempotent so install, update, and `orgasmic doctor --fix` can re-assert them. --no-modify-path (or ORGASMIC_NO_MODIFY_PATH=1) writes the env file but never edits startup files, for CI and self-managed PATH.

Source-binary resolution: the contributor symlink is resolved across target/release and target/<triple>/release (newest wins), so --target-qualified builds relink instead of dangling.

Surfaces: `orgasmic path ensure|print`, `orgasmic doctor --fix` (relink + wire), and a read-only doctor 'cli on PATH' finding. install.sh resolves the real binary, calls path ensure, and verifies `orgasmic` resolves in a fresh login shell before declaring success.

Scope: macOS and Linux (POSIX shells; also WSL/Git-Bash on Windows). Native Windows (PowerShell/cmd, %USERPROFILE%) is out of scope here and tracked separately.
