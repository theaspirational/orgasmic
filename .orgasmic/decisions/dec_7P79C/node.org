* dec_7P79C Inconclusive claude auth detection does not promote an unchosen ambient key
:PROPERTIES:
:DECIDED_AT: 2026-07-28
:ID: dec_7P79C
:SOURCE: TASK-KKBTP
:END:

** Context
The claude adapter picks a credential mode by asking `claude auth status`. That
question has three answers, not two: `loggedIn: true`, `loggedIn: false`, and
"could not be asked" — the command failed to spawn, exceeded the 5s
`STATUS_TIMEOUT`, or answered in a shape the adapter does not recognise (an
older harness, an error banner).

TASK-S0QRM folded the third answer into the second: `Unknown` was treated as
`Absent`, so an ambient `ANTHROPIC_API_KEY` selected the light `--bare` path
whenever detection was inconclusive. TASK-Z8WEJ's reviewer blocked on the
consequence and asked for the policy to be decided explicitly: an inconclusive
answer let a transient timeout change the credential tier between two otherwise
identical dispatches.

** Decision
An unchosen ambient `ANTHROPIC_API_KEY` does **not** win on inconclusive
detection. With `Unknown`, only a credential the operator *declared* selects
bare mode: the `credential_mode` override, a configured `api_key_env`, or an
`apiKeyHelper` written into their claude settings file. Otherwise the run takes
native-login mode, and the inherited key is neutralised as native mode always
neutralises it.

A definitive `loggedIn: false` is unchanged: there, an ambient key or a helper
still selects bare mode, because the harness has ruled that there is no login to
prefer.

The reasoning is not symmetry — the cost of being wrong is the same size in both
directions, a dispatch that dies at startup after taking ownership — but
likelihood. `Unknown` means the status command could not answer. A key-only
operator with no login gets `loggedIn: false` from a near-instant local read, so
they are served by the definitive branch and never reach this one. The operator
for whom the status command has real work to do — a keychain to unlock, a
credential to read — is the operator who *has* a login. Inconclusiveness
correlates with a login existing, not with its absence, so promoting a leftover
environment variable on that evidence is promoting it against the odds. This is
also the principle the TASK-S0QRM precedence reversal already rests on: a login
is evidence, an inherited variable is a leftover.

** Consequences
- Deterministic key selection remains available three ways, and each of them
  still wins under `Unknown`. What loses is only a variable nobody chose for
  this dispatch.
- One population is worse off: an operator with no login, no declared
  credential, and a `claude` whose `auth status` cannot answer at all. Their
  dispatch now fails with "run /login" rather than launching on the ambient key.
  They are unblocked by setting `credential_mode: bare_api_key` or `api_key_env`.
- The residual this does not remove: `Unknown` still selects a different tier
  than `Present` would, so two dispatches a minute apart can differ. What it can
  no longer do is select a different tier *within* one dispatch. TASK-KKBTP
  resolves the credential plan once, before the dispatch owns a lease, a session
  or a worktree, and the launch applies that plan verbatim — so whatever tier is
  chosen is the tier the preflight ruled on and the tier `RunMeta` records.
- The evidence state (`present`/`absent`/`unknown`) is carried in the pinned
  plan and persisted with the driver config, so a failed run says whether its
  mode was chosen on evidence or on the absence of it.
