* dec_NFZY2 In-flight dispatch-close guards are persisted and inherited by the replacement daemon
:PROPERTIES:
:DECIDED_AT: 2026-07-28
:ID: dec_NFZY2
:SOURCE: TASK-AK6EM
:END:

** Context
`orgasmic manager dispatch-close --worktree-remove` is destructive: it salvages,
runs `git worktree remove`, and deletes a branch. TASK-1T3FZ moved the liveness
verdict into the daemon and had the CLI hold a daemon-owned worktree
reservation ("close guard") across that filesystem work, because the competing
`POST /runs/:origin/recover` acquires in another process.

The guard is therefore held by a process the daemon does not own, while living
only in `Supervisor::Inner.cleanup_reservations`. TASK-ATAXN then made daemon
replacement a routine, budgeted operation: it publishes `daemon.shutdown`,
drains, drops the instance lock and clears the marker, without waiting for or
transferring externally held guards. A replacement builds an empty reservation
map, so a daemon restart anywhere between the guard response and the end of the
CLI's cleanup reopened exactly the race TASK-1T3FZ was filed to close. A
SIGKILLed daemon has the same effect and never runs any shutdown path at all.

Three boundaries could own this. The reviewer deliberately did not pick.

** Decision
The guard is persisted by the daemon and restored by its replacement, with a
holder-identity check at restore.

- `reserve_dispatch_close` writes the reservation to
  `$ORGASMIC_HOME/state/close-guards/<guard-id>` once — and only once — the
  verdict is `Reserved`. `finish_dispatch_close` and every reclamation delete it.
- A new `Supervisor` loads that directory at construction, before the daemon
  binds, and reinstates every guard whose holder is still alive. Guards whose
  holder is gone are deleted, not inherited.
- Holder identity is `owner_pid` where the daemon can probe pids (Unix), and a
  renewal lease (`.../close-guard/renew`, TTL 90s, renewed every 30s by the
  holder) everywhere else. Which of the two governs is fixed when the guard is
  taken, so it cannot change under an installed reservation.
- Release stays by guard-id UUID.

Rejected: **refuse or delay shutdown while a live holder exists.** It makes
daemon shutdown depend on an unrelated process — one wedged CLI would block
every restart — and it is unsound where it matters most: a killed daemon runs no
shutdown path, so the guard is dropped anyway. It would also have meant changing
the ATAXN shutdown budgets, which this round was explicitly not to touch.

Rejected: **move the destructive mutation behind the daemon's own cleanup
authority.** This is the strongest end state — the daemon would own salvage,
worktree removal and branch deletion, and no external holder would exist — but
it is a redesign of `dispatch-close`, not a fix to the handoff, and it would
have to be built while the live race was open. `POST .../dispatch/cleanup`
already does daemon-side rollback cleanup, so the path exists if a later round
wants to converge the two. Persisting the guard does not block that: it is the
same fence, held across a restart.

** Consequences
- A close guard now outlives both a graceful replacement and a killed daemon; a
  replacement refuses acquires and reattaches for that worktree until the holder
  finishes or is proven gone.
- Holders must renew. A CLI that stops renewing loses its guard one TTL later on
  targets with no pid probe (Windows). On Unix an alive pid retains the guard
  regardless of the lease, preserving the reviewer-cleared conservatism: a
  recycled pid reads as alive and retains, never frees.
- `$ORGASMIC_HOME/state/close-guards` is daemon-owned state; an unreadable or
  malformed record is deleted rather than trusted.
- On Windows a daemon outage longer than the lease TTL can drop a guard whose
  holder is alive, because there is no pid to fall back on. The holder is told
  (`renew` answers `unknown`) and says so on stderr, but it is not fenced during
  that window.
