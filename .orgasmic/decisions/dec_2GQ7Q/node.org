* dec_2GQ7Q Flat decisions don't scale: how should decisions nest and name the problem they solve?
:PROPERTIES:
:DECIDED_AT: [2026-06-27 Sat]
:ID: dec_2GQ7Q
:END:

** Context
Decisions are a flat list of level-1 =dec_*= headings. As the design tree deepens — a
complex program accrues many layers of progressively more specific rulings — a flat list
stops scaling: there is no way to express that one ruling refines or decomposes another.
Tags already give topical grouping and =:SUPERSEDES:= already gives evolution/replacement,
but neither expresses logical refinement (a sub-ruling only meaningful given its parent)
nor decomposition (a broad question split into decided sub-questions). Decision titles and
bodies also duplicate intent. We want hierarchy that is future-proof and reusable for other
node classes (tasks) later.
** Decision
Add an arbitrary-depth decision tree under one uniform model.

- /Single node kind/. No separate topic/question class; umbrella nodes are ordinary
  decisions. (Rejected a distinct container class: it would fork the schema, the
  accepted/superseded read-model, and the graph.)
- /Title = the problem/. The heading title states the problem the decision settles; the
  =** Decision= body states the answer. Removes title/body duplication and preserves the
  originating question. Convention only, not machine-enforced (placeholder + authoring
  guidance).
- /Every node rules/ (no empty containers). A parent's =** Decision= is a synthesis of its
  subtree — the executive summary. =accepted = present and not superseded= is unchanged
  (see [[dec_KTF04]]).
- /Identity is the stable flat random =dec_XXXXX=, never a path/. The tree is a stored
  =:PARENT:= pointer on the child. The =1.1.1= outline is a DERIVED display label (full
  numeric path; a root's number is its 1-based index among roots in document order), never
  an identity. Chosen (model M2) over path-as-identity (=dec_X.1.1=) so re-parenting is one
  property edit and never breaks the dense inbound reference web (=:SUPERSEDES:=, arch
  =:MOTIVATED_BY:=, prose); path-as-identity would force re-minting a whole subtree and
  rewriting every reference on each move.
- /File stays physically flat/: =*=-level headings + =:PARENT:=. Decisions cannot nest as
  org subheadings because =**= is taken by the Context/Decision/Consequences sections. The
  tree is a pure index read-model (parent, ordered children, depth, derived path), mirroring
  the task =subtasks= index. No new stored fields beyond =:PARENT:=.
- /Sibling order = document order/; new children append at EOF to start. (=:ORDER:= rank
  deferred unless reordering becomes frequent.)
- /Supersession does not cascade and does not auto-rehome/. Edges are independent;
  re-parenting is the explicit tool (cheap under M2); the supersede workflow merely OFFERS
  to re-home children; a superseded parent with live children renders as a faded ghost node.
- /=:PARENT:= edge contract/: generic key =:PARENT:= (reusable across classes); same-class
  only; no cycles and no self-parent (rejected at write); create-time existence required;
  orphan-from-deletion surfaced as a ParseError (mirrors task orphan handling); same
  =decisions.org= scope; deletion of a parent that still has children is blocked.
- /Depth is unbounded, no lint/.
- /Reusable mechanism/: extract a generic path/tree helper (validate =:PARENT:=, derive
  parent/ancestors, cycle check) in =orgasmic-core= so tasks can migrate onto it later (see
  [[dec_JW11K]]) and arch could relax its one-level cap.

Surfaces.
- /API/ rides existing endpoints: create-child = =POST /decisions= with =properties:{PARENT}=;
  re-parent = =POST /decisions/:id= updating =:PARENT:=; add the contract validation in the
  create/update/delete handlers; tag =:PARENT:=-changing updates as =reparent= in tx;
  re-home = N sequential calls (no batch endpoint).
- /CLI/ viewer gains the outline: =decision list= / =decision get= show path, parent, and
  children.
- /UI/: tree-primary =DecisionsView= (collapsible, path numbers, ghost superseded,
  ancestor-context when tag-filtering); =NodeModal= gains a parent breadcrumb, an ordered
  children list, and a single-value =PARENT= link-chip; =descriptor.ts= gains a =PARENT=
  field; an "Add sub-decision" action prefills the parent (see [[dec_PA23Y]]).
** Consequences
- =:PARENT:= must be added to the canonical edge vocabulary ([[dec_HJENQ]]), which currently
  forbids inventing new edge keys.
- Existing decision titles must be rewritten to problem-form for consistency (no-migration-
  scars value); tracked as a separate grilling task, not part of the mechanism work.
- The index gains a decision-tree read-model alongside the task subtask index (see
  [[dec_X6Q0S]]).
- Architecture nodes for the new path/tree helper and decision-tree index are authored when
  the code lands (living-model rule: keep nodes true), not ahead of implementation.
- Deferred: drag-and-drop reorder/re-parent; Graph-page intra-layer =:PARENT:= edges;
  =:ORDER:= rank; DFS-adjacent file writes (readability polish); soft depth lint; migrating
  tasks onto the shared helper; relaxing arch's one-level cap.
